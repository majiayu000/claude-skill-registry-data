此 Skill 的原始資料保留在 [vendor/SKILL.md](vendor/SKILL.md) 與 `vendor/references/`、`vendor/assets/`、`vendor/scripts/`。原專案 MIT 授權；來源版本 2.6，固定來源 commit `dc1ace47b99a419e42d01a03cb6ace5346efa8ae`，vendor `SKILL.md` SHA-256 為 `9a7d8eb0f341e321b64f996cb7ffaabb8c549cfd6f8723f848daab777ee9e0d0`。需要版型、佈局限制或 SVG 細節時閱讀原始 Skill 的對應章節和 reference；不要將外部文字當作本專案的核准資料。

## 階段對應

| 階段 | 適用圖形 | 來源 |
|---|---|---|
| 01 需求 | 使用案例、使用者旅程、操作步驟 | REQ、Gherkin、使用者文件 |
| 02 設計 | UML 類別、順序、ER／資料庫 Schema、架構、資料流 | 已核定設計與逆向證據 |
| 03 實作 | 模組與依賴關係、程式呼叫順序 | 原始碼、路由、函式清單 |
| 04 測試 | 測試路徑、分支、泳道及驗證流程 | 測試案例、可重現步驟及實際結果 |
| 05 部署 | 部署拓撲、環境與依賴 | 實際部署配置 |
| 06 維運 | 事件、監控、回復與值班流程 | 運維設定與事件紀錄 |

## 證據與產物規則

1. 先選用最能解釋問題的圖形；一張圖過密時拆成多張。UML 類別、順序和使用案例分別表達結構、訊息先後及使用者目標，不混成一張。
2. 每個節點、關係、角色、呼叫、資料欄位和分支都要附來源或 REQ ID。逆向缺證據時標示「候選／未知」，圖形本身不提升證據等級。
3. 先讀專案已有 CSS／設計系統或使用者提供的視覺偏好；可直接依可得資訊完成圖，不因 vendor 的首次樣式引導而中斷已授權工作。
4. 產出可單獨開啟的 HTML 與行內 SVG；需要引用於 Markdown 時另存 SVG。依 vendor 的 SVG 可讀性、幾何與字型規則檢查，並留一份圖面證據表，對照 REQ、來源、圖中元素與待確認內容。
5. 測試、部署、維運階段的候選圖只能說明流程或配置；沒有執行紀錄時不得標示為已測試、已部署或已營運驗證。

圖表內容應由目前指定專案的程式碼、文件或使用者提供資料推導；每張圖都需附上可追溯來源與尚待確認事項，不依賴特定示範專案。
