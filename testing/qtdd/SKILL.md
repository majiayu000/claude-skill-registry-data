# Qtdd — 테스트 먼저

이 스킬의 목적은 **테스트가 버그를 잡을 수 있다는 것을 증명하면서 만드는 것**이다.
실패하는 것을 직접 보지 않은 테스트는, 그것이 맞는 것을 검사하는지 아무도 모른다.
나중에 쓴 테스트는 이미 있는 코드에 맞춰지기 때문에 처음부터 통과하고, 그래서 아무것도
증명하지 못한다. 먼저 쓴 테스트는 "이 코드가 무엇을 해야 하나"에 답하고, 나중에 쓴
테스트는 "이 코드가 무엇을 하나"에 답한다.

이 스킬은 길의 한 단계가 아니라 **실행 안에서 쓰는 방법**이다. 새 기능 요청은 여전히
`Qunderstand`부터, 버그는 `Qdebugging`부터 시작한다. 그 안에서 코드를 쓸 때 이 순서를 따른다.

## 순서: 빨강 → 초록 → 정리

### 1. 빨강 — 실패하는 테스트 하나

- 동작 하나를 보여 주는 테스트 하나. 이름이 그 동작을 말한다. 이름에 "그리고"가 들어가면 둘로 나눈다.
- 테스트 본문을 쓰기 전에 **이 테스트를 깨뜨릴 코드 변경이 무엇인지** 이름 붙인다. 자세한
  방법과 좋은 테스트의 조건은 [testing.md](testing.md)에 있다.
- 진짜 코드를 쓴다. mock은 정말 피할 수 없을 때만.

### 2. 빨강 확인 — 실패하는 것을 직접 본다

돌리고 출력을 읽는다. 다음 셋이 모두 맞아야 제대로 된 빨강이다.

- **오류가 아니라 실패다.** import 오류, 오타, 문법 오류로 빨간 것은 빨강이 아니다. 고치고 다시 돌린다.
- **기대한 이유로 실패한다.** 실패 메시지가 내가 예상한 그 메시지인가.
- **기능이 없어서 실패한다.** 이미 통과하면 이미 있는 동작을 검사하고 있는 것이다. 테스트를 고친다.

### 3. 초록 — 통과할 만큼만

테스트를 통과시키는 가장 단순한 코드를 쓴다. 테스트가 요구하지 않는 옵션, 설정, 일반화는
넣지 않는다. 그것들은 아직 아무 테스트도 증명하지 않는 코드다.

### 4. 초록 확인 — 전체를 돌린다

이 테스트만이 아니라 **프로젝트 전체 테스트**를 돌린다. 내 작업 범위는 만들 것을 정할 뿐,
확인할 범위를 줄이지 않는다. 내가 만들지 않은 실패도 이름을 적어 보고한다. 테스트가
실패하면 테스트가 아니라 코드를 고친다(테스트가 틀렸다는 근거가 없으면).

### 5. 정리 — 초록일 때만

중복을 없애고 이름을 다듬는다. 동작은 바꾸지 않는다. 정리할 때마다 다시 초록인지 본다.
그다음 동작을 위한 다음 빨강으로.

## 먼저 짠 코드가 있을 때

테스트보다 코드를 먼저 썼다면, 그 코드를 참고로 두고 테스트를 쓰면 결국 그 코드에 맞는
테스트가 나온다. 테스트를 먼저 쓰고 실패를 본 뒤 다시 구현하는 편이 결과를 믿을 수 있다.
이미 들인 시간은 어느 쪽을 골라도 돌아오지 않는다. 어떻게 할지 애매하면 사용자와 정한다.

## 이 순서를 쓰지 않아도 되는 경우

버릴 시제품, 생성된 코드, 설정 파일처럼 테스트가 증명할 동작이 없는 것. 이때도 혼자 정하지
말고 사용자에게 한 줄로 말한다.

## 막힐 때

| 막힘 | 읽는 법 |
|---|---|
| 무엇을 테스트할지 모르겠다 | 원하는 사용법을 먼저 코드로 쓴다. 단언부터 쓴다. 그래도 모르면 사용자에게 묻는다 |
| 테스트가 너무 복잡하다 | 설계가 복잡하다는 신호다. 인터페이스를 단순하게 |
| 전부 mock해야 한다 | 코드가 너무 얽혀 있다. 의존성을 밖에서 넣게 바꾼다 |
| 준비 코드가 길다 | 도우미로 뽑는다. 그래도 길면 설계를 다시 본다 |

## 이런 생각이 들면

| 생각 | 실제 |
|---|---|
| "너무 단순해서 테스트할 필요 없다" | 단순한 코드도 깨진다. 테스트는 금방 쓴다 |
| "나중에 테스트하겠다" | 나중 테스트는 바로 통과하고, 그래서 아무것도 증명하지 않는다 |
| "손으로 이미 확인했다" | 손 확인은 기록이 없고 다시 돌릴 수 없다 |
| "테스트가 바로 통과했다, 좋다" | 이미 있는 동작을 검사한 것이다. 빨강부터 다시 |
| "왜 실패했는지 설명은 못 하지만 빨강이다" | 이유를 모르는 빨강은 맞는 것을 검사한다는 증거가 아니다 |

## 끝내기 전에

- 새 함수·동작마다 테스트가 있다.
- 각 테스트가 기대한 이유로 실패하는 것을 봤다.
- 전체 테스트가 통과하고, 출력에 오류·경고가 없다.
- 빈 값, 잘못된 입력, 실패 경로처럼 사용자가 마주칠 경우가 덮였다.

하나라도 아니면 아직 끝나지 않았다.
