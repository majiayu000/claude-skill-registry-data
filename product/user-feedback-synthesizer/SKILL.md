# 用户反馈综合器

## 中文简介

**用户反馈综合器**：把访谈、工单、评论、问卷和销售记录转成可追溯的主题与候选机会。它保留原始证据、分群、矛盾和样本限制，不把重复声音、用户给出的方案或少量材料写成已验证需求或路线图承诺。

## 使用背景

当团队要判断哪些问题在已收集的反馈中出现、影响谁、证据有多强，以及下一步应修复、补充研究、做原型还是暂缓时使用。产出服务于产品决策的输入，不替代代表性调研、因果验证、成本评估或路线图排序。

## 核心原则

- 先固定决策、反馈单位、时间窗、渠道、样本范围和分群，再编码；不知道时标为 `[未知]`。
- 原始记录、去重后的反馈事件、编码、主题、研究者洞察和产品假设必须分层，且均可回到来源记录。
- 频率只描述指定分母中的出现情况；严重性描述影响强度、风险或阻塞，二者不能相加后伪装成优先级。
- 用户提出的功能或方案是线索，不自动等于其底层问题、实际行为或已验证需求。
- 矛盾、反例、未覆盖分群、渠道偏差和未知项与支持证据同等重要；不能用多数意见消除它们。

## 适用场景

- 综合有来源的访谈、工单、评论、问卷、销售记录或可定位的混合反馈，找出在特定分群和情境中的候选问题。
- 清理重复工单、转发内容、同一用户的追问或批量事故反馈，并保留原始记录和去重理由。
- 需要把高频功能请求改写为可验证的问题假设、支持/削弱证据和下一步研究或实验。

## 不适用场景

- 需要总体比例、市场规模、统计显著性或因果结论；便利样本、少量访谈和渠道反馈不能单独证明这些结论。
- 没有原始材料、来源、样本范围或可定位摘录，却要求“用户都需要什么”或主题排名；先索取材料或只提供采集与编码方案。
- 需要在容量、成本、依赖、战略和风险之间排路线图；先用本 Skill 形成候选机会，再交给 `roadmap-prioritizer`。

## 输入要求

先收集或确认以下输入；缺失项目可以保留，但必须写成 `[未知]`：

1. 要支持的决定、目标产品区域和截止时间。
2. 原始反馈、记录标识或可定位摘录；每条的渠道、时间、作者/账户（可匿名）、用户阶段和可用分群。
3. 反馈单位与样本范围：是独立用户、会话、工单、评论还是销售机会；纳入/排除规则和时间窗。
4. 已知重复模式、批量事件、转发内容、机器人/内部测试记录，以及隐私、保留和访问限制。
5. 目标分群、未覆盖分群、渠道构成，以及准备据此作出的产品决定。

## 信息不足时的处理

- 只有五条零散、无来源或无时间的反馈：不输出总体需求、比例、排名或优先级；标记 `[未知]` 的渠道、作者、分群、时间和重复状态，只给最小编码表、待确认项和补样计划。
- 没有原始记录、仅有他人摘要：把摘要作为 `[二手线索]`，不能生成可追溯频率或代表性引文；要求记录标识、摘录和样本范围。
- 分群、渠道或时间窗不明：不合并不同来源计数；先按可见来源分别报告，说明不能比较或不能外推的原因。
- 同一问题有相反反馈：并列保留支持、反例和各自适用分群/情境；先检查产品版本、熟练度、账户类型、渠道和时间，不用总数覆盖冲突。
- 被要求把最高频需求直接排期：拒绝把频率当路线图结论；交付候选机会、未决的严重性/战略/成本证据、验证动作和移交 `roadmap-prioritizer` 的条件。

## 工作流

1. **建立综合卡。** 写明决策、反馈单位、范围、时间窗、渠道、分群、纳入/排除规则、未知项和不能主张的结论。
2. **建立来源与去重台账。** 给每条原始记录分配来源编号；保留原文、时间、渠道、匿名作者、版本和定位。按相同事件/账户/内容/时间窗判定重复，选择规范记录并记录合并理由；不确定时保留为“待核”。
3. **先写编码本，再编码。** 用问题、期望结果、情境、当前做法、影响、方案请求和情绪等可复用代码；每条编码写证据片段、编码者/规则和置信度。方案词须同时追问其底层目标，不能单独成为需求主题。
4. **检查一致性与冲突。** 对相近代码合并前检查定义、分群、版本、渠道和时间；记录边界案例、反例和相反结果。无法解释的冲突仍是发现，不强制归并。
5. **按分群和情境形成主题。** 主题至少包含独立反馈数、独立用户数（若可得）、分母、渠道、时间窗、严重性证据、反例、覆盖缺口和可定位记录编号。
6. **分开评估频率与严重性。** 频率报告“多少独立事件/用户在什么分母中出现”；严重性报告阻塞、时间/金钱损失、风险、替代成本或任务失败及其证据。没有统一口径时不计算总分。
7. **从洞察转成假设。** 将“在已覆盖分群/情境中观察到的模式”写成有限洞察，再提出可被削弱的问题或机会假设、替代解释、验证方法与通过/停止条件；不要直接许诺功能。
8. **执行质量门槛。** 按 `references/checklists.md` 检查证据追溯、去重、编码、冲突、分群、偏差和路线图边界后交付。

## 专业判断规则

### 编码与去重规则

- `原始记录` 是收到的每个工单、评论、访谈片段或销售记录；`反馈事件` 是经过去重后可独立计数的用户经历。不能把两者的数量混用。
- 去重先使用稳定标识：账户/参与者、工单关联、事件号、会话或明确转发链；再谨慎比较相同问题、时间窗、版本和文本。相似措辞不等于重复，多个用户对同一事故的独立经历仍分别保留。
- 合并记录保留所有来源编号，写明规范事件编号、合并规则、时间窗和不合并的例外。缺少稳定标识时，只标“疑似重复”，不得减少独立用户数。
- 编码本需定义代码、纳入/排除条件、正例、反例及修改日期。先在一小批样本试编码，修订后记录版本；新出现的模式可加代码，但不得在事后改变旧代码含义而不留痕。
- 每条主题相关记录至少区分 `[用户表达]`、`[可观察行为/事实]`、`[研究者编码]`、`[研究者推断]` 和 `[未知]`。引文证明表达，不能替代行为或总体结论。

### 频率、严重性与分群规则

- 频率必须写成 `x 个去重反馈事件 / y 个纳入事件`；如可识别用户，再另写 `x 个独立用户 / y 个已识别用户`。渠道混合时分别列分母，不能直接相加为“用户比例”。
- 严重性使用明确证据分级，例如：阻塞核心任务/造成合规或安全风险为高；显著返工、延误或付费损失为中；可绕过的困惑或偏好为低。没有影响证据则写“未评估”，不要由抱怨语气推断。
- 不把频率和严重性压成自动优先级分数。只有已定义且经决策方认可的权重、战略目标、可行性和风险输入齐全时，才可生成可解释的候选排序；缺项保持 `[未知]`。
- 先比较同一分群、工作流、产品版本、地区/语言和渠道内的模式；跨群差异应分开写。未覆盖分群不是“没有问题”。

### 证据追溯、冲突与偏差规则

- 每个主题、严重性判断和洞察都要关联事件编号、原文或安全摘录、渠道、时间、分群和编码版本。引用匿名化并遵守最小化访问原则。
- 矛盾证据按“谁、在何情境、何版本、何渠道、何时间”拆开；记录支持数、反例数和无法归类项。不能解释时，结论应为冲突或未知，并提出判别性采样/研究动作。
- 报告样本量、去重前后数量、纳入/排除规则、渠道占比、可识别用户比例和已知偏差。支持渠道天然偏向遇到问题的人，评论偏向自愿发声者，销售记录偏向潜在收入，访谈偏向被招募者。
- 不将单一大客户、高声量用户、内部员工、机器人、同一事故或便利样本的出现次数推广为全体用户需求。

### 从洞察到假设的边界

- `主题` 描述已编码材料；`洞察` 只说明已覆盖分群中可观察到的模式；`问题假设` 说明可能存在的底层需求及可被削弱的预测；`方案` 只是一个待测试响应。四者不能互换。
- “用户要求导出 CSV”应先写为方案请求，再追问其目标，例如交接、分析或合规留档；现有材料不足时，底层问题仍为 `[未知]`。
- 进入路线图前至少补齐：目标分群与决策目标、问题/影响证据、反例与覆盖限制、替代解释、可行性/成本/风险输入，以及验证或停止条件。否则仅称为“待验证候选机会”。
- 高严重性风险可触发紧急排查或缓解建议，但仍须说明证据范围；这不是把频率规则倒置，也不等于已验证长期产品需求。

## 输出契约

输出按 `references/templates.md`，至少包含：

1. 综合卡：决策、反馈单位、范围、渠道/样本、分群、时间窗、未知项和结论边界。
2. 来源与去重台账：原始记录、规范事件、合并/未合并理由、纳入状态和可追溯位置。
3. 编码本与编码记录：代码定义、版本、证据片段、分类证据、边界案例和冲突。
4. 分群主题表：分母明确的频率、独立用户/事件、严重性证据、反例、偏差、置信度和记录编号。
5. 洞察与候选机会：已观察模式、不能断言的范围、问题假设、替代解释、验证动作、通过/停止条件和路线图所缺输入。

## 质量门槛

- 不交付没有来源编号、分母、时间窗、渠道和分群的主题频率。
- 不交付把原始记录数、去重事件数和独立用户数混为一个“反馈数”的报告。
- 不交付没有编码定义、去重理由、反例或冲突处理的主题归纳。
- 不交付由方案请求、单一引文、高声量客户或单一渠道直接推导的已验证需求、总体比例或优先级。
- 不交付把频率与严重性相加成优先级，或把候选机会直接写进路线图；缺少决策输入时明确标为 `[未知]`。
- 交付前阅读 `references/checklists.md`；需要最小输入和暂停条件时读取 `references/usage-guide.zh.md`，需要表格和边界示范时读取 `references/templates.md` 与 `references/examples.md`。

## 常见失败与修正

| 失败 | 修正 |
|---|---|
| 把 100 条工单各算一票 | 先识别同一账户、关联工单、事故和转发链；分别报告原始记录、去重事件与独立用户。 |
| 把五条评论写成“用户普遍需要” | 记录渠道、时间、作者和覆盖缺口；只称为五条材料中的线索，补样前不外推。 |
| 多人要求一个功能，就把功能名作为主题 | 将方案请求与情境、目标、当前做法和影响分开编码，先验证底层问题。 |
| 用总出现次数压掉反例 | 按分群、版本、渠道和情境保留冲突；不能解释时报告冲突并补采样。 |
| 将频率乘严重性后宣布最高优先级 | 展示两项独立证据及缺少的战略、成本、风险和可行性输入，输出候选机会与验证门槛。 |
| 只留一段“代表性引文” | 为每个结论保存事件编号、原文/摘录、渠道、时间、分群、编码和限制。 |
