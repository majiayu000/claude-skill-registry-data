# next

Read the product model, build the list of everything that could happen next —
strategy (vision, understand, shape, roadmap), realization (the seven lens docs across
the functional and non-functional tracks, then /measure), grilling, execution
(implement, validate, launch), learning (learn), and strategy refresh once everything
is delivered — put it in the finish-the-slice-first order, and show it: one
**next-best-action** plus the ordered list, every entry carrying the exact command and a
plain-language line on why.

The recommendation is advice, never action. The play writes nothing to the model,
opens nothing, launches nothing. Its only durable products are the recommendation it
presents and — when evidence recording is on — the evidence record; every transient
working file is deleted once the recommendation has been presented (C10).

## Role

You are the orchestrator. Three things happen, in order: a script reads the model, a
script builds and orders the list, and you present it. Every mechanical part is a
bundled script — the model scan, the decision tree and the ordering — never re-reasoned
prose. Your one piece of judgment is wording the presentation; you never reorder, add,
or drop an entry. At close you delete the working folder yourself — the play leaves no
scratch behind; the evidence record is never deleted.

**Forbidden:** writing anything under the product model; creating issues, branches, or
work items; launching another play from this one; deriving or ordering candidates by
reasoning instead of `scripts/derive_candidates.py`; consulting any backlog or project
store (none exists — the model is the only source).

**Agent boundaries:** none. This play dispatches no agents and no skills — there is no
judgment step a script cannot own, and no git/issue machinery (read-only, position none).

## Workflow

### Phase: Preparation

**Step 1 — Scan the model** · Owner: play · Depends on: pre-flight
Snapshot the model's state, read-only. The scan reads the model the way the
model-writing plays write it (C13, ADR 026): the spine `_spine.yaml` is the index of
record for the profile, domains, capability detail, slices (status / order / effort /
depends_on) and epics; lens presence is the seven `lens/<type>.md` docs per slice; a
slice record is read only for its name and functionalities, never for its status. A tree
with files but no spine is recorded as `spine_exists: false` — never read from legacy
per-node files:

```
python3 scripts/scan_model.py --product-base <product_base> \
        --out <working>/model-state.json
```

A missing model is a valid snapshot (`model_exists: false` — the /vision branch), never
an error.
**SE-1 (C1/C2/C13, F3):** `model-state.json` exists and was read from `<product_base>`
only (C1); the scan and every later script write only their `--out` file under
`<working>` and the play has no model-write step and launches nothing, so nothing under
`product-os/` changes (F3/C2); the snapshot's profile, slices and epics come from the
spine (C13).

**Step 2 — Build and order the list** · Owner: play · Depends on: Step 1
Run the decision tree and the ordering as one pure function of the snapshot. The tree
spans strategy → both realize tracks of `standards/rules/pipeline-next.md` (the
functional track ux → agentic → marketing and the non-functional track arch → quality →
run, each offering its first missing lens doc) → /measure once both are done (it stamps
the slice realized, so a planned slice with all seven docs is a /measure repair) → grill
→ execute → learning → refresh. Track order is pipeline-next's recommendation, not a
readiness gate. The ordering then finishes a slice first: repair anywhere → every step
of the focus slice (the lowest roadmap-order slice with work left) → strategy → other
slices' steps by roadmap order, flagged parallel → learning → refresh:

```
python3 scripts/derive_candidates.py --state <working>/model-state.json \
        --out <working>/candidates.json
```

**SE-2 (F1, F2, F6 / C6, C8, C9):** `candidates.json` exists carrying the ordered
`candidates` and the `inconsistencies` report (present even when empty — F2's detection
always runs); every candidate cites the gates that admit it, matching its target play's
own readiness rule (F1/F6); other-slice steps cite the roadmap order that permits them
(C6); the tree's branches span the full loop (C9); the file records a `derivation_hash`
so the same model state is shown to give the same ordered list (C8).
**SE-3 (F11 / C5, C14):** checkable from `candidates.json` alone — every repair
candidate ranks above every non-repair candidate (C5); every step of `focus_slice` ranks
above every strategy step, every other slice's step, and every learning or refresh step
(C14); every other slice's step carries `parallel_lane: true`. On a GAP apply REC11.
**SE-4 (F5 / C3, C4):** `entries` holds at most 11 candidates in rank order, each with a
`command` and a plain-language `why` sentence (C3/C4); `cut_for_cap` names every
candidate id past the cap — nothing is silently dropped (F5).
**SE-5 (F8/C11):** for every slice with a `delivered` epic that declares a user-facing
surface (`web_dashboard`/`server_api`/`cli`) **and is not `surface_verified`**, the
inconsistency report carries a `surface-debt` entry for that slice, a
`repair/{slice}/surface` candidate is present in the `repair` lane, and EVERY live
execute epic of that slice is `blocked` naming the surface debt — no runnable execute
candidate survives for a slice in surface debt. A delivered user-facing epic that **is**
`surface_verified` raises no debt. On a GAP, apply REC8 and re-run derivation.

### Phase: Scenario Validation

**Step 3 — Scenario evals (quick)** · Owner: play · Depends on: Step 2
One call, well under a second — the regression file builds small spine-shaped models in
a temp folder and checks the read, the tree and the order. It carries the independent
reader (`scripts/check_model_agreement.py`, which does not import the scanner), so a
wrong read cannot confirm itself. It runs before the list is shown, so a failure halts
the run before anything is presented:

```
python3 scripts/test_derive_candidates.py
```

**SE-7 (F1, F6, F10, F11 / C13):** the file exits 0 — the read cases prove the spine
and lens-doc read against the independent reader (F10/C13), the tree cases prove each
branch offers the action its target gate admits (F1/F6), and the order cases prove a
slice is finished first (F11). On a failing read case apply REC10; on a failing order
case apply REC11 — either way halt before Step 4.

- **SCE-1 (S1 — builder, product mid-delivery):** `case_realized_missing_lens_s1` —
  with a realized-but-lens-missing slice and a ready epic behind it, rank 1 is the
  repair (the missing lens play) and the blocked epic names the missing lens.
- **SCE-4 (S4 — founder, fresh start):** `case_cold_start` — with no product model,
  the only and first command is `/vision`.
- **SCE-5 (S5 — product owner, everything delivered):** `case_all_delivered_learn_s5`
  — with the slice realized and every epic delivered, the list holds `/learn`.
- **SCE-6 (S6 — team running parallel agents):** `case_focus_slice_first` and
  `case_griffin_like_s7` — slice 2's step appears, flagged parallel, ranked below every
  slice-1 step, its gates citing roadmap order 2.
- **SCE-7 (S7 — product owner, roadmap merged):** `case_griffin_like_s7` — profile set,
  four planned slices at order 1–4, the functional-track docs on the order-2 slice: no
  strategy action, the order-2 slice's action is `/arch`, and the independent reader
  agrees with the snapshot.
- **SCE-8 (S8 — builder finishing a slice):** `case_ready_epic_outranks_next_slice` —
  slice 1 realized with a ready epic and slice 2 planned: rank 1 is slice 1's
  `/implement`, and slice 2's `/ux` ranks below it.

### Phase: Present

**Step 4 — Present recommendations** · Owner: play · Depends on: Step 3
Write `<working>/recommendations.md` from `candidates.json` `entries` and output it to
the user **inline**: the next-best-action (rank 1) as the lead, then the list in rank
order with one plain-language line each (built from `why`), the slice being finished
named once, parallel lanes marked as such, a short repair section when
`inconsistencies` is not empty, and a count of `cut_for_cap` when it is not empty. The
operator (or each parallel agent) picks an entry and runs its command themselves.
**SE-6 (C2, C3, C8):** `recommendations.md` exists; its entries appear in the same rank
order as `entries`, every command in it is a command from `entries`, and none is added
or dropped (C8); every entry has its plain-language line (C3); nothing was launched (C2).

## Recovery

| For | Trigger | Direction | Handoff |
|-----|---------|-----------|---------|
| F1 | a recommended command would halt at its own gate | record the divergence between the tree's rule and the target play's gate, fix the tree, and add a regression case | human |
| F2 | downstream work halts on an inconsistency the run reported nothing about | record the missed inconsistency class, extend the consistency scan, add a regression case | human |
| F3 | anything in the model changed, or a play was launched, during the run | halt immediately and surface exactly what changed — nothing is auto-reverted | human |
| F5 | more than 11 entries, or an entry with no explanation | re-run the ordering script, which caps the list and templates every explanation | autonomous |
| F6 | the readiness gates admit an action the list lacks | re-run derivation; if the action is still missing, the derivation rules are incomplete — record the gap and add a regression case | autonomous |
| F7 | working files remain after the run completes | delete the working folder; the already-presented recommendation is the only product | autonomous |
| F8 | a slice has surface debt (a delivered epic with unmet required user-facing surface) and /next would recommend its next execute epic | surface the debt as a blocking inconsistency, recommend the surface-repair action for that slice in the next-best-action slot, and withhold every further execute epic of that slice until the debt clears | autonomous |
| F9 | the close would report COMPLETED without the Done means held | evaluate the stop condition and surface the unmet clauses; re-run the producing step (derivation or presentation) to restore the missing artifact, or close HALTED with the verdict recorded | autonomous |
| F10 | the regression test file fails a read or agreement case | halt before presenting — nothing built on the wrong read is shown; surface the failing cases so the scanner is fixed | human |
| F11 | an ordering case fails, or a presented list ranks another slice's step above the focus slice's | halt before presenting, surface the mis-ordered entries, and fix the ordering script | human |
