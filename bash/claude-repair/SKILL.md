# Claude Desktop: диагностика и восстановление

Результат: приложение доступно пользователю, исходный сценарий повторён. Сам факт PID или успешного запуска команды недостаточен.

Портируемость: Windows MSIX проверен на a test Windows machine 04–05.10.2026. На macOS адаптировать пути и штатный запуск; этот путь не проверен. Для иных ОС сначала установить, какое именно приложение/обёртка используется. PowerShell/MSIX-команды не переносить на другие ОС.
Рельса: локальные команды и UI, без платного API. Независимое ревью изменения скриптов: доступный другой вендор через штатную рельсу.

## 1. Сначала различить продукт и симптом

- RECALL: прошлый ремонт, текущая версия, актуальные логи. Предыдущая причина является гипотезой до свежей улики.
- Различать Claude Desktop, Claude Code CLI и веб-сайт. Этот скилл ремонтирует Desktop; для CLI сначала установить его собственный текст ошибки.
- Windows: записать `Get-AppxPackage *Claude*` (Name, PackageFullName, PackageFamilyName, Version, Status), процессы с путями, PID, временем создания и SessionId, видимые окна. Проверить свежесть `main.log` в **обоих** местах: `$env:APPDATA\Claude\logs` и `$env:LOCALAPPDATA\Claude\logs`; при отсутствии проверить LocalCache установленного пакета. После обновления лог может переехать, старый хвост не описывает новую попытку.
- Не завершать все процессы с именем claude: рядом могут жить независимые CLI-сессии и remote control. Путь и command line помогают различить роли, но **не доказывают принадлежность к AppX Job**. `GetPackageFullName=APPMODEL_ERROR_NO_PACKAGE` тоже не исключает унаследованный Job. Для остановки потомков нужны фактический список участников Job и оценка их работы; сырые командные строки могут содержать секреты.
- До перезапуска проверить незавершённые задачи и несохранённые данные. Закрывать штатно только нужный Desktop-процесс. Не удалять профиль, чаты или учётные данные ради диагностики.

## 2. Выбрать ветку по свежим данным

**MSIX установлен, окна нет:** прочитать существующий `$HOME/.claude/scripts/desktop_app_launch.ps1`, если он есть. На проверенной машине он активирует зарегистрированное приложение через ApplicationActivationManager. Запустить его штатно, затем проверить окно и журнал. Если скрипта нет, использовать штатную активацию установленного приложения, не придумывать путь к exe из старой версии.

**`Not main instance, returning early from app ready`:** это признак отказа второго экземпляра, не доказательство повреждения профиля или stale lock. Сопоставить процессы, интерактивную сессию и окно. Успешная активация может восстановить доступ без доказательства первоначальной причины.

**Процесс живёт в Session 0:** проверить источник запуска и principal задачи планировщика. Процесс в служебной сессии не подтверждает окно у пользователя. Менять запуск только после подтверждения этой причины, с бэкапом исходной задачи.

**Обновление/пакет/служба:** текущий пакет и свежие логи должны подтвердить неисправность. Старые события staging или CoworkVMService не достаточны. Не запускать исторические heal/reset-скрипты до чтения их действий; переустановка и сброс данных не являются первым шагом.

**`Modified, NeedsRemediation` / `0x80073CFC`:** отделить повреждение регистрации от блокировки запуска. Штатный `winget repair --name Claude --exact --source winget --silent --disable-interactivity` может вернуть успех, не восстановив запуск; повторно читать статус и пробовать активацию. Если `winget` отсутствует в PATH, проверить установленный `Microsoft.DesktopAppInstaller`, а не объявлять инструмент отсутствующим. Регистрация существующего manifest не возвращает потерянные файлы. При необходимости восстановления пакета: сохранить конфигурацию, взять официальный подписанный MSIX, проверить издателя и установить поверх без удаления профиля. `CodeIntegrity.cat` отсутствует / событие 3010 есть — это улика для проверки, **не доказанный корень**. После каждой попытки ветку выбирает новая ошибка; не крутить перерегистрацию по кругу.

**`Status: Ok`, но `0x80070020` + AppModel-Runtime `215/208`, `converting the job`:** сразу читать [ветку старого контейнера](references/windows-stale-container.md). Старый пользовательский Job может удерживаться `python`, WSL, shell, git или сервером, когда самого Claude уже нет. Сначала read-only перечисление участников, при `AccessDenied` узкая проверка с повышением прав. Затем оценить побочные эффекты, завершить только разрешённые и повторно проверенные процессы, подтвердить уничтожение старого контейнера событием 217 и запуск нового событием 201. Не останавливать службы, всю WSL, все Python/Claude или хаб наугад.

**Окно открывается, но падает при действии:** сохранить свежий crash/log и воспроизведение; исследовать именно действие. Ошибки сети/авторизации не лечить сбросом MSIX наугад.

## 3. Доказать результат и оставить откат

1. Проверить видимое окно в пользовательской сессии, Responding и UI. В журнале найти новые boot/input/renderer-ready события после попытки, не старые строки.
2. Вторым способом проверить пользовательский сценарий. Для отказа запуска: повторная активация плюс видимое доступное окно. Для отказа сообщений: новая сессия с коротким безопасным ответом без инструментов, если это входит в задачу.
3. Не объявлять холодный запуск проверенным, если проверена только повторная активация. Не закрывать рабочие задачи ради дополнительного теста.
4. Если менялись файлы/задачи: сохранить до/после, хэши и точную обратную операцию. Если ничего не менялось, написать «откат файлов не требуется».
5. Итог: симптом; доказанная причина либо UNKNOWN; действие; две проверки; непроверенное. Записать результат в существующий журнал ремонта/изменений с ts, node, actor, event, outcome. Документ не создаёт нового фонового сторожа.
6. Отдельно перечислить прерванные фоновые задачи и проверить нужных потребителей после восстановления. Окно Claude не доказывает сохранность WSL-приложения, локальных серверов или авторизации. Если UI-инструмент остановлен, больше не посылать через него ввод; окно/Responding + свежие логи дают ограниченное подтверждение, а отсутствие визуальной проверки назвать прямо.

Запрос «срочно открой / доведи до конца» означает продолжать доступный безопасный ремонт после неудачного перезапуска. Не отдавать пользователю промежуточную диагностику как финал при наличии следующего шага. Реальный блок на правах или рискованном действии назвать конкретно.

## Проверенный прецедент 04.10.2026

Claude Desktop 1.37937.3.0: лог отказа второго экземпляра, видимого Desktop не было; две живые CLI-сессии сохранены. Штатная AAM-активация дала видимое responsive-окно, input/renderer ready и завершение boot; повторная активация сохранила рабочее окно. Профиль не сбрасывали. Первопричина исходного отказа и холодный запуск остались непроверенными.

## Проверенный прецедент 05.10.2026

После восстановления пакета статус стал Ok, но старый пользовательский Job продолжал блокировать запуск. Очистка подтверждённых участников восстановила активацию; подробные улики, побочные эффекты и границы доказанного находятся в [единственном описании прецедента](references/windows-stale-container.md#улики-и-границы-прецедента).
