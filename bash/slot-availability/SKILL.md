候補日程一覧(調整さん等の日程調整サービス、LINE・メールでの空き日程の
問い合わせ等)とユーザーのカレンダーを素朴に「時間指定予定と重なるか」
だけで突き合わせると、終日イベントとして登録された試験・研修等
(Google Calendar 上は `transparent` = 予定なし扱いのことが多い)を見落とし、
実際には拘束される日を ○ と誤判定する。判定ルールを毎回その場で言葉で
組み立てるとブレが出るため、判定ロジック(判定コア)は決定的なスクリプトに
固定し、Claude は候補一覧の取得・構造化、MCP 経由の読み書き、合意形成
(判定表の提示・承認)を担う。

候補一覧の取得元は調整さんに限らない(LINE アンケート・Spir・TimeRex・
口頭やチャットでの自由文など、さまざまな形で来る)。判定コア
(`scripts/slot-hit.sh` の `judge` サブコマンド。bash + yq + jq のみで動く
— ADR-0010〔private な person-state リポジトリ〕D13)は取得元を問わない構造化
JSON だけを入力に取るため、下記「汎用手順」はどの取得元でも共通に使える。
取得元ごとに異なるのは「候補一覧をどう読み取り構造化するか」と「判定後の
回答をどう書き戻すか」の2点だけで、これを個別の節(現時点では調整さん
向けの1本のみ)に分けている。次の取得元が実際に必要になった時点で、
その節を追記する。

## いつ発動するか

- 人から提示された候補日程一覧(調整さん等のサービス、チャットでの
  日程列挙など)を、ユーザーの Google Calendar の空き状況と突き合わせて
  回答したい場面
- 押さえた候補にカレンダー側へ仮予定(マーカー)を作りたい場面

## 前提: 個人設定

判定ルール(コマの時間境界・判定元カレンダーの allowlist・除外プレフィクス
等)はこのリポジトリに置かない — ユーザー個人のカレンダー構成・所属団体名
を含むため。既定の読み込み先は `~/.config/slot-availability/config.toml`。
存在しなければ、どこに置くか・どう作るかをユーザーに確認する(個人の主
カレンダーに無断で書き込まないのと同じ理由)。設定スキーマは
`docs/agents/slot-availability.md` を参照(スキーマの正本は
`config.toml` を読む `slot-hit.sh`/`lib.jq` の実装そのもの)。

## 汎用手順

どの取得元でも共通の手順。手順1と手順7は取得元ごとに具体的なやり方が
異なる — 下記「調整さん向け具体手順」のような節を都度参照する。

1. 候補日程一覧を取得し、構造化 JSON(`[{"date": "YYYY-MM-DD",
   "time": "HH:MM"}, ...]`)に変換する。日付が年を含まない・自由文である
   等、取得元によって表記はさまざまだが、この手順の出口は必ずこの
   構造化 JSON に揃える(判定コアはこの形式以外を受け付けない)。
1-0. **日程の候補を読む前に、その依頼が載っていた会話・メッセージの全文を読む(#1577)。** 日程の候補は、LINE・メール・
   LinkedIn・調整さんのコメント欄など、相手との会話の中で出される。候補の一覧だけを抜き出して回答すると、同じ会話にある
   別の依頼(質問・書類・期限)を落とす。会話の始めからの、相手の未決の依頼すべてを列挙し、日程への回答は、その一部として
   書く(共有 AGENTS.md「相手のいる会話へ返すときは…」)。日程以外の依頼は、このスキルが答えず、返信の下書き
   (`inbox-adjudication`)で、`reply-coverage check` を通して答える。日程の回答と同じ返信に載せるときは、載せた本文の全体を
   検査する。
1a. **設定に `[inbox]` があっても、取り込み待ちの予定で判定を止めない(手順2〜の前の検査は、止める条件ではなくなった)。**
   一回きりの約束(歯医者・通話・会食など)は、主カレンダーが正本で、型付きデータへ取り込まない運用に変わった。主カレンダーの
   予定は、手順 2 の allowlist の `list_events` で読み、そのまま空き判定に数える。取り込み待ちが残っていても、
   重なる候補は、重なる予定として ×・△ に判定される。取り込み待ちの一覧を見たいときだけ、`[inbox]` の `calendar_id` を
   `list_events` して、生のレスポンスを `<inbox.json>` に置き、次を実行する(終了コード 1 = 取り込み待ちあり。これは情報で、
   判定を止める理由にしない)。
   ```
   bash scripts/slot-hit.sh inbox-check --config <config.toml> --events <inbox.json>
   ```
   取り込み待ちに数えないのは、印の付いた予定(`marker_prefix`・`marker_prefix_aliases`・
   `[inbox]` の `exclude_prefixes`。別の仕組みが招待者なしで直接書く `[outing] ` などは、
   ここに並べる)、キャンセル済み、終了済み、他人が主催の招待。確定した予定を型付きデータへ取り込む運用(付随の作業を導く予定
   など)が残る設定では、この一覧が、取り込み忘れの確認に使える。
1b. **仮押さえを書き込んだことがあれば、判定の前に、取り込み済みの仮押さえの残りを検査する。**
   確定した予定を型付きデータへ取り込んでも、主カレンダーの仮押さえのマーカーが残っていると、
   実際には空いている枠を塞ぐ。`marker_calendar` を `list_events` して生のレスポンスを
   `<markers.json>` に置き、`adopted_from` を持つデータの TOML(型付きの予定ファイルと、試験などの
   ディレクトリの TOML)を `--adopted` に渡す(終了コード 1 = 残りあり)。
   ```
   bash scripts/slot-hit.sh adopted-check --config <config.toml> --markers <markers.json> \
     --adopted <events.toml> [--adopted <別の TOML> ...]
   ```
   残りがあれば、表を本人に見せる。同じ候補日程一覧の他の仮押さえも、確定したので消す対象として
   出る。削除は本人が決める(この検査は消さない)。消してから判定に進む。
2. 設定の `[[calendars]]` allowlist が持つ `id` をそのまま使い(`list_calendars` で ID 解決しない。
   それは、そのアカウントから見える全カレンダー(他人の予定表を含む)を全欄つきで返す)、
   候補期間を覆う最小の範囲で、カレンダーを 1 つずつ `list_events`(`timeZone` を設定の
   `timezone` に、`pageSize` は大きめ)する。コネクタの `list_*` は予定の全欄(説明欄の会議リンクや
   パスコードなど)を返し、欄を選ぶ引数が無いので、読む範囲と件数だけが絞れる。レスポンスは
   ファイルに置いて判定に渡し、判定に要る分以外を会話に貼らない。`active = false` のエントリは
   判定に使わないので `list_events` しない(参加が流動的なカレンダーを
   allowlist から消さずに外すための切り替え。省略は有効)。1 レスポンスがサイズ超過で
   ファイル保存になった場合はそのファイルパスをそのまま次の手順に渡す。
3. 判定は `scripts/slot-hit.sh judge` に任せる。手で ○△× を組み立てない
   — バッファ・終日イベントの扱いなど、その場の判断にブレが出やすい
   要素を全てスクリプトに閉じているため。
   ```
   bash scripts/slot-hit.sh judge --config <config.toml> \
     --candidates <candidates.json> --events-dir <dir> \
     --event-title <イベント名> --source-url <候補日程一覧の URL> \
     --out-plan <plan.json>
   ```
   `--candidates` は手順1で作った構造化 JSON。`--events-dir` は手順2で
   得た `list_events` の生 JSON レスポンスを `<calendarId>.json` の
   ファイル名で置いたディレクトリ。
4. **終日イベントが `soft_day_prefixes` に一致し、かつ同日に時間指定の
   確定予定が無い場合、スクリプトはエラー終了する。** これは「実際の
   拘束時間が Google Calendar に正規化されていない」ことを意味する —
   エラーを握りつぶして ○ を出さない。一次情報(公式サイト等)で拘束
   時間帯を調べ、`create_event` で時間指定の予定として書き戻してから
   (下記「カレンダーの正規化」)再実行する。
5. スクリプトが出す判定表(Markdown)を提示し、AskUserQuestion で
   承認を取る。判定はカレンダーに載っている情報だけを反映する旨を明記
   する(購読カレンダー側が更新されていない可能性がある)。
6. 承認後、○/△ の全コマにマーカー予定を作る。
   - `search_events` で候補日程一覧の URL を含む既存マーカーを検索し、
     見つかれば `delete_event` してから作り直す(再実行の冪等化)。
   - 件名: `<marker_prefix><イベント名>`(△ は末尾に ` [△]` を付ける)。
     `marker_prefix` は設定の値で、機械可読な英数字の形(例: `[hold] `)にする。
     かつての `【調整中】` は、設定の `marker_prefix_aliases` に並べると、読み取り専用の
     別名として自分の印の判定・確定化・受付箱検査に使われる(新しく作る印には使わない)。
   - 説明欄: 候補日程一覧の URL と、その枠を選んだ理由(空き/バッファ内)。
   - `opaque`、コマの時間区間そのまま、書き込み先は設定の
     `marker_calendar`(主カレンダーに書く場合は事前にユーザーへ確認済み
     であることが前提 — 本人裁定が無ければ確認してから作る)。
7. 判定表の承認後、取得元に回答を書き戻す。書き戻し方は取得元ごとに
   異なる(下記「調整さん向け具体手順」参照)。
8. 相手側(主催者等)が候補日程一覧から最終的な枠を裁定したら、「裁定後の
   確定化」(下記)でカレンダー側を「調整中」から「確定」に更新する。

## カレンダーの招待に返答するとき(`respond_to_event`)

招待への返答(承諾・辞退・仮承諾)を行うと主催者に通知される。返答の前に招待の説明欄および他の出席者・主催者のコメントを確認し、そこに記載された依頼(資料の持参、会場や時間の変更に関する相談、出欠以外の確認事項)に対して返答のコメントで応じる(#1577)。出欠の回答だけで済ませず、説明欄の依頼を見落とさないようにする。システムによる自動的な制限はないため(`respond_to_event` は下書きを経由しない)、この手順を厳守する(検出のみ)。本人以外を招待する予定の作成や修正といった操作も、外部への発信と同様に下書きで止める規則に従う(共有 AGENTS.md)。

## 候補一覧が無いとき(空きコマを出す側)

「いつ空いてる?」とだけ聞かれ、相手の候補一覧が無いときは、手順1の
「取得・構造化」の代わりに、期間内の全コマを候補として機械生成する。判定
そのものは手順2〜6と同じ `judge` に任せる — 逆方向の判定ロジックを別に
持たない(候補集合だけを作る)。

```
bash scripts/slot-hit.sh enumerate --config <config.toml> \
  --from <YYYY-MM-DD> --to <YYYY-MM-DD> \
  [--weekdays 0,6] [--slots evening] --out <candidates.json>
```

- 出力は手順1と同じ構造化 JSON(`[{"date","time"}]`)。`time` は各コマの
  開始時刻で、コマは開始時刻順に並ぶ。
- `--weekdays` は曜日番号(0=日〜6=土)、`--slots` は設定の `[slots]` の
  名前。省略は全曜日・全コマ。期間は 400 日まで(誤入力で巨大な出力を
  作らないため)。
- 以降は手順2(各カレンダーの `list_events`)→ 手順3(`judge`)と同じ。
  `plan.answers` は候補と同じ順に並ぶので、`○` の候補だけを取り出して
  相手に提示する文面にする(`△` は理由を添えて別枠で見せる)。

### 分単位の時間窓は、このスキルの判定では答えられない

このスキルの判定は朝・昼・夜の 3 コマ単位で、「15〜75 分の具体的な時間窓が空いているか」には答えられない
(コマの中に予定が 1 つでもあれば、コマ全体の判定が動くため)。分単位の窓が要るときは、`list_events` の
出力を手で `jq` で絞って突き合わせない。本人の予定のデータを持つリポジトリが、空き時間の区間を計算する
スクリプトを提供している場合があるので、先にその有無を探し、あればそれを使う。無いときは、手で絞った
ことと、その結果が分単位の確認でない部分を、報告に書く。

## 発行側の打診(候補を出す側)

こちらが候補を出して相手に選んでもらう場面(合わせの日程打診など)。
受け取る側の手順(手順1〜8)の鏡像ではなく、次の 2 点だけが違う。

1. **候補コマは新しい逆方向ロジックで作らない。** 上の「候補一覧が無い
   とき」の `enumerate` で期間内の全対象コマを候補 JSON として機械生成し、
   既存の `judge` に流す(判定コアは 1 つのまま)。`○` のコマが、こちらから
   出せる枠になる。
2. **予約型サービスでは調整中のマーカー(`marker_prefix`)を作らない。** 予約型(相手が
   枠を予約した時点で即確定する予約ページ)は、予約ページ自体が仮押さえの
   役目を担う。そこへマーカーを重ねると、提示したい枠そのものが busy に
   なって潰れる。マーカーを作るのは、候補一覧型(調整さん等、相手の裁定を
   待って確定させる)の従来の運用だけ。

### 候補を相手に出すときの順序(仮押さえを先に作り、読み戻してから送る)

相手に候補を提示する操作と、自分のカレンダーの仮押さえは、別のシステムなので、1 つのトランザクションに
できない。**順序と巻き戻しで、「提案だけがあって押さえが無い」状態を作らない**(#1315)。候補一覧型
(`marker_prefix` を使う場合)は、次の順に行う。

この順序は `worklog offer` が状態として持つ(#1319。ジャーナル・遷移表・回復の表は
`docs/agents/slot-offer.md`)。カレンダーの操作と送信はスクリプトからできない(コネクタはエージェントしか
呼べない)ので、スクリプトは次の手を JSON で出し、エージェントが実行して結果を `record` で返す。

1. 意図を記録する: `worklog offer begin <提案 id> --thread <スレッドの識別子> --slot <開始>/<終了> ...`
   (メール本文・氏名は渡さない)。
2. `worklog offer plan <提案 id>` の `create_hold` を実行する。題名は `title`(`marker_prefix` の `[hold] `)、
   説明欄は `description` をそのまま使い、同じ印の予定が既にあれば作らない。
3. 説明欄の `search` で押さえを読み戻し、`worklog offer record <提案 id> holds --holds <n=予定id,...|none>` で返す。
   全スロットが揃うまで 2 に戻る。**1 件でも作れていなければ送らない**(`record offered` が拒否する)。
   作れなかった提案は `worklog offer abort <提案 id>` の計画で押さえを消す。
4. 送信前の確認(画面・全文・宛先。`inbox-adjudication` の「代行送信の前に、本人の確認を取る」)を経て送る。
   確認のページに、押さえの一覧を載せる。送信済みの画面を読み戻したら `worklog offer record <提案 id> offered`。
   送信に失敗した・本人が送らないと決めたら、`worklog offer abort <提案 id>` の計画で押さえをすべて消し、
   読み戻して `record cancelled --holds none`。
5. 相手が日を選んだら `worklog offer record <提案 id> chosen --slots <n>` を返し、下の「裁定後の確定化」へ進む。
   選ばれなかった枠の押さえは、そこで消える。

セッションの開始時と、途中で止まった提案があるときは、`worklog offer list` で終端でない提案を見て、
`worklog offer recover <提案 id> --sent yes|no|unknown --holds ...` の計画に従う。送信済みの画面が読めなかった
ときは `--sent unknown`(`no` と書かない)。`ask_person` の手は、本人に状態を見せて聞き、勝手に消したり
送ったりしない。

予約型サービスの空き時間への反映に公開 API が無いときは、反映の操作自体は
サービスの UI 経由になる。その区間計算は、手順として LLM に毎回逐語実行
させず、決定的なスクリプトに閉じる(同じ操作列の繰り返しは、安定の兆候が
出たら決定論へ昇格させる)。

## 裁定後の確定化

候補日程一覧の相手側が最終的な枠(1つとは限らない)を裁定したら、その
枠だけを残して他の仮マーカーを片付け、確定した予定として書き換える。
この対応付け(既存マーカー × 確定枠 → update/create/delete)は手で
組み立てず `scripts/slot-hit.sh finalize` に任せる — 「確定枠が候補日程
一覧に無かった枠だった」「候補と裁定で開始時刻が僅かにずれた」といった
エッジケースは会話判断に戻すとブレるため、判定コアに固定してある。

1. `list_events`(`calendarId` は設定の `marker_calendar`、`fullText` に
   `marker_prefix`、期間は候補日程一覧が覆っていた範囲)で、このイベント
   の自マーカーをまとめて取得し、生 JSON をファイルに保存する。
2. 相手側の裁定結果を構造化 JSON(`judge` の `--candidates` と同じ
   `[{"date": "YYYY-MM-DD", "time": "HH:MM"}, ...]`)にする。裁定枠が
   候補日程一覧に無かった(相手が別の時間帯で決めた)場合や、候補と
   裁定で開始時刻がずれている場合も、そのまま裁定後の値を書く —
   `finalize` 側が対応関係を解決する。
3. `finalize` を実行する:
   ```
   bash scripts/slot-hit.sh finalize --config <config.toml> \
     --decided <decided.json> --markers <markers.json> \
     --event-title <イベント名> --source-url <候補日程一覧の URL> \
     --today <YYYY-MM-DD> --venue <場所、未定なら省略可> \
     --out-plan <plan.json>
   ```
   `--decided` は手順2の JSON。`--markers` は手順1で得た `list_events` の
   生レスポンス。`--today` は裁定日(説明欄の記載に使う)。
4. 出た計画表(裁定枠 / 操作 / 対象マーカー)を提示し、AskUserQuestion で
   承認を取る。想定される操作:
   - `update`: 確定枠と同日かつ区間が重なる自マーカーがあれば、その
     予定を確定枠の時刻・件名・説明に書き換える(候補と裁定で時刻が
     ずれていても、この操作で吸収される)。
   - `create`: 対応する自マーカーが無い確定枠(候補日程一覧に無かった
     枠で裁定された場合など)は新規作成する。
   - `delete`: どの確定枠とも対応しない自マーカーは削除する。
5. 承認後、計画どおりに `update_event` / `create_event` / `delete_event`
   を実行する(`delete_event` は `notificationLevel: NONE`)。確定予定の
   件名は接頭辞(`marker_prefix`)や `[△]` を落とした素の `<イベント名>`、
   `opaque`。場所が未確定なら location は空欄のまま、説明欄に
   「場所: 未定(裁定日 時点)」「裁定: 裁定日(主催者側で確定)」
   「候補日程一覧: URL」を書く(下記「カレンダーの正規化」と同じ理由 —
   場所が確定した時点で location と説明欄をまとめて書き換える)。
6. 調整さん等への回答の書き戻しは、主催者側の裁定を受けて回答内容が
   変わる場合だけ行う(既に回答済みなら不要)。

## 調整さん向け具体手順

上記「汎用手順」の手順1・手順7を調整さん(chouseisan.com)で行う場合の
具体的なやり方。

**手順1(候補一覧の取得・構造化)**: ブラウザで開き、日程候補の表を
1 列ずつ読む。表記は `M/D(曜) H:MM〜` で年を含まない。年は
`scripts/slot-hit.sh infer-year --month <M> --day <D> --weekday <曜> \
--today <YYYY-MM-DD>` で解決する(今日以降で最初に曜日が一致する年を
1 行で返す)。手で曜日と年の対応を数えない — 閏年・年末年始をまたぐ候補が
混ざると誤りやすいため、必ずこのコマンドに委ねる。

**手順7(回答の書き戻し)**: 名前だけでログイン不要のサービスが多く、
一度投稿すると同じブラウザからしか編集できない仕様があるため、承認を
経ずに投稿しない。判定表の承認後、投稿直前にユーザー名を再確認してから
「Add Attendance」ボタンを開き、`plan.json` の `answers` 配列を候補一覧の
表示順どおりに各行の ✔/?/X ボタンへ反映し(○→✔、△→?、×→X)、コメント欄に
△の理由があれば一言添えてから送信する。送信後はスナップショットで全行が
意図通り反映されたことを確認する。

## カレンダーの正規化(調べて分かった事実は Calendar に書き戻す)

判定のために外部の一次情報(公式サイト等)を調べて拘束時間が判明したら、
その事実は判定スクリプトの設定ファイルに転記せず、**Google Calendar 側に
時間指定の予定として書き戻す**。設定ファイルは判定ルール(コマ境界・
allowlist)だけを持ち、個々の予定の事実(いつ拘束されるか)は Calendar
1 箇所を正本にする — 同じ事実を 2 箇所で管理すると、どちらかが古くなった
ときに判定が静かに誤る。

書き戻す予定には、説明欄に出典 URL・取得日・(該当すれば)未確定要素
(会場未公開など)を明記する。既存の終日イベント(「その日は試験」といった
粗い印)は残してよい — 追加するのはその中の具体的な時間帯の予定。

## 外部サービスへの書き込みはサニタイズ対象

候補日程一覧サービスやカレンダーに送る文章は、`agent-tooling-authoring`
§3.2「外部サービスへ送る文」に従ってサニタイズする(禁止項目の一覧は正本のみ)。

## 事例

- **候補外枠での裁定**(2026-09-26): 調整さんの候補一覧に無かった日時
  (候補は同日の別コマのみ)で主催者側が裁定するケースが実際にあった。
  `finalize` は対応する自マーカーが無い確定枠を `create` として扱う
  (会話で「候補に無いのでどうするか」を都度判断する必要はない)。
- **候補と裁定の時刻ズレ**(2026-09-26): 候補日程一覧では 19:00〜 だった
  枠が、主催者側の裁定では 18:00〜21:00 として確定するケースがあった。
  `finalize` は自マーカーとの重なりで対応付けるため(完全一致は要求
  しない)、このズレは `update` 1 件として吸収される。
