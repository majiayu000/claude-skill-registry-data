会話で受けたものを**次のセッションにも効く形**へ還元します。ここで拾わなければ、同じことをもう一度言わせることになります。

**書く前に「これは1回きりか」を判定します。** 1回きりの指示を資産化すると、**関係ない場面でも毎回ロードされる**だけになります。

## プロジェクト側に同名があれば、そちらを使う

**この名前はリポジトリ側の `.claude/skills/` にも置かれていることがあります。** そのときは**リポジトリ側を優先する**。そのリポジトリの資産の置き場と承認の流れを知っているのはそちらです。

- **判定はファイルの場所で行う。** 同じ名前のスキルは個人側しか一覧に出ないので、一覧を見ても見つかりません。リポジトリの直下の `.claude/skills/learn-rules/SKILL.md` があれば、それを Read して従う
- 本スキルは、**リポジトリ側に無いときの土台**として働く

## 進め方

### 1. 1回きりか、繰り返し効くかを判定する

**これが最初の関門です。** 通らなければ何もしません。その場で従えば足ります。

| 資産化する | しない |
| --- | --- |
| **同じ指摘を2回以上受けた** | この作業だけの都合（「今回は main を使って」） |
| **理由が語られた**（「〜だから〜して」） | 対象が1つに限られる（「このファイルだけ」） |
| **頻度が示された**（「毎回」「今後は」「基本方針として」） | 好みではなく事実の訂正（それは記憶違いの訂正） |
| **既存の資産が実態と食い違っていた** | 既定の挙動や既存資産で既に覆えている |

**既存資産との重なりを先に見る。** `ls ~/.claude/rules/` と `ls ~/.claude/skills/` を出し、**語ではなく主題で**近いものを探す（ `verify_before_asserting.md` ）。近いものがあれば**新設せず、そちらへ足す**。

### 2. 種類と置き場を見立てる

**2つの軸で決まります。** どちらか片方だけ決めても置けません。

**軸1: 何の資産か。**

| 性質 | 置き場 |
| --- | --- |
| 常に効かせたい振る舞いの規約 | `rules/*.md` |
| 呼ばれたときに踏む複数手順 | `skills/<name>/SKILL.md` |
| **「毎回必ず」が要件** | **`settings.json` の `hooks`**。ルールは読み飛ばされうるが、フックは必ず走る |
| 知っていれば判断が変わる前提 | `AGENTS.md` |
| **そのリポジトリだけの事実** | **`projects/<project>/memory/`** |

**軸2: 公開してよいか。**

| 内容 | 実体の置き場 |
| --- | --- |
| 汎用の規約・手順 | `home/` （**GitHub 上で全世界から読める**） |
| 社内の呼称・リポジトリ名・GitHub ID・プロダクトの状況 | `private/` |

**迷ったら `private/` に倒す**（ `no_internal_names_in_public_assets.md` ）。公開は取り消せません。

**既存を直す場合は、実体がどちら側かを確かめる。** `~/.claude/` はリンクなので、`readlink -f` で実体を見ないと判別できません。

### 3. 既に規約があるのに守られなかった場合

**「重複だから何もしない」で終わらせない。** 規約があって指摘を受けたなら、**規約側に欠陥があります**。

| 原因 | 直し方 |
| --- | --- |
| **書き方が曖昧**（2通りに読めた） | 判定基準を1通りに絞る |
| **置き場所が悪い**（読まれない所にある） | ルールへ引き上げる / 実行時に開く手順へ落とす |
| **要らない**（既定に取り込まれた・実行できない） | 消す |

直す前に、文章で頼むのをやめて構造で止められないかを、pstack の `principle-encode-lessons-in-structure` で見る。止める段の探し方は `/organize-rules` の `references/when-rules-fail.md` の「6つ目」。

**「次から気をつける」で閉じない。** 同じ逸脱が繰り返されるルールは、内容ではなく形に問題があります（ `rule_conventions.md` ）。

### 4. 承認を受ける

**必ず `AskUserQuestion` を出す**（ `ask_before_editing_claude_assets.md` ）。案が1つでも「はい / いいえ」の2択にします。地の文の問いかけは読み飛ばされ、答えないまま既成事実になります。

出すもの。

- **何を足す / 直すか**を1行
- **どこに置くか**と理由。既存を直すなら、**どの記述がどう実態とズレているか**を引用する
- **その案を推す理由**

**承認を得たら、書く前に他セッションへ1行予告する。** グローバル資産の実体は1つで、どのセッションからも同じファイルが見えます。**ユーザーの承認は予告を代替しません**（ `ask_before_editing_claude_assets.md` ）。対象を名指しして送り、返事を待ってから書く。相手が同じ箇所を諮っている最中なら、そのまま任せる。

### 5. 書く

書き方は置き場ごとの規約に従う。

| 置き場 | 従う規約 |
| --- | --- |
| `rules/` | `rule_conventions.md` （章立て・命名・量） |
| `skills/` | `rule_conventions.md` （書式）、`/organize-rules` （frontmatter・命名・引数） |
| `hooks` | 下記「フックを書くときだけの注意」 |

**自分が実行できない規定を書かない。** 途中でユーザーへ渡すことになるなら、それは規約ではなく依頼です。

#### フックを書くときだけの注意

**実物の入力で1回通す。** 自分で組み立てた payload は自分の想定どおりの形なので、**キー名が違っていても全ケース通ります**。捕捉用のフックを一時的に登録して実際の JSON を控え、形を確かめてから本実装に移る。

**出力は `hookSpecificOutput.additionalContext` に入れる。** `systemMessage` はユーザーの画面にしか出ず、素の stdout はどちらにも届きません。

**発火条件は狭く。** 誤検知は毎プロンプト出るので、ノイズになった時点で読まれなくなります。

### 6. 棚卸しまで済ませる

**手を入れたら、その置き場全体を見直すまでが1セット**（ `rule_conventions.md` ）。

- **分割**: 1ファイルに主題が2つ以上ある
- **マージ**: 同じ主題が複数に散っている
- **削除**: 無くても挙動が変わらない・既定に入った・実行できない
- **相互参照**: `## 関連` を**双方向に**張る。片方だけだと、もう片方から辿れない
- **手順への落とし込み**: ルールが求める作業が、**それを実行するスキルの手順に入っているか**

### 7. コミットする

**`home/` 側は git 管理下なので、コミットしないと環境を作り直したときに消えます。**

```bash
sh scripts/git-hooks/pre-commit    # 公開側の固有名を検査
```

- メッセージは Karma スタイル（ `karma_commit_style.md` ）。scope は `claude` / `hooks` / `mise` 等
- **`private/` 側は `.gitignore` 対象**なのでコミット不要
- dotfiles 以外のリポジトリで作業しているなら、**自分でコミットせず dotfiles のセッションへ依頼する**（ `notify_related_repo_sessions.md` ）

## 出力の目安

- **判定を先に1行**。「1回きりの指示なので資産化しません」で終わることもある
- 提案は `AskUserQuestion` に寄せ、本文には**背景と根拠だけ**を置く
- 反映後は**何をどこへ置いたか**と、棚卸しで何を確認したかを3〜5行

## やってはいけないこと

- **1回きりの指示を資産化すること。** 繰り返しの兆候が無いなら、その場で従えばよい
- **確認なしに作る・変える・消すこと。** 何を常時ロードさせるかはユーザーの領分
- **地の文で「〜しますか？」と書いて済ませること。** 答えないまま流れる
- **近い主題があるのに新設すること。** 既存へ足すか、`## 関連` で繋ぐ
- **語で「無い」と判定すること。** 同じ主題が別の言葉で書かれていれば当たらない
- **手を入れた資産だけ直して終えること。** 棚卸しまでが1セット
- **`home/` を編集してコミットしないこと。** 環境を作り直すと消える
- **フックを自分で作った入力だけで検証すること。** 形が違っていても全ケース通る

## 関連

- `ask_before_editing_claude_assets.md` （設定は尋ねてから）: **土台。** 気づく手掛かり・置き場の見立て・承認の形はあちらが定める。本スキルは**実行の手順**を足す
- `rule_conventions.md`: ルールとスキルの置き分けと整理。**5と6の中身はあちらが持つ**
- `no_internal_names_in_public_assets.md` （公開側に社内固有名を書かない）: 2の軸2の根拠
- `verify_before_asserting.md` （断定の前に裏を取る）: 「無い」を語で判定しない、フックは実物の入力で通す
