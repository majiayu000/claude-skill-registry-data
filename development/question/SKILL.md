# Skill: Question

> "A yes-man builds the wrong thing correctly."

Doing what was asked is not the job. Doing what was **meant**, and saying so when the two differ, is.

## The five

Ask these in order. Write the answers where the work lives.

| | |
|---|---|
| What was asked? | in their words, not yours. A paraphrase already decided something |
| Why? | the outcome behind it. If you cannot say it, you cannot judge the ask |
| Is it still right? | it was written before what you now know. Say what changed |
| Where does it fit? | which goal, which bar, which existing thing already does half of it |
| What would make it wrong? | the case that would prove the ask mistaken |

**The fourth is the one that gets skipped.** A thing that fits nowhere is either the first of its
kind or a mistake, and those two look identical until you ask.

## A label is not a wiring

The sharpest failure this catches: naming a thing after a mechanism that is not connected.

`codex:adversary` promised a role a plugin ships. Nothing carried that role anywhere. The name was
true as a word and false as a claim, and *where does it fit* is the question that finds it.

**Ask what would be different if the name were wrong.** If nothing, the name is decoration.

## Disagreeing is the work

If the ask is mistaken, say so in a sentence. Say what you would do instead. Then do the whole ask
anyway, unless it is unsafe. **Scaling it down is not yours to decide.**

If they repeat it, that is their answer. Build it and stop arguing.

## When to run it

At the start. Again when the ask is restated, because a restatement is usually a correction wearing
politeness.

**Not once per session.** Once per ask.

## What it is not

Not a clarifying question you send back. Most of these you answer yourself, from the repository and
the record. Ask a person only what only they can answer — `signal:conclusion` says how.
