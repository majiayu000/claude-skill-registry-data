# Glow Up 文章 SEO 內外鏈

這個技能處理 `articles.json` 裡文章內文（`content` 欄位，styled HTML）的連結：
**內部連結**（連到站內真實商品頁/看板頁/其他文章）跟**外部連結**（連到站外權威來源）。
兩者的可信度來源完全不同，處理方式也不同——**內鏈可以直接動手做，外鏈絕對不能編網址**。

## 核心原則：內鏈直接做，外鏈搜尋驗證後才做

- **內部連結是機械式的真實資料比對**（文章裡提到的商品名 vs `scores-data.json` 裡有真實
  評分的品項、文章主題 vs 子分類看板頁、文章主題 vs 其他文章的分類/標籤），判斷完就可以
  直接實作，不需要先列清單等使用者確認——這是已經跟使用者確認過的既定流程。
- **外部連結必須先用 `WebSearch` + `WebFetch` 實際搜尋、打開、驗證網址真的存在、內容也
  對得上主題，再列成表格（網址／建議錨點文字／建議安插位置）給使用者選，等使用者明確
  同意才動手加進去。絕對不能憑訓練資料裡的印象編一個看起來合理的網址**——那極可能是假的
  或已經失效，加進真實上線的網站是可信度風險。這條規則不能因為「使用者很趕」或「這個
  網域看起來很眼熟」而跳過。

## Part A：內部連結

### A1. 商品連結（文章內文 → `item-detail.html`）

1. 從文章 HTML 抓候選商品名：`<table>` 每列的第一個 `<td>` 純文字，加上內文裡所有
   `<strong>...</strong>` 包住的文字。
2. 跟 `scores-data.json` 裡 `composite != null`（有真實評分）的品項做比對，**只連有真實分數
   的品項，沒有評分的品項不連**（連過去會是空的商品頁，等於自砸招牌）。
3. 比對時容易漏配的兩個坑（都是這次專案實測踩過的）：
   - **品牌別名**：`scores-data.json` 裡有些品牌是英文（`CHANEL`／`DIOR`／`M.A.C`／`YSL`／
     `Bobbi Brown`／`MAKE UP FOREVER`），但文章內文常常只寫中文品牌名（「香奈兒」「迪奧」
     「魅可」），純字串比對「CHANEL」不會比對到「香奈兒」。比對時要準備一份品牌別名表
     （英文 ↔ 常用中文寫法），兩邊都比對過一輪才算完整。
   - **商品名尾綴**：`scores-data.json` 裡有些商品名帶著括號暱稱尾綴，例如
     「紅妍山茶花修護精華（小紅瓶）」「特潤超導全方位修護露（小棕瓶）」，但文章內文
     通常不會寫出「（小紅瓶）」這幾個字。比對前要先把商品名尾端的 `（...）`／`SPF...`
     這類尾綴剝掉再比對，剝完才比對得到。
4. 命中的商品名用 `<a>` 包起來，格式：
   ```html
   <a href="item-detail.html?item=<urlencode 商品名，不含品牌>&amp;from=board" class="text-[#f2a7b5] font-bold underline decoration-2 underline-offset-2">原本的文字</a>
   ```
   `item=` 只放商品名（`scores-data.json` 的 `name` 欄位），不含品牌，這是站內既有的連結格式
   （`script.js` 的 `topItemsForSubcat` 等函式都是這樣產生連結的，保持一致）。
5. 同一個商品在文章裡通常會出現兩次以上（表格 + 內文段落），**只連第一次出現的位置**，
   避免同一頁對同一個商品重複連結太多次（對 SEO 跟閱讀體驗都不好）。

### A2. 看板頁連結 + 文章互連（「延伸閱讀」區塊）

每篇文章結尾（`FAQ`／最後一個 `<h2>` 之前）加一個固定格式的區塊：

```html
<h2 class="text-2xl font-black mt-10 mb-4"><strong>延伸閱讀</strong></h2>
<ul class="list-disc pl-6 mb-6 text-gray-600">
  <li class="mb-2"><a href="detail.html?sub=<子分類>&amp;from=board" class="...">X看板：真實社群評分排行 ➔</a></li>
  <li class="mb-2"><a href="article.html?id=<其他文章id>" class="...">其他文章標題</a></li>
  ...
</ul>
```

- **看板連結**：依文章主題對應的子分類（通常就是文章的 `tag` 或商品連結最集中的那個
  `subcat`）。如果文章橫跨多個子分類（例如同時比較蜜粉/氣墊粉餅/定妝噴霧），可以連
  一個以上的看板。
- **文章互連**：找 2-3 篇主題相關的既有文章（同類別、同標籤、或內容邏輯上相關，例如
  護唇膏文章連唇妝比較文章、防曬乳搓泥連乳液搓泥）。**判斷相關性时可以把文章依內容
  分成幾個群組**（例如「搓泥現象系列」「清潔卸妝routine」「底妝教學系列」「眼妝系列」
  「唇妝系列」），群組內的文章互相連結最自然。

### A3. 雙向連結（新文章上線時，也要回頭幫既有文章加反向連結）

新文章連了哪幾篇既有文章，**要回頭在那幾篇既有文章的「延伸閱讀」`<ul>` 裡也補上連回新
文章的 `<li>`**，不要只有新文章單方面連出去。作法：在既有文章的
`<h2><strong>延伸閱讀</strong></h2><ul...>` 區塊的 `</ul>` 前插入新的 `<li>`。

## Part B：外部連結

### B1. 找候選來源

針對文章裡的醫學/科學性主張（膚況原因、成分作用、皮膚科建議），搜尋方向優先順序：

1. **政府機關**：衛福部（`mohw.gov.tw`）、食藥署（`fda.gov.tw`）——最高權威，但內容通常
   偏法規面（例如 SPF 標示規範），不一定每個主題都有對應頁面。
2. **醫院衛教**：台大醫院等醫院的衛教文章知識庫（例如 `ntuh.gov.tw`）。
3. **皮膚科診所衛教文章**：真人皮膚科醫師掛名撰寫的文章（例如林政賢皮膚科診所），比
   一般美妝媒體更有專業背書。
4. **獨立媒體**：Marie Claire台灣、ETtoday、Heho健康等有記者掛名、非品牌自營的媒體。

**絕對要避開的**：搜尋結果裡很多是**競品美妝品牌自己的官網文章**（例如某品牌官網的
「畫眉毛教學」，內容其實是導購）。連到這種頁面等於把連結權重跟讀者導去競爭對手那裡，
對這個網站沒有任何好處。同一個主題如果只找得到品牌自營內容，寧可換一個角度搜尋（例如
從「彩妝師專訪」「臉型分析」切入）找到中立媒體來源，也不要將就用品牌網站。

### B2. 驗證

**每一個候選網址都要用 `WebFetch` 實際打開，確認**：
1. 網址真的存在、能正常讀取內容（不是 404 或需要登入）。
2. 標題／內容主題真的對得上要引用的主張，不是望文生義猜的。
3. 如果 `WebFetch` 回傳 403 或其他錯誤（某些網站會擋自動化讀取，例如 CosDNA 這類成分
   資料庫常見），**不要因此當作它不存在就放棄，但也不能當作已驗證**——如實跟使用者說
   「這個網址我沒辦法自動驗證，你要用的話建議自己點開確認一次」，把最終判斷權交還使用者，
   不要幫使用者做「應該還活著」的樂觀假設。

### B3. 列表給使用者選

驗證完，用表格列出：**文章｜建議連結（含來源標題＋網址）｜建議錨點文字｜建議安插位置
（哪一段、接在哪句話後面）**。等使用者明確回覆同意（或指出要調整的地方）才動手加。

### B4. 實作格式

```html
<a href="<驗證過的網址>" target="_blank" rel="noopener noreferrer" class="text-[#f2a7b5] font-bold underline decoration-2 underline-offset-2">錨點文字</a>
```

> ⚠️ **不要用 `<em>` 斜體包住錨點文字**（`<em>錨點文字</em>`）。這個專案早期的做法（AI
> 草稿內容留下來的舊習慣）是外部連結錨點文字加斜體，但斜體 + 底線的組合在某些字體下會
> 讓文字最後一個字被視覺上遮住一部分，使用者實測發現過這個問題。純色文字（`text-[#f2a7b5]`）
> + 底線（`underline decoration-2 underline-offset-2`）已經足夠跟一般內文區分，不需要再加
> 斜體。這是使用者明確反饋過的規則，不要因為「看起來比較正式」又加回去。

外部連結安插位置盡量選在文章原本就有相關論述的段落**之後**，用一句銜接語帶出來（例如
「XX機構／醫師也提到...」），不要生硬地把連結丟在段落開頭或跟原文語氣脫節。

## 完成後

1. 用 Python 檢查 HTML 標籤配對（`<a>`/`</a>`、`<p>`/`</p>`、`<ul>`/`</ul>` 等 open/close
   數量相等），確認沒有因為字串替換破壞既有結構。
2. Bump cache-busting 版本號。**這一步有兩個地方要一起改，只改一邊等於沒改**：

   a. `script.js` 裡的 `fetch('articles.json?v=NN')`；
   b. **專案根目錄所有 HTML 檔的 `<script src="script.js?v=NN">`**（`index.html`、
      `article.html`、`item-detail.html`、`detail.html`、`news.html`、
      `skincare-blog.html`、`review-base.html`、`review-landing.html`、
      `board-landing.html`、`privacy-policy.html`，共 10 個，用
      `grep -rl "script.js?v=" *.html` 確認當下清單）。

   兩個號碼**設成同一個數字**，日後一眼就看得出有沒有漏。

   > ⚠️ 為什麼兩邊都要改（2026-09-23 實際踩到）：`articles.json?v=NN` 是寫在
   > `script.js` **內部**的。如果只改它、沒動 HTML 裡的 `script.js?v=`，那個 URL 就沒變，
   > 瀏覽器會直接沿用**快取中的舊 `script.js`**——舊檔裡指的還是舊版 `articles.json`，
   > 於是文章內容看起來完全沒更新。這個 bug 當時已經存在一段時間（HTML 停在 `v=73`，
   > 中間好幾次改稿都只動了 `script.js` 內部的號碼），症狀是本機預覽與正式站的**回訪**
   > 讀者都看不到新內容，但用新分頁／無痕視窗開又是對的，很容易誤判成「我沒改到」。
   > 驗證方式：`curl -s "<頁面網址>" | grep -o "script.js?v=[0-9]*"`，
   > 再對照 `grep -n "articles.json?v=" script.js`，兩個數字必須一致。

   `site-data.json`／`scores-data.json` 有各自獨立的版本號軌道，改文章時不用動。
3. 開瀏覽器實際打開改過的文章頁，確認連結有正確渲染、可以點擊、導到正確頁面。
4. **commit + push 前，把這批（含新文章）的標題列出來給使用者看，等明確同意才繼續**
   （2026-08 使用者定案：標題要每篇客製化找獨特切角，不套固定公式——見
   `beauty-seo-article-writer` skill 的標題規則，但客製化寫法品質比套公式風險更高，
   所以要求 commit 前先人工把關，不能自己判斷「應該可以」就跳過）。使用者同意後才能
   commit + push；內鏈跟外鏈可以分開兩次 commit（內鏈已核准可先推，外鏈等使用者確認
   後再推），方便回溯。
