# Weaver Pulse (MCP Integration Specialist)

Scheduled cron pulse for the Weaver profile. Every cycle: gate on quiet hours, sweep the MCP fleet, do ONE meaningful integration action, log to PULSE.md + daily digest, deliver a compact Discord report.

## Execution Sequence

### 1. Quiet-hours gate (do this FIRST)
```bash
TZ='EST5EDT,M3.2.0/2,M11.1.0/2' date +%H
```
- Hour 00–06 → respond exactly `[SILENT]`, skip all work.
- Hour 07+ → proceed with the pulse. Use `date` for the report timestamp (ET) and `date -u` for the PULSE.md header (UTC).

### 2. Fleet health sweep
Run live heartbeats through the MCP tools themselves (they prove server + transport both work), plus a port sweep for non-tool servers:
- Live tool heartbeats: BizDev `bizdev_heartbeat`, Job Agent `heartbeat`, Git Stars / Personal Intel `health_check`, Postgres `pg_execute_query`, Firefox `health` (or `firefox_health`), trading-signals `market_summary`, gbrain `get_health` (track `page_count`, `orphan_pages`, `brain_score` — every PULSE.md entry historically records these).
- Port sweep: `netstat -ano | grep LISTENING | grep -E ":(3000|3002|5432|8501|8888|33000|9223|11434)\s"` — 3000 Buzz relay, 3002 Cal.diy, 5432 Postgres native, 8501 AI Scientist, 8888 Open Coscientist, 33000 Job Agent, 9223 Firefox BiDi, 11434 Ollama.
- Identify unknown/contested listeners: `tasklist //FI "PID eq <pid>"` silently returns EMPTY in git-bash — use `powershell -NoProfile -Command "Get-CimInstance Win32_Process -Filter 'ProcessId=<pid>' | Select-Object ProcessId,Name,CommandLine | Format-List"` for the owning process + full command line, and `curl -s -m 5 http://localhost:<port>/` (response body) to fingerprint the service. A port can carry BOTH a docker-proxy listener (PID = com.docker.backend/wslrelay) and a native process — enumerate every PID netstat shows for the port, don't stop at the first.
- Docker: `docker ps --format '{{.Names}} {{.Status}}'` for container health. Cross-check container start times against `com.docker.backend` / `wslrelay` process start times: identical `Up X minutes` across the fleet + a fresh Docker backend start = a daemon restart, not N independent container crashes. After a daemon restart, GPU compose stacks (e.g. `yt-anim-ollama`, `yt-anim-comfyui`, `yt-anim-fishspeech`) commonly exit (255) and DON'T auto-restart — re-probe their ports fresh instead of carrying a stale "down" flag forward. A container can report `(healthy)` while the app still returns curl 000 (healthcheck passed, app not yet serving) — re-probe once more before flagging it down.
- Git activity: `find . -maxdepth 2 -name .git | xargs git log --since="24 hours ago"` scan over the github root (see `recurring-status-checks` for large-repo fallbacks). **⚠️ MSYS absolute-path false-zero:** `find ${MY_REPOS}/...` + `git -C "$d"` with absolute MSYS paths SILENTLY returns zero commits even when repos are active — the scan is lying, not the repos. On a zero result, re-verify from the github root with relative paths (`cd ${MY_REPOS} && for r in _project website-landlord ghl hermes-config; do git -C "$r" log --oneline --since='48 hours ago' | wc -l; done`). Live example Aug 7 2026: absolute scan 0 commits, relative scan ghl 17 + website-landlord 4 + hermes-config 1.

### 3. One meaningful integration action
Pick ONE concrete fix/discovery per cycle (see Pitfalls for the recurring ones). Verify end-to-end before reporting; do not just describe intent.

**Quiet-cycle fallback — gbrain orphan cross-linking** (cheap, deterministic, clears chronic PULSE.md Next Actions): if the fleet is healthy and no fix is pending, run `mcp__gbrain__find_orphans` and cross-link orphan pulse pages to their chronological predecessors with `precedes` edges (`link_source: integration-lead-pulse`). Verified Aug 7 2026: 2 orphans → 0, brain score 83 → 85 in 4 tool calls. Full sequence + slug-naming/temporal notes: `references/gbrain-orphan-crosslinking.md`.

### 4. Logging
- **PULSE.md** (`${USER_HOME}\AppData\Local\hermes\profiles\integration-lead\PULSE.md`) — append with a quoted heredoc (zero truncation risk, no read-back needed):
```bash
TS=$(date -u +%Y-%m-%d\ %H:%M)
cat >> PULSE.md <<'EOF'

## Pulse @ $TS UTC
- **Status**: 🟢 Nominal / 🟡 Attention Needed / 🔴 Issue Found
- **Focus**: [what you investigated this cycle]
- **Findings**: [specific and actionable]
- **Next Action**: [one thing to do next]
EOF
```
- **Daily digest**: `python "${MY_REPOS}/Documents/github/_project/scripts/append-digest.py" "Weaver Pulse" "- finding1\n- finding2"` — use the literal `E:/...` Windows path (MSYS `/e/...` breaks cross-drive Python calls). Check the digest file exists before assuming it was written. **The script prints `[SILENT]` + `Quiet hours (00:00-06:59 EST) — saved to digest only` when its OWN clock check fires (observed at 21:24 ET = 01:24 UTC — it keys on UTC, not ET). That output is the script's internal digest-mode message, NOT a directive to suppress the report.** The step-1 ET gate is the ONLY authority on `[SILENT]` delivery. If the script prints it during non-quiet ET hours, the digest WAS still appended — confirm via the file/echo, then deliver normally.

### 5. Report
Follow `discord-report-format`: emoji header + ET timestamp, compact bullets, box-drawing separators, **🔍 Checked:** footer. Keep under 1500 chars. Start with a notice line if any listed skill was skipped.

## Pitfalls (learned the hard way)

- **`@henkey/postgres-mcp-server` ignores `DATABASE_URL`** — its tools error `No connection string provided` unless `POSTGRES_CONNECTION_STRING` is in the server's `env:` block. Configs commonly carry a stale `DATABASE_URL` (asyncpg scheme → dead port/instance that rejects creds) that the server never reads. **Live-verify before wiring:** pass the candidate string as the per-call `connectionString` tool arg and run `SELECT datname FROM pg_database` — success proves the exact value; then commit it to config `env:` (activates on next restart).
- **`enabled: false` in config is the real blocker, not the restart.** A server that never comes up across many pulses may be disabled in config. Grep the config entry (`grep -A6 "<server>:" config.yaml`) for `enabled: false` before scheduling yet another "restart overdue" action. (AI Scientist was mislabeled restart-blocked for 16 days; the actual cause was `enabled: false`.)
- **Firefox MCP bridge: registered tools ≠ functional bridge; port up ≠ bridge connected (Aug 8 2026).** `ultimate-firefox-mcp` tools appeared in-session for the first time ever, but `list_tabs` failed `Cannot detect Firefox: No Firefox found on BiDi:9239 or CDP:9239` — a port mismatch, not a crash. Config `args --port 9239` ≠ live headless Firefox on **9223** (`--headless --no-remote --profile <hermes-profile> --remote-debugging-port 9223`). ALWAYS confirm registration with a read-only tool call (`list_tabs`); when a bridge can't find its browser: (1) `netstat -ano | grep LISTENING | grep -E ":(9223|9239)\s"` for the real listener; (2) `powershell Get-CimInstance Win32_Process -Filter "ProcessId=<pid>"` for the actual `--remote-debugging-port`; (3) enumerate ALL non-contentproc Firefox cmdlines (`Where-Object { $_.CommandLine -notmatch 'contentproc' }`) — two headless instances on the same profile+port = profile-lock risk, kill the loser with `taskkill //F //PID`; (4) BiDi liveness: `POST /session` → `400 The handshake request must use GET method` is spec-CORRECT alive (WebDriver BiDi handshake is a GET WebSocket-upgrade), `/json/version` 404 = BiDi-only not CDP — don't misread either as dead. Fix: align bridge `--port` to the live listener (or relaunch browser on the configured port), dedupe instances, restart Hermes. Full recipe: `references/firefox-bidi-bridge-diagnostics.md`. **Structural root cause found (Aug 10 2026)**: the bridge was broken INDEPENDENTLY of the port mismatch — (1) `_check_bidi` called `websockets.connect(..., timeout=)` but websockets 15.0.1 renamed the kwarg to `open_timeout` → TypeError → silent False → "Cannot detect Firefox" forever (CDP fallback also dead: Firefox 129+ removed `/json/version`); (2) Firefox returns `children: null`, and `ctx.get("children", [])` yields None → `for child in None` crash in the flatten helper. Fixed `open_timeout=timeout` (main.py) + `(ctx.get("children") or [])` (tools/__init__.py), then relaunched a fresh headless Firefox. **VERIFIED WORKING end-to-end (Aug 11 2026) — first-ever full round-trip.** Canonical proof pattern: `list_tabs` (baseline) → `navigate(url, wait="complete")` (returns `navigation_id`) → `list_tabs` again and confirm the tab's URL updated. If those three calls round-trip, the bridge is production-ready for browse/QA workflows. Do NOT treat `curl http://localhost:9223` → 000 as a down signal — BiDi is a WebSocket GET-upgrade, not HTTP; the bridge liveness check is the tool call itself.
- **trading-signals `N/A` / openbb-finance errors = shared OpenBB install version skew, FIXED via durable venv (Aug 1 2026).** Root cause: openbb 4.7.x meta-package's generated `package/equity.py` statically imports `OBBject_EquityInfo` from `openbb_core.app.provider_interface`, but openbb-core 1.6.13 (latest) only creates `OBBject_*` types DYNAMICALLY via `ProviderInterface._generate_return_annotations()` (181 models incl. EquityInfo) and never injects them into the module namespace — so the import fails and every OpenBB-dependent server (trading-signals, openbb-finance) breaks at the same line. Verified byte-identical to official wheel + sdist; no module `__getattr__` anywhere. Downgrading openbb 4.7.2→4.7.1→4.6.0 did NOT help on the system (build regenerates the same broken import) — but a clean venv with openbb 4.6.0 + openbb-core 1.6.13 works (system is polluted by editable `.pth` finders pre-registering extensions before auto_build). **Fix applied**: durable venv `${USER_HOME}\AppData\Local\hermes\venvs\openbb-trading` (openbb 4.6.0 + mcp 1.28.1), rewired `trading-signals` + `openbb-finance` `command:` to that venv's python in root config. Verified: server module loads all 4 tools, live SPY quote works. Full recipe: `references/shared-dependency-version-skew.md`.
- **trading-signals `market-summary` N/A survived the venv fix — second root cause in the server code itself (Aug 2 2026).** Two independent bugs in `trading-signals-mcp.py`, independent of the version skew above: (1) `obb.equity.price.quote(sym)` with NO provider → OpenBB default provider routing hangs without API keys; fix `provider="yfinance"`. (2) extraction assumed row dicts, but openbb-core 1.6.13 `OBBject.to_dict()` returns COLUMN-oriented dicts (`{'bid': [744.11], ...}` — list values, no `price`/`close`/`c` keys) → every symbol silently resolves to "N/A" even on successful quotes. Fix: unwrap `{k: (v[0] if isinstance(v, list) and v else v) for k, v in data.items()}`, fall back to `bid`, compute change% from `prev_close`. Verified in-process: SPY 744.11 live, all 5 symbols numeric.
- **trading-signals `market-summary` 0.0/−100% regression (Aug 3 2026) — the `bid` fallback was itself a third bug.** yfinance quote `to_dict()` has NO `price`/`close`/`c` key at all; `bid`/`ask` are literally `0.0` outside trading hours (pre-market/overnight). The Aug 2 fallback `data.get("price", data.get("bid", ...))` resolved to `bid=0.0` → change% computed `(0−prev)/prev = −100%` for SPY/DIA/IWM/VXX (QQQ only "worked" because yfinance had populated its bid). **Durable fix**: price fallback chain `last_price → price → open → close/c → nonzero bid/ask` (skip zero values), and never compute change% when `price` is falsy. `open` is reliably populated pre-market. Committed `890da31`. Full detail + raw `to_dict()` evidence: `references/trading-signals-data-shape-fixes.md`.
- **Audit EVERY tool in a file after a data-shape fix.** `technical_signals` had the identical column-oriented-`to_dict()` bug that the Aug 2 fix addressed only in `market_summary` — it still errored `Unexpected data format: dict` because `historical().to_dict()` is also column-oriented (`{"close": [...]}`) while the code only handled list-of-dicts. Fix: extract the `close`/`c` column directly from the dict form. When a shape quirk hits one tool, grep the same file for other `to_dict()` / `data.get` consumers.
- **MACD signal-line unit mismatch (Aug 4 2026) — `MACD_BULLISH` unreachable, fixed + committed `9113836`.** `signal_line = sum(closes[-9:]) / 9` was SMA of the last 9 **closes** (price units, ~$770) while `macd = ema12 − ema26` is ~2–3 units → `macd > signal_line` was always false → the tool could only ever print `MACD_BEARISH`. Second latent bug: `ema12`/`ema26` were simple averages of the last 12/26 closes, not true EMAs. Fix: full EMA-12/26 series over all closes, then `signal_line = EMA-9 of the MACD series` (standard MACD(12,26,9)). Verified live: SPY macd 2.56 / signal 0.56 / hist 2.0 → `MACD_BULLISH` fires for the first time. **General lesson: a one-sided indicator comparison usually means unit mismatch (indicator scale vs price scale) — verify BOTH branches are reachable, not just the one live data shows.** Branch-coverage recipe + diff: `references/trading-signals-macd-fix.md`. Existing `scripts/verify-trading-signals.py` still covers Bugs 1–3 (compile, index prices, technical_signals shape); add the MACD unit-scale + branch checks from the reference if you touch MACD again.
- **A patched MCP server file does NOT go live until its subprocess restarts** — the running process holds the old module in memory, so live tool calls still show old behavior after a correct on-disk fix (trading-signals ran stale code for hours; fresh-import of the file proved the code was right). Verify fixes against a FRESH import of the on-disk file, report "goes live on next restart", don't misdiagnose the live server. After config rewiring to a new venv, check for **duplicate server PIDs** (stale subprocess on the old python survives alongside the new one — only ONE config entry exists).
- **Verify MCP fixes with a focused assertion script, not just eyeballed output.** Reusable ad-hoc verifier: `scripts/verify-trading-signals.py` (asserts py_compile clean; every index price > 0 and change ≠ −100.0; `technical_signals` ≥ 20 points with no dict-format error; exits non-zero on failure). Run with the venv python and `env -u PYTHONPATH` — the agent process PYTHONPATH carries Python-3.13 ABI packages that break 3.11 venv servers. Place under the OS temp dir with a `hermes-verify-` prefix when writing ad-hoc variants; clean up after.
- **`openbb-trading` venv can break silently between cycles (`importlib_metadata` missing, Aug 4 2026)** — `import openbb` failed `ModuleNotFoundError: No module named 'importlib_metadata'` at `openbb_core/app/extension_loader.py` (line 8), so trading-signals live tools errored `OpenBB not installed` while openbb-finance (spawned earlier, openbb imported at module load) kept working — the mismatch is the diagnostic clue. Fix: `pip install importlib-metadata` into the venv (`${USER_HOME}/AppData/Local/hermes/venvs/openbb-trading/Scripts/python.exe -m pip install importlib-metadata`). **Self-heal property**: trading-signals tool functions lazy-import openbb INSIDE each call, so after fixing the venv on disk the RUNNING server recovers on the next call — no Hermes restart needed. Verify with live `market_summary` + `technical_signals` MCP calls, not just in-process imports.
- **REMAINING (trading-signals): OpenBB tool calls hang inside the FastMCP worker-thread context.** Not reproduced Aug 3 — the live server returned `market-summary`/`technical-signals` quickly (wrong values, not hangs), so the hang may be resolved by the venv rewiring or only manifest post-restart with the patched code. Re-check after the next Hermes restart. `market-summary` AND `technical-signals` over stdio MCP hang indefinitely (or `McpError: Connection closed` — server process dies mid-call) while identical code runs 2–5s in the main thread. Isolation technique: load the module with `importlib.util.spec_from_file_location` and call the tool function directly in the main thread — fast JSON ⇒ data layer fine, hang is the `anyio.to_thread` context; suspected openbb-core extension auto-build thread-safety. Debug next: pre-warm OpenBB at module import (main thread, before `mcp.run()`), or wrap tool bodies in a dedicated thread; escalate to Forge with repro if confirmed. Full case study: `mcp-endpoint-testing` → `references/fastmcp-thread-context-hang.md`.
- **Clean-venv control test before cycling versions**: when a Python MCP server's tool calls fail with `N/A`/`ImportError` from a shared library, build a throwaway venv (`python -m venv C:/tmp/testvenv` — Windows path!), install the SAME versions, rerun the import. If the venv works, the system install is polluted — don't downgrade blindly, isolate the server in a durable per-server venv instead and point `command:` at it.
- **Ghost-package quirk in fresh venvs**: right after `python -m venv`, `pip list` may show a package (e.g. `mcp`) that `import` cannot find — pip resolved it from the base interpreter's metadata. Fix: `pip install --force-reinstall --no-deps <pkg>==<ver>` inside the venv, then re-verify the import.
- **Windows venv creation needs `C:/...` paths**: `python -m venv /c/tmp/foo` (MSYS path) silently creates nothing; use `C:/tmp/foo`. Same for `pip download -d` — MSYS `/c/...` args get mangled; pass `C:/...`.
- **Long-running known-down state (MemPalace 3001, AI Scientist 8501):** reference previous PULSE.md entries for the known cause instead of re-diagnosing from scratch every cycle. Note whether it moved, don't re-litigate.
- **Config edits are write-blocked:** edit `config.yaml` via a small Python script executed through `terminal()` (read → assert unique anchor → replace → verify → clean up), not `write_file` directly.
- **Decommissioned compose project → orphaned container-name squatting (Aug 7 2026).** A compose project whose dir was emptied/deleted can leave containers behind, still squatting on `container_name:` values the ACTIVE stack's compose needs. `docker compose up -d` from the active dir silently does nothing for those services, and the dependent app runs degraded with no job engine (postiz app pointed at `TEMPORAL_ADDRESS=temporal:7233`; no `temporal` server container existed — only Exited orphans from deleted `GradientRun/postiz` whose compose dir was empty). Detect: `docker compose ls` shows a project whose CONFIG FILES dir is empty; `docker inspect <container> --format '{{index .Config.Labels "com.docker.compose.project"}} | {{index .Config.Labels "com.docker.compose.project.working_dir"}} | {{index .Config.Labels "com.docker.compose.project.config_files"}}'` reveals the squatter's true origin; grep the active compose for the same `container_name:`. Fix: `docker rm` only the squatter containers (NOT `docker compose down` — that takes the running app down), then `cd /path/to/active && docker compose up -d <engine> <admin-tools>`, then `docker update --restart unless-stopped` on the new containers (orphans typically had `restart=no` — the exact reason they stayed dead after a daemon restart). Verify beyond "Up": service port open, query the engine from its admin container (`docker exec <admin-tools> tctl --address <engine>:7233 namespace list` — namespaces registered = serving), `docker exec <app> getent hosts <engine-host>`, app logs clean. **Hermes terminal guard blocks `docker compose up -d` in foreground** (\"appears to start a long-lived server/watch process\") — run via `terminal(background=true)` then `process(action='wait')`; `docker rm` alone runs fine in foreground, so split the steps.
