自分が担当している open な PR を**表1つ**で見渡せるようにします。「**何を対応していて / 何と紐づいていて / 今どれを動かせるか**」が即座に分かる状態がゴールです。

## 進め方

### 1. 対象 PR を集める（横断が既定）

**カレントリポジトリだけを見ない。** 1つのプロダクトが FE / BE / インフラに分かれており、**PR は単独で完結しません**。片方だけ見ても、何が何を待っているか分からない。

- 対象はローカルにクローン済みの関連リポジトリ全部（ `~/Documents/repositories/github.com/<org>/` 配下を `ls` で列挙）
- **リポジトリごとの取得は独立なので、単一メッセージ内で並列に発行する**

  ```bash
  gh pr list --author "@me" --state open --json number,title,headRefName,isDraft,mergeStateStatus,updatedAt
  ```

- 引数にリポジトリ名があればそれだけに絞る
- **open PR が0件のリポジトリは表から省く**（行だけ増えて読みづらい）。全リポジトリで0件なら1行で返して終了
- **マージ済み・クローズ済みは扱わない。** 「一連の対応がすべて済んでいるか」を聞かれても、**済んだものを並べずに「未マージは無い」と答える**。手が要らないものを並べると、行動の要る PR が埋もれる

### 2. 各 PR の状況を取る（並列実行）

**PR ごとの取得は独立なので、単一メッセージ内で並列に実行する。** 直列にすると PR 数だけ待ち時間が積み上がる。

| 取るもの | コマンド |
| --- | --- |
| CI | `gh pr checks <PR>` |
| マージ可否 | `gh pr view <PR> --json mergeStateStatus` |
| **approve の有無** | **`latestOpinionatedReviews` を GraphQL で引く**（下記。`reviewDecision` と `latestReviews` は使わない） |
| コメント欄 | `gh api repos/OWNER/REPO/issues/<PR>/comments` を**投稿者を問わず**読む。自分の保留メモと、**レビュアーの申し送り**の両方が要る |

**CI が fail のときは原因まで見る。** `approval required` （レビュー承認待ち）のようにコードと無関係な失敗があり、これを「壊れている」と報告すると誤解を招く。`gh run view <id> --log-failed` で末尾を確認する。

### 3. ブランチとの対応を見る

- カレントブランチがどの PR に対応するかを明示する
- ローカルに未 push のコミットや未コミット変更があれば添える（ `git status --porcelain` / `git rev-list --count @{upstream}..HEAD` ）
- base ブランチが進んでいれば、その旨も（ `git rev-list --count HEAD..origin/<base>` ）

### 4. 紐づきを洗い出す

**横断で見る一番の目的がここ。** 各 PR の**本文と自分のコメント**から PR 参照を抽出し（ `owner/repo#123` / 同一リポジトリの `#123` / コメントへのアンカー付き URL）、参照先の状態を引く（ `gh pr view <ref> --json state,mergedAt,isDraft` （approve が要るなら `latestOpinionatedReviews` を併せて引く））。**リポジトリをまたぐ参照も対象**。

紐づきが分かったら、**どちらが待たせている側か**まで判定する。

| 関係 | 見分け方 | 報告 |
| --- | --- | --- |
| **相手が律速** | 依存先が open で未 approve | こちらは待ち |
| **こちらが律速** | 依存先が **approve 済み / マージ待ち** | **こちらを進めれば相手が動く**。最優先 |
| マージ順の制約 | 本文に「〜が先」と書いてある | 順序を明記する |

**「依存先が open だからこちらも待ち」と短絡しない。** 契約が固まっていて片側先行が安全な変更では、**遅れている側が相手を止めます**。

#### 参照の鮮度も見る

**片方がマージされると、もう片方の参照が古くなる**ことが構造的に起きる。よくある形は次のとおり。

| 古くなり方 | 例 |
| --- | --- |
| 依存先がマージ済み | 「〜が前提です」と書いた PR が既に入っている。前提ではなく完了事項 |
| 参照先がクローズ | 別 PR に置き換わった。リンクが行き止まりになる |
| 正本が移動した | コメントの内容が別 PR へ移された。アンカー付き URL が古い場所を指す |

参照先の**状態が変わっただけ**（open → merged）なら本文の書き換えが要るとは限らない。**「前提」「〜待ち」と書いてあるのに満たされている**ものを優先して挙げる。

**このスキルは検出だけで、直さない。** 古くなった参照を見つけたら、報告に「該当 PR で `/update-pr-description` を打つと本文とコメントを直せる」と添える。修正は1 PR 単位の作業なので、一覧のついでにやると対象を取り違える。

### 5. 「何待ちか」を判定する

一覧の価値は**次に何をすればいいか**が分かることにあります。各 PR について、以下のどれかに分類する。

| 状態 | 判定材料 |
| --- | --- |
| **動かせる** | ready / CI 緑 / approve 済み → マージできる |
| **レビュー待ち** | ready だが approve 未取得 |
| **こちら待ち** | draft のまま / CI が fail（コード起因）/ 未 push の変更がある |
| **外部待ち** | 他リポジトリの PR やデプロイが前提。**PR 本文やコメントに書かれた保留条件を読み取る** |

外部待ちは本文の「動作要件」節や `[fyi]` コメントに書かれていることが多い。**依存先の PR 番号があれば、その状態も併記する**（ `owner/repo#123` を `gh pr view` で引く）。

#### draft は「今 ready にしてよいか」まで判定する

**draft をまとめて「こちら待ち」にしない。** 実際には「出せるのに出していないだけ」と「出すべきでない」が混ざっており、前者は放置すると依存先を止めます。

| 判定 | 材料 |
| --- | --- |
| **出せる** | CI が緑（ `approval required` の fail は除く）で、依存先がマージされていなくてもレビューは成立する |
| **出さないほうがよい** | 前提が未確定で**レビュー中に設計が変わりうる** / 依存先の契約が固まっていない / 他 PR とマージ順を調整中で先に出すと誤解を招く |

**依存先が未マージだから出せない、ではありません。** 判定は「**レビュアーが今読んで、指摘が無駄にならないか**」で行う。契約が固まっていて FE 先行が安全な変更（nullable 化・新フィールドの受け入れなど）は、依存先が open でもレビューに出せます。むしろ**こちらが遅れると依存先を止める**ので、その旨を添える。

依存先が approve 済み・マージ待ちなら、**こちらが律速になっている**ことを明記する。

**ready 化そのものは絶対にしない**（ `no_auto_ready_pr.md` ）。判定を示して、実行はユーザーに委ねる。

### 5.5. レビューの急ぎ度を判定する

**全部を同じ温度で出すと、レビュアーは順序を自分で決めることになる。**

```bash
gh pr view <PR> --json files -q '[.files[].path]'
```

**2つの軸で見る。** まず「**その変更がプロダクトに届くか**」、届くなら「**挙動が変わるか**」。

| 急ぎ度 | 判定 |
| --- | --- |
| **高** | **リリース済み機能の不具合修正**。今ユーザーが困っているので、早くリリースしたい |
| **中** | **挙動が変わる**もの。新機能・未リリース機能への追加・仕様の変更 |
| **低** | **挙動が変わらない改善**（リファクタ・CI とビルド・命名の統一）と、届かないもの |

**「届く」だけで中にしない。** リファクタは届くが挙動を変えないので低です。**動くものが増えないぶん、後回しにしても失うものがない**。

**例外: 網羅を固定するテストは中。** 定義を足したときの追随漏れを検知する形のテスト（列挙の全値を走査する等）は、**入っていない間だけ漏れが素通りします**。後回しにするほど守れなかった期間が伸びるので、他の改善系より前に置く。

**高と中の分かれ目は「その機能が今、ユーザーに使われているか」。** `fix` の PR でも、**未リリースの機能や feature flag で塞がれている機能の修正は中**です。直しても今困っている人はいません。

**「デプロイ済み」と「ユーザーが使える」は違う。** リリースされていても flag で塞がれていれば中。

まず PR 本文の「影響範囲」を読む。「表示は変わりません」「flag OFF で未露出」と書いてあれば中、「〜が表示できなくなる」「誤った値が出る」なら高の候補です。

**ただし本文に flag の状態が書かれていないことがあります。** 不具合修正に見えても、その機能が実際に使われているかは運用を知らないと分かりません。**判断がつかなければ高に上げず、ユーザーに聞く。** 急ぎでないものを高と呼ぶと、本当に急ぐものが埋もれます。

**パスは手がかりであって、判定の根拠ではありません。** 下の例は**網羅ではない**ので、リストに無いパスを機械的に「低」へ落とさない。

| | 高・中になりやすい | 低になりやすい |
| --- | --- | --- |
| FE | `apps/` / `packages/` / `package.json` / `turbo.json` | `.claude/` / `docs/LLM/` / `.agents/` |
| BE | `internal/` / `cmd/` / `pkg/` / `go.mod` | `docs/agents/` / `.claude/` |

**分類に迷ったら中身を見る。** パスが見慣れなければ、その変更が動くコードに影響するかを確かめる。ビルド設定・依存・デプロイ設定は、パスがどこであれ「届く」側です。

**テスト・Storybook・型定義も「届く」側。** 実装と同じリリースに乗るので、パスを理由に低へ落とさない。`packages/` は**複数アプリから使われるぶん影響がむしろ広い**。

**そのうえで、テストは一律ではない。** 網羅を固定するものは中、既存の挙動を後から確認するだけのものは低（挙動が変わらないため）。

**例外で「低」から引き上げるもの。** 次に当たるときだけ。

- **今まさに他の作業を止めている**（CI が壊れて全員がマージできない状態が続いている）
- **他リポジトリを待たせている**（相手が approve 済みでこちらが律速）
- **本番に影響する**（デプロイ設定・feature flag の切り替え）

**CI やビルドの改善は、それ自体では引き上げない。** 「あると嬉しい」程度なら低のままです。引き上げるのは**放置すると作業が止まる**ものだけ。回避策があるなら止まっていません。

**引き上げるかどうかに迷ったら、引き上げない。** 急ぎでないものを急ぎと言うと、本当に急ぐものが埋もれます（分類そのものに迷ったときは上記のとおり中身を見る。こちらは例外適用の話）。

### 6. 表で出す

**リポジトリごとに節を分けず、1つの表に混ぜる。** 分けると紐づいた PR が別の表に散り、横断で見た意味が失われる。

**まず表で出す。収まらなければ別の形へ落とす。** 表は一覧性が高い一方、**ターミナル幅を超えると縦積みのカードに化けて、かえって読みにくくなります**。日本語は1文字が2桁ぶんの幅を取るので、見た目の文字数より早く溢れる。

**情報を削って表を守らない。** 削るのは順序として最後で、先に試すのは「短く言い換える」「列を減らして下へ逃がす」。それでも入らないなら**表をやめる**。

| 優先 | 手 |
| --- | --- |
| 1 | **セルを短い語に言い換える**（ `ready / CI 緑` → `ready緑` ） |
| 2 | **列を減らし、外した情報は表の下へリストで出す**（まず「紐づき」から） |
| 3 | **表をやめて箇条書きにする**。1 PR 1行で `PR — 何を（状態・急・次）` の形 |

**5列を目安にする。** 6列以上は溢れやすい。

| 列 | 中身 | 目安 |
| --- | --- | --- |
| PR | `FE v2 #395` のように**通称 + 世代 + 番号**。**v1 / v2 を必ず付ける**。番号だけではどちらの世代か判別できない | 12桁 |
| 何を | **1行の説明**。PR タイトルの写しではなく「何が変わるか」 | **15字以内** |
| 状態 | `ready緑` / `draft緑` のように詰める。approve 済みは記号1つ（ `✓` ）で足す | 8桁 |
| 急 | `高` / `中` / `低`。列名も1字にする | 2桁 |
| 次 | `マージ可` / `ready可` / `approve待ち` / `外部待ち` | 10桁 |

**「紐づき」は最初に外す列。** 依存関係は文字数が読めず、`スタック土台。上に 3 本` のような説明が入ると一気に溢れます。**幅に余裕があれば列のままでよく、危なければ表の下へ**。

**「何を」の列は必ず入れる。** 横断で10本を超えると、番号だけでは何の PR か思い出せません。ただし**15字を超えたら削る**。差分の説明は PR 本文の仕事で、ここは思い出すための手がかりです。

**セルに理由や条件を書かない。** `外部待ち：各環境の DB で status = 4 が 0 件になるまで` のような説明は、**列を1つ壊すだけで表全体が縦積みになります**。`外部待ち` とだけ書き、条件は表の下へ。

表の後に置くのは次の4つだけ。

1. **紐づき**（依存先・スタックの段・他リポジトリとの対）
2. **表に入らなかった条件**（保留理由・マージ順の制約）
3. **レビュー依頼用の URL 一覧**（下記）
4. **古くなった参照**があれば別立てで

#### レビュー依頼用の URL を、温度感 → 紐づきの順で並べる

**そのままコピーして依頼に貼れる形**にする。表からは番号しか拾えず、URL を組み立て直すことになるため。

**温度感で分けたうえで、その中を紐づきでまとめる。** リポジトリ順に並べると「BE を全部見てから FE を全部見る」進め方を促してしまい、**対になった変更を別々のタイミングで読むことになります**。契約の整合はペアで見ないと確かめられません。

**全体を `---` で囲む。** どこからどこまでをコピーすればよいかが目で分かる形にする。**優先度の間には入れない**。区切りが増えると、どこまでが1かたまりか分からなくなる。

```
---

[優先度: 中]
変更履歴の記録経路
1. https://github.com/OWNER/BE_REPO/pull/2954
2. https://github.com/OWNER/BE_REPO/pull/3002
3. https://github.com/OWNER/BE_REPO/pull/3068

一括版メソッドの命名統一
- https://github.com/OWNER/BE_REPO/pull/3065

変更履歴フィクスチャの整合
- https://github.com/OWNER/FE_REPO/pull/424

[優先度: 低]
エージェント運用の設定
- https://github.com/OWNER/FE_REPO/pull/425

---
```

- **優先度は `[優先度: 中]` の形**。そのまま依頼文の一部になる
- **空行を入れるのはグループの間だけ。** `[優先度: 中]` の直後も、見出しと URL の間も詰める。**空行が多いと1かたまりに見えない**
- **URL は1行1本、行末で終わらせる**。タイトルや状態を後ろに付けるとリンクが壊れる（ `report_formatting.md` ）
- **順序に意味があるかで記号を変える。** スタックは `1. 2. 3.`、独立した PR は `- `

  | 形 | 記号 | 理由 |
  | --- | --- | --- |
  | **スタック**（下段から読む必要がある） | **番号付き** | 順序そのものが情報。下段が通らないと上段は動かない |
  | 独立した PR | 箇条書き | 番号を振ると、**無い制約があるように見える** |

- **枝分かれは別グループにする。** スタックの本線と、途中から生えた枝を同じ番号列に混ぜると**一本道に見える**。枝は見出しを分けて箇条書きで置く
- **グループに1行の見出しを付ける**。何の対応かが分かると、レビュアーが読む順を決められる
- **読んでほしい順に上から並べる。** 優先度の中でも順序を付ける

  | 上に置く | 理由 |
  | --- | --- |
  | **他を止めているもの** | スタックの土台、他リポジトリを待たせているもの。**1本通ると複数が動く** |
  | **ペアになっているもの** | 契約の整合はペアで見ないと確かめられない。分断されると読み直しになる |
  | 独立していて小さいもの | 短時間で片付き、滞留しにくい |
  | **読む量が多いもの** | 後回しでも困らない。時間が取れるときに読んでもらう |

  量は差分行数で見る（ `gh pr view <PR> --json additions,deletions` ）。

  **条件が並んだら BE を先に。** 契約を出す側なので、**BE が固まらないと FE が動けない**ことが多い。ものによるが既定はこの順。
- ペアなら **BE → FE の順**に並べる。契約を出す側から読むほうが理解が早い
- **見出しは何の対応かだけを書く。** draft の相方・マージ済みの依存先・スタックの段数といった内部事情は入れない。**そのまま依頼文に貼るので、レビュアーが読む必要のない情報はノイズ**（状態は表を見れば分かる）
- **ready かつ approve 未取得のものだけ並べる。** draft は依頼できず、approve 済みは原則として依頼する相手がいない
  - **例外: レビュアー自身が再依頼を求めている場合は並べる。** 判定はコメント欄で行う（下記）
- 該当が無い優先度はブロックごと省く

**approve の判定は `latestOpinionatedReviews` で行う。** `state == "APPROVED"` が1件でもあるかで判定する。**COMMENTED を除いて、レビュアーごとの最新の賛否だけ**を返すフィールド。

**`reviewDecision` と `latestReviews` はどちらも取りこぼす。** 実測41 PR での正答は次のとおり。

| フィールド | 正答 | 外す条件 |
| --- | --- | --- |
| `reviewDecision` | 32 / 41 | ruleset の `required_approving_review_count` が0のリポジトリでは、**approve 済みでも `null`** |
| `latestReviews` | 40 / 41 | **approve が入らない PR がある**（機構は未特定。approve 後の追加レビューでは説明できなかった） |
| **`latestOpinionatedReviews`** | **41 / 41** | 未観測 |

**`null` を「未取得」と読まない。** `reviewDecision` が `null` でも approve 済みのことがあり、リポジトリの ruleset 次第です。**値ではなくレビュー一覧を見る。**

疑わしいときは `reviews(first:100)` を全件引き、レビュアーごとに `submittedAt` が最新の賛否を自分で数える。これが最終的な裏取りの手段。

#### approve が付いていても、レビューが終わったとは限らない

**フィールドは「何が起きたか」しか持たず、「相手がどうしたいか」は会話にしかありません。** レビュアーが依頼より先に見たときも approve は付きますが、**本人は正式な依頼を待っている**ことがあります。

そのため **approve 済みの PR ほどコメント欄を読む**。次のような申し送りが残っていたら、依頼リストへ並べる側です。

| コメントの型 | 意味 |
| --- | --- |
| 「まだ依頼が来ていなかった」「re review を押して」 | **依頼し直してほしい**。approve は先行して見た結果 |
| 「一旦 approve するが〇〇だけ直して」 | 条件付き。直した後に再依頼が要る |
| 「次の PR と合わせて見たい」 | 単独では動かせない |

**approve の有無だけで「依頼する相手がいない」と決めない。** 状態を見て意図を決めつけると、レビュアーが待ち続けます。

```bash
gh api graphql -f query='query{repository(owner:"OWNER",name:"REPO"){pullRequest(number:NNN){latestOpinionatedReviews(first:20){nodes{state author{login}}}}}}'
```

## 出力の目安

- PR 0件: 1行
- PR 1本: 表にせず3〜4行
- PR 複数: 表1つ + 「動かせるもの」1行。**PR ごとに節を作らない**（一覧性が落ちる）
- **横断で10本を超えても表は1つ**。リポジトリで分けたくなったら、代わりに「次の一手」で並べ替える

## してはいけないこと

- **PR ごとに直列でコマンドを打つこと**。取得は並列にする
- CI の fail を、原因を見ずに「失敗」とだけ報告すること。**approve 待ちなのかコード起因なのかで意味が正反対**
- 本文やコメントを読まずに「レビュー待ち」と判定すること。**保留条件が書かれていることがある**
- **「何を」の列を1行に収めないこと**。差分の説明は PR 本文の仕事で、ここは思い出すための手がかり
- **セルに理由や条件を書くこと**。**幅を超えると表が縦積みのカードに化け、一覧性が失われる**。長いものは表の下へ
- **表に収めるために情報を落とすこと**。落とすより、短く言い換えるか表の下へ逃がす。それでも入らないなら**表をやめる**
- **リポジトリごとに表を分けること**。紐づいた PR が散り、横断で見た意味が失われる
- **依存先が open なだけで「待ち」と判定すること**。契約が固まっていれば片側先行が正しく、**遅れている側が相手を止めている**
- 参照先の状態が変わっただけで「古くなっている」と報告すること。**本文の主張と食い違っているか**で判定する
- **マージ済み・クローズ済みの PR を出すこと**。表に混ぜるのはもちろん、**別表や補足として並べるのも含む**。取得は `--state open` に限る
- 状態を変える操作（ready 化・マージ・close）を勝手に行うこと。**一覧を出すだけ**
- 古くなった参照を見つけて**その場で本文を直すこと**。検出に留め、修正は `update-pr-description` に渡す
