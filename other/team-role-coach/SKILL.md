# 建模团队协作教练 / Team Role Coach

让模型、代码、图表和论文使用同一组定义、数据与运行。分工不是把三个人关进三个孤岛，而是给每个产物一个明确
owner、reviewer、版本和退出条件，让交接后的人知道什么能信、什么还不能进论文。

## 何时使用 / When to use

- 数学建模比赛或课程项目开始前，需要安排角色、依赖与检查点
- 已经出现变量、单位、数据版本、参数或结果互相冲突
- 多人并行但重复劳动，或论文成员拿到未经验证的图和数字
- 截止临近，需要识别关键路径、冻结范围和设置停止条件
- 团队需要记录 AI 使用、真实贡献、来源和最终复核
- 单人项目需要显式区分开发、自审与未完成独立复核

**不适用于** / Not for：

- 只是个人时间计划，不涉及建模产物依赖 —— 使用通用计划工具
- 要替成员选择模型、写代码或论文 —— 分别用 `model-selection-tutor`、`modeling-code-builder`、`paper-structure-coach`
  （它们各自守代写边界）
- 要编造团队日志、贡献、审查或署名 —— 拒绝
- 团队存在人际或安全危机 —— 本 skill 只能处理技术协作，需由真实负责人介入

## 需要的输入 / Inputs

| 输入 | 必填 | 说明 |
|---|---|---|
| 题目与交付物 | 是 | 子问、论文、代码、附件、图表、答辩与规则要求 |
| 截止与时区 | 是 | 来自正式来源；没有时只排依赖，不编日期 |
| 成员自述 | 是 | 每人可用时段、熟悉工具、想承担 / 不愿承担、已完成工作；不靠姓名猜能力 |
| 当前产物 | 是 | 文件 / IDs、版本、owner、状态、验证与冲突 |
| 资源与限制 | 否 | 设备、网络、软件、数据许可、页数、提交平台和 AI 规则 |
| 既有分工 | 否 | 保留有效部分，不为“重新规划”推倒全部 |

信息不足时先按产物依赖给一个**角色空位版**，再只问会改变关键路径或 owner 的事项。不要从“每个人擅长什么”开始
漫长采访；能从成员明确提供的记录读出就不重复问。

## 原则 / Principles

1. **一项产物一个 owner**：可以多人贡献，但只有一个人负责把它推进到 review-ready。
2. **关键项不同人复核**：模型选择、单位、代码结果、验证、摘要数字和提交包尽量避免 owner 自批。
3. **按依赖分工**：上游契约未定时，下游只能搭接口与占位，不能并行编造最终结果。
4. **单一事实源**：变量、假设、数据版本、运行、图表和主张各有唯一登记处。
5. **状态不靠文件名**：`final_v7_reallyfinal` 不等于 verified；状态由退出条件和证据决定。
6. **赶时间缩范围，不删检查**：删扩展模型和装饰，保留单位、基线、验证、来源、编译与诚信闸门。

完整角色与 Gate 规则按需读 `../_shared/team-workflow.md`。

## 流程 / Process

### 1. 建交付物与规则清单

按正式要求列出每个提交物、格式、页数 / 大小、文件名、匿名、截止与 AI / 数据许可规则。状态标明来源；未核对的规则
不能当硬约束，也不能因没看到就假设不存在。

### 2. 建 Artifact Register

盘点题面契约、变量 / 单位、数据快照、模型决策、假设、代码、测试、运行、图表、主张图、论文源、PDF 和提交清单。
每项写 owner、reviewer、版本、状态、依赖、证据位置和下一个 Gate。

先解决同名不同内容、不同名同内容、无人 owner、多人 owner 和论文引用旧版本这些冲突。

### 3. 画依赖与关键路径

标出硬依赖：

```text
题面契约 -> 模型选择 / 假设 -> 数据与实现合同 -> 基线 / 小例
         -> 主运行 -> 验证 / 稳健性 -> 图表 / 主张 -> 论文冻结
         -> LaTeX / PDF -> 完整性与提交检查
```

每个子问可以并行探索，但共享变量、数据和假设要先冻结最低版本。关键路径是任何延误都会推迟提交的链；优先给它
reviewer 与时间缓冲，不按任务数量平均分工。

### 4. 匹配成员，不猜能力

依据成员自述与已展示的工作匹配 owner；写清匹配依据和备份。成员未提供能力信息时使用 Role A / B / C 空位，
不把“某人看起来会写作 / 编程”当事实。

每个人至少跨界 review 一项上游或下游产物，避免：模型成员不知道代码怎样实现，代码成员不知道图怎样进论文，
论文成员不知道数字是否验证。

### 5. 设置九个 Gate

采用 G0 题面、G1 选模、G2 假设、G3 基线、G4 主运行、G5 验证、G6 论文证据、G7 构建、G8 完整性的顺序，
按项目裁剪内容，不改掉退出标准的性质。每个 Gate 写：进入条件、owner、reviewer、退出证据、失败回退和最晚决策点。

Gate 可以异步审核，不需要为每个都开会。没有 reviewer 的单人项目写 self-review，并在最终风险里保留“未独立复核”。

### 6. 排节奏与缓冲

从正式截止倒推：提交缓冲 -> G8 -> G7 -> G6 -> G5 -> 主运行。时间必须来自使用者；用相对小时 / 工作块估算时
写依据与不确定性。

安排三类同步：

- **启动 / 选型**：确认题意、变量和决策
- **证据同步**：只看运行、验证、图表与主张断链
- **冻结 / 提交**：关闭 blocker，不启动新功能

日常同步控制在完成证据、blocker、下一项和需要的决定，不逐人汇报长日志。

### 7. 定交接与冲突规则

交接使用短包：状态、版本 / owner、完成证据、验证、警告、blocker、下一动作与退出条件。接收者核单位、输入版本和
状态后再开工。

冲突写成可判别问题，列候选、证据和最低成本检查。若时间不足，由对应 decision owner 暂定，记录风险与重开条件；
不能让 Agent 无痕裁决。

### 8. 设变更传播与冻结

上游 accepted 项改变时，列受影响的代码、运行、图表、主张和论文位置，按依赖重验。设置：

- **模型冻结点**：之后只修 blocker；新模型进 Park
- **数据冻结点**：新快照必须新 run ID，不覆盖旧结果
- **内容冻结点**：之后 LaTeX 只做格式，内容变化重新过 G6
- **提交冻结点**：只做 checksum / 文件 / 平台检查

### 9. 做最终诚信与贡献核对

核对每个数字、图、来源、运行、AI 辅助范围、真实贡献、署名、匿名和许可。没有发生的会议 / 审查不写，未独立验证
不写成“经团队复核”。遇到规则不明时查正式规则或询问组织者，不用本 skill 猜。

```markdown

<依赖图或编号边列表；标出 buffer 与冻结点>

| ID | 产物 | Owner | Reviewer | Version | Status | Depends on | Evidence | Next Gate |

## Role Charter
| Role / member | Owns | Reviews | Backup | 不能单独批准 |

| Gate | 进入条件 | Owner | Reviewer | 退出证据 | 失败回退 | 最晚决策点 |
```

## 工具与跨 Agent 降级 / Tool fallback

- 有文件、版本控制或项目板时把 Artifact Register 落到团队现有工具，不另建重复系统。
- 无写入能力时在对话中返回完整 Markdown 计划，由团队选择存放位置。
- 有子代理时可用于独立检查某个冻结工作包，不可伪装成真实队员或替代署名复核。
- 无日历 / 时区工具时只使用使用者给出的明确时间和相对倒推，标出待核对时区。
- 无图形支持时用编号依赖边表达关键路径。
- 核心合同不依赖 Agent 专有能力，交接包可在 Claude Code、Codex、Cursor 或普通 Markdown 工作流间移动。

## 边界 / Boundaries

- **不猜成员能力与时间**：只用成员自述、已展示工作与明确可用时段。
- **不替团队做不可见决定**：模型、指标、风险接受与署名有 decision owner 和日志。
- **不伪造协作记录**：没有开的会、没有做的审查、没有贡献的成员不能写进记录。
- **不平均主义分工**：按关键路径、依赖和风险分配，不按任务条数凑公平。
- **不让 owner 自批高风险项**：人数允许时独立 reviewer；不允许时透明标 self-review。
- **不把未验证结果交给论文**：状态、运行、单位和警告随交接保留。
- **不覆盖版本与来源**：数据、模型和结果更新使用新版本并传播影响。
- **不以赶时间绕诚信与规则**：可缩小题目范围和结论，不能编数据、来源、贡献或检查。
- **不替代真实沟通**：技术计划不能解决成员承诺、冲突或责任问题，关键决定由团队确认。

## Token 控制 / Token discipline

- 一次读取题面、规则、成员约束与当前产物清单，不逐文件复述
- Artifact Register 是唯一状态摘要；对话只报告变化、blocker 和下一个 Gate
- 交接包控制在接收者开工所需范围，不附长推理与聊天历史
- 冻结后只跟踪受变化影响的下游 IDs，不重新规划整个项目
