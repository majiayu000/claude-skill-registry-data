# 简历面试问题文档

面向想快速备题的候选人。站在只看得到指定简历条目的面试官视角出题，默认再补简短参考回答。处理项目/实习经历和专业技能，不要求提供整份简历，也不限技术栈。

## 输入

- 必需：候选人指定的一条或多条简历条目。可以只给项目/实习经历，或只给专业技能。缺少条目时请候选人提供，不要求补齐其他部分。
- 可选：岗位 JD、候选人级别、用于回答的项目代码、项目文档或补充说明。级别未提供时直接出题，不开启模拟面试的配置流程。
- 默认生成**问题和参考回答**，不询问产出模式；用户明确只要问题时，生成纯问题文档。回答所需的项目材料不足时仍直接产出，在无法证实的回答处标“待补充”并指出缺少什么信息。

## 先出题，再写答案

1. **出题阶段**读取指定的简历条目和 [常见问题](references/common-questions.md)；专业技能部分还可读取用户提供的 JD。即使代码、项目文档或补充说明已经给出，也先不读取、不检索其内容，避免提出不是从面试官视角出发的伪面试问题。把全部主问题和追问写成纯问题 Markdown 文件，文件成功保存才算出题完成；这份文件就是固定的问题稿，不要求候选人逐题确认。
2. **逐类覆盖常见问题**：遍历常见问题文件中的每个分类和每道题，判断是否适用于本次输入。输入包含项目或实习经历时，覆盖适用的介绍、亮点/难点/故障、具体条目、个人成长和软技能问题；团队协作、故障等背景未写在简历里，仍可问是否遇到过，不预设它已发生。仅排除有明确适用条件而本次不满足的题，以及考察角度实质相同的重复题；不要因为题目偏软技能、缺少现成答案或想控制数量而略过。库中以后新增的题也逐条检查。同一段经历的整体问题只问一次。JD 不参与项目/实习出题；把简历所写职责视为候选人的职责。
3. 专业技能题以条目写出的技能为主，同样逐条检查常见问题文件中适用的专业技能问题。JD 可以调整提问优先级和深度，也可以带出少量简历未写、但 JD 明确重视的技术问题；这些问题标注“来自 JD”。只有输入包含专业技能条目时才补充这类题。保持 JD 题为少数，不让它淹没简历题。
4. 对每条具体工作，结合常见问题文件中的条目追问和简历内容出题，再沿原理、边界、取舍、验证深入；候选人给出级别时据此调整深度。相同问题可以合并，合并后要保留原有不同的考察角度。保存问题稿前，对照常见问题文件逐类检查每道适用题已被覆盖或合并，尤其检查亮点/难点、个人成长和软技能分类。问题只从简历可见信息和常见面试话题出发，不用项目代码或文档反推隐藏细节。
5. **问题稿已保存后**，若选择回答模式，才读取相关代码、项目文档、补充说明或可靠的公开技术资料。只在原有主问题和追问下补回答，保留所有分类、条目、问题和追问标题的原文与顺序；材料中才出现的术语、实现或故障只能进入答案，不能成为新问题或追问。完成前对照已保存的问题稿检查标题。简历已写的职责、数据和结果可直接用于项目回答；未写的具体实现或细节需要材料支持，否则写“待补充”并指出缺少的信息。项目回答以候选人口吻表达；常见问题文件中的回答架构可用于组织答案。团队、流程、故障、冲突和个人收获等事实缺失时保留待补充位置。专业技能的通用技术事实可依据可靠资料，个人使用经历仍以候选人材料为准。版本相关结论说明适用版本或条件。

## 文档

- 文档以常见问题文件的 `##` 分类标题及顺序组织，适用的分类直接使用原文标题，例如“整段实习或项目：介绍类问题”“整段实习或项目：亮点、难点与故障”“个人成长”“软技能类问题”；不要改成“整体经历”等新分类。普通分类使用 `###` 主问题、`####` 追问；“针对具体的一条简历内容”和“专业技能及简历关键词”分类内先用 `###` 标出输入条目，再用 `####` 主问题、`#####` 追问。只在特定回答后适用的追问，简短注明触发条件。
- **只要问题**：仅包含分类、条目分组、主问题和追问，不附考察点、评分、答案或其他说明。
- **问题和回答**：每个主问题及追问下都附简短、可口述的参考回答；未获证实的个人事实标“待补充”。
- 除非用户指定其他路径，否则在调用时的当前工作目录下创建 `./resume/`（如不存在），先将纯问题稿保存为新的 UTF-8 Markdown 文件，回答模式再在同一文件中补入答案。文件名使用可区分的时间或序号；若重名则另取新名，不覆盖已有文档。不要把候选人的简历、代码、JD 或生成文档写入 skill 源码目录。完成后给出保存路径。
