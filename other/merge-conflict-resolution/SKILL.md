# Merge Conflict Resolution

这个 skill 解决的是“冲突出现以后怎么稳妥地解掉”。重点不是机械选 `ours` 或 `theirs`，而是先理解冲突来源，再按文件类型和语义风险决定解决方式，并在继续操作前做验证。

## 何时使用

- rebase 产生冲突
- merge 产生冲突
- update branch 失败
- cherry-pick 或 backport 产生冲突

不适用：

- 还没有实际冲突
- 只是担心将来可能冲突
- 当前问题不是 merge/rebase，而是普通 review 评论

## 产物

每次使用本 skill，默认产出以下最小集合：

1. 冲突现场
   - 冲突操作类型
   - 冲突文件列表
   - 冲突原因摘要
2. 解决策略
   - 手工合并
   - ours / theirs
   - 重新生成
   - 延后人工判断
3. 解决后状态
   - 冲突是否清空
   - 跑了哪些验证
   - 是否还存在语义风险

默认要求：

- 先看清冲突双方分别改了什么，再决定怎么解
- 一次只解决一类或一组强相关冲突
- 解完后必须做最小但真实的验证
- 如果还有语义不确定性，显式保留为待确认事项，不强行继续

## 工作流

1. 识别冲突上下文
   - 当前是 merge、rebase、update branch 还是 cherry-pick
   - 目标分支和当前分支分别是什么
2. 盘点冲突文件
   - 源码
   - 测试
   - 锁文件
   - 生成物
   - 文档
3. 选择解决策略
   - 源码：优先理解两侧语义后手工合并
   - 锁文件 / 生成物：优先按项目生成方式重建
   - 重命名 / 删除冲突：先确认最终文件组织
   - 风险过高时，明确升级为待确认事项
4. 逐文件解决
   - 清理冲突标记
   - 保留必要语义
   - 避免把无关改动混进来
5. 验证与继续
   - 跑与冲突区域最相关的验证
   - 再继续 `rebase --continue`、完成 merge 或进入下一步协作动作
6. 回写状态
   - 记录本轮冲突原因、解决方式和剩余风险
   - 若冲突发生在协作流程中，同步当前状态和阻塞是否已清空

## 决策约束

- 不要盲选 `ours` / `theirs`
- 不要把锁文件和源码冲突用同一种策略处理
- 不要在没验证的情况下宣称冲突已解决
- 这个 skill 负责冲突处理，不替代 PR merge 条件判断

## 失败信号

- 看到冲突就机械接受一边版本
- 解决了文本冲突，但没看语义是否破坏行为
- 解完没有运行任何验证
- 冲突虽清空，但没有把结果同步回当前 PR 状态
