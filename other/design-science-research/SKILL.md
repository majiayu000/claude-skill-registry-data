# デザインサイエンス研究スキル (Design Science Research)

## 目的
DSR 論文において、Hevner et al. (2004) のガイドラインに沿った構造化、**存在例（existence proof）と因果実証の区別**、および Git コミット・AI セッションログ等の**プロセスエビデンス**の管理を支援する。アーティファクトと論文の共調進化を記録し、Modality（主張の強さ）の一貫性を保つ。

## 発動タイミング
- DSR パラダイムを採用する論文の設計・執筆時
- アーティファクト（ツール・スキル・システム）と論文を同時開発する場合
- 「これは構成できた証拠か、効いた証拠か」の区別が必要な時
- 査読者から「存在例と実証の混同」を指摘された時

## 前提
- [`research-plan-workshop`](../research-plan-workshop/SKILL.md) で研究計画が確定していること
- [`scholarly-concept-modeling`](../scholarly-concept-modeling/SKILL.md) でドメイン概念が定義されていること

## 処理手順

### Step 1: DSR ガイドライン照合
Hevner et al. (2004) の7ガイドラインに照らし、本研究の位置づけを確認する：

| ガイドライン | 確認点 |
| :--- | :--- |
| 1. Design as an Artifact | アーティファクトは何か（スキル・ツール・方法論） |
| 2. Problem Relevance | 解決する実践的・理論的問題は何か |
| 3. Design Evaluation | 評価方法は何か（存在例・ケーススタディ・実験等） |
| 4. Research Contributions | 貢献は設計命題・存在例・実証のいずれか |
| 5. Research Rigor | 構成・評価の厳密性をどう担保するか |
| 6. Design as a Search Process | 探索プロセスをどう記録するか |
| 7. Communication of Research | 技術者・研究者両方への伝達方法 |

### Step 2: 存在例 vs 因果実証の区別
本文の各主張について、以下のいずれかに分類する：

| 種類 | 定義 | 語彙例 |
| :--- | :--- | :--- |
| **設計命題** | こう設計すべきという提案 | 「〜すべきである」「〜が望ましい」 |
| **存在例** | 構成・観察できたこと | 「〜が構成可能であった」「〜が観察された」 |
| **因果実証** | それが原因で良くなったこと | 「〜により改善した」「〜が効果をもたらした」 |
| **一般化** | 他の文脈にも適用可能 | 「〜に一般化できる」「普遍的である」 |

**Invariant**: 存在例の記述に因果実証の語彙を使わない。n=1・単一ケースでは統計的一般化を主張しない。

### Step 3: プロセスエビデンスの管理
DSR では設計・構築の過程がエビデンスとなる。以下を構造化して記録する：

| エビデンス | 管理方法 |
| :--- | :--- |
| Git コミット履歴 | 表形式の監査索引（時刻・マイルストーン・ハッシュ） |
| AI セッションログ | 対話ログの収録・redact 方針（ローカルパス・PII 除去） |
| 実行環境 | `Agent:`/`Model:` トレーラーの検証 |
| 負例（棄却・非機能） | NC-XX 形式の構造化記録 |

### Step 4: アーティファクト ↔ 論文の対応管理
アーティファクトのバージョンと論文記述の対応を追跡する：

```markdown
| アーティファクト版 | 論文記述 | 対応コミット |
| :--- | :--- | :--- |
| v2.0.0 | 第4章 §4.2 参照実装 | `abc1234` |
| v2.4.0 | 第4章 §4.3 共調進化 | `def5678` |
```

### Step 5: Modality 較正レポート
`docs/design/dsr-structure.md` に以下を出力する：
- DSR ガイドライン照合結果
- 存在例/因果実証の分類表
- プロセスエビデンス索引
- アーティファクト対応表
