# mvp-pressure-launch

## When to Use

当有一个新产品/服务想法，但陷入“准备不足”的拖延中，需要验证想法并快速启动时description

## Core Logic

# 执行步骤

1.  **定义最小可行产品（MVP）与报价**
    *   **输入**：一个产品/服务创意。
    *   **操作**：剥离所有非核心功能，定义出能解决用户一个核心痛点的最小功能集合。基于此，创建清晰的产品/服务名称、价格和核心价值描述。
    *   **判断标准**：MVP描述是否能让目标用户立刻理解其核心价值；报价是否明确。
    *   **输出**：MVP核心功能列表与初步报价方案。

2.  **创建预售材料并公开承诺**
    *   **输入**：MVP核心功能列表与初步报价方案。
    *   **操作**：
        a. 制作一个产品预售着陆页，包含：产品价值主张、核心功能、价格、明确的购买按钮（或预订链接）。
        b. 设定一个具体的公开发布/交付日期（建议3-4周后）。
        c. 通过现有渠道（社交媒体、邮件列表等）发布该着陆页，宣布产品并接受预订/购买。
    *   **判断标准**：着陆页是否上线并可访问；发布日期是否已公开；是否已开始接受潜在客户的访问和意向。
    *   **输出**：一个已上线、接受流量的产品预售页面，及一个公开的交付截止日期。

3.  **承接压力并交付MVP**
    *   **输入**：预售页面流量及可能产生的订单/预订。
    *   **操作**：
        *   **IF** (收到订单/预订)：**则** 将客户压力和交付截止日期作为最高优先级，集中所有资源，在承诺日期前构建并交付定义好的MVP。
        *   **IF** (未收到订单/预订)：**则** 将此视为市场验证失败信号。立即收集页面访问者反馈，分析价值主张或渠道问题，快速迭代或放弃该想法。**压力解除**。
    *   **判断标准**：是否在截止日期前向付费客户交付了符合承诺的MVP；或是否基于零销售数据做出了清晰的迭代/放弃决策。
    *   **输出**：已交付的MVP产品及首批客户反馈，或经过验证的放弃/迭代决策。

# 输出格式要求
以项目看板形式向用户汇报：
1.  **MVP状态**：[已定义/已交付]
2.  **预售页状态**：[URL链接] | 流量：[数值] | 订单：[数值]
3.  **交付截止日**：[日期]
4.  **当前压力等级**：[高/中/低] - 基于订单情况和剩余时间
5.  **下一步关键动作**：[如“开发核心功能X”、“联系第一位客户确认需求”]
