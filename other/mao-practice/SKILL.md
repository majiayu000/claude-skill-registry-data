# 调查验证

完成一个可执行、可验收的调查或验证交付物。PT只是工作流入口，不是本Skill的专属问题。

## 工作流程

1. 用 `references/problem-catalog.yaml` 识别当前调查要支持的决策和候选PT。
2. 分开已确认事实、用户解释、工作假设和决定性未知项。
3. 在 `references/normalized-solutions.yaml` 中按 `problem_refs` 找相关NSL，用适用条件、失效边界和证据要求选择方法。
4. 只保留一个最能改变当前结论的验证目标；信息不足时每轮只问一个决定性问题。
5. 根据任务生成问卷、访谈提纲、样本方案、最小实验、观察指标或复盘表，并预先定义支持、削弱和推翻假设的结果。
6. 从已选NSL的 `source_solution_refs` 读取 `references/source-solutions.yaml`，再用 `references/source-index.jsonl` 核对2～4条原典依据。

## 交付契约

默认给出：

1. **主要判断**：当前最值得验证的假设及匹配PT。
2. **事实边界**：事实、解释、假设和未知项。
3. **验证工具**：可直接执行的提纲、问题、实验步骤或复盘表。
4. **样本与指标**：对象、数量、记录方式、通过标准和偏差风险。
5. **下一检查点**：何时复盘、带回什么数据。
6. **证伪条件与原典依据**：什么结果推翻假设，以及原文为什么支持这个验证设计。

## 继续与交接

- 当前任务尚未完成时继续完善同一交付物，不讨论下一站。
- 行动明确但结果尚未出现时等待现实反馈，停止追加推演。
- 用户带回结果时，先判断假设被支持、削弱还是推翻，再决定继续验证或完成交付。
- 若任务变成整体战略重评，保留事实、PT和验证结果并交回 `$mao-strategy`；主入口未安装时明确本Skill边界。不要直接指定另一个专业Skill。
- 目标达成或验证已足够时明确结束。

不要把“实践”解释为盲目行动，也不要用持续调查逃避必须作出的决定。只引用已核对短引文；遵守合法、非暴力和高风险专业边界。
