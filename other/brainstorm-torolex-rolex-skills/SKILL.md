# Brainstorm

用户可能无法从空白处定义标准，却能对具体候选作出反应。先发散，再收集反应；不把未确认的推荐当成需求。

1. 读取已有目标、约束、盲点发现和 references。事实自己查；只询问生成候选必需的缺口，不在这里跑完整访谈。
2. 判断发散对象：
   - **介入点：** “从哪里下手？”搜索 codebase 和相关资料，从保守到大胆列出不同方法，注明价值、成本、约束和真实证据，避免范围过窄或过宽。
   - **设计或行为方向：** “长什么样／怎样用？”提出结构或交互真正不同的方向。需要可运行 UI 或 state model 时，调用 Skill 工具传入 `prototype`，把要回答的问题、候选方向和约束交给它，不复制其制作规则。
   - **非视觉产物：** API response、文件格式、报告等，用带标注的实际样例让用户比较，不强迫它们成为 UI prototype。
3. 用户无法表达想借鉴的行为或风格时，在 unknowns 内返回其 References 分支；独立使用时询问参考物，用户委托后再派子代理寻找。
4. 候选尽量使用同一份真实数据；假数据明确标注。原型回答当前设计问题，不把探索扩张成后端接线或完整功能实现。
5. 提供简短的选择方式：保留／舍弃／组合，以及“哪些有共鸣，为什么？”。然后停下，等待真实反馈。
6. 把反馈记录为偏好、约束或新的显式问题。在 unknowns 中回交地图，留给 known unknowns 阶段收敛；独立使用时建议用 grilling 处理剩余歧义，不自动进入实现。

完成：用户已对具体候选反应，保留、拒绝、组合的理由已记录；未决定的事项有清晰问题或 OPEN 解锁条件。
