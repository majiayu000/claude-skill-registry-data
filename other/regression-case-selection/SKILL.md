# 回归用例筛选Skill

## 适用场景
功能变更后的回归测试环节,基于变更影响分析从全量用例中筛选回归范围,兼顾覆盖率与执行成本。

## 执行步骤
1. 收集变更输入:代码 diff、需求变更说明、配置变更、接口变更清单。
2. 影响分析:逐变更点推导影响链路(变更点 → 受影响模块 → 受影响功能链路 → 关联用例)。
3. 筛选用例,按影响程度分层:
   - 直接影响:变更模块自身用例,全量回归。
   - 间接影响:存在调用/数据依赖关系的模块,筛选其核心链路用例。
   - 高风险区:公共组件、底层服务、数据结构、接口协议变更,扩大相邻模块回归范围。
4. 定优先级:P0 核心链路必测 / P1 变更直接相关 / P2 相邻功能抽查。
5. 输出回归用例清单,每条标注筛选依据(对应哪条影响链路)。

## 规范要点
- 影响分析必须有依据:从代码 diff/接口变更推导,禁止凭感觉圈范围;分析过程留档可追溯。
- 区分全量回归与增量回归:日常迭代用增量回归;大版本、架构改造、公共组件变更用全量回归。
- 排除的用例要说明排除理由(变更无关/已被新用例覆盖),防止遗漏核心链路。
- 结果如实呈现:回归执行中未执行的用例必须标注未执行,不得假设通过;回归不通过如实上报。
- 回归范围与变更点双向可查:每个变更点能查到对应用例,每条用例能查到为什么入选。

## 输出模板
```
## 回归用例筛选清单
| 变更点 | 影响链路 | 用例编号 | 优先级 | 筛选依据 |
## 回归范围说明(全量/增量 + 排除清单与理由)
## 回归执行结果(通过/失败/未执行)
```

## 自检清单
- [ ] 每个变更点有影响链路分析
- [ ] 每条入选用例有筛选依据
- [ ] 核心链路覆盖完整,排除有理由
- [ ] 执行结果如实记录,未执行已标注
