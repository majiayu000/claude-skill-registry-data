# Fix PR

この skill は明示的に呼び出された場合のみ使用する。

```text
$fix-pr
$fix-pr pr#123
$fix-pr owner/repo#123
```

- 引数なし: 現在のブランチに対応する PR を対象にする
- `pr#<number>`: 現在の repository の指定 PR を対象にする
- `owner/repo#<number>`: 指定 repository の PR を対象にする

この skill の呼び出し自体を、対象 PR に対するコード変更・commit・push の許可として扱う。

レビュースレッドへの返信は、ユーザーの明示的な確認を得るまで送信してはいけない。

## Workflow

1. 対象 PR と PR のブランチを特定する
2. 未解決のレビュー指摘を取得する
3. 各指摘の妥当性を確認する
4. 妥当な指摘だけを修正する
5. 関連するテスト・型チェック・lint・build を実行する
6. Conventional Commits 形式で commit する
7. PR のブランチへ push する
8. 各レビュースレッドへの返信案を作成する
9. 返信案をユーザーに提示する
10. 承認された返信だけを送信する

## 指摘の確認

レビュー指摘は、その内容をそのまま正しいものとして扱わない。

コード・呼び出し元・テストを確認し、以下を判断する。

- 指摘している問題が実際に成立するか
- 既存の validation、型、ガードなどですでに防がれていないか
- 指摘された修正が既存設計や仕様と矛盾しないか

妥当な指摘だけを修正する。

既に対応済み、または問題が成立しない場合はコードを変更しない。

仕様判断が必要な曖昧な指摘は、推測で修正しない。

## 修正

修正は、指摘された問題を解消するための最小限の変更にする。

- 無関係な箇所は変更しない
- 指摘内容を超えて仕様を変更しない
- 既存の設計・命名・テストパターンを優先する

回帰を再現できる場合はテストを追加する。

複数の指摘が同じ根本原因から発生している場合は、1つの修正として扱ってよい。

## Commit

commit message は Conventional Commits 形式にする。

```text
<type>(<scope>): <subject>
```

例は次のとおり。

```text
fix: handle retry without duplicate writes
fix(auth): enforce tenant ownership
test: add regression coverage for expired sessions
```

複数のレビュー指摘を1つの変更として安全にまとめられる場合は、1つの commit にまとめてよい。

## 返信

push が成功した後、対応したレビュースレッドごとに返信案を作成する。

返信案はレビューコメントと同じ言語で、何を変更したかを簡潔に説明する。

必要な場合だけ、修正理由やコード上の根拠を補足する。

返信案をユーザーに提示し、明示的な承認を得るまで送信してはいけない。

ユーザーが文面を修正した場合は、その文面を使用する。

## Rules

- PR のブランチ以外へ push しない
- レビュー指摘を検証せずに修正しない
- ユーザー確認なしで返信しない
- Git の破壊的な操作を避ける

## Completion

完了時に以下を短く報告する。

- 対応した指摘
- 修正しなかった指摘と理由
- 実行したテスト・検証
- commit / push の結果
- 未解決のレビュー指摘
