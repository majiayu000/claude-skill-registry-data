# ingest — 소스 흡수 워크플로우

`raw/`의 소스를 읽어 `wiki/`에 sources/entities/concepts 페이지를 생성·갱신한다.
세부 규칙(페이지 생성 임계 기준, frontmatter, Obsidian 링크, 도메인 태그)은 항상 `wiki/CLAUDE.md`(위키 스키마)를 따른다.

## 모드 판단

- **단일/인터랙티브**: 소스 1개를 줄 때. 2단계 분석 결과를 사용자와 논의한다.
- **배치**: "배치로", "한꺼번에", 여러 소스를 동시에 줄 때. **논의만 생략하고 분석은 수행한다.** 끝에 요약 보고서를 한 번 제공한다.

**ingest는 분석 → 생성 2단계다. 읽자마자 파일을 쓰지 않는다.** 분석을 건너뛴 배치 ingest가 판본 관계 누락·모순 미등록의 주된 원인이다.

## 단계

1. **읽기**: 대상 파일을 읽는다. 이미지가 있으면 텍스트를 먼저 처리하고, 데이터·도표·텍스트가 담긴 이미지만 이후 별도로 본다. 단순 장식·배너는 건너뛴다. 텍스트 전용 소스면 이미지 단계 생략.
2. **분석** (파일 쓰기 전, 배치 모드도 필수): 아래를 먼저 글로 정리한다. 단일 모드면 사용자와 논의, 배치 모드면 기록만.
   - 엔티티·개념 후보 + 각각 페이지 생성 임계 기준 충족 여부
   - **판본 관계**: 무엇을 대체/무엇에 대체되는가, 범위가 일부면 무엇만인지(→ `status`·`superseded_by`·`scope` 근거)
   - **기존 위키와의 모순**: 어느 페이지 어느 서술과 어긋나는가(→ open-questions 등록 대상)
   - **해소되는 기존 미결** + 그 결론을 반영해야 할 하류 페이지
   - **동음이의 위험**: 같은 용어가 다른 맥락에서 다른 규격을 갖는가(→ concept 페이지가 분리·해명)
3. **sources/ 페이지 생성**: `wiki/sources/[파일명].md`에 요약 페이지를 `wiki/CLAUDE.md`의 템플릿대로 작성한다. 프론트매터에 `status: current`(+ 대체한 구판본이 있으면 `supersedes:`)를 반드시 넣는다.
3b. **구판본 상태 갱신**: 이 소스가 기존 판본을 대체하면 **그 구판본 프론트매터**를 `status: superseded`(일부만 대체면 `partial` + `scope:`)로 바꾸고 `superseded_by: [이 소스]`를 넣는다. **파일명 계열이 달라도 대체 관계면 갱신한다** — 상태의 단일 진실은 프론트매터다.
4. **entities/ 업데이트**: 페이지 생성 임계 기준(2개 이상 소스에 등장 OR 단독 재참조 가능성 높음)을 만족하는 엔티티만 생성/병합. 모순 발견 시 해당 섹션에 `> ⚠️ [날짜] [[원본파일]] 과 상충` 마커를 추가하고 `open-questions.md`에 항목 등록.
5. **concepts/ 업데이트**: 임계 기준을 만족하는 개념만 신규 생성/업데이트.
6. **overview.md 갱신**: 이 소스가 현재 논지를 강화·반박하면 `wiki/overview.md`를 갱신.
7. **index.md 업데이트**: 새 페이지를 카탈로그에 추가하고 프론트매터 `status`를 그대로 투영한다 (`current` → `**현행 정본**`, `superseded`/`partial` → `🔁 [[대체본]]으로 대체됨`).
8. **log.md 추가**: 파일 끝에 `## [YYYY-MM-DD] ingest | [원본 제목]` 한 줄 기록.
9. **검사**: `python3 wiki/script/lint.py` 실행 → **위반 0건 확인 후 종료**. 사용자가 lint를 요청할 때까지 기다리지 않는다.

## 배치 완료 보고

전체 완료 후: "N개 소스 처리, M개 페이지 생성/업데이트, K건 모순 발견" 형식으로 한 번에 보고. 모순·불명확한 판단이 필요할 때만 중간에 사용자에게 확인.

## 주의

- `raw/`는 읽기 전용. 절대 수정·생성·삭제하지 않는다.
- 내부 링크는 `[[파일명]]` 형식만 사용.
