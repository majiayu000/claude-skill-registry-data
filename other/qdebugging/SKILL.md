# Qdebugging — 디버깅

이 스킬의 목적은 **근본 원인을 찾기 전에는 고치지 않는 것**이다. 증상만 덮은 수정은
실패다. 다른 곳에서 다시 터지고, 무엇이 고쳤는지 아무도 모른다. 찍어 보는 수정보다
체계적인 조사가 대개 더 빠르다. 간단해 보이는 버그도 원인이 있고, 간단한 버그에는
이 과정도 금방 끝난다.

## 길 안에서의 자리

- **새 버그 요청** — 요청에 이유 또는 완료 기준이 빠졌으면 `Qunderstand`를 먼저 호출한다. 인터뷰에서 기대 동작을 정했다면 인터뷰 창은 확정한 intent.md를 인계한다. 새 작업자는 기존 재현 절차와 로그, 코드 읽기로 원인을 조사한 뒤 Qplan에서 승인을 받는다. 가설 확인에 코드나 테스트 수정이 필요하면 그 실험을 계획에 넣어 승인 후 실행한다.
- **실행 중** — `Qexecute`의 확인이 예상 밖으로 실패하면 여기로 온다.
- **검증 중** — `Qverify`에서 원인 모를 미충족이 나오면 여기로 온다.

## 1. 원인 조사 (어떤 수정보다 먼저)

1. **오류 메시지를 끝까지 읽는다.** 경고, 스택 트레이스, 줄 번호, 파일 경로, 오류 코드.
   답이 거기 그대로 있을 때가 많다.
2. **안정적으로 재현한다.** 정확한 절차는? 매번 일어나나? 재현이 안 되면 추측하지 말고
   데이터를 더 모은다.
3. **최근 변경을 본다.** `git diff`, 최근 커밋, 새 의존성, 설정, 환경 차이.
4. **여러 구성요소가 얽혀 있으면 경계마다 증거를 모은다.** 각 경계에서 들어가고 나오는
   값, 설정·환경 전달, 각 층의 상태를 한 번 찍어 보고, **어디서** 깨지는지 확인한 뒤 그
   부분을 판다.
5. **값의 흐름을 거슬러 올라간다.** 잘못된 값이 처음 생긴 곳은? 누가 그 값으로 불렀나?
   출처를 찾을 때까지 올라가서, 증상이 아니라 출처에서 고친다.
   스택만으로 호출자가 드러나지 않으면 현재 작업 트리의 `trace_path`에서 호출 경로를 찾는다.
   도구를 쓸 수 없으면 소스에서 호출자를 찾고, 후보 경로는 스택이나 재현으로 확인한다.

추적 방법, 테스트끼리 오염될 때, 가끔만 실패하는 테스트처럼 막히기 쉬운 경우의 기법은
[techniques.md](techniques.md)에 있다.

원인 분석은 `qe-framework:analyst`, 로그·지표 분석은 `qe-framework:data-analyst`에 맡길 수 있다.
전문 에이전트가 보이지 않으면 일반 서브에이전트로 분석을 맡긴다.
서로 독립인 실패가 여럿이면 각각을 서브에이전트에 나눠 맡길 수 있다. 같은 파일을
건드리면 `isolation: "worktree"`로 격리한다.

## 2. 패턴 비교

- 같은 코드베이스에서 **비슷한데 동작하는 코드**를 찾는다.
- 따라 만든 참조 구현이 있으면 훑지 말고 **끝까지** 읽는다.
- 동작하는 것과 깨진 것의 차이를 작은 것까지 모두 적는다. "그건 상관없겠지"라고 넘기지 않는다.
- 의존하는 구성요소, 설정, 환경, 가정을 확인한다.

## 3. 가설과 확인

1. **가설은 하나.** "X가 원인이다, 왜냐하면 Y" — 구체적으로 적는다.
2. **가장 작은 변경으로 확인한다.** 한 번에 변수 하나. 여러 개를 한꺼번에 바꾸지 않는다.
3. 맞으면 4로. 틀리면 **새 가설**을 세운다. 틀린 수정 위에 수정을 쌓지 않는다.
4. 모르면 "X를 이해하지 못했다"고 말한다. 아는 척하지 않는다. 더 조사하거나 사용자에게 묻는다.

## 4. 수정

1. **실패하는 테스트를 먼저** 만든다. 가장 단순한 재현으로, 가능하면 자동 테스트로.
   테스트 틀이 없으면 일회용 스크립트라도. 실패하는 것을 직접 본다. 자세한 방법은 `Qtdd`.
2. **근본 원인 하나만** 고친다. "하는 김에" 개선이나 리팩터링을 섞지 않는다.
3. 테스트가 통과하는지, 다른 테스트가 깨지지 않았는지, 원래 증상이 정말 사라졌는지 확인한다.

**인터뷰 인계가 필요 없고 수정이 작으면** 이 자리에서 고치고 `Qverify`로 간다. 작업 폴더가 있으면 원인을
plan.md "원인"에, 재현 테스트와 결과를 verify.md에 남긴다. 아주 작은 버그면 문서 없이
결과만 보고한다. 사용자가 원인 분석을 HTML·아티팩트로 달라고 하면 `Qreport`의 틀을 쓴다.

**수정이 크면**(여러 파일, 설계 변경, 사용자가 정할 것이 있음) 원인과 근거를 plan.md
"원인"에 적고 `Qplan`으로 넘어간다.

## 고쳐도 안 될 때

- 멈추고, 지금까지 몇 번 시도했는지 센다.
- 시도할 때마다 다른 곳에서 새 문제가 드러나거나, 고치려면 큰 구조 변경이 필요하다면
  가설이 틀린 게 아니라 **구조가 틀린 것**일 수 있다. 세 번째 시도가 실패했다면 다음
  수정을 하기 전에 사용자와 구조를 다시 이야기한다.

정말 환경·타이밍·외부 원인이라면: 조사한 것을 기록하고, 알맞은 처리(재시도, 시간 제한,
오류 메시지)를 넣고, 다음 조사를 위한 로그를 남긴다. 하지만 "원인 없음"의 대부분은
조사가 덜 된 것이다.

## 멈추고 1로 돌아갈 신호

- "일단 고치고 나중에 조사하자", "X를 바꿔 보고 되나 보자"
- 여러 군데를 한꺼번에 바꾸고 테스트하려 할 때
- "아마 X일 거야, 고치자" — 흐름을 따라가 보기 전에 해결책을 내놓을 때
- 사용자가 "그거 확인해 봤어?", "추측하지 마", "막힌 거야?"라고 할 때
- 테스트가 틀렸다는 근거 없이 테스트를 고쳐서 통과시키려 할 때
- "가끔 실패하니 재시도를 늘리자", "대기 시간을 늘리자"고 생각할 때
