# Qreview — 코드 리뷰 요청

이 스킬의 목적은 **변경을 만든 쪽과 다른 눈으로 보는 것**이다. 자기가 쓴 코드를 자기가
리뷰하면 같은 맹점을 공유한다. 깨끗한 컨텍스트의 리뷰어는 내 설명이 아니라 코드만 본다.
문제는 일찍 잡을수록 싸다. 다른 작업이 그 위에 쌓이기 전에 본다.

## 언제

- 사용자가 diff, 브랜치, PR 리뷰를 요청할 때
- 큰 변경을 끝냈을 때, merge 전에
- `Qverify`의 최종 리뷰도 같은 기준([reviewer-prompt.md](reviewer-prompt.md))을 쓴다

## 순서

1. **범위를 정한다.** 브랜치면 기준 브랜치와의 merge-base를 BASE로(`git merge-base <기준 브랜치> HEAD`; 기준 브랜치는 main이라고 단정하지 말고 확인한다),
   HEAD까지. PR이면 PR 번호. 요구사항이 있는 곳(plan.md, 이슈, PR 설명)을 찾는다. 범위가
   분명하지 않으면 사용자에게 묻는다.
2. **새 서브에이전트에 맡긴다.** [reviewer-prompt.md](reviewer-prompt.md)를 채워 넘긴다.
   판단이 필요한 일이니 상위 모델을 지정한다(생략하면 세션 모델을 물려받는다). 대화 이력은
   넘기지 않는다. 리뷰어가 알아야 할 것은 요구사항과 범위뿐이다.
   - 변경이 아주 작으면(몇 줄) 내가 같은 기준으로 diff를 한 번 읽어도 된다. 그때는 그렇게
     했다고 사용자에게 말한다.
3. **결과를 그대로 보여 준다.** 지적을 등급과 함께 사용자에게 먼저 보여 준다. 리뷰어가
   판단을 보류한 항목도 숨기지 않는다. 내 생각에 틀린 지적이 있으면 그 이유를 옆에 적는다.
4. **반영은 사용자가 원할 때.** 사용자가 고치기를 원하면 `Qfeedback`으로 지적마다 맞는지
   확인하고 반영한다. 작업 중인 길(`Qexecute`·`Qverify`) 안이라면 그 스킬의 흐름을 따른다.

## 하지 않는 것

- 리뷰어의 "문제없음"을 검증 대신 쓰지 않는다. 리뷰는 코드를 읽는 것이고, 동작 확인은
  테스트와 `Qverify`의 일이다.
- 리뷰 결과를 받자마자 고치기 시작하지 않는다. 보여 주고, 정하고, 고친다.
