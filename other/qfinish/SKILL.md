# Qfinish — 마무리

이 스킬의 목적은 **검증이 끝난 작업을 사용자가 고른 방식으로 안전하게 닫는 것**이다.
merge, push, 브랜치 삭제는 되돌리기 어렵고 다른 사람에게 영향이 간다. 그래서 무엇을 할지는
사용자가 고르고, 나는 고른 것을 확인하며 실행한다.

길의 다섯 번째 단계다: 이해 → 계획 → 실행 → 검증 → **마무리**. 보통 `Qverify`가 "완료"로
끝난 뒤 이어서 온다.

## 순서

### 0. 검증이 끝났는지 본다

QE 작업 폴더(`~/.qe/tasks/<목표>/`)가 있으면 그 status.json을 본다.

- **`state`가 `done`이 아니면** 아직 마무리할 때가 아니다. `done`은 레드팀 검수 기록이 있어야만
  쓸 수 있으니, done이 아니라는 건 검수를 통과하지 않았다는 뜻이다. `Qverify`로 간다. 사용자가
  검증 없이 마무리하겠다고 하면 merge·PR은 하되, 목표는 done으로 표시하지 않고(관문이 막는다) 문서도
  내보내지 않는다. 검증되지 않은 기록을 저장소에 완료본처럼 남기지 않기 위해서다. 목표를 닫으려면
  사용자에게 확인받고 `state`를 `stopped`로 쓴다.
- **done이면** `done.branch`·`done.commit`이 지금 마무리할 브랜치와 같은지 본다. 검증한 뒤 코드 커밋이
  더 쌓였으면 검증한 것과 지금 코드가 다르다. 사용자에게 알리고 다시 검증할지 묻는다. `docs/qe/`
  내보내기만 담은 커밋은 코드를 바꾸지 않으니 다시 검증할 필요가 없다.
- **QE 작업 폴더가 없는 일반 브랜치면** 아래에서 기록 단계(4)는 건너뛴다.

### 1. 테스트를 다시 돌린다

지금 통합하려는 그 트리에서 프로젝트 전체 테스트를 돌린다. 아까 통과한 결과는 아까의 트리에
대한 증거다. 실패하면 여기서 멈추고 실패를 보여 준다. 고치는 것은 `Qexecute`나 `Qdebugging`의 일이다.

### 2. 기준 브랜치를 확인한다

이 작업이 어느 브랜치에서 갈라졌는지(implement-plan.md, 대화, upstream 설정에서). 분명하지 않으면
"`<추정>`에서 갈라진 게 맞나?"라고 묻는다. 엉뚱한 브랜치로 merge하면 되돌리기 비싸다.

### 3. 선택지를 보여 주고 사용자가 고른다

```
작업이 검증을 통과했습니다. 어떻게 마무리할까요?

1. <기준 브랜치>에 로컬로 merge
2. push하고 Pull Request 만들기
3. 브랜치를 그대로 두기 (나중에 직접)
```

사용자가 이미 정해 두었으면(예: "끝나면 PR까지 해") 다시 묻지 않고 그대로 한다.

### 4. 기록을 먼저 남긴다

merge나 PR 뒤에 쓰면 커밋이 하나 더 생기거나 다시 push해야 하고, worktree를 정리한 뒤라면 쓸 곳이 없다.

1. `~/.qe/tasks/<목표>/`의 verify.md에 `- 마무리: <고른 것>` 한 줄을 쓰고, status.json `done.finish`에
   `merge`(로컬 merge) | `pr` | `keep`(그대로 두기)을 쓴다. PR이 squash·rebase로 합쳐지면 `done.commit`은
   기준 브랜치에 들어가지 않으니, 이 표시가 없으면 `Qboard`가 고칠 수 없는 보관본에 "안 합쳐짐"·"브랜치 없음"
   경고를 계속 낸다.
2. **내보낸다.** 그 폴더의 `*.md`(plan.md, implement-plan.md, verify.md, handoff.md 등)와 Qreport 보고서(`report*.html`)를 검증한
   브랜치(`done.branch`)의 `docs/qe/<목표>/`로 복사한다. status.json, `verdicts/`, `.stop-blocked-*`
   표시 파일은 복사하지 않는다. 그것들은 이 PC의 관문 기록이라 저장소에서는 뜻이 없다.
   설계와 검증 기록이 코드와 함께 남아야 나중에 "왜 이렇게 만들었지?"를 저장소에서 찾을 수 있다.
3. **커밋은 사용자에게 묻고** 한다.

완료된 `~/.qe` 폴더는 지우지 않고 이후 고치지 않는 보관본으로 남긴다. 고치지 않으니 내보낸 사본과
어긋나지 않고, `Qboard`가 이 보관본으로 "검수 후 코드 바뀜" 같은 경고를 계속 낸다.

### 5. 고른 것을 실행한다

- **로컬 merge**: 기준 브랜치가 열려 있는 checkout(작업이 worktree에서 진행됐다면 원래
  checkout)으로 가서 최신으로 받고 merge한다.
  - **충돌이 나면** 멈추고 충돌 파일을 보여 준다. 해결할지, merge를 취소(`git merge --abort`)할지
    사용자와 정한다.
  - **merge한 결과에서 테스트를 다시 돌린다.** 실패하면 멈추고 실패를 보여 준 뒤, merge를
    되돌릴지(아직 push 전이라 가능하다) 고칠지 사용자에게 묻는다.
  - 통과하면 worktree를 먼저 정리하고(6) 그다음 작업 브랜치를 지운다. worktree에 checkout된
    브랜치는 지울 수 없다.
- **PR**: 작업 브랜치를 push하고, 저장소의 PR 템플릿과 관례를 따라 PR을 만든다. 본문에는
  무엇을 왜 했는지와 검증 결과(verify.md 요약)를 넣는다. PR 주소를 사용자에게 준다. 리뷰 댓글이
  달리면 `Qfeedback`으로 처리한다.
- **그대로 두기**: 브랜치 이름과 위치만 알려 준다.

push가 거부되면 원격이 그사이 움직인 것이다. 조사한다. force-push는 사용자가 분명히 요청할 때만.

### 6. 정리한다

`Qexecute`에서 worktree를 썼다면, 로컬 merge 뒤에만 정리한다(작업 브랜치를 지우기 전에). PR이나 그대로 두기라면 그
worktree에서 이어서 일할 수 있으니 남겨 둔다. 정리하려는 worktree에 커밋하지 않은 파일이 있으면
지우지 말고 사용자에게 보여 주고 묻는다. 내가 만들지 않은 worktree는 건드리지 않는다.

## 작업을 버릴 때

사용자가 분명히 버리자고 할 때만 한다. 먼저 무엇이 사라지는지(브랜치, 커밋 목록, worktree)를
보여 주고 확인을 받는다. 선택지 목록에 "버리기"를 먼저 내밀지 않는다.

## 이런 생각이 들면

| 생각 | 실제 |
|---|---|
| "아까 테스트 통과했으니 됐다" | 지금 합치려는 트리에서 다시 돌린다 |
| "검증은 했으니 done은 나중에" | status가 done이 아니면 검수를 통과한 게 아니다. Qverify로 |
| "당연히 merge하길 원하겠지" | 통합 방식은 사용자가 고른다 |
| "기준 브랜치는 당연히 main" | 확인한다. 틀리면 되돌리기 비싸다 |
| "push가 거부됐으니 force로" | 원격이 움직였다. 조사하고, force는 요청이 있을 때만 |
| "merge 결과가 실패한 건 일시적이겠지" | 멈춘다. merge는 아직 로컬이라 되돌릴 수 있다 |
