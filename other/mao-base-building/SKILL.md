# 建设扩张

完成一份可执行的能力建设路径、最小落脚点和扩张门槛。PT只是工作流入口，不是本Skill的专属问题。

## 工作流程

1. 用 `references/problem-catalog.yaml` 明确当前是在验证稳定基础、补承载能力还是判断扩张时机，并匹配候选PT。
2. 区分一次性成果与可重复能力，盘点需求、现金流、人才、关系、渠道、知识、流程和质量控制。
3. 在 `references/normalized-solutions.yaml` 中按 `problem_refs` 读取NSL，比较适用条件、关键证据和失效边界。
4. 选择能产生真实反馈并可持续积累的最小落脚点；事实不足时每轮只问一个决定性问题。
5. 给出能力补齐顺序、维持标准、分批扩张门槛、暂停或回撤条件。
6. 从已选NSL进入 `references/source-solutions.yaml`，再用 `references/source-index.jsonl` 核对2～4条原典依据。

## 交付契约

默认给出：

1. **主要判断**：当前应建设、巩固还是扩张，并说明匹配PT。
2. **基础盘点**：已有资产、关键依赖、脆弱点和决定性缺口。
3. **最小落脚点**：最小稳定用户、供给、现金流或反馈闭环。
4. **建设路径与扩张门槛**：能力补齐顺序、质量标准、放量条件和回撤条件。
5. **下一检查点**：何时检查、带回哪些稳定性和承载数据。
6. **证伪条件与原典依据**：什么事实推翻当前阶段判断，以及原文与现实方案的关系。

## 继续与交接

- 当前任务尚未完成时继续同一建设交付物，不讨论下一站。
- 建设动作已开始但结果尚未出现时等待现实反馈，停止追加推演。
- 用户带回数据时，先判断基础或承载假设被支持、削弱还是推翻，再调整节奏或结束。
- 若长期目标或整体战略需要重评，保留基础事实、PT和结果并交回 `$mao-strategy`；主入口未安装时明确本Skill边界。不要直接指定另一个专业Skill。
- 稳定门槛已达成、决定不扩张或无需继续时明确结束。

不要把“根据地”机械理解为地理占有，不要只积累资产而忽略真实需求，也不要用长期建设拒绝短期反馈。扩张建议必须尊重质量、安全、法律和参与者权利。
