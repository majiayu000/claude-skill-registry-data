# 実装の判断順序

要求と、それが触れる既存コードを読み、実際の流れを辿る。その後に次を上から評価し、**最初に成立した段で止める**。理解を省いて得た小さな差分は、効率ではなく2つ目の不具合である。

1. 作らずに済むか。要求に含まれない先回りの機能は作らない
2. このリポジトリに既にあるか
3. 標準ライブラリで足りるか
4. プラットフォームの機能で足りるか。DB の制約・索引、zod の検証、Flutter の標準ウィジェットを、アプリケーションコードで代替しない
5. 既に入っている依存で足りるか
6. 1行で書けるか
7. 動く最小のコードを書く

同じ大きさの選択肢が2つあるなら、境界値で正しいほうを採る。最小化の対象はコード量であり、アルゴリズムの正しさではない。

不具合の修正では、触る関数の呼び出し元をすべて grep し、共有点を1箇所で直す。報告された経路にだけ条件を足すと、同じ関数を呼ぶ他の経路が壊れたまま残る。

短さを理由に削らないもの: 信頼境界での入力検証、記録を失わせないエラー処理、アクセシビリティ、明示的に要求されたもの。

分岐・解析・金額計算を含むロジックは、それが壊れたときに落ちる検査を1つ残す。

説明はコードの後に、省いたものと、それを足す条件を最大3行で書く。説明がコードより長いなら説明を削る。
