# 设计模式评估Skill

## 适用场景
架构评审环节,识别代码中实际使用的设计模式,评估其是否解决真实问题,识别「为模式而模式」的过度设计与「该抽象不抽象」的设计不足,输出调整建议。

## 执行步骤
1. 识别模式:对照 23 种经典设计模式与常用架构模式(分层、插件、发布订阅等),标注使用位置。
2. 逐模式评估:它解决的变化点是否真实存在?引入的间接层是否值得?
3. 识别两端问题:过度设计(预留无用的扩展)、设计不足(重复/巨型/条件堆积)。
4. 输出评估结论与调整建议,附证据。

## 评估标准
| 判定 | 信号 |
|---|---|
| 使用得当 | 模式解决的痛点真实存在且有 ≥2 处使用点;类职责单一;间接层带来可测试性/可扩展性收益 |
| 过度设计 | 抽象只为「将来可能」的需求;单一实现却建了接口+工厂+策略全套;理解成本 > 收益;新成员无法快速看懂 |
| 设计不足 | 重复逻辑 ≥3 处未抽取;类型分支 if/else ≥5 个未用策略/多态;巨型类(超 500 行或 >3 个职责);硬编码散落各处 |

## 规范要点
- 每个评估结论必须附代码证据:文件 + 行号 + 该处为何属于过度/不足的具体理由。
- 建议「移除模式」时,给出移除后的替代写法说明(直接实现/简单工厂/仅接口)。
- 建议「引入模式」时,说明引入后消除的具体重复或分支。
- 与全局规范一致:超 3 层嵌套必须重构、重复逻辑必须抽取公共方法。

## 输出模板
```
## 设计模式评估报告
| # | 模式 | 使用位置(文件:行号) | 评估(得当/过度/不足) | 证据与理由 | 调整建议 |
## 过度设计项(建议简化)
## 设计不足项(建议抽象)
```

## 自检清单
- [ ] 每个结论附代码位置与具体理由
- [ ] 过度/不足判定有量化信号支撑
- [ ] 调整建议给出替代写法说明
- [ ] 未发现模式的位置也扫描过(避免漏报设计不足)
