## 何时使用
- 需要把设计稿、Design-Brief.md 或 Product-Spec.md 转成可实现、可运行、可验收的开发 Phase 时使用。
- 项目技术栈、依赖、运行方式或测试方式不明确，必须先验证再规划时使用。
- 需要拆分多人/多 agent 并行工作，避免范围冲突、验收口径不清或阶段无法独立运行时使用。

## 依赖输入
- 设计稿优先，其次 Design-Brief.md，再次 Product-Spec.md；三者冲突时按该优先级处理并显式记录。
- 仓库实际证据：目录结构、包管理文件、构建配置、脚本、测试入口、运行命令、框架版本和已有约定。
- 需要目标平台、交付边界、并行编辑范围、质量门槛、验收命令、不可改文件和风险偏好。
- 长技术说明、框架细则、迁移背景和架构资料放入 `references/`，Phase 只引用必要结论。

## 第一性原则与边界
- Agent Harness 5.0 规划必须由目标、标准、边界驱动；每个 Phase 都要说明完成后用户能验证什么。
- 必须先验证技术选型和运行事实，再输出开发计划；不能只根据记忆、文件名或愿望假设技术栈。
- 每个 Phase 都应是可运行、可演示、可验收的增量，不输出只有内部整理价值的空转阶段。
- 规划不替代实现；不发明未验证依赖，不跨越用户指定写入边界，不覆盖并行 agent 的工作。
- 当证据不足时，将未知项变成验证门槛，而不是静默写进计划。

## 验收标准
- 已列出实际技术栈、运行/构建/测试入口及验证依据。
- 每个 Phase 都包含目标、范围、交付物、验收命令或人工验收点、依赖关系和退出标准。
- Phase 顺序能先降低最大技术风险，再扩展体验和功能完整性。
- 并行工作边界、共享文件风险、阻塞项和需要用户确认的问题被明确标注。

## 产出
- 一份 Phase 计划，包含技术选型验证摘要、阶段目标、实施边界、验收方式、风险和开放问题。
- 必要时附 references 索引、验证命令清单和适合分派给其他 agent 的任务切片。
