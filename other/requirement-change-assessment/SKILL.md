# 需求变更评估Skill

## 适用场景
需求在评审后、开发中或已上线阶段发生变更请求,需要量化变更影响(范围/工期/依赖/风险),给出可决策的评估结论。

## 执行步骤
1. 记录变更内容:变更请求按「现状 → 变更为 → 变更原因(业务驱动/缺陷修正/政策要求)」三段式记录。
2. 识别影响面:逐项评估——已交付物(PRD/设计/代码/用例)、下游依赖方(前后端/测试/数据)、关联功能、发布计划。
3. 评估工作量:增量工时 = 新增开发 + 改动开发 + 回归测试 + 文档更新,给出量级(人日)而非拍脑袋数字。
4. 评估工期与节奏:变更插入对当前版本的影响:本版本吸收 / 下版本顺延 / 单独加急版本,各方案写明代价。
5. 评估风险:技术风险(改动核心模块)、进度风险(里程碑冲击)、合规风险(政策变更类),逐条列缓解措施。
6. 输出评估结论:建议接受/拒绝/延后,附理由与替代方案(不做变更有何替代解法)。

## 规范要点
- 变更必须留痕:变更编号、提出人、日期、原因、评估结果、决策人,与 PRD 变更历史表打通。
- 影响面按「已产出物」盘点:明确列出「已完成的哪些产出需要返工」,返工成本单列。
- 工期结论给区间不给点值:写「新增 3-5 人日,发布延期 1-2 天」,附不确定性来源。
- 拒绝变更要给替代方案:不能只说"不做",要说"当前方案下用户如何实现该诉求"。
- 紧急变更(线上缺陷/合规)单独通道:标注紧急级别,允许先执行后补评估,但补评估不豁免。

## 输出模板
```
# 需求变更评估单 CR-xxx
1. 变更内容(现状 → 变更为 → 原因)
2. 影响面清单(已交付物返工/下游依赖/关联功能/发布计划)
3. 工作量评估(新增/改动/回归/文档,附量级)
4. 节奏方案对比(本版本吸收/顺延/加急,各列代价)
5. 风险与缓解措施
6. 结论建议(接受/拒绝/延后 + 理由 + 替代方案)
```

## 自检清单
- [ ] 变更三段式记录完整,编号留痕
- [ ] 已交付物返工清单无遗漏
- [ ] 工作量分项列明且给了量级区间
- [ ] 三种节奏方案均列出代价
- [ ] 拒绝/延后结论附替代方案
