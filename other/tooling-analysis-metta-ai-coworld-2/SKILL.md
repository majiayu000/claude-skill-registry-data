#### 1. Bypass the coworld/cogames CLI when it lags the server (pydantic ValidationError)
`loop` · **negative result** · ⚠ _session-derived, unverified_ · tool: `scripts/fetch_episodes.py`

When the installed coworld/cogames CLI is older than the server, its episode/replay/membership commands crash with a pydantic ValidationError (Field required) before emitting any JSON (--json does not help: validation runs first, prints zero bytes, exits non-zero). Schema drift cause: client model V2EpisodeRequestRow still requires assignments/policy_version_ids/participants/scores but live rows omit assignments, and LeaguePolicyMembershipPublic requires is_active/is_champion while the server now returns a status field (e.g. 'qualifying'). Workaround: call a rooted raw REST endpoint such as `/v2/policy-versions/{id}/episode-requests` or `/v2/rounds/{id}/episode-requests` with a plain httpx client and parse dicts yourself, or use scripts/fetch_episodes.py which hits skew-immune raw JSON routes.

#### 3. The coworld CLI (not the web UI) is ground truth; key off the episode request ID, and beware scripting hazards
`loop` · **negative result** · tool: `coworld`

The Coworld CLI is the ground truth for debugging a hosted player. Use the public `coworld` CLI through `uv run coworld` and inspect local `--help`. Key off the episode request ID (`ereq_...`) for stats, results, logs, replays, and replay-open. Inspect a round through `rounds`, `results`, `episodes --round ROUND_ID`, then the selected request's logs and results. `coworld episodes` and `coworld replays` require exactly one `--round` or `--policy`. #### 6. Choose the right Coworld run mode: download, run-episode, play, certify
`loop` · tool: `coworld`

Use 'coworld download <slug-or-cow_id> --output-dir <dir>' (flag is --output-dir/-o NOT --output; default ./coworld, override COAGENT_COWORLD_DIR; --refresh re-pulls) -- it writes the manifest, images json, and AGENTS.md and re-tags baseline images runnable; first download pulls the game's Docker image (hundreds of MB, cached/idempotent, not stuck) then runs offline (the downloader resumes after a read-timeout when rerun with the same -n N). Pass the bare coworld-id to 'coworld play' or 'coworld run-episode'. run-episode is headless and writes artifacts but always runs only the manifest's certification.game_config smoke test (e.g. a 3-step cogsguard fixture), NOT the league mission, and has no --variant; 'coworld play' runs the actual league variant (e.g. CvC machina-1-daily, 10000 steps) for the live browser viewer; to smoke a fuller game headlessly pass an episode_request.json whose game_config is the variant. In run-episode the positional image is reused for ALL slots (self-play) -- pass one image per slot to mix; there is no single-slot override and reference players are used only with zero images. coworld certify does NOT accept player_images (cannot substitute a policy); use run-episode for the strictest pre-flight (asserts client/WS reachability, token rejection, non-empty first global message). 'coworld play' produces only an uncompressed replay.json while run-episode/certify produce BOTH replay.json and replay.json.z (account for it when a downstream tool expects compressed). Prefer stable cow_/cow_id ids over names for reproducibility. Expect version drift (coworld download crewrift may pull 0.1.45 vs a doc's 0.1.40).

#### 7. Coworld auth lives in its own credential store; probe with a read call
`loop` · tool: `coworld`

Authenticate to the Coworld Observatory backend once with 'uv run softmax login'; there is no whoami, so probe auth with any auth-requiring read like 'coworld leagues'. A sudden failure on the SECOND API message (package clearly installed) means the token expired (401/403), not a missing package. The 'coworld' CLI authenticates from its OWN store (~/.softmax/credentials.yaml) and does NOT read the standalone 'softmax' CLI's token store, so 'softmax set-token'/'status' do not affect coworld; if using 'softmax login' use the softmax binary bundled with coworld, not a separate install. #### 11. Histogram trace events first, and harden jq against non-JSON lines and role-gated absence
`loop`

Before querying a game-policy JSONL trace for whether an event happened, run an event-type HISTOGRAM first (jq select kind=='trace', project .event, sort | uniq -c) so an empty later query reads as 'that event did not occur' rather than 'wrong query/file/not captured.' Trace defaults drift (per-tick decision_snapshot/metrics move off by default) and role/phase-gating makes 'missing' normal (e.g. crewrift: a crewmate episode has no kill_* events, an imposter has no suspicion_snapshot, role may read 'dead' after death). When piping a hosted log to jq, prefilter with grep '^{' (final line is plain text, collector-error lines interleave) and guard select(.kind=='trace') / (.event//'') before test() because metric lines carry metric_kind/name/value/tags with no event field. Engines write PREFIXED event names (crewborg: domain.meeting_*, not bare meeting_llm_decision) -- grep the names ACTUALLY emitted, not names read in mode code.

#### 12. Emit merged stdout+stderr per tick; the per-slot log is the runtime source of truth
`loop`

Per-agent logs (logs/policy_agent_{N}.log / policy_agent_{slot}.txt) are the richest behavioral record of a Coworld episode and the runtime source of truth when debugging, while results.json and the episode row drive scoring. Emit diagnostics to stdout/stderr (not stderr-only) and flush each tick or set PYTHONUNBUFFERED=1, because the runner captures BOTH streams merged into the per-slot log -- the only channel by which player-side traces survive for retrieval via 'coworld episode-logs ereq_... --agent <slot>'. This merged log is marked diagnostic-only with NO header/prefix/separator -- do not assume a line format, and do NOT filter out 'INFO -' lines as noise (they are usually the agent's real Python logging); the CLI's own bracketed console.print messages can be mistaken for captured lines. For guided_bot, structured JSONL trace streams surface in hosted logs only when GUIDED_BOT_TRACE_DIR=stderr and GUIDED_BOT_TRACE_LEVEL is non-off (off/events/decisions/full); absent trace lines means env vars are unset, not a connection failure. Never dump raw per-frame perception into hosted logs -- use summarized diagnostics. Make artifact downloads best-effort and idempotent: record a missing replay/log rather than aborting, and skip already-complete episode dirs unless forced. Treat OFFLINE developer tools (asset bakers, nav baker, waypoint/frame editors, frame-to-text dumper) as exempt from any Coworld-only run restriction because they only produce or inspect checked-in baked artifacts and recorded traces; never conflate them with a live raw-frame-capture run path.

#### 13. Design player tracing as tiered structured JSONL with a lean hosted-cap default; emit domain events post-step
`loop`

Design a player's tracing as tiered structured JSONL (OFF < EVENTS < DECISIONS < VERBOSE/FULL, each a superset, emitted as category+data+level so analysis is machine-parseable not free-text scraping), with a lean DEFAULT that fits under hosted log caps. By default emit only durable low-volume DOMAIN events (meeting context, vote cast, chat sent/received, phase/role/task changes, high-level actions) and drop per-tick payloads (decision snapshots, belief/suspicion ticks, framework-boundary traces, viewer frames, metrics) behind an opt-in debug/viewer flag -- a decision_snapshot per-tick object is usually the single biggest volume contributor (one session produced ~380k trace lines across three games; raw frame dumps reach ~63 MB / 4000 frames; emit those only at 'full'). Gate ALL instrumentation behind env vars (output dir + verbosity) with a single early `if trace == nil: return` guard so every log call is near-zero cost when off, and gate expensive instrumentation behind the verbosity check BEFORE computing it. Emit game-level domain events from an on-step-complete hook rather than inside agent 'modes', because attempt events key on the produced wire command (modes never see it) and outcomes like task-completion conclude only after the mode runs; post-step emission keeps the strategy layer pure and reads off the finalized belief. Route all traces through ONE sink (full for local/tests; an env-aware factory returning the filtered/metrics-off sink by default in the hosted bridge) plus a bridge-level test that fails if the hosted path starts sending metrics again. Provide env knobs (CREWBORG_TRACE_GROUPS=decision|voting|action, CREWBORG_TRACE_INCLUDE/EXCLUDE globs, CREWBORG_TRACE_DECISION_FIELDS, CREWBORG_METRICS=1) to capture one event family without full volume. EXCEPTION: promote the COMPACT decision geometry (mode, target color, target distance/position) into the always-on lean stream (crewborg's decision_snapshot in events.py) so thrash/flee bugs are diagnosable without resimulating; keep the FULL per-tick payload debug-only. Keep policy logic clean by splitting the decision into a pure core (decideNextMaskCore) plus a thin trace-owning wrapper (decideNextMask); never export an internal field just so a call site can derive a value. Decouple analysis from behavior: emit analysis-only annotations (vote_bandwagon_detected, goal-tier) into decisions.jsonl read by NO policy code. Log the FINAL emitted action mask, not only upstream intent (a trace logging only intent blocked a navigation diagnosis; '535 identical decisions, 2 transitions, 0 events, 0 LLM calls' localized it in minutes), treat perception inputs (e.g. chat OCR) as first-class trace events, and log every LLM round trip with raw_response, prompt/response token counts, latency, validation status, published directive. For a deduction agent the single highest-value forensic record is one 'suspicion snapshot' at the start of every meeting carrying ranked posteriors, each suspect's event log, the would-be vote, and the decision bar. Make it purely additive over a green suite (keep the old Callable[[str],None] interface and exact legacy strings; emit structured entries only when a real Logger is passed; inject clock+sink for deterministic tests), each controlled slot writes its OWN trace file, and read the existing struct/enum defs and trace writer FIRST so field names and phase/role/mode stringifies match.

#### 14. Prove an optional feature engaged before tuning it; absence of success is ambiguous
`loop` · **negative result** · ⚠ _session-derived, unverified_

When an LLM-augmented (or any optional) feature underperforms, FIRST prove it actually fired before tuning prompts or strategy -- absence of success events is ambiguous between 'feature off', 'tried and failed', and 'precondition never met'. Concrete diagnosis: (1) check the trace CHANNEL exists at all (a [trace:guidance] channel carrying snapshot_sent/llm_response/directive_published absent, with every decision showing directive_source 'reflex'/'default' and never 'llm', means the path never engaged); (2) grep the ACTUALLY emitted prefixed event names, not names read in mode code (a scan for meeting_llm_decision found zero while logs used domain.meeting_* prefixes); (3) confirm the precondition occurred (a meeting actually happened) before blaming the feature. A single llm_call_failed reason=no_key meant the guidance layer never ran the whole match and the bot ran purely on its symbolic fallback. Distinguish decision-layer from execution-layer failure: count LLM responses/directives separately from meeting-actions-received and actual button presses/vote_attempted -- a high response count with few meeting actions (or ~39% noop, most 'skip' decisions never reaching vote_attempted) means the model decided right but the action never landed, so chase the action loop not the model. Make engagement greppable with a one-shot startup trace (e.g. llm_init once per match) recording provider selected and credential-presence signals, self-contained so it survives ring-buffer eviction; and verify the full prompt/snapshot payload is actually persisted (a design doc referenced snapshot_sent but live runs emitted none), not just the response.

#### 15. Debug the trace, not the outcome or the on-screen moment; re-run at the right log level; trust server-confirmed over agent-side menu completion
`loop`

You cannot debug an outcome, only a trace: pivot immediately from a win/loss to the player's internal reasoning stream -- the gap between what was objectively true and what the policy believed/chose is where the mechanism lives. Visible behavior is an effect with a long causal delay, so trust the trace tick over the on-screen moment: a visible stop-and-turn at tick ~390 was actually caused by a target-commitment timer expiring at tick 319, the body bleeding momentum over ~70 ticks. The default log level often omits the decision telemetry you need (early analysis had only events-level logs and lacked meta_decide_reason, emitted only at decisions level), so re-run at the verbose/decisions level and reproduce on a fixed seed before forming root-cause hypotheses. A server/global log of 'X happened' is NOT proof the agent EXPERIENCED X: server 'opened whisper' events looked like success but the agent's own frames never showed the whisper view (events belonged to other players or a player-index mismatch), and in persephone a whisper_exchange_outcome with server_confirmed=false only means the agent completed/timed-out a menu sequence, NOT that a win-relevant exchange happened -- only server_confirmed=true or the authoritative server full.log ('joined','offered role','shared roles','winner') proves a real exchange; when agent-side perception and server state disagree (client still seeing PLAYING/overworld pixels while the server's whisper state was active), debug the transport/timing path rather than trusting that menu completion implies a server effect. Read game progress from the right channel: a player's spatial-memory tick= lines stop updating once local territory stops being newly observed and make a run look stalled -- read the game tick from declarative-memory lines instead.

#### 16. Use per-agent action histograms and mode churn as cheap stuck-detectors, decoded against tick rate
`loop` · ⚠ _session-derived, unverified_

A healthy match shows many distinct action types (~18) with movement/interaction spread; a distribution collapsed onto one action -- especially noop (a bot pinned on a wall shows huge noop plus one directional button) -- flags stuck/idle/crashed behavior. CAVEAT: subtract legitimately-idle frames first; raw NOOP looked ~20% but interstitial/voting frames are noop by design and true gameplay NOOPs were ~0.4%. Compare per-bot counts before/after a fix to confirm the bot actually moves. A flat modes log (one mode at setup, never transitioning) means transition triggers are unwired. A regular fixed-period idle cycle (a repeating ~72-tick = 3s @ 24Hz DisciplineNoOp loop) is a scan/cooldown timer firing with no actionable condition -- convert tick spans to seconds and match against game constants (the 72-tick span did NOT match the 1200-tick kill cooldown, ruling it out). But interpret in light of role speed: low-speed agents rarely trigger a COAST branch because a path-following deadband catches arrivals first -- few coast events is not a bug. Diagnose a stuck crewmate from action traces by a long single-task dwell dominated by ONE repeated d-pad direction: a slot spent 984 consecutive ticks (~41s) on one complete_task, 837 monotonic RIGHT and 72 ticks of A -- a wall-wedge against impassable geometry (the task only 'completed' ~200 ticks later because ghosts slide through walls). #### 17. Distinguish a kicked slot from a finished one via game_over and a known-good opponent
`loop` · ⚠ _session-derived, unverified_

To tell whether a player slot ended naturally or was cut mid-game, diff it against a known-good full-game opponent slot in the SAME episode on frame/tick count and end-event: a healthy slot processed ~4841 frames over ~200s and saw game_over, while a cut player closed at ~880 frames having never seen game-over -- 'did this slot receive game_over?' is a clean kicked-vs-finished test. #### 18. Triage episodes by failure CLASS and a quantitative fingerprint before reading events
