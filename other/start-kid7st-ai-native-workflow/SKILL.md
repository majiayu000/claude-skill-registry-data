# /start —— 开始并推进一个需求

用户只需要说业务问题，不负责记流程、判断下一条命令或在工具之间搬运上下文。
你负责识别当前位置、调用相应能力、保留证据，并明确区分：可以自主推进的工作、必须由人决定的事。

## 输入

接受一句自然语言问题，例如：

```text
/start 订单列表没有数据时是一片空白，希望让用户知道当前没有订单。
```

也接受“继续昨天的需求”“看看现在做到哪里”等恢复请求。信息不完整时先读取已有事实，再只问会改变
需求方向的问题；不要把内部流程问题抛给用户。

## 开始时先恢复现场

先读取 `../sw/SKILL.md`，按它的只读规则获取项目全景，再结合下面的证据判断当前阶段。
读取当前仓库的 `AGENTS.md`、README、相关文档、未提交改动、当前分支、最近提交，以及能够访问的
Meegle 工作项和 GitLab MR。根据证据判断需求处于哪个阶段，不要求用户回忆。

- 项目尚未接入：说明需要先初始化，得到确认后按 `../init/SKILL.md` 执行。
- 已有同一需求的工作项、SPEC、计划、分支或 MR：从最近一个有证据的阶段继续，不重复创建。
- 现场存在来源不明的修改、冲突或多个可能对应的需求：停下说明，不覆盖、不猜归属。
- 工作流版本可能过旧或命令不可用：报告安装或升级问题，不用临时做法绕过。

首次回复最多包含三件事：你理解的问题、已经找到的相关事实、当前唯一需要用户回答的问题。
如果没有关键问题，直接进入需求澄清。

## 自主推进的主线

到达一个阶段时，读取对应 `SKILL.md` 并遵守其中的事实来源、产物、验证和停止条件。不要让用户逐个
输入这些命令，也不要假装调用了没有执行的能力。

| 阶段 | 使用的能力 | 你负责推进到哪里 |
|---|---|---|
| 恢复现场 | `../sw/SKILL.md` | 读取仓库、Meegle 和 GitLab，判断当前阶段与下一步 |
| 理解问题 | `../pd/SKILL.md` | 读取业务事实、澄清问题，形成产品需求和工作项草稿 |
| 放进全局 | `../bl/SKILL.md` | 查重复、依赖和优先级，形成排期建议 |
| 定义完成 | `../s/SKILL.md` | 从已确认并排期的工作项形成可验证 SPEC |
| 设计做法 | `../p/SKILL.md` | 读代码、形成可验证计划，并记录真实选型理由 |
| 实施 | `../b/SKILL.md` | 按计划逐片测试先行、实现、验证和提交，直至计划完成 |
| 验证 | `../t/SKILL.md` | 对照 SPEC 验收并完成相关回归 |
| 独立检查 | `../rv/SKILL.md` | 在本地对整条变更做一次语义 review，处理完实际发现 |
| 交付审核 | `../mr/SKILL.md` | 准备并创建 MR，随后停止，不合并、不发布 |

普通需求默认走完整主线。只有对应阶段已经有可信产物且仍然有效时才跳过，并说明依据。

## 只在四类关口停下来

### 1. 业务决定

包括需求含义、范围、非目标、优先级和验收行为。给出基于事实的建议，并把用户真正要决定的内容压缩成
一个清楚的问题。未确认前不创建或批量修改 Meegle 工作项，不把假设写成需求。

### 2. 方案决定

在 SPEC 与计划成形后，用业务语言汇总：最终会改变什么、明确不改变什么、准备怎样验证、有哪些取舍。
得到确认后，实施阶段按计划自主连续推进；不要在每个文件、每条测试或每个可回滚提交上反复请示。

### 3. 风险或权限

涉及项目外文件、来源不明的修改、认证与权限、密钥、生产数据、支付、删除、迁移、部署、发布，或任何
难以撤回的操作，必须在执行前说明对象、影响和恢复方式并等待明确授权。缺少外部权限时报告真正阻塞，
不建议“强制”“忽略检查”或绕过保护。

### 4. 对外交付

本地结果和检查全部通过后，先让用户确认可见结果。确认后可以创建 MR；创建成功立即停止，返回链接、
检查状态和待审核事项。永远不替用户合并或发布。

## 推进方式

- 一次只呈现当前阶段，不预先倾倒整条流程。
- 每次汇报固定回答：**现在发生什么、你已完成什么、是否需要用户决定什么**。
- 没有需要用户决定的事就继续工作，不用“要不要继续”制造审批。
- 用户说“不懂”时改用业务结果和画面解释，不要求其学习 Git、分支、commit、SPEC、CI 或 MR 术语。
- 用户中途改变需求：停止实施，先按 `../pd/SKILL.md` 更新正式需求，再依次更新下游产物；不在代码里
  偷偷适配新范围。
- 同一症状第二次修复仍失败：读取 `../ct/SKILL.md`，先重新定位问题层级，不继续叠补丁。
- 大型变更或同一区域反复迭代后，需要结构检查时读取 `../rf/SKILL.md`；普通小改动不机械执行。
- MR 收到反馈时读取 `../fb/SKILL.md`，先汇总和判断全部意见，得到处理方案确认后再修改。

## 给用户看的进度

不要输出命令清单或长篇过程日志。使用下面的最小结构，省略没有内容的行：

```text
现在：确认“没有订单”时用户应该看到什么。
已完成：读取现有页面和相似需求，没有发现重复工作项。
需要你决定：刷新失败时，是保留空状态，还是显示错误提示？
```

阶段切换时用一句话说明原因。最终输出 MR 链接、可见变化、验证证据和仍需人工审核的事项。

## 不能做的事

- 让用户选择“下一条应该运行哪个命令”
- 只因进入下一阶段就要求用户回复“继续”
- 在没有读取事实或下游产物的情况下宣称流程已完成
- 为了不中断而猜需求、替用户批准方案、跳过测试或 review
- 把一次需求扩成重构、平台改造或顺手修复
- 合并 MR、部署或发布
