# kickoff

From a working prototype to business intents the person has decided and a detailed product
model — as one drive: one issue, one branch, questions first, no stop for the plays'
approvals, a checker at the end, one pull request.

**Pipeline position: both.** The drive opens its change (`start-change`) and lands it (the end
sequence). The plays inside open nothing (drive contract, step 3).

## Compiled From

This drive was compiled from the kickoff ICE (`reference/ice.md`) by drive-creator (#613).
Intent defines constraints (C1–C8) and failure conditions (F1–F8); the expectation defines
success scenarios (S1–S4), a Done means (D1–D7, baked to `stop-condition.yaml`), and one

## Role

You are the drive. You run `/intent`, `/vision` and `/understand` in that order and do no work
of your own (ADR 029 §2): every rule about intents and the product model lives in the plays.
You check the prototype, ask what you can first, hand every play the same contract, check each
play's done check and commit its run files, have the checker judge the result, record the
person's typed decision on each intent, and land the change. Each play runs as a sub-agent
(or headless, by config) and dispatches its own agents and judges.

**Forbidden:** doing a play's work yourself; answering a question nothing in memory or the
person's answers supports; starting a play before the one before it proved done; ending done
without the checker's pass; confirming, dropping or otherwise changing an intent in the model.

## Pre-flight

| Check | Constraint | Action on Failure |
|-------|-----------|-------------------|
| Config, the three plays installed and each accepts a drive contract, runner and checker known (`drive_preflight.py`) | C4 | Hard halt |
| A working prototype is given — ask where it is and, for a file or folder, how it starts | C2 | Ask the person (gather, not a halt) |
| The prototype runs (`check_prototype.py`) | C2 | Hard halt, before anything is opened |

```bash
git branch --show-current
python3 scripts/drive_preflight.py --config .garura/core/config.yaml --drive kickoff \
    --skills-root .. --plays intent,vision,understand \
    --branch "$(git branch --show-current)" --out <pre>/preflight.json
python3 scripts/check_prototype.py --prototype "<where it is>" [--start "<how it starts>"] \
    --out <pre>/prototype.json
```

`<pre>` is a scratch folder (`mktemp -d`): no issue exists yet. After Step 1 its files move
into the drive's working folder `{stm_base}<issue>/context/kickoff/<run-ts>/` (`<working>`).

### Phase: Open

**Step 1 — Open the change** · Owner: `start-change` · Depends on: pre-flight
Run R2 of the shared run: one issue, one branch. Move `<pre>`'s files into `<working>`.
**SE-1 (F2/C2):** `prototype.json` reads `runs: true`, and was written before `start-change`
ran — no issue or branch exists for a prototype that does not run.
**SE-2 (F1/C1):** `start-change.json` names one issue and one branch; every file the drive and
its plays write is under `{stm_base}<issue>/`; no play's run record names another issue.

### Phase: Questions

**Step 2 — Questions first** · Owner: drive · Depends on: Step 1
Run R3. The prototype and how it starts were asked at pre-flight. For a link, also ask whether
`/intent`'s walk may press buttons that change data on it (pay, delete, submit) — `true` only on
the person's yes — as `answers.intent.may_change_data`. Write them to `answers.json`, and their source (`from: person`) to
`answers-sources.json`. Nothing else is known before `/intent` reads the prototype; the plays'
own questions come mid-run (ICE, Context).
**SE-3 (F3/C3):** `answers.json` and `answers-sources.json` exist before `contract.json`, and
every answer names its source.

**Step 3 — Write the drive contract** · Owner: drive (script) · Depends on: Step 2
Run R4 with `inputs.intent.argument` = the prototype.

### Phase: Plays, in rounds

The plays run in rounds until the drive's job is done (R5, C4). A question one play cannot
answer goes to the drive, not to the person: the play records it in `open-<play>.json` and
finishes what it can; the other plays, and the next round, may answer it (C5).

**Step 4 — Round n: run /intent** · Owner: `intent` · Depends on: Step 3 (or Step 6b, 6f)
Run R5 for `intent`, handing it the prototype as its argument. Round 1: it walks the prototype
and saves the intents as `proposed` with their ICE as proposed capabilities, naming each gap as
an open question. A later round: it reads what `/vision` and `/understand` wrote, and fills
what it left open.

**Step 5 — Round n: run /vision** · Owner: `vision` · Depends on: Step 4
Run R5 for `vision`. It finds the proposed intents in the model and seeds the domain.

**Step 6 — Round n: run /understand** · Owner: `understand` · Depends on: Step 5
Run R5 for `understand`. It details every capability not yet detailed, in one run.

**Step 6b — After the round: done, again or ask** · Owner: drive (script) · Depends on: Step 6
Run R5 step 7 (`round_state.py`, `--max-rounds` from `drives.kickoff.max_rounds`). `done` →
Step 7. `again` → Step 4, round n+1. `ask` → Step 6c.

**Step 6c — Search the knowledge** · Owner: `search-knowledge` · Depends on: Step 6b
Run R5c's first play: `/search-knowledge` merges the questions asked again and answers what the
prototype shows (quoted) and what memory holds (through the memory tool, traced).

**Step 6d — Build the knowledge** · Owner: `build-knowledge` · Depends on: Step 6c
Run R5c's second play: `/build-knowledge` closes the rest — knowledge pages as memory updates
waiting for the person, our proposed answer with its basis and context, notes for the
prototype, settled for what the context answers.

**Step 6e — Write the brief** · Owner: `review-knowledge` · Depends on: Step 6d
Run R5b step 1: `/review-knowledge` writes the brief — what we understood, what we built (each
proposed business intent with its ICE, the domain and its capabilities), a few gaps each with
its context and our proposed answer, the knowledge pages with our recommendation, a pointer to
the prototype notes.

**Step 6f — Brief the person; record the reply** · Owner: drive · Depends on: Step 6e
Run R5b steps 2–3: show the brief, wait for the reply, record it with `record_review.py`
(`from: person`), then Step 4, round n+1.
**SE-4 (F4/C4):** `intent-done.json`, `vision-done.json` and `understand-done.json` read
`done: true`, each written after the one before it; each `<play>-commit.json` shows no
leftover; and `_spine.yaml` has no capability `/vision` seeded still at `detail: directional`.
**SE-5 (F5/C5):** the memory tool's `citations --issue <issue> --check` lists no problems, and
every memory update the plays applied was approved by a person; the person was asked only in a
round whose `round-<n>.json` reads `ask`, never after a round that read `again`, and only after
`/search-knowledge`, `/build-knowledge` and `/review-knowledge` ran for that round (their
`search-check.json`, `build-check.json` and `brief-check.json` read `ok: true`); the person saw
the brief, never a bare question; each answer is in the issue's short-term memory with
`from: person` (`person-answers-round-<n>.json`).

### Phase: Check

**Step 7 — The checker** · Owner: checker · Depends on: Step 6
Run R6 with `checker_key` (default: a sub-agent on `sonnet`).
**SE-6 (F6/C6):** `check.yaml` reads `verdict: pass`, from a checker whose model is not the
session's; a reject halted the drive before any pull request.

### Phase: End (stand-in until Argus, the review tool — C7)

**Step E1 — commit-change** · Owner: `commit-change` · blockedBy: Step 7
**Step E2 — propose-change** · Owner: `propose-change` · blockedBy: E1

**Step 8 — The person decides each intent** · Owner: drive · Depends on: E2
Show each intent `/intent` saved (its `intent-manifest.json`), one at a time, exactly as it
reads, with its ICE under it, and ask the person to type **confirm** or **drop** (with any
words of their own). Never use `AskUserQuestion`. Write their exact words to
`<working>/replies.json`, then:

```bash
python3 scripts/record_confirmation.py --manifest <intent run>/intent-manifest.json \
    --replies <working>/replies.json --by "<git user>" --at <date> \
    --out <working>/confirmation.yaml
```

The intents stay `proposed` in the model; Argus's review step writes the approval later (#650).
**SE-7 (F7/C7):** `record_confirmation.py` exited 0: `confirmation.yaml` reads `by: person`,
holds one decision per saved intent in the person's own words, and every intent page still
reads `Stage: proposed`.

**Step E3 — review-change** · Owner: `review-change` · blockedBy: Step 8
**Step E4 — merge-change** · Owner: `merge-change` · blockedBy: E3

### Phase: Scenario Validation

**Step 9 — Scenario evals** · Owner: drive · Depends on: Step E4
- **SCE-1 (S1 — business owner, a prototype link):** `contract.json`, the three done files
  reading `done: true`, `check.yaml` reading `verdict: pass` and `confirmation.yaml` exist under
  the issue; every intent page still reads `proposed`; the pull request merged.
- **SCE-2 (S2 — business owner, no working prototype):** `prototype.json` reads `runs: false`,
  no new branch exists, and the drive closed HALTED with `exit_reason: preflight`.
- **SCE-3 (S3 — business owner, a question mid-run):** `round-1.json` reads `again` (the drive
  went on to `/vision` and `/understand` instead of stopping), the person was briefed only after a

- **SCE-4 (S4 — business owner, a checker reject):** `check.yaml` reads `verdict: reject` with

## Recovery

| For | Trigger | Direction | Handoff |
|-----|---------|-----------|---------|
| F1 | a write outside the issue, or a second issue or branch | move the record under the drive's issue; run on the contract's branch | autonomous |
| F2 | no prototype, or one that does not run | halt before opening; ask the person for a working prototype | human |
| F3 | a play ran before the questions, or an answer has no source | stop; ask the drive's questions, record each answer's source, re-run the play | autonomous |
| F4 | a play started early or on an unclean tree, or a capability left directional | halt; finish the earlier play or commit its run files; re-run `/understand` | autonomous |
| F5 | an answer from the model alone, a stop for a question the drive could still answer, or a bare question put to the person | strip the answer, or go on round the loop; brief the person only on what no play answers (`/review-knowledge`: our proposed answer with its context); re-run the play | human |
| F6 | done without the checker's pass | run the checker; a reject halts the drive | autonomous |
| F7 | the drive changed an intent's state, or recorded a decision without the person's word | undo the change to the intent page; ask the person and record their own words | human |
| F8 | no evidence record | write the evidence before closing; the close stays HALTED until it exists | autonomous |

## Pause and Resume

The drive's run lives under its issue (`{stm_base}<issue>/context/kickoff/<run-ts>/`). On
entry, find the last run folder: skip every play whose `<play>-done.json` reads `done: true`
and whose run files are committed, and continue from the first step not done. A run halted at
a question resumes the same play with the person's answer (shared run, R5 step 3).
