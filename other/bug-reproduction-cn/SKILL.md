# Bug Reproduction CN

用于把中文 bug report、失败日志、截图或模糊复现描述整理成维护者可以直接验证的最小复现场景。目标是先确认问题是否真实、稳定、可定位，再决定是否进入修复。

## 适用场景

- 用户要你“复现这个 bug”“把 issue 变成最小复现”“判断是不是回归”。
- issue 有日志或截图，但缺少环境、版本、输入、期望行为或实际行为。
- 需要把大项目问题缩小到一个脚本、测试、命令序列或最小仓库片段。
- 维护者需要回复报告者，说明还缺哪些复现信息。

## 不适用场景

- 用户已经提供了明确失败测试，并要求直接修复代码。
- 复现需要访问私密账号、生产数据、付费资源或未脱敏日志。
- 问题属于安全漏洞披露，应转入私密安全响应流程。

## 工作流

1. 读取并整理现有证据。
   - 提取版本、平台、运行命令、输入数据、完整错误、期望行为、实际行为。
   - 标记缺失字段，不要凭空补关键复现条件。

2. 建立复现假设。
   - 区分环境问题、配置问题、数据问题、依赖升级、代码回归和文档误用。
   - 如果有最近提交或发布记录，列出最可能的回归范围。

3. 缩小复现面。
   - 优先写一个最小命令、最小测试、最小输入文件或最小配置。
   - 删除与失败无关的网络、账号、缓存、随机数据和大型依赖。
   - 保留能触发失败的关键版本、参数和边界值。

4. 验证并记录。
   - 运行最相关的复现命令或测试。
   - 记录通过/失败结果、命令、环境、commit、日志摘要。
   - 如果只能静态分析，明确说明还需要报告者补充哪些信息。

5. 输出维护者动作。
   - 给出 issue 状态建议：needs-repro、confirmed、environment-specific、regression-suspected、docs-clarification。
   - 提供给报告者的简短中文回复。
   - 给出下一步：补测试、定位提交范围、修复、更新文档或等待更多信息。

## 输出格式

```text
复现状态：confirmed / needs-repro / environment-specific / regression-suspected
最小复现：
1. 环境：...
2. 命令：...
3. 输入：...
4. 观察到：...
5. 期望：...

验证记录：
- commit / version：...
- 命令：...
- 结果：pass / fail / not-run，因为 ...

判断依据：
- ...

建议回复：
...

下一步：
1. ...
2. ...
```

## 安全边界

- 不要要求报告者公开 token、cookie、私有仓库、生产日志或用户数据。
- 日志里出现密钥、邮箱、手机号、内部 URL 时，先脱敏再引用。
- 不要把无法稳定复现的问题说成已确认 bug；用证据区分猜测和结论。
- 需要访问外部服务或账号状态时，先给出本地可验证的最小替代步骤。

## 验证方式

- 最小复现必须包含环境、命令、输入、实际行为和期望行为。
- 结论必须对应具体日志、测试输出、commit 或版本信息。
- 至少给出一个后续可执行动作：补充信息、添加回归测试、定位提交范围或更新文档。
- 不能运行验证时，说明缺少的环境、权限或数据，并提供报告者可复制的验证命令。
