# 讨论会话交回主脑

本会话是讨论会话，不是主脑，也不是实施会话。交回只做三件事：**分类结论、写成文档、通知主脑**。不改代码，不派活，也不替主脑做验收。

## 1. 分类（先给用户过目，用户确认后再往下做）

把本会话的结论逐条列出来，每条归入一类：

| 类别 | 判断标准 | 去向 |
|---|---|---|
| 不交回 | 只是解释、澄清，没有要改的东西 | 不写文档；告诉用户这个会话可以归档 |
| 待拍板 | 产品、设计、口径上的变更，包括用户在本会话里说"就这么定了"的 | 写提案 |
| 缺陷/缺口 | 文档、契约、代码之间对不上，或者有遗漏 | 写 gap-report |

用户在本会话里口头定下的事，要**引用原话、写明时间**，归入"待拍板"。它要等用户在主脑那边确认后才生效，本会话不能把它说成"已定"。

## 2. 写文档

- **位置**：台账里写了「交回目录：」的，就写到那里；否则，项目已有 gap-report 目录的写到那里；都没有的话，写到台账同级的 `inbox/<日期>-<主题>.md`。
- **每条结论写这几项**：
  - 结论（一句话）
  - 类别
  - 证据（文件:行号、命令输出、链接）
  - 建议改法
  - 会碰到哪些模块
  - 待拍板的，再写上用户原话和选项
- **文件开头的 frontmatter**：目录里已有文件的，先沿用它们的字段格式，再补上缺的：`状态: 待主脑处理`、`来源会话: <本会话名>`、`日期`。待拍板条目逐条标 `待确认`。
- **合并同源条目**：同一个现象引出的几条结论合成一条。用户在讨论中顺带提的要求（比如"顺手修了"）写进这一条的备注里，并说明本会话没有执行。
- **提交**：直接提交到 main，先 `pull --rebase` 再 push。只动 inbox 或 gap-report 目录，和主脑提交台账是同一种性质，不开分支，这样主脑能直接读到。

## 3. 通知主脑

1. 找到主脑的会话名：
   - 先用项目记忆里的 `brain-ledger` 指针找到台账；
   - 没有指针，就在仓库里 grep「当前主脑会话：」，这一行所在的文件就是台账；
   - 读出这一行写的会话名。
2. 用 `ListAgents` 确认它还在线，然后用 `SendMessage` 发送下面的回报格式。
3. 找不到主脑、主脑不在线，或者本环境没有 `ListAgents` / `SendMessage`：只提交文档。回复用户时，第一行写"**主脑未收到，需要你转发**"，下面附上回报原文。

```
<主题> 讨论交回：<一句话>
【文档】<仓库> <分支> <commit>，路径 <path>
【待拍板】编号 · 问题 · 用户原话（<时间>） · 选项 · 建议
【缺陷/缺口】编号 · 现象 · 证据 · 建议改法 · 触碰模块
【不交回】<几条，一句话带过>
```

## 4. 回复用户

说明三件事：交回了什么、文档在哪里、主脑有没有收到。然后提醒用户：本会话里定下的事，需要在主脑那边确认一次才生效。

## 红线

| 念头 | 实际 |
|---|---|
| "用户让我顺手修了" | 讨论会话不改代码。把它写成缺陷，交给主脑派活；并告诉用户为什么不在这里修：主脑要负责验收和合入。 |
| "用户坚持要在这里改" | 用户说了算，但要按实施会话的规矩来：在 worktree 分支上改，不合 main，附上变异验证。改完后按 dispatch-template 的回报格式交给主脑验收，不按讨论交回处理。 |
| "消息发过去就行，不用写文档" | 消息会随主脑的压缩丢失。必须先提交文档，消息里只放指针和摘要。 |
| "用户已经拍板了，直接写进 decisions" | decisions 由主脑写。这里只能标"待确认"。 |
| "这个结论可能有用，先都交回去" | 没有要改动的结论就不交回，否则会淹没主脑的队列。 |
| "我直接派个会话去修" | 派活权只在主脑。 |
