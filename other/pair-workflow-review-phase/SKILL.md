# /pair-workflow-review-phase — One Head, One Verdict, From Someone Who Did Not Write It

Judge the whole result on its own merits, adversarially, from the story (acceptance criteria), the PR (diff + description), the code and the cycle's evidence (contracts, seals, ledgers — claims to reproduce, never author context to trust). Custody first, a script decides; then evidence you re-run yourself; then the review passes the tier requires. Nothing the author wrote for themselves reaches you.

## Algorithm

**Headless execution (single owner: `.pair/knowledge/guidelines/technical-standards/ai-development/skill-conventions/headless-stage-execution.md`)** — this stage runs headless: never leave a command in the background and never end your turn while a command runs (a push with a pre-push gate, a quality gate): use the maximum tool timeout, poll to completion in the same turn, and ALWAYS end with the stage's structured result — on partial progress `{ status: "failed", reason: "incomplete", detail, branch, outputHead }`.

### Step 0: Resolve the durable state (mandatory)

```bash
SKILL_DIR="$(dirname "<absolute path of this SKILL.md>")"
MAIN="$(pwd)"                                   # the main checkout — you have not cd'd yet
RUN_DIR="$MAIN/.pair/working/runs/$run/$story"
AC_HASH="$(node "$SKILL_DIR/scripts/cycle-state.mjs" ac-hash --story $story --dir "$RUN_DIR" | node -pe 'JSON.parse(require("fs").readFileSync(0,"utf8")).acHash')"   # canonical card hash — the SAME input every stage resolves with
node "$SKILL_DIR/scripts/cycle-state.mjs" resolve --dir "$RUN_DIR" --workflowVersion $workflowVersion \
  --policy '$policy' --entry $entry --story $story --inputs $inputs --acHash "$AC_HASH" --runsRoot "$MAIN/.pair/working/runs" --pr $pr --head "$(git ls-remote origin refs/heads/$branch | cut -c1-40)"
```

- `status: other-run` ⇒ return `{ status: "other-run", runId }`. `incompatible | invalid` ⇒ return `{ status: "redirect", next: { step: "blocked", reason: "failed-resume", detail: <reason> } }`.
- `next` is `blocked` with `reason: awaiting-scope-decision` ⇒ BEFORE redirecting, discover the decision the maintainer may already have posted on the PR (canary v9, B — a fresh run directory does not remember it): `REPO="$(gh repo view --json nameWithOwner -q .nameWithOwner)"; node "$SKILL_DIR/scripts/cycle-state.mjs" apply-scope-decisions --dir "$RUN_DIR" --repo "$REPO" --pr $pr --workflowVersion $workflowVersion` (no `--decision-ref`: the script reads the PR's comments back and applies every decision-shaped one through the same authenticated path, oldest first), then run `resolve` again and act on THAT `next`. You never author a decision.
- `next.step` is not `verify`, or `next.phase` is not `$phase` ⇒ return `{ status: "redirect", next }` verbatim. Spend no judgment. When `next` names THIS dispatch (`verify`, `$phase`) — `inputsChanged` or `headMoved` included — you ARE the step: continue, never return a redirect to yourself.
- `$contractSpec` given ⇒ BEFORE any judgment, invoke `/pair-workflow-contract-phase` with it and keep the returned contract: its `vocabulary` and `severityRanks` are what you review and rank against, and `templateContract` goes into your result (Step 5.6 publish does not need it; the coordinator adopts it and validates THIS review's verdict against it post hoc). Missing or failed ⇒ return `templateContract: { status: "failed" }` and review with the prompt's default vocabulary.
- Otherwise continue; `next.attempt` is your attempt number.
- `next.step: done` on a completed cycle whose remote head still equals its `reviewedHead` is returned as a redirect too: a cheap identity check, no judgment, no publication.

### Step 1: Isolation and pacing

1. Never switch the main checkout's branch. `git worktree remove --force $worktree 2>/dev/null; git fetch origin -q; git worktree add --detach $worktree origin/$branch; cd $worktree`, then run the adopted `worktree-setup-command` (`way-of-working.md`; absent ⇒ none) before any gate — the fresh tree has no dependencies or build; a `worktree-setup-command` non-zero exit HALTs the review — no gate runs on a broken setup (`status: failed`, `reason: worktree-setup-failed`); never symlink another checkout's `node_modules`/`dist` (spurious gate failures). Record `setup: <cmd> exit N` alongside the gates actually run with their exit codes; a gate not run is never reported green. Remove it when done — every handoff you write goes to `$RUN_DIR` in the main checkout, never here.
2. **PACING (mandatory)**: a supervisor kills any agent that goes 180 seconds without a TEXT message. After EVERY file you inspect, write ONE SHORT LINE. List the changed files first (`git diff $head...origin/$branch --name-only`), say the order, go file by file.
3. **Blind (mandatory)**: do NOT read `.pair/working/` except `$RUN_DIR` (contracts, seals, handoffs, prior reviews — cycle evidence) and `$reviewLog` (to synthesize). Checkpoints are the author's private context.

### Step 2: Custody (deterministic — the script decides)

```bash
SKILL_DIR="$(dirname "<absolute path of this SKILL.md>")"
cd $worktree && node "$SKILL_DIR/scripts/red-snapshot.mjs" verify-chain --pr $pr --base <cycle base> --run-dir "$RUN_DIR" --base-ref $base   # ONE call: the chain lists every seal between the base and HEAD under EVERY identity (pr=0 initial chain, pr=$pr remediation groups); `--pr` is informational; `--run-dir` lets the SCRIPT decide whether this cycle sealed a contract
```

`<cycle base>` is the head the cycle's FIRST seal sits on (`inputHead` of the earliest sealed `red-verify` handoff in `$RUN_DIR` — `a0`'s for a story on the sealed `a0` path, the first remediation group's otherwise). **When `$RUN_DIR` holds no sealed `red-verify` handoff at all, this cycle has sealed nothing**: the first review of a FRESH card (its first handoff is `a0-implement-phase`, built test-first above the base with no up-front contract — US-506) or of a PR-entry cycle, before any remediation round. A fresh card's custody starts at the base: there is no `a0` segment, and the implementation's own commits precede every seal. Pass `--base $head` and ALWAYS `--run-dir "$RUN_DIR"`: the script derives the expectation from the run directory itself (t9d-9) — no sealed `red-verify` handoff ⇒ `contract: 'none'`, snapshots left by earlier, CONCLUDED cycles are returned as `historicalSnapshots` and are not breaches of the cycle starting now; a sealed handoff present ⇒ the strict walk, whatever you assert. `--contract-expected false` is a claim the script checks, never a bypass: beside a sealed handoff it is the typed breach `contract-expected-refused`. Do not walk from the branch's merge-base hoping to find the cycle's seals: a finished cycle's snapshot commit lives in the branch forever, and treating it as binding makes every file it sealed untouchable outside the workflow for good — a hand fix, a hotfix or a merge from main then fails the NEXT cycle at its first review, with no way out, because a successor seal needs `validate` and custody blocks at `r0` (canary 481-v5). The chain answers `contract: "none"` and custody is `verified: true`, because a cycle with no contract has no custody to violate. Do NOT omit the call and do NOT invent a base — say out loud that there was nothing to check. Without that flag the chain reports `snapshot-missing` and the coordinator reads it as `failed-custody`, killing the cycle at r0 with nothing wrong (canary 481-v2). The flag is a STATEMENT ABOUT THE CYCLE, never a way past a breach: if `$RUN_DIR` does hold a sealed handoff, the strict default applies and a missing snapshot is the rebase breach it has always been. Run it ONCE: a later seal ends the previous seal's segment whatever identity it carries, so a per-identity run would report the first remediation round's commits as breaches of the `a0` segment (T-9, t9-1); a single-snapshot group with no revision may also be checked with `verify --phase`. Any breach (`snapshot-missing`, `parent-not-base`, `test-blob-changed`, `unlisted-test-changed`, `out-of-scope`, `behavioral-adds-or-moves-module`, `test-mode-production-change`, …) ⇒ `custody: { verified: false, contractBreach: true, breaches }`, no review, publish the handoff, return — a breach is terminal for the attempt and preserves the trusted snapshot.

`--base-ref $base` (US-506 AC-11): when the story branch merged its base (`origin/main`), the files that merge brought in — paths the merge commit itself changed AND the base changed since the fork, byte-identical to the base at the segment end (or deleted by the base, when they predate the branch split) — are the base's changes, not the PR's: the script leaves them out of every segment and lists them under `mergedBase.paths` (copy it into `custody` like `overriddenBreaches`). A file edited after the merge differs from the base and is still a breach; so is a PR-owned file deleted anywhere, and a fixer's own edit that restores base content on a path the merge did not change; a merged branch that is not the base earns no exemption; a sealed blob is checked by identity regardless. **The base moved while the cycle ran (AN):** a path BOTH sides edited in different places merges clean, so its blob is neither the base's nor the story's — the script RECOMPUTES the merge (`git merge-tree`) and attributes the path to the base only when the merge commit carries exactly the recomputed blob (conflict resolution, an evil merge, or any edit before or after the merge stays a breach); a SEALED test changed this way is listed under `mergedBase.sealedPaths` instead of `test-blob-changed`. **Generated files (AN2):** mirrors regenerated after the merge (a path under a mirror root byte-identical to a dataset file of the same name; a mirror deleted because its dataset origin is gone) and the `.pair/llms.txt` index (every changed line an index line, every added link resolving) are not the agent's changes — the script lists them under `generated.paths`; copy it into `custody` like `mergedBase`. A diverging mirror, a mirror-root file with no dataset counterpart, or prose in the index stays a breach. Never write a custody override for a base merge or for generated files.

An override the script HONORED comes back as `overriddenBreaches`: the breach that would have blocked, with `override: { authorizedBy, reason, at, verifyAgainst? }` attached. Whenever `verify-chain` returns that array, copy it into your `custody` VERBATIM — `custody: { verified: true, contractBreach: false, overriddenBreaches }` — and name it in the review body. The published handoff is the ONLY durable record of who authorized which exception and on what evidence; a `custody: { verified: true }` that drops the array erases the attribution the override exists to preserve (observed on PR #494, where the human authorization left no trace in the record). Never omit it because custody came back green, never summarize it, never re-derive it: the script’s array, exactly as printed. The overrides themselves are human-authored in `<runDir>/custody-overrides.json` and are NEVER yours to write, edit or add to — you report what the script honored, you do not authorize anything.

### Step 3: Evidence (re-run, never trust)

**`mode: doc` groups** (`.pair/knowledge/guidelines/collaboration/automation/doc-remediation-groups.md`): there are no witnesses to re-run. Verify each `checklist` item of the sealed contract against the diff AND its authority (the changed text really states the requirement and agrees with the source), re-run the usual conformance/link tests for the touched files, and treat any change outside `fixScope` prose as a custody breach.

0. **Fresh card, `first` pass — the tests, judged per AC (US-506 AC-3).** There is no sealed contract to re-run: the tests the implementer wrote together with the code ARE the evidence, so judge them qualitatively. For EVERY acceptance criterion of the card name the test(s) that prove it and assess them: `proven` (the test would fail without the behavior the AC claims), `weak` (it exists but cannot fail for the defect it should catch — e.g. `toHaveReturnedWith` on an async mock, an assertion on a value the setup fixes), `missing` (no test proves the AC). Record it as `acAssessment: [{ ac, tests, assessment, findingId? }]`. A `weak` or `missing` row is an ORDINARY finding (`kind: defect`, no new class) and names it in `findingId` — `publish` refuses the table without it (`acAssessment-missing`, `acAssessment-invalid:<ac>`, `acAssessment-finding-missing:<ac>`). A **mutation probe** (break the production line an AC depends on in an isolated copy, re-run its test) is a tool you MAY use to confirm a suspicion — never a required step. No evidence of test-first is asked for or checked.
1. Re-run every sealed witness and control command from the manifests: witnesses green, controls green. A witness that FAILS is a finding `kind: approved-test-failing` with `groupId` and `rowId` — it routes the group back to GREEN on the same seal. (Only a group that SEALED a contract has approved tests: on a fresh card `a0` has none, and a test weakness there is an ordinary finding.)
2. Re-run every row of the fixers' evidence ledgers (`$RUN_DIR/*-green-fix.json`, `implement-phase.json`): `observed` must reproduce. A ledger is an input to verify, never proof by assertion. Every new fixture field or table column is consumed by an expectation (trace it).
3. `$required`: re-run its oracle on this head; if the defect is still present it is a finding (`kind: regression`).
4. Full adopted gates on THIS head: run `$reviewSkill`'s gate step (or `/pair-capability-verify-quality` for the tier); a test result is reusable only under an identical `test-identity` recorded in the fixers' handoffs — otherwise rerun. The final gate set is the adopted full set.

### Step 4: Classify, then review passes by tier (declared before running, each once)

**Classify FIRST — the tier is COMPUTED, never merely read.** `/pair-capability-publish-pr` creates the PR without classification tags, so an untagged PR is the NORMAL state at review time, not evidence of risk: it is the cue to run `/pair-capability-classify`, never an answer by itself. Compose `/pair-capability-classify` with `$context: review` against the PR diff at `$head`: the story's `risk:*` label (read from the card — `$story` — through the bound host adapter) is the **floor**; the diff may RAISE it (confirm-or-raise), never lower it. The result is the handoff's `tier`, with `tierSource: "classified"`. Fall back to the fail-safe `risk:red` ONLY when classification itself fails (`/pair-capability-classify` not installed, the card or the diff unreadable, no resolvable story tier): then state it explicitly — `tierSource: "classification-failed"`, plus the reason in the review body ("classification failed: <why> — fail-safe risk:red") — and never present it as a classification of the diff. A docs-only diff, or an untagged PR, never short-circuits this step.

Declare the passes, run each once, never sample a pass again hoping for a different answer:

| Tier | Passes |
| ---- | ------ |
| `risk:green` | **general** — `$reviewSkill` phases 1–4 (validation, technical review, adoption compliance, completeness) |
| `risk:yellow` | general + **security** (`/pair-capability-assess-security $mode=review`) + **boundary**: for every changed parser, state machine, configuration or command-output domain, a finite decision table of supported states plus their invalid/boundary pair, probed at the real producer/consumer |
| `risk:red` | yellow's set + **architecture** (`/pair-capability-assess-coupling $scope=diff`) + an **adversarial second general pass** that starts from the acceptance criteria and tries to break each one |

- `first`: the full PR surface. **Contract inventory**: map each changed observable contract to its authoritative producer, inputs, consumers and representations before reporting the first hole.
- `re-review`: every `$openIds` finding gets a transition — `resolved` (you verified the fix, not the claim), `open` (still present, same id, same severity unless `severityEvidence` names a NEW failure case or changed impact), `superseded` (absorbed by another finding you name). Then ONLY the delta `git diff $head...origin/$branch --name-status`, its directly changed producer/consumer boundaries and the **cross-group interactions** of the groups fixed this round (two individually green groups whose outputs feed each other are checked together). A new finding is `kind: defect` if it is in this delta or a boundary changed by it; a real defect on unchanged code that the earlier review missed still blocks under the unchanged policy, is marked `missedUpstream: true` and gets a regression row in the next preparation; a gap in a sealed contract's coverage is `kind: contract-gap` with `groupId` — it revises that group only (`groupId: "a0"` for a SEALED initial acceptance contract: the cycle prepares `a0-rev<m>`, seals it as a successor and implements again on the same branch; on a fresh card `a0` sealed nothing, so a coverage gap there is an ordinary finding and routes the test-first remediation).
- Union the passes; deduplicate by (owner, location, observable defect) keeping every rationale; on severity disagreement keep the highest evidenced severity.

Every finding is REAL, EVIDENCED and CONCRETE (US-506 AC-3): it carries a **reproducer** — `reproducer: { command }` or `reproducer: { testRef }`, an executable reference with no shell syntax — or a **concrete failure scenario** — `failureScenario: { input, actual, expected }` (this input ⇒ this wrong result). `publish` refuses an OPEN finding with neither (`finding-unevidenced:<id>`); a closure (`resolved`/`superseded`/`human`) transitions a finding evidenced when it was opened, and a `question` claims no defect. **A difference of taste ("I would have done it differently") is not a finding and is not recorded** — not as a Minor, not as a question, not in the report. The handoff records ONLY the activities of this independent review: never the implementer's self-review, never a narrative of how the author worked. Then: `id` (`r<n>-<k>`, or `r<n>-<letter>-<k>` when `$reviewer > 1`; a prior finding keeps its id), `location` (File:Line, or the card / PR body for an `external: true` finding — a location, never acceptance), `severity` ∈ {`$severities`}, `description` = the failure case (inputs/state → wrong output), `recommendation` ending `VERIFY: …; ORACLE: …; ASSERT: …`, `kind`, `transition`, `blocking` = `!nonActionable && transition ∉ {resolved, human} && kind ≠ question && rank(severity) ≥ rank($floor)` computed from `$ranks`. `nonActionable: true` ONLY when fixing would be genuinely wrong (byte-consistent with a source of truth, an existing convention, an ALREADY-EXISTING tracked story — cite its number; do not create one — or something that resolves only after merge), always with `disposition`. An `external` finding resolves only with read-back `evidence` (the exact command and what it showed) or a `transition: human` the card supplied. **DO NOT FILE NEW ISSUES**; never invoke `$writeIssue`. **History rewrite**: `needsHumanDecision: true`, `humanDecisionKind: "history-rewrite"` (any other mandatory human decision sets `needsHumanDecision: true` too — the kind only says why, and the escalation precedes every automatic transition either way). Name EVERY finding that owes a human decision in `humanDecisionIds` (US-506: ids of this review's own findings, `publish` refuses an unknown one) — the cycle stays `escalate` until `cycle-state.mjs decide` has recorded each of them. **A finding carrying an ACTIVE `regressionRisk` is `blocking: true`** (US-479 F-9): an active risk IS an open blocker, `publish` refuses the handoff otherwise, and the severity floor never applies to it — a regression a remediation introduced is not a defect the floor may carry unfixed. The DISCHARGE of that same risk is the mirror image: `transition: resolved`, `blocking: false`, and `publish` refuses it the other way round. State follows the risk, not the finding.

**Stale-claim sweep** (US-582): before writing a finding about documentation (guideline, ADL/ADR, docs page, mirror, changeset) that states behaviour the PR changed, search the whole PR diff (`git diff $base...origin/$branch`) and the repository docs for the same claim — the specific claim, not the topic — and list EVERY location in that one finding's `location`. A generated mirror is listed with its dataset source (`<mirror> ← <dataset path>`) and fixed at the source. One stale claim ⇒ one finding, never N findings over N rounds: a later hit of a claim already reported joins that finding (its id, no new one). The doc group red-spec plans from it must cover every listed path (`finding-location-outside-scope`, `doc-remediation-groups.md`).

**US-479 (ADL 2026-09-12) — `worked`: what was already RIGHT.** When this review leaves any
obligation open or any regression active, also record the decisions you verified were correct in the
work that may be discarded: `worked: [{ id, claim, appliesTo, evidence }]`, where `evidence` has the
same shape as `closureAssertions` (`{ id, command | testRef, expected }`). A design decision no
command can demonstrate is legal as `notVerifiable: true` WITH a `rationale` — the same bargain
`nonActionable`/`disposition` strikes. The contract already says what must work again and what must
not break; nothing says what was already right, so a rebuild from an earlier head repeats the
discarded round's mistakes. You are the only participant who looked at the code closely enough to
know. Ids are stable across rounds, and `appliesTo` (paths or obligation ids) must not be empty: a
note that applies to nothing reaches no rebuild. An `evidence[].command` is an executable reference,
never shell code: `publish` refuses (`worked-evidence-unsafe:<id>`) a command containing `;`, `&`, `|`,
a backtick, `$(` or `../` — the same filter reproducers and counterexamples pass. One plain command per
evidence row; a pipeline or a chain belongs in a `testRef`, not in `command` (canary v9).

**Scope proposals are NEVER findings (US-479 T-22, S2/S5):** something demonstrably absent from the story's baseline/adoption/supported boundary — not a violation of anything approved — is `scopeChanges[]: { id: "sc-<n>", type: "new-requirement" | "scope-extension", proposal, baselineEvidenceRefs: [the evidence it is new, not a defect], discoveredAtReviewId, status: "pending" }`. It NEVER carries `severity`, is NEVER `blocking`, NEVER enters a remediation fix plan, and is never counted as a defect. `sc-<n>` ids are assigned once, under the same lock as finding ids (max existing numeric `sc-` id + 1), and stay stable across rounds. Cite the accepted obligation a finding violates; a proposal has none — if you cannot tell which it is, keep the classification visibly unresolved rather than moving a real defect into `scopeChanges`.

### Step 5: Verdict, readiness, publication (idempotent)

1. `reviewedHead` = `git rev-parse origin/$branch` AFTER inspection, lower-case 40-hex. `readiness.remoteHead` = `git ls-remote origin refs/heads/$branch` read back at the very end, ALWAYS present as lower-case 40-hex; `readiness.ready` = no blocking finding AND `remoteHead == reviewedHead` AND the full adopted gates passed on it. A `ready: true` without that head is unproven: the coordinator refuses it and the cycle state re-verifies (T-9, t9-3).
2. `first` ⇒ write the report to the [skeletal model](../../../.pair/knowledge/guidelines/technical-standards/ai-development/shrink-discipline.md#skeletal-output-model) within the template's `word-limits` and run `node "$SKILL_DIR/scripts/word-limits.mjs" check --template <$template> --body <report.md>` (exit 1 ⇒ shorten the listed sections, re-run); then post the full report as ONE PR comment in the `$template` structure with `$marker` verbatim as line 1: `node "$SKILL_DIR/scripts/pr-comment.mjs" upsert --pr $pr --marker "$marker" --body-file <report.md> --dir "$RUN_DIR"` — the script reads the PR's comments back and edits an existing marker comment in place, so a restart under another invocation never posts a second first review.
2b. **A re-review that opens NEW findings is never silent.** After you publish the handoff, run `node "$SKILL_DIR/scripts/cycle-metrics.mjs" findings --dir "$RUN_DIR" --story $story --pr $pr --runId $run --out <findings.md>`: when it answers `needed: true` (a finding was first reported by a re-review), `upsert` that file with its own marker line `<!-- pair:findings #$story PR#$pr run:$run -->` (`pr-comment.mjs upsert --body-file`) — the "Open findings" comment lists every open finding and those the re-review opened, with severity, round found, status, location and summary. `finalize` upserts the same comment by marker as a guarantee, so a skipped step never leaves an opened finding invisible. Silence is allowed ONLY when the re-review opened nothing new.
3. **US-479 S11 — regression risks.** A finding is `origin: introduced-by-remediation` only with ALL of: the approved obligation it violates (`obligationIds`), an executable `reproducerRef`, the `lastCleanReviewedHead` where that reproducer passes, the `firstFailingHead` where it fails, the `introducedByRemediationBatchId` that produced the failing head, `closureAssertions` and `affectedBoundaryRefs`. Publish it as `regressionRisk: { ..., state: 'active' }` and name the batch in `invalidatedBatchId`; `publish` stamps the `riskId` itself and refuses the claim when a proof is missing or the failing head did not come from that batch. Anything less is `origin: unknown` — an ordinary finding — and a new or changed requirement is a `scopeChanges` proposal, never a risk. You never write the active matrix: it is derived from the ledger.

To DISCHARGE a risk you must be the independent review bound to the EXACT new head: execute its closure assertions, show the cited obligation passing, confirm the batch's original findings are closed, re-test the affected boundaries, then publish the same `riskId` with `state: 'discharged'`, `dischargedHead` equal to the head you reviewed and `dischargedByReviewId`. ## Notes

- Read-only on code: never edit, commit, push, fix or merge. The only writes are the marker-keyed PR comments, the `pair-review` commit status and the ONE `pr-state:*` label at conclusion (Step 5.7, last non-partial reviewer only — t9d-24) and the handoff.
- The verdict is the template's; control flow keys on `blocking` and `next`, never on a verdict string. Individual green groups never imply approval: only this stage's `ready` on the exact remote head does.
- A resumed cycle whose LAST handoff is a `recordType: decision` record (published by `cycle-state.mjs apply-scope-decisions`, never by this skill) is not yours to re-judge: `resolve`'s `next` already routes it (a targeted remediation for an approved `extend-current-card`, or `done` once every proposal is dispositioned) — you only reach that step through the normal dispatch, same as any other `next`.
- **Host runtime (US-479 T-25, S7) — `entry`/`observe`/`reconcile` are never yours to invoke; `finalize` is yours ONLY when no host runtime is present (Step 5.3, canary v9 A).** The coordinator's launch recipe — NOT this skill, NOT the sandbox — runs `cycle-runtime.mjs entry` before dispatching the first phase and `observe`/`reconcile`/`finalize` around it, using the shell executor it already has; when it does, `$RUN_DIR/.runtime-checkpoint.json` or `.run-terminal.json` is there and you leave `finalize` to it. `observe` tails ONLY the journal/usage sources it is given, on a 5-second default interval, updates `metrics.json`/`metrics.md` at every observed step boundary, and stops after a durable terminal result and reconciliation (or a 30-second grace period leaves it partial, never fabricated). **US-479 B4:** the host journal carries no tokens and no timestamps, so the cost source is PRODUCED from the harness's per-agent transcripts — `usage-extract` (also run inside `observe`/`reconcile`/`finalize` when `--transcripts` is given) joins them to the journal on `agentId`, counts each provider request's fixed fields once and its final block's output, and reads no message content; `dispatch-stats` derives the four admin counters from the engine's own returned result. **US-479 F8:** the observer stops on `mark-terminal`, the host's record of the workflow's OWN returned result — the harness journal has no end-of-run record, is never modified, and the end of a run is never inferred from the agents observed so far; after `finalize` no late tick can overwrite the finalized view. A run directory that CONTINUES an older one is bound to it first, read-only, with `cycle-state.mjs migrate-acknowledge` — the lifetime metrics then fold every predecessor that persisted metrics and name every one that did not, so a new run directory is never read as a clean new PR. Every phase's own handoff publish already updates phase-level observations through `cycle-state.mjs`, so a missing provider usage source never erases durable progress — it only leaves that one dimension partial.

**What the PR shows (AK).** The final `pair:synthesis` comment ALWAYS carries a findings table (id, severity, round found, status/transition, location, one-line summary, resolution evidence); its late-defects line reads `missedUpstream` and `origin` from the review handoffs; and with no host usage the metrics say `not recorded (in-session)` (tokens, models) with the elapsed time taken from the handoff timestamps — never "unknown" repeated. **The verdict is published as the required `pair-review` check and the state label, not as a GitHub PR review** (approve / request-changes): the code-host adapters expose no review/vote operation, GitHub refuses an approval or change-request on one's own pull request (the automation account that opened it is usually the reviewer), and the check already gates the merge. Azure DevOps could carry a reviewer vote, but that needs a new adapter capability and an identity that is not the author — not implemented; documented here so the Reviews tab being empty is understood, not mistaken for a missing review.
