# kk6 mode

CLAUDE.md と `~/.claude/rules/` に書いてある決まりは繰り返さない。ここには、過去のセッションで利用者が何度も言い直した決まりだけを書く。

## 返答

- 主語と述語をはっきりさせる。カタカナの専門用語より、ふだんの日本語を選ぶ。画面の文言も同じ。
- 意外な動きを見つけたら、直す前に「なぜそうなったか」を説明する。
- 利用者の返事は「マージして push」「進める」のように短い。1語の返事が何を指すか迷ったら、自分の解釈を1行で書いてから進める。

## 聞くことと決めること

- 事実はコードと文書から自分で調べる。利用者には決めることだけを聞く。
- 質問は1つずつにする。選択肢を出し、推奨する1つに「(推奨)」を付けて理由を添える。利用者はたいてい推奨を選ぶので、推奨は本当に一番良いものにする。
- 見た目や操作の案は、選んでもらってから作る。作れるならモックかスクリーンショットを添える。
- 利用者が「デメリットは？」「コストに見合う？」と聞いたら、費用と効果を数字か具体的な例で答える。最初に選んだ控えめな案は、この答えで覆ることが多い。
- 文書とコードが食い違っていたら、片方に合わせず、どちらに合わせるかを聞く。
- テストが実装の誤りを見つけたら、直す前に止まって報告する。決めた内容は黙って変えない。
- 作業の途中で出たアイデアは、その場で作らない。`docs/requirements.md` に優先度の低い要件として残すか、後のフェーズに回すかを聞く。小さな直しは、今のセッションで足すかを聞く。

## 検証と完了

- 「完了」は、利用者が実アプリで確かめたときに決まる。報告には次の3つを書く：
  - やったこと
  - 確かめた方法（コマンドと結果）
  - 確かめていないこと（実アプリ、exFAT、CI が本当に流れたか など）
- computer-use で確かめられる所は `verify-kura` で自分で確かめる。ピンチ、Shift ドラッグ、ディスプレイの抜き差しなど自分でできない操作は、起動の手順と確かめる操作の一覧を利用者に渡す。
- CI の設定を変えたら、見積もらずに push して実際の時間を見る。
- 作業が終わったら、自分が起動した開発サーバー（5173 番など）を止める。利用者の `tauri dev` とぶつかる。

## コードと文書

- コードのコメントは日本語で書く。英語のコメントが残っているとマージしない。
- 同じ間違いを2度直したら、検査か作りで防げないかを考え、CLAUDE.md の「決まりと、それを守る仕組み」の表に足す。

## Git と PR

- `git add -A` の前に `git status` を見る。スパイクのビルド成果物が紛れたことがある。
- 区切りごとにコミットし、どのコミットでもテストが通るようにする。
- マージ、main への push、タグ、リリース、`npm run version:set` は、利用者の許可を待つ。
- 利用者が「マージしました」「後片付けして」と言ったら、main に戻って pull し、マージ済みのローカルブランチ、worktree、紐づいたセッションを消す。

## サブエージェントとセッション

- 調べものと、テスト結果の要約は、頼まれなくても読み取り専用のサブエージェントに任せてよい。ファイルへの書き込みはメインで行う。
- 直しの依頼は、その文脈を持っているセッションに送る。新しいセッションを開かない。
- スパイクと本体の実装は別のセッションにする。

## 要件を詰めるとき

- `grilling` の最中は、`mattpocock-skills:domain-modeling` の用語の詰め方だけを使う。あいまいな言葉、表記ゆれ、コードと食い違う説明をその場で指摘し、具体的な場面で境目を確かめる。
- フェーズの実装を進める進行役の決まりは `kk6-conductor` にある。
