**`/request-ai-reviews` と `/resolve-ai-reviews` を一続きで回す**ラッパーです。1周は「 `/ai-review` 投稿 → ワークフロー完了待ち → 指摘があれば対応」。

引数で回数を渡せば、その回数を上限に繰り返します。指摘があった周は `/resolve-ai-reviews` が修正を push するため、**次の周は変わった差分に対するレビュー**になります。

## 進め方

### 1. 引数の解釈と対象の特定

- **PR 番号**: **第1引数**。番号でも URL でもよい。無ければ `gh pr view --json number` で現在のブランチから特定する（該当 PR が無ければユーザーに確認）。
- **周回数**: **`--rounds N`**。**省略時は `1`**（課金が発生するため、明示されない限り回さない）。**上限は5** で、超える値が渡されたら5に丸めてその旨を報告する。
  - **裸の数値を周回数として解釈しない。** PR 番号と見分けが付かず、順序を間違えても通ってしまう。`--rounds` が無ければ既定値を使う。
- **リポジトリの対応可否は判定しない**。`/request-ai-reviews` が内部でトリアージするので、そちらに委ねる。
- 開始前に**周回の予定**を1行で伝える。2周以上なら**課金が回数分かかる旨**も添える。

### 2. 1周の実行

各周で以下を順に行う。**周回数は「成功した周」だけを数える**（Step 3参照）。

1. **起動**: `/request-ai-reviews` を Skill ツールで呼ぶ（PR 番号を渡す）。投稿と、**起動前の run ID** の取得までを担う。
2. **完了待ち**: `/wait-for-ci` を Skill ツールで呼ぶ。ワークフロー名 `AI Review`、イベント `issue_comment`、1で控えた**起動前の run ID** を渡す。**ここで待ち方を自前に書き直さない**（述語を間違えやすく、`wait-for-ci` に集約してある）。
3. **指摘の確認**: 完了後に対象 PR のインラインコメント件数を数える。

   ```bash
   gh api repos/OWNER/REPO/pulls/<PR>/comments --paginate -q '[.[] | select(.in_reply_to_id == null) | select(.user.login | test("\\[bot\\]"))] | length'
   ```

   Summary コメントは `<!-- Sticky Pull Request Comment... -->` で**毎回上書きされる**ため、周回ごとの記録は残らない。**各周の結果はスキル側で控えて**最終報告にまとめる。

4. **対応**: 指摘があれば `/resolve-ai-reviews` を Skill ツールで呼ぶ（PR 番号を渡す）。指摘ゼロならスキップして Step 4の打ち止め判定へ進む。

### 3. 周の成否判定と再リクエスト

- **ワークフローが `success`**: その周を **1周としてカウント**する。
- **`failure` / `cancelled`**: レビューコメントが未生成なので**カウントしない**。同じ周をやり直す（Step 2の1から再実行）。
  - ただし**連続2回失敗したら中断**し、conclusion と run URL を添えてユーザーへ報告する。ワークフロー側の問題を疑う。

### 4. 打ち止めの判定

次のいずれかで打ち止める。

| 条件 | 扱い |
| --- | --- |
| **指摘ゼロ** | 回数が残っていても打ち止める（同じ差分へ投げ直す意味が薄く、課金だけかかるため） |
| **指定周回数に到達** | 打ち止める |
| **連続2回のワークフロー失敗** | 中断してユーザーへ報告 |

指摘があった周は Step 2の4で `/resolve-ai-reviews` が修正を push しているので、**次の周へそのまま進む**（差分が動いているため、投げ直す意味がある）。

### 5. 仕上げ (全周終了後に1回だけ)

指摘に対応した周が **1周でもあれば**、最後にその PR の番号を渡して `/finalize-prs` を Skill ツールで1回呼ぶ。周ごとに呼ぶと点検3種が周回数だけ走って無駄になるため、**まとめて最後に1回**。

指摘ゼロで打ち止めた場合（差分が動いていない）はスキップしてよい。

### 6. 完了報告

- 周ごとに **run ID / conclusion / 指摘件数 / 対応内容（あれば push ハッシュ）** を1行で並べる。
- 打ち止めた理由（指摘ゼロ / 回数到達 / 失敗による中断）を明記する。
- 対応が入った周があれば、そのコミットハッシュを直接列挙する（ `report_formatting.md` ）。

## 出力の目安

- **1周で終わった場合**（省略時のデフォルト、または1周目で指摘ゼロ）: run ID と指摘件数を添えて3〜4行。
- **複数周回した場合**: 周ごとの1行サマリを並べ、最後に打ち止め理由と push したコミットを示す。
- **失敗で中断した場合**: 何周目で何回失敗したか、conclusion と run URL を明記する。

## やってはいけないこと

- **待ち方を自前に書き直すこと**。完了待ちは `/wait-for-ci` の責務で、本スキルは周回の管理だけを担う（待機ロジックが2箇所に散ると、片方だけ直る事故が起きる）。
- 指摘ゼロなのに残りの周を消化すること。**課金が発生する**ので、収束したら止める。
- 上限5を超えて回すこと。引数で大きい値が渡されても5に丸める。
- ワークフローが `failure` / `cancelled` の周を1周としてカウントすること（レビューが実行されていない）。
- 失敗のたびに無制限に再リクエストすること。**連続2回で中断**する。
- **周ごとに `/finalize-prs` を呼ぶこと**。点検3種が周回数だけ走る。Step 5でまとめて1回にする
- 周と周の間に**追加のコード変更を挟むこと**。レビュー対象が周ごとに変わる原因が `/resolve-ai-reviews` 以外にも増え、どの修正がどの指摘に対応したのか追えなくなる。

## 例外

- ユーザーが「指摘ゼロでも N 周回して」と明示した場合は、Step 4の「指摘ゼロで打ち止め」を無効にして回数分回す。
- ユーザーが上限5を超える回数を明示的に要求した場合は、課金額の目安を添えて確認したうえで従う。
