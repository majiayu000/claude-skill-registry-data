# 기능별 비정합성 점검

`/consistency-audit 세션 재개` 또는 “주문 수수료 비정합성 점검해줘”처럼 요청한다.
기능을 생략하면 현재 대화에서 정한 대상을 사용한다. 대상이 여러 개로 해석되고 범위를 정할 근거가 없을 때만 어느 기능을 볼지 묻는다.

## 점검

1. **대상과 판단할 질문을 정한다.** 예를 들어 “어떤 세션을 재개할 수 있는가?”를 기준으로 현재 작업 트리를 읽는다. 커밋이나 diff가 없어도 진행한다. 코드맵이 있으면 관련 진입점을 찾고, 기능명·상태값·이벤트와 호출부를 검색해 실제 코드로 확인한다.
2. **공유 판정 기준을 읽는다.** 프로젝트의 `skills/code-reviewer/SKILL.md`, 현재 CLI의 활성 스킬 루트, 전역 `SKILLS-CATALOG.md`에서 `code-reviewer` 행의 ‘읽을 경로’ 순으로 찾는다. Grok은 Claude의 카탈로그를 사용한다. frontmatter 이름이 `code-reviewer`인 실제 파일을 확인하고, 그 디렉터리의 `references/business-rule-consistency.md`를 직접 읽는다. 이 source-only 모듈의 기준 파일을 찾지 못하면 누락 경로와 `NOT RUN`을 알린다.
3. **같은 결정을 내리는 경로를 끝까지 따라간다.** 확인한 UI·API·배치 등의 진입점에서 실제 판정 또는 공통 구현까지 읽고, 같은 입력과 경계값에서 결과를 대조한다. 공유 기준에 따라 발견과 의도된 차이를 구분한다.

## 결과

점검한 기능과 경로를 밝히고, 발견마다 **판정 · 비교한 입력/상태 · 양쪽 결과와 영향 · 양쪽 `file:line`**을 제시한다. 관련 테스트를 직접 실행했다면 실행 근거를 붙이고, 코드를 읽어 도출한 결과는 정적 판단으로 표시한다. 접근하지 못한 경로나 계약이 불분명한 부분도 남긴다. 발견이 없으면 실제로 대조한 범위 안에서만 결론을 내린다.

기본 점검은 읽기 전용이며 결과는 대화로 반환한다.
