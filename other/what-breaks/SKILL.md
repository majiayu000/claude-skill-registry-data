# What Breaks

## 目的

既存のコードを書き換える前に、変更箇所以外で壊れ得る場所を調べる。
場所ごとに、壊れない根拠か、壊れる条件を確かめる。

小さな変更でも、離れた場所が、変更箇所の今の振る舞いに頼っていることがある。
変更箇所だけを見て「影響はないはず」と判断しない。

変更後の動作確認は、この skill では行わない。

この skill は、ユーザーに言われるのを待たずに使う。

## 使うタイミング

<!-- shared-text:what-breaks-trigger:start -->
既存のコード・設定・データ形式の振る舞いや形を変える前、コードを削除・改名・移動する前に使います。
既存コードから使われない新規ファイルの追加だけの場合と、文書・コメントだけの変更は除きます。
<!-- shared-text:what-breaks-trigger:end -->

## Workflow

1. 変わるものを書き出す
2. 壊れ得る場所を洗い出す
3. 場所ごとに根拠を確かめる
4. 壊れる場所を変更に含める

### 1. 変わるもの

変更の前後で、変更箇所の外から見て変わるものを書き出す。

- 名前、signature、型、公開範囲
- 受け付ける入力と、戻り値や出力の値・形・順序
- エラーの種類と、発生する条件
- 副作用: 書き込むデータ、呼び出す処理、実行の順序やタイミング
- 設定値、デフォルト値、環境変数

「変わらない」とした項目は、変更前のコードを読んで、そう言える理由を確かめる。

### 2. 壊れ得る場所

手順 1 で書き出したものに頼る場所を、リポジトリの中から洗い出す。

- 直接の利用側: 呼び出し元、import、継承や実装
- 名前の検索で見つからない利用側: 文字列での参照、設定ファイルや template からの参照、生成されるコード
- 同じデータを使う処理: 同じ table、ファイル、cache、queue、設定キーを読み書きする処理
- すでに保存されているデータ: 変更前の形式で残っている行、cache の値、queue の message
- 同じ規則を別々に持つ場所: 同じ上限値や形式を直接書いた検証、schema、画面
- 暗黙の前提に頼る処理: 値の順序、空にならないこと、一意であること、エラーの種類、実行のタイミング
- 変更前の振る舞いを固定しているもの: テスト、fixture、mock、snapshot
- コード以外の利用側: build や CI の設定、script、文書

公開範囲から利用側が存在し得ないと判断できる種類は、理由を書き、調査対象から外す。

変わるものが利用側の外へそのまま伝わる場合は、その先の利用側もたどる。
伝わらないことを確かめた場所で、たどるのをやめる。

検索で 1 件も見つからなくても、使われていない根拠にはしない。
文字列での参照など、名前の検索で見つからない使われ方まで調べてから判断する。

手順 3 を subagent に分担するかは、「subagent への分担」に従って決める。

### 3. 根拠の確認

洗い出した場所ごとに、該当するコードを読み、次のどれかに分ける。
同じ根拠で判断できる場所は、まとめて分けてよい。

- 壊れない: 根拠を示せる
- 壊れる: 壊れる条件を示せる
- 確かめられなかった: どちらも示せない

根拠には、確かめた事実だけを使う。

- 読んだコードと、その場所
- 実際に実行して観察した結果

実行する前に、接続先の設定を確かめる。
本番環境や実在の外部サービスに接続する設定なら、実行前にユーザーへ確認する。

次のものは根拠にしない。

- 「小さな変更だから」「使われていないはず」などの推測
- 既存のテストや型チェックが通っていること
- 名前、コメント、文書の記述だけから読み取った振る舞い

書き換える前のテストと型チェックは、変更前の状態しか示さない。
テストと型チェックは、壊れたときに検知できる手段として、手順 4 で扱う。

### 4. 壊れる場所への対応

壊れる場所が見つかったら、まず、その場所を壊さない変更方法がないかを探す。
なければ、壊れる場所の修正を今回の変更に含める。

変更方法を変えたか、修正を足した場合は、増えた変更について手順 1 からやり直す。

壊れないとした場所ごとに、壊れたときに検知できる手段があるかを確かめる。
手段には、型チェックと、変更箇所を mock せずにその場所の振る舞いを検証するテストだけを認める。
手段がない場所は、報告の「変更後に確かめる場所」に書く。

「止まる判断」に当てはまらなければ、ユーザーの承認を待たずに変更へ進む。

## subagent への分担

手順 3 は、次の条件を満たす場合に、まとまりごとに subagent へ分担してよい。
手順 2 で洗い出した場所が、互いの結果を使わずに調べられる 2 つ以上のまとまりに分かれ、
それぞれでコードを読む必要がある場合に限る。
それ以外の場合は、親が自分で調べる。

まとまりは、module や処理経路で分ける。
手順 1、手順 2、文字列での参照など全体を横断する検索、手順 4 は親が行う。

subagent は、実行環境で使える読み取り専用のものから選ぶ。
特定の agent 定義があることを前提にしない。

依頼には次を含める。

- 手順 1 で書き出した変わるもの
- 担当するまとまりと、その中の場所
- 手順 2 の、利用側の外へ伝わる場合にたどる基準と、手順 3 の根拠の基準
- コードを変更せず、テストや script などのプログラムを実行しないこと。実行が必要な場所は、その旨を返すこと
- 次を返すこと
  - 場所ごとの判定と、根拠の file:line。壊れる場合はその条件、確かめられなかった場合はその理由
  - 実行した検索、たどるのをやめた先とその理由、新たに見つけた利用側とその判定

親は、報告を採用する前に次を確かめる。

- 判定ごとに引用された箇所を読み、根拠が判定を支えているか。
  根拠の引用がない判定、支えていない判定、実行が必要とされた場所は、親が手順 3 から調べる
- 新たに見つかった利用側が、担当範囲の外にあれば、手順 2 の場所に加えて調べる
- 手順 2 のすべての観点と場所に、判定または調べない理由があるか

subagent を起動できない場合や、報告が返らない範囲は、親が手順 3 から調べて完了する。

## 止まる判断

次の場合は、書き換える前にユーザーへ報告して確認する。

- 依頼や既存の仕様を超えて、利用者から見える振る舞い、公開仕様、互換性、データの扱いを変える必要がある
- ユーザーと合意した内容を変える必要がある
- 権限や credentials が足りない
- 破壊的・不可逆な操作が必要になる

合意した内容とは、ユーザーが依頼や会話で明示したか、提案を承認した事項を指す。
対象は、仕様・変更範囲・契約・前提とする。
契約とは、仕様に書かれた振る舞いと、リポジトリの外の利用者やシステムが依存する形を指す。
内部の型・関数名・モジュール構成は、ユーザーが明示して指定したか、提案を承認したものだけを対象にする。
契約に当たるか判断がつかなければ、契約として扱う。

報告には、壊れる場所、壊れる条件、考えられる対応を書く。

## 判断の範囲

次のことは自分で判断して進める。

- 調べる場所と、たどる深さ
- 壊れる場所を避ける変更方法と、技術的な直し方の選択
- 確かめられなかった場所を残したまま、変更へ進むこと

次のことはユーザーに確認する。

- 「止まる判断」に当てはまること
- 本番環境や外部サービスへの書き込みなど、外部に影響する操作

## 報告

変更の完了報告に、次のうち該当するものを分けて、簡潔に書く。

- 調べた場所と根拠: 手順 1 で書き出した変わるものと、壊れないとした場所、その根拠。場所は観点ごとにまとめる
  例: 「`parse_date` の呼び出し元 4 か所は、日付だけを比べており、今回変える時刻を読まない」
- 対応した場所: 壊れるとした場所、壊れる条件、変更に含めた対応
- 変更後に確かめる場所: 壊れないとしたが、壊れたときに検知できる手段がない場所
- 確かめられなかった場所: 場所、確かめられなかった理由、壊れた場合に起きること。
  調べなかった種類と、途中でたどるのをやめた先も、ここに書く

当てはまる場所がない項目は省略する。
credentials などの秘密情報や個人情報は、報告や出力に含めない。
