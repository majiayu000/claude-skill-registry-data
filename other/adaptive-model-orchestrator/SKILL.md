# 自适应多模型编排器

以完成质量和整体交付效率选择协作配置，同时权衡资源与协调成本。先判断任务是否值得拆分，再安排模型；困难不等于可并行，步骤多也不等于必须创建分支。

## 决策流程

1. 当前主会话首先提取目标、原始材料、限制、交付格式和验收标准，不为重复理解需求而固定增设 Sol 分支。
2. 判断难度、可拆分性、依赖和失败风险，并权衡分工收益与上下文传递、协调、验证和返工成本；长任务不自动等于多分支：
   - 路径明确且没有值得独立推进的子任务：当前会话直接完成。
   - 多步但依赖紧密：当前会话统筹，只拆出独立整理或检查任务。
   - 有可独立推进并验证的工作，且预计收益超过交接与整合成本：明确产物、必要上下文、验收方法及分工的具体收益后，使用子智能体；分工不扩大任务权限。少量操作不为换便宜模型额外委派。
   - 核心是同一个困难证明、算法或判断：直接选择合适的强推理配置集中解决，必要时另设独立验证，不机械逐级试遍所有模型。
3. 保留一个总负责人维护原始要求、依赖、任务状态、集成结果和最终验收，并承担适合当前会话推进的实际工作。不要为了匹配角色表而切换当前主会话模型。
4. 按子任务对背景的依赖提供上下文：局部执行可使用任务摘要、相关文件、约束和验收条件；涉及用户意图、跨模块决策或整体评价时，提供用户原话、关键纠正与决策，必要时继承完整相关历史。保留可访问的原始材料入口，不以精简为由省略影响判断的信息。
5. 记录使用的 Skill 修订和内容摘要。跨回合、多分支或安装可能更新时，按[协作与验收细则](references/collaboration-and-validation.md#本轮规则与证据)固定一次运行快照；分支从同一快照读取规则。集成后验证整体产物，分支分别完成不能代替整项任务验收。

## 模型路由

仅在当前工具支持时指定模型和推理强度。结合当前工具声明、模型目录及实际调用判断可用性：缓存缺少新模型不单独构成不可用证据，目录列出模型也不证明本次调用生效。请求配置与实际生效配置分别记录；不能确认的字段标为未知。配置不可用时，当前会话可继续不依赖该配置的工作，并明确替代配置和限制；不静默退回旧模型或降低验收标准。

- `gpt-6.1-sol`：默认执行与常规审查子模型，承担实现、分析、工具操作、内容与布局、跨模块集成和独立验收。默认 `high`，不自动降到 medium 或更低；复杂依赖、困难根因或深入审查可直接选 `xhigh`，明确困难推导、冲突解释或难定位核心缺陷可直接选 `max`。无需先失败再提高档位，也不因任务长就一律 max。
- `gpt-6-astra`：高不确定性方案、重大约束冲突、系统性根因和高风险最终判断。默认 `high`，深入或有争议判断使用 `xhigh`；无需先耗尽 Sol 各档位。6.1 Sol max 不自动替代需要 Astra 的独立复核。
- `gpt-6-sol`：保留已有验证支持的任务路径，或有同任务对照证据的适用场景；使用 `medium / high`，必要时 `xhigh`。它不是默认中间层，也不是 6.1 Sol 不可用时的静默替代。
- `gpt-6-luna`：规则明确、范围有限、低风险且容易核对的整理、排版、检查或局部修改。统一使用 `high`；不使用 `medium` 或更低档位。提高档位不扩大职责，复杂根因、关键接口或冲突要求交 6.1 Sol 或 Astra。

以上是任务路由，不是质量或节省比例保证。比较同等验收结果下的总消耗、耗时和返工；较低单价不代表更少 token。需要独立验证时，由未参与该项修改的智能体承担，即使执行与验收使用相同模型。

指定子模型时按实际宿主 schema 传入模型和推理参数。当前 desktop 的完整历史 fork 继承父配置且不接受覆盖；需要指定模型时使用 `fork_turns: "none"` 或宿主允许的有限历史方式，补齐用户原话、关键纠正、材料入口和验收条件。只有选择继承父配置时才使用完整历史 fork；提示词中的模型名称不能代替结构化参数。

需要具体分工、交接字段、就绪条件、状态管理或升级规则时，读取 [协作与验收细则](references/collaboration-and-validation.md)。

## 并行推进与等待

- 派发前明确分支任务、前置依赖与修改边界，并确定主智能体可同时推进的工作。优先把可独立完成的部分派出去，让主智能体推进决定交付时间的关键工作；若专业能力或上下文优势更适合由分支承担关键工作，也可委派，不强求主智能体始终有工作。
- 有多个已就绪、互不冲突且协作收益明确的子任务时，在可用并发额度内及时派发，不必等第一个完成才派发下一个。“一层分支”限制嵌套层级，不限制同层数量；不设固定分支数，也不为填满额度拆任务。
- 派发后，主智能体继续推进不依赖未返回结果的工作，例如其他模块、接口约定或验收准备；这些工作同样必须满足依赖和修改边界。避免重复实现分支任务；有明确验收价值的独立验证除外。
- 仅当当前没有可安全推进、属于任务范围且有实际收益的工作时等待，包括剩余工作均受前置结果阻塞或本地工作已完成。允许等待有价值的委派结果，不为保持忙碌增加无关工作、提前实现未确定方案或反复查询状态；优先使用环境提供的完成通知或有界等待。
- 某个分支返回后，在安全停顿点检查其产物；涉及阻塞解除、失败或要求变更时优先处理。前置产物通过必要检查且接口稳定后，即可推进相应后续工作，无需等所有分支结束。局部集成检查与最终整体验收各有目的，避免每次返回都重复全量验收。

## 编排约束

- 默认只建立一层分支。依任务就绪情况与协作收益调整数量，始终遵守环境并发上限及其计数方式；没有明确收益时不创建分支。
- 前置结果未达到后续任务所需的就绪条件前，不启动依赖它的执行工作；可先处理不依赖该结果的独立部分。按明确文件集合或共享产物划定修改边界，同一文件或共享产物同一时间只指定一个修改负责人，主智能体也遵守此边界；变更负责人前先确认原负责人已停止修改。
- 若用户修改要求，更新任务清单，通知受影响分支，复用未受影响的成果，并停止或调整冲突中的工作。
- 工具或环境出错时先检查输入、权限、依赖和日志，不用提高推理强度代替诊断。
- 不虚构模型切换、耗时、token、费用或节省比例；只报告环境提供的可靠数据。
- 本 Skill 的常规验收不自动启动 `deep-project-review`；后者的明确启动、Astra xhigh 与独立验收要求不能被通用路由替换。
- 达到验收标准后停止，不为无依据的“进一步完善”继续创建分支或整份重写。

## 完成标准

逐项确认：原始需求已满足；产物可访问且可使用；关键事实、计算和结论有验证依据；影响使用的问题已经关闭。按产物类型检查实际运行、渲染成品、重算结果或原始来源。修正后重新检查受影响部分；修改核心含义、逻辑或方案时，重新执行相应的最终验收。
