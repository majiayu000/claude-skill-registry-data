# grill-me-ab Skill

## 概要

人は 20 個並べて「重要な順に並べてください」と言われると答えられない。
しかし「A と B ならどっち」には即答できる。**この非対称を使う。**

比較は人間が担い、集約はエージェントが担う。二択を重ねて、最後に順位へ畳む。

## 使ってよい条件

```
材料が既に存在する      ファイル、リポジトリ、これまでの会話、findings
順位だけが未定          何が大事かは本人の中にあるが、言語化されていない
出口が決まる            トップ N、採用する 1 つ、削る一覧
```

**要件が曖昧なとき、作るものが決まっていないときには使わない。**
それは元の grill-me の仕事。

## 手順

### 0. 聞く前に調べる

**答えが材料の中にあるものは、質問にしない。**
README、コード、過去のメモを先に読む。ここを省くと、本人が既に書いたことを
聞き返すことになり、貴重な質問枠を無駄にする。

### 1. 先に決める 5 つ

```
材料      どのファイル / ディレクトリ / 会話を候補の出どころにするか
目的      何を決めるための順位か (何を主役にするか / 何を削るか / どれを先にやるか)
回数      何問やるか。先に宣言する
出口      トップ 10 / 採用 1 案 / 削除リスト
記録先    途中経過を書き出すファイル。先に作る
```

**回数を先に決めるのが要。** 決めないと 10 問で満足して終わる。
50 問なら序盤に大枠を、中盤で候補を絞り、終盤を勝ち残り同士の総当たりに使える。

### 2. 質問の作り方

```
選択肢は必ず 2 つ            3 つ以上にすると比較が濁り、集約が壊れる
両方とも材料から取る          思いつきを混ぜない
それぞれに具体を添える        実測値、件数、実例。抽象語同士を比べさせない
1 回に 4 問まで              AskUserQuestion で束ねる。header は 12 文字以内
```

悪い例。

```
A. 技術的な話    B. 運用の話
```

良い例。

```
A. deep FT の 100%   112/112、非空保証、380MB で Pi 5 上 25.8 tok/s
B. 広島市の連鎖      OSM 側の事情 + モデル側の事情 + 回避策が一つの問いに集まる
```

### 3. 巡ごとの進め方

```
序盤 (1 割)    大枠。何の話か、誰に何を持ち帰らせるか、トーン
中盤 (4 割)    章ごとに中身を割る。候補を材料から掘り出す
終盤 (5 割)    勝ち残り同士の総当たり。上位が確定するまでぶつける
```

**毎巡、前の答えを踏まえて次の対戦相手を組み替える。**
同じ問いを繰り返さない。決着した組は二度と出さない。勝った者は勝った者と当てる。

各巡の冒頭で、更新された信念を 1 行で述べる。

```
更新。「分かったこと」を中心に、ただし自前ホスティング寄り、
再現可能性を持ち帰らせたい、話したいのは地図と OSM。
```

これは本人の確認にもなり、誤読していれば早く訂正が入る。

### 4. 自由記述が最も重い

**A/B を無視した回答は、選択より重い情報として扱う。**

「両方」「どちらでもない」「そもそも前提が違う」と書かれたら、
**それは私の質問の立て方が間違っていたということ。** 対立させたつもりの二つが
同じ一つの主張の二つの面だった、という場合がある。

質問を出すとき、逃げ道を明示しておく。

```
A/B のどちらでもない、両方だ、という答えも歓迎します
```

自由記述が出たら、その場で構造を組み替える。次の質問に反映する。

### 5. 出口

宣言したトップ N に畳む。各項目に次を添える。

```
一言の主張        スライド 1 枚に載る形で
根拠となる材料    実測値、実例
支持した質問番号  Q30 A / Q33 B / Q43 A のように
```

**落とすものも明示する。** 何を捨てたか、なぜかを書かないと、
後で「あれはどうなった」と蒸し返される。

## 注意

### 計算していない数値を出さない

**事後確率めいた数字を並べない。** ここで実際に走らせているのは選好のトーナメントで、
分布を計算してはいない。根拠は質問番号で示す。
「Q33 で三構成が deep の 100% を上回った」のように書く。

これは「ベイズは比喩だから信用するな」という話ではない。**比喩かどうかとは無関係に、
計算していないものを計算したように見せてはいけない**という話。

### 順位は復元ではなく共同構成である

**本人の中に隠れていた真の順位を掘り当てたのではない。** 往復の中で作られたものである。
順序を変えて問えば、別のトップ N になった可能性がある。上位 3 つは信頼してよいが、
8 位と 10 位の差は誤差だと断ってよい。

これは弱点ではない。記号創発システム論が言う「正解は存在しない」に対応する。
記号と対象の関係は固定ではなく、解釈主体によって変わる。

### 「両方」は記号が合っていない信号である

私が `A` と `B` に切り分けるとき、その分節は**私の側のもの**である。
本人にとって対象がそう分かれていなければ、A/B のどちらも選べない。

だから「両方」「どちらでもない」が返ってきたら、それは回答の拒否ではなく
**分節が対象に合っていないという観測**として扱う。その場で切り分けをやり直す。
今回いちばん重要な答え (Q41) はこの形で出てきた。

## 背景

コミュニケーションを、各自が信念を持ち他者の発話を観測として更新していく過程と
捉える見方がある。谷口忠大の記号創発システム論では、複数のエージェントが各自の
信念に基づいて他者の発話を選別しながら記号を共有する過程が、
**分散的なベイズ推論として数学的に帰着**されている。

https://www.repre.org/repre/vol45/special/taniguchi/

本スキルの往復は、その小さな一例として読める。エージェントが順位についての信念を
持ち、回答を観測として更新し、次に何を問うかを信念から決める。
そして分節が合わなければ、記号のほうを作り直す。

## 実例

2026-08-28、FOSS4G 2026 の登壇準備で 50 問。記録は `tmp/grill-me.md`。

```
Q1-4     大枠      中心は「分かったこと」、時間は自前ホスティング、地図と OSM の話
Q5-16    章割り    構築と規模、全部 OSS、地名と行政境界、正本を 1 つに保つ
Q17-28   深掘り    続編としての枠、deep の 100%、貫く主題としての「小さくする」
Q29-50   総当たり  三構成 > deep 100%、中間言語 > 広島、続編 > deep 100%
```

**決定的だったのは Q41 の自由記述。** 私は「問題を小さくする」と「2023 の続編」を
対立させたが、返ってきたのはこれだった。

> 両方。言いたいのは「私は実は 2023 年から問題をいかに小さくするかということが
> 小型モデルにとっては重要だともう分かっていた」

二つは同じ主張の二つの面で、これが発表の背骨になった。
**二択に押し込まれていたら出てこなかった。**

反省点。Q16 で「一番長く話すリポジトリは」と聞いたが、
`text2geoql-dataset/README.md` を先に読んでいれば聞かずに済んだ。
手順 0 を守れていなかった。

本スキルはその派生で、解いている問題が違う。

```
grill-me     発散を収束させる    何を作るか    出口は実装計画

```

元スキルの原則は、こちらでもそのまま守る。
