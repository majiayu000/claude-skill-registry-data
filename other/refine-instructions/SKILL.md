# Refine Instructions

この skill は明示的に呼び出された場合のみ使用する。

```text
$refine-instructions
$refine-instructions <対象の指示書>
```

## 目的

CLAUDE.md・AGENTS.md を、チームにとって役立ち、管理しやすい指示書に改善する。
指示書は書いた後に見直されず、コードや運用が変わっても古いまま残りやすい。
足りない事実があればエージェントは間違える。曖昧な記述や古い記述があれば判断がぶれる。
不要な記述は、必要な指示を埋もれさせる。

良い指示書とは、エージェントが読んで初めて正しく動ける事実が、行動を決められる形で書かれているものとする。
該当するのは、コード・設定・ツール・ほかの文書から得られない事実とする。
記述を減らすのは改善の手段であり、目的ではない。行数の目標は設けない。

## 対象

- 対象の指定がなければ、リポジトリで Git が追跡している CLAUDE.md と AGENTS.md を対象にする。
  サブディレクトリにあるものも含める。
- 指定があれば、その指示書を対象にする。
- 個人の指示書は、指定されたときだけ対象にする。
  `~/.claude/CLAUDE.md`、`~/.codex/AGENTS.md`、`CLAUDE.local.md` などが該当する。
- 指示書から読み込まれるファイル（`@path` の import など）は、重複の確認に読む。
  指定されなければ編集しない。

## 指示書に書くべき事実

- チームで決めた禁止事項、承認が必要な操作、責任の分担
- 通常の推測が外れる箇所。慣習と違うコマンド、手で編集してはいけない生成ファイルなど
- 正本の所在。「検証手順は CONTRIBUTING.md を正本とする」など
- 名前から役割が分からない場所や、似た場所の使い分け

書く記述は、いつ・何をするかと、適用条件が分かる形にする。

## 改善の観点

### 足りない事実を足す

次の根拠から、指示書に書くべき事実のうち欠けているものを足す。

- リポジトリの設定・コード・文書から確かめられる事実
- この会話でユーザーが訂正した内容
- この会話でエージェントが繰り返した間違い

共有の指示書に会話から足すのは、今回の作業に限らず、チームの誰が作業しても当てはまる事実だけにする。
今回だけの指示や、チームで合意したと確認できない個人の好みは足さない。
個人の指示書へ移す候補として報告する。
個人の指示書が対象のときは、本人が明示した、今回の作業に限らない指示を足してよい。
足す位置は既存の見出しに合わせる。合う見出しがなければ、最小の見出しを足す。

### 曖昧な記述を具体化する

「きれいに」「適切に」「注意して」など、行動を一意に決められない記述は、具体的な基準に書き換える。
基準は、文書・設定・コード・この会話から確かめられるものに限り、推測で作らない。
確かめられない記述は残し、何を決めれば具体化できるかを確認事項として報告する。

### 古い記述を直す

存在しないパス・コマンド・スクリプトや、コードや設定と食い違う記述は、現状に合わせて直す。
どちらが正しいか判断できない場合は、記述を残し、確認事項として報告する。

### 代わりが利く記述を減らす

| 記述の種類 | 扱い |
| --- | --- |
| lint、formatter、型チェック、CI などで検出済みのルール | 検出される範囲だけを削除する |
| ツールで検出できるが、まだ設定されていないルール | 残し、ツールへ移す候補として報告する |
| 既存コードに手本があるコード例 | 手本のパスへの参照に置き換える |
| 手本がなく、例がないと守れない規約のコード例 | 最小の例だけを残す |
| ディレクトリの一覧、使用ライブラリ、関数の説明など、コードや設定から分かること | 削除する |
| `package.json` の scripts などから分かるコマンドの一覧 | 定義している場所への参照に置き換える |
| CLAUDE.md と AGENTS.md の間、またはほかの文書との重複 | 正本を 1 か所にし、ほかは参照に置き換える |
| 特定のディレクトリや作業だけに関わる指示 | 残し、サブディレクトリの指示書や専用の skill へ移す候補として報告する |

根拠は、確認したファイルと設定項目で示す。
検出済みかどうかは、ツールの検査対象と除外範囲で判断する。
`.editorconfig` のように設定を宣言するだけのファイルは、検出の根拠にしない。

重複をまとめる前に、統合後も同じ指示が同じ範囲に届くことを確認する。
各指示書が適用されるディレクトリ、指示書どうしの優先順位、コピーや配布の先で参照が読めるかを確認する。
利用するハーネスが参照の方法に対応しているかも確認する。
たとえば Claude Code は、CLAUDE.md から `@AGENTS.md` で AGENTS.md を読み込める。
同じ指示が届かなくなる場合は、重複を残す。

認証情報や個人情報を見つけた場合は、内容を出力せず、場所だけを報告する。

## Workflow

1. 対象の指示書と、読み込まれるファイルを読む。
2. 根拠を集める。lint・formatter・CI などの設定、`package.json` などのタスク定義を確認する。
   README・CONTRIBUTING などの関連文書と、記述が参照するパス・コマンドの有無も確認する。
   この会話でのユーザーの訂正と、エージェントが繰り返した間違いも振り返る。
3. 改善の観点ごとに、変更する記述と内容を決める。
4. 指示書を作業ツリー上で編集する。
5. 編集後の指示書を検証する。
6. 報告する。

## 編集時の制約

- 追記・書き換えは、確かめた事実か、元の意図を保つものに限る。
- ほかの文書やツールから参照されている見出しとアンカーは変えない。
  参照の有無は、編集する前にリポジトリ内のリンクを検索して確認する。
- lint 設定、skill、ほかの文書への移動先の作成は行わない。候補として報告する。
- 作業ツリーにある無関係な変更は、stage 済みのものも含めて保持する。
- commit・push は行わない。チームでの確認は PR で行う。

## 検証

- リポジトリに Markdown の lint やスペルチェックがあれば実行する。
- 編集後に残る参照先のパス、コマンド、リンクが存在することを確認する。
- 削除・書き換えた記述の内容が、残した記述や参照先で失われていないか差分を読んで確認する。
  失われてよいのは、代わりが利くとして減らしたものだけにする。

## 完了時の報告

報告するのは、ユーザーにしか判断できないことだけにする。
判断できず残した記述ごとに、場所と、答えてほしい点を 1 行で書く。

それ以外は、修正した事実だけを短く伝える。
修正したファイル、検証の結果、移せる候補の有無を伝える。
変更ごとの内容や根拠は書かず、差分に任せる。
変更の根拠や候補の詳細は、ユーザーから聞かれたときに示す。
