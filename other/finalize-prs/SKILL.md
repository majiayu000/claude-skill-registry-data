自分の PR を仕上げるオーケストレーターです。個々のチェック・コミット・PR 説明の更新は既存のスキルに任せ、本スキルは順序と、対応が要るかの判断だけを持ちます。

## 引数で、1本か横断かを決める

| 引数 | 仕上げる範囲 | 進め方 |
| --- | --- | --- |
| PR 番号 または URL を1つ | その1本 | 「1本を仕上げる」 |
| リポジトリ名 | そのリポジトリの担当 PR | 「横断で仕上げる」 |
| 省略 | 関連リポジトリの担当 PR 全部 | 「横断で仕上げる」 |

**AI が自分の判断で呼ぶときは、必ず PR を1つ指定する。** ほかのスキル（ `/loop-ai-reviews`・`/resolve-human-reviews` など）から呼ぶときも同じです。横断は複数の PR へまとめて push するので、ユーザーが「全部」「一通り」と頼んだときだけ行います。

「この PR を仕上げて」のように今いるブランチの PR を指しているなら、`gh pr view --json number -q .number` で番号を引いて渡します。

## 1本を仕上げる

以下を **上から順に** 実行する。前段で修正が入った場合、後続の判断はその修正後の状態で行う。

1. **ベースとの統合を確かめる（点検と並行して始める）**: **CI はブランチ単体しか見ていない**ので、ベースが進んでいると緑でも壊れていることがある。

   ```bash
   git fetch origin --quiet
   git rev-list --count HEAD..origin/<base>   # ベースからの遅れ
   ```

   **0なら「ベース最新」と1行書いて次へ**。1以上なら、**作業ツリーを汚さずに** worktree で取り込んで確かめる。

   ```bash
   git worktree add -q --detach <一時パス> HEAD
   cd <一時パス> && git merge --no-edit origin/<base>
   ```

   - **コンフリクトしたら**、衝突ファイルを添えて報告する。**実際の取り込みはユーザーの指示を待つ**（取り込み方は `no_rebase_under_human_review.md` ）
   - **通ったらビルドし、続けて変更したパッケージのテストを流す**。ここで落ちたものは2で直す
   - 確認が済んだら `git worktree remove --force <一時パス>`

   **遅れが大きいほど CI 緑の意味が薄れる。** ベース側が同じコードを作り変えていても、ブランチ単体のビルドは通ってしまう。

2. **点検の実行**: `triage-why-comments`・`review-conventions`・`review-tests` を**順に** Skill ツールで呼ぶ。3つは観点が独立しており（コメント品質 / 規約遵守 / テストの過不足）、結果は互いに干渉しない。

   **この3本は同時に呼んでも並列にならない。** `Skill` には**手順書を自分の文脈へ読み込ませる形**と、**サブエージェントで完結して結果だけ返す形**があり、点検3種は前者（ `allowed-tools` を持ち、ツールを打つのは呼び出し側）。3つ同時だと手順が混ざって取り違えるので、**1つ呼び、その手順を実行し、結果を得てから次へ進む。**

   **並列化するのは各点検の中。** 依存の無い `Read` / `grep` を1メッセージへまとめて発行する。終わるまでの時間が縮むのはここ。

   `triage-why-comments` と `review-tests` は常に呼ぶ。`triage-why-comments` はコードコメントの評価を内部で `/review-code-comments` に任せ、インラインの `[fyi]` もあわせて整える。`review-conventions` はリポジトリ側のスキルなので、`.claude/skills/review-conventions/` があるときだけ呼ぶ。無ければ、規約の点検をしていないことを報告に書く。

   全部の結果が揃ってから3の修正判断に進む。

3. **修正の適用**: 1の統合検証と2の点検で「対応必要」と判定された内容を反映する
   - `[must]` に相当する違反は原則すべて対応する
   - `[imo]` / `[nits]` に相当する示唆は「直した結果が本当に良くなるか」で判断し、非対応なら理由をユーザーへ報告する
   - コメントの点検と規約の点検から出た指摘が同じ箇所に重なったら、1件にまとめて対応する
   - 対応後は影響範囲のテスト・lint・format を通す（プロジェクトの `Taskfile` 等で規定されているコマンドを使う）。**テスト一式は `run_in_background: true` で流し、待つ間に残りの修正を進める**
4. **コミット & プッシュ**: `commit-push` を Skill ツールで呼ぶ
   - `commit-push` 側の早期離脱判定に任せる (変更なしなら空コミットは作らない)
5. **PR 説明の更新要否判断**: 以下のいずれかに当てはまれば `update-pr-description` を Skill ツールで呼ぶ
   - 3で本文に反映すべき挙動変化・トレードオフ・レビュー観点が増えた
   - タイトルが差分の核と乖離した
   - 影響範囲・テスト内容の記述が現実と乖離した
   - いずれも該当しなければ呼ばない（同じ内容を送り直さないため）
   - **呼ぶときは `--skip-triage` を渡す。** コードコメントと `[fyi]` は手順2で整えてあり、渡さないと `/review-code-comments` が2回走る

## 横断で仕上げる

`list-prs` が**状態を見せる**のに対し、横断は**状態を直す**。走査して仕上がっていない PR を見つけ、1本ずつ上の「1本を仕上げる」で仕上げます。

**判定基準が `list-prs` と違います。** あちらは「今どれを動かせるか」を見ますが、こちらは「**その PR が完成しているか**」を見ます。draft でも未完なら対象で、ready でも完成していれば何もしません。

### 1. 対象と状況を集める

**`list-prs` の手順1〜2で集める。** 関連リポジトリの横断・並列の取得・引数での絞り込み・取る項目は、あちらが持つ。ここでは表を作らず、取った状況を次の判定に使う。

**他人の PR は対象外。** 仕上げるのは自分が出したものだけ（他人のは `review-pr` の領分）。

### 2. 仕上がりを判定する

**1本ずつ、次を機械的に確かめる。** 1つでも欠けていれば「未完」。

| 見るもの | 未完の条件 |
| --- | --- |
| **未解決のレビュースレッド** | 1件でも残っている |
| **CI** | 失敗がある（**原因を見る**。承認待ち等はコード起因でないので除外） |
| **ベースとの乖離** | ベースが進んでいて、統合すると壊れる |
| マージ可否 | `CONFLICTING` |

**ready 化そのものは判定に入れない。** draft のまま完成していることはある（スタックの上段など）。

**`skipped` と `failure` を混同しない。** 条件で除外されただけのチェックは失敗ではない。

### 3. 未完のものを1本ずつ、自分用の worktree で仕上げる

**共有の作業ツリーで `git checkout` しない。** 同じディレクトリで別のセッションが動いていると、その足元が変わる（ `notify_related_repo_sessions.md` ）。

1. `git worktree add -q .claude/worktrees/finalize-<PR 番号> <ブランチ>` で取り出す。**そのブランチを別の作業ツリーが開いていて失敗したら、その PR は飛ばす**（誰かが作業中）
2. `EnterWorktree` の `path` でその worktree へ移り、上の「1本を仕上げる」を実行する
3. 終えたら `ExitWorktree` （ `keep` ）で戻ってから `git worktree remove` で消す。消えたことを `git worktree list` で確かめて次の PR へ

**`EnterWorktree` で入れるのは、起動したリポジトリの worktree だけ。** ほかのリポジトリの PR は仕上げず、報告の表に「未着手（別リポジトリ）」と載せる。

**並列にしない。** 1本ずつ終えてから次へ進む。

**途中で失敗したら、そこで止めて報告する。** 残りを飛ばして続けると、どこまで終わったのか分からなくなる。worktree が残っていれば、それも報告に書く。

### 4. 報告

- 1つの表で、**走査した全 PR** を出す。仕上げたものだけでなく「元から完成していた」ものも並べる（**何を見たかが分かる**）
- 列は PR / 判定（完成 / 仕上げた / 未完のまま / 未着手）/ 何が欠けていたか / 対応したコミット
- **ready 化は絶対にしない**（ `no_auto_ready_pr.md` ）。仕上がった旨を報告して、実行はユーザーに委ねる

## 出力の目安

| 場面 | 返し方 |
| --- | --- |
| 1本で、統合クリーン・点検で修正なし・PR 説明も現状維持 | 「ベース最新・点検クリーン、追加のコミット / PR 説明更新なし」と3〜4行 |
| 1本で、修正が入った | 対応した内容、非対応にした指摘とその理由、push したコミットハッシュ、PR 説明更新の有無 |
| 横断で、全部完成していた | 「N 本走査、すべて完成」と2〜3行 |
| 横断で、仕上げが入った | 表1つ + push したコミットの列挙（レンジ表記は使わない） |
| 中断した | どの PR のどの段階で止まったかを明記する |

## やってはいけないこと

- **AI の判断で、PR を指定せずに呼ぶこと**。横断はユーザーが頼んだときだけ
- 個々のチェックや `commit-push` / `update-pr-description` の内容をこのスキル本文で再定義すること。各スキルの規約が正で、本スキルは順序のみ管理する
- 点検の結果を待たずに `commit-push` を先に走らせること（点検 → 修正 → コミット の順を守る）
- **点検の中の調査を1つずつ直列に発行すること**。依存の無い `Read` / `grep` は1メッセージにまとめる
- **呼び出し側でリポジトリ種別を判定すること**。各スキルが内部で判定するので、ここでは分岐しない
- 一部の点検結果だけを見て修正判断を先行させること。全部の結果が揃ってから3に進む
- **ベースとの統合検証を飛ばすこと**。CI が緑でも、ベースが進んでいれば統合時に壊れうる
- 検証のために**作業ツリーへ直接ベースを取り込むこと**。worktree を使い、実際の取り込みはユーザーの指示を待つ
- `update-pr-description` を無条件に呼ぶこと。差分と本文が既に整合しているなら呼ばない
- `[must]` を根拠なく見送ること
- **共有の作業ツリーで `git checkout` すること**。別のセッションの足元が変わる。自分用の worktree で仕上げる
- **横断で並列に仕上げること**。どこまで終わったのかが追えなくなる
- 他人の PR を対象にすること
- **draft を対象外にすること**。draft でも未完なら仕上げる
- CI の失敗を、原因を見ずに「未完」と判定すること。**承認待ちはコード起因ではない**
- 仕上がった PR を ready にすること
- 仕上げに使った worktree を残したまま終えること

## 前提

- ブランチが PR に紐づいていることを確かめるのは各下位スキルの責務。本スキルでは重ねて確かめない
- `decide_or_ask` / `karma_commit_style` 等のグローバルルールは `commit-push` 側が既に見ているため、本スキルで重複して参照しない

## 関連

- `list-prs` （一覧を出す）: **横断の対象と状況の集め方はあちら**。状態を見せるのがあちら、直すのがこちらで、判定の観点も違う
- `no_auto_ready_pr.md` （レビュー依頼は明示指示のみ）: 仕上げても ready 化・再依頼はしない
