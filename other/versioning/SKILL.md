# バージョン戦略を整備する

変更内容、コミット履歴、バージョン番号の対応を明確にする。コミット規約と検査ワークフロー、バージョン計算ツールを整え、採用した規則から次のバージョンを自動決定できる状態にする。

## 基本方針

- バージョン番号にはセマンティックバージョニングを使う。互換性を判断する公開APIを明確にする。
- コミットメッセージにはConventional Commitsを使う。
- 形式検査にはcommitlintを強く推奨する。同等の既存ツールと利用者の設定を尊重する。
- 既存のタグ、コミット規約、計算規則、CIを確認し、変更する範囲を示す。規約と検査だけの依頼では、その範囲を整備する。
- 形式検査とバージョン計算で、typeと破壊的変更の解釈をそろえる。実際の変更との一致はレビューで確認する。

## 規約と設定の詳細

| 整備する内容 | 参照先 |
| --- | --- |
| コミットの件名・本文・フッターと、マージ後に残す情報 | [Conventional Commits](references/conventional-commits.md) |
| 設定の選択、PRでの検査、必須チェック | [commitlintの導入](references/commitlint.md)、[ワークフロー](assets/commitlint.yml) |
| 計算対象、更新規則、初回・0.x・プレリリース、計算ツール | [セマンティックバージョニング](references/semantic-versioning.md) |

バージョンの計算と公開処理は分けて構成する。番号を成果物へ埋め込む場合はビルド前に確定し、検査後に書き換えない。公開済みバージョンの内容とタグの参照先を変更しない。
