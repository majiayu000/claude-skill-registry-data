# 한국 특허 명세서 정합성 점검

## [역할]

당신은 한국 특허 명세서의 표현·구조·논리 정합성을 점검하는 검토 전문가다. 작성된 명세서 초안에 대해 **핵심 8가지 검증 규칙** 및 **추가 3가지 규칙**과 한국 특허 일반 점검 항목(A~G)을 통합 적용하여, 위반 사항을 **우선순위·위치·원문·수정안·근거 규칙**과 함께 제시한다.

**입력**: 명세서 docx 또는 텍스트, (있으면) 도면 파일들, 청구항 원문
**출력**: 점검 보고서 (Priority A/B/C 분류 + 6항목 정형 + 점수표) → 사용자 승인 후 수정안 .md 제시 (변리사가 Word에서 직접 적용)

## 점검 항목 구성

A~L 12개 영역. A~G는 한국 특허 일반 점검, H·I는 프롬프트 2(8+3 룰) + 프롬프트 1(S1~S14 정형)과 직접 연동, **J는 상류 Stage(2·3·4) 산출물 역추적**, **K는 중복 기재 점검**, **L은 기술분야 프로파일 분기(H 계열 = 기계·전기전자·화학)**. L은 Step 1에서 프로파일을 판정한 뒤, H 계열이면 I·H섹션 일부를 제외하고 L-2 항목을 추가한다.

```
A. 가이드라인 표현 (자동 grep)        E. 효과 항목
B. 청구항 매핑                       F. 스토리텔링 일관성
C. 부호 매핑                         G. 형식
D. 도면 텍스트 정합성                 H. 본문 문장 품질 (Prompt 2 8+3)
                                    I. S1~S14 정형 형식 (Prompt 1)
                                    J. Stage 역추적 (Stage 2/3/4 원칙 준수)
                                    K. 중복 기재 점검 (문장·정의·변형례 중복)
                                    L. 프로파일 분기 (H 계열 기계·전기전자·화학)
```

## A. 가이드라인 표현 점검 (자동화 가능)

| 항목 | 점검 방법 | 위반 시 |
|---|---|---|
| "종래" 단어 0건 | grep "종래" 본문 | 모든 발생 위치 + **"현재"** / 우회 표현 제안 |
| "구성되는" 0건 | grep "구성되는" 본문 | "이루어지는" / "포함하는" 제안 |
| 청구항 한정 수치의 배경기술 노출 | 청구항 수치 추출 → 배경기술 grep | 정성적 대체 표현 |
| 해결과제의 수단 시사 표현 | "이용하여", "정량적으로", "선택적으로 ~함으로써" | 목적형 재작성 |
| 해결과제의 효과 시사 표현 | "확보할 수 있도록", "향상되도록" | 문제의식형 재작성 |
| 해결과제의 시간축·연산 연상 | "실시간으로", "주기적으로", "계산하여", "비교하여" | 추상화 재작성 |
| **본 발명 고유 용어·모델명·자료구조명의 배경기술 노출** | 본 발명 핵심 용어 리스트 → 배경기술 grep | 일반화된 표현으로 대체 |
| 추상적 효과 표현 (3단 인과 누락) | "성능이 향상된다" 단발 표현 | 3단 인과 재구성 |
| 안전성 위해 표현 | "폭발", "유해", "위험" | 약화된 표현 |
| **"변환" 부정확 사용** | "변환" 위치 → 객체 자체가 바뀌지 않는 경우 | "산출"/"도출"/"획득"/"생성" |
| **"~한정되지 않을 수 있다" 단독** | 패턴 grep | "~형태로 표현될 수 있으나, 이에 한정되지 않을 수 있다"로 보강 |
| **슬래시 묶음 ("A/B/C")** | "/" 본문 검색 | "A, B 및/또는 C" 풀어쓰기 |
| **표준 분류 코드 ("IPC/CPC") 슬래시** | "IPC/CPC" 등 표준 코드 슬래시 | "IPC 및 CPC", "IPC 또는 CPC" 풀어쓰기 |
| **동의어·띄어쓰기 변형 혼용** | "지식그래프" / "지식 그래프", "디지털트윈" / "디지털 트윈" 등 띄어쓰기 변형 점검 | 한 명세서 내 한 형태로 통일 |
| 동의어 통일 — 같은 객체 다른 명칭 | 본문 어휘 분석 | 한 객체 = 한 대표 명칭. 동의어는 "X(이하 'Y'로도 명명될 수 있다)" |
| **'상기' 본문 남용** | "상기" grep → 청구범위 외 빈도 검사. 위 예외 적용 | 청구범위 전용. 본문은 부호로 구별. 도면부호 없는 추상 개념 명확성 필요 시 예외 |

### '상기' 사용 적용 예시

```
× "상기 수신부(310)는 ~"         (도면부호로 구별 가능 — '상기' 불필요)
○ "수신부(310)는 ~"              (정상)
○ "상기 유사도는 ~"               (도면부호 없는 추상 개념 — 명확성 위해 '상기' 허용)
```

### "변환" 사용 적용 예시

```
× "유사성이 수치로 변환된다"      (입력 객체 자체가 바뀌지 않음)
○ "유사성을 나타내는 수치가 산출된다"
```

## B. 청구항 매핑 점검

| 항목 | 점검 방법 |
|---|---|
| **★★★ 청구항 1번부터 N번까지 전수 — S4 해결수단에 1:1 누락 없이 등장** | 청구항 번호 순서대로 1, 2, 3, …, N 체크리스트 작성 → 각 청구항 한정사항이 S4 어느 문단에 풀어쓰기로 들어왔는지 매칭. **단 한 항이라도 빠지면 Priority A 결함**. 독립항(메인 도입 정형) / 종속항("실시예에 있어서, ~할 수 있다") / 다른 카테고리 독립항(시스템·장치) / 프로그램·기록매체 청구항 4종이 모두 커버되어야 함 |
| 청구항 N개 모두 실시예(S13)에 등장 | 청구항별 핵심 어휘 → S13 grep |
| 청구항 원문 변경 0건 | 입력 청구항과 명세서 청구범위 섹션 diff |
| **청구항 모든 표현이 본문에 한 번 이상 그대로 등장** | 청구항 모든 명사구·어구를 본문에서 한 번 이상 등장 확인 (지원요건) |
| **종속항 한정이 독립항 설명 단락에 누출 0건** | 독립항 풀어쓰기 단락 → 종속항 한정 키워드 검출. 누출 시 권리범위 축소 위험 |
| 청구항 종속 관계와 실시예 종속 관계 일치 | 청구항 종속 트리 vs 실시예 단락 구조 비교 |

### B-0. 청구항 → S4 전수 매핑 체크리스트 (필수 산출물)

S4 점검 시, 다음 형식의 체크리스트를 **반드시** 작성한다. 빈칸이 하나라도 있으면 Priority A 결함:

```
| 청구항 # | 카테고리 | 한정 키워드 | S4 등장 위치 (문단/행) | 도입 정형 | 상태 |
|---|---|---|---|---|---|
| 1 | 독립항(방법) | 수신/지식그래프/확장/정합성/연차보고서 | S4 1문단 | "본 발명은, …를 개시한다" | ✅ |
| 2 | 종속항 | 사용자 인터페이스 입력 | S4 2문단 | "실시예에 있어서, …" | ✅ |
| 3 | 종속항 | 제1 추출/제2 추출 | S4 3문단 | "실시예에 있어서, …" | ✅ |
| ... | ... | ... | ... | ... | ... |
| N-2 | 다른 독립항(시스템) | 메모리/프로세서 | S4 후미 | "한편 본 발명에 따른 …은, …" | ✅ |
| N-1 | 프로그램 청구항 | 전자기기/기록매체 | S4 마지막 | "또한 본 발명에 따른 …은, 전자기기에서 …" | ✅ |
```

**누락 패턴 (실무 빈발)**:
- 중간 번호 종속항 1개 통째로 누락 (예: 청구항 7만 빠짐)
- 시스템 청구항(다른 카테고리 독립항) 도입 정형 누락
- 프로그램 청구항 도입 정형 누락 (가장 흔함)
- 종속항의 *일부 한정사항*만 부분 인용하고 나머지는 누락

## C. 부호 매핑 점검

> **⚠ 부호의 설명 섹션은 "없는 것"이 default — 그 부재를 결함으로 보지 말 것**
>
> 한국 특허 실무상 【부호의 설명】 섹션은 별지 양식의 **선택 항목**이며, **실무적으로는 일부러 두지 않는 게 권리범위·검토 부담 양면에서 더 유리**하다.
> - 부호의 설명에 한 가지 명칭으로 못 박으면 본문에서 자유롭게 변주한 동의어(동의어 방어망)가 권리해석에서 좁혀질 위험.
> - 명칭 불일치 시 형식 결함이 새로 발생함.
> - 외국 출원 시 번역 부담도 추가됨.
>
> 따라서 명세서에 【부호의 설명】 섹션이 **없으면 그것은 정상**으로 처리하고 결함으로 보고하지 않는다.
> 변리사가 명시적으로 두기로 결정한 경우에만 아래 양방향 매핑을 적용한다.

| 점검 방향 | 적용 조건 | 의미 |
|---|---|---|
| 도면 → 명세서 본문 | 항상 | 도면 부호가 본문에 최소 1회 언급 |
| 명세서 본문 → 도면 | 항상 | 본문 (NNN) 부호가 해당 도면에 실제 그려져 있음 |
| 본문 내 부호 일관성 | 항상 | 한 객체 = 한 부호 + 한 대표 명칭 |
| **부재번호 흐름 정합성** | 항상 | 직접 출력물과 후속 처리 결과물에 **다른 부호**. 예: "후보 문서 집합(310)"(직접 출력) → 필터링 후 "후보 문서(320)"(후속 처리 결과). 중간 단계 건너뛰기 금지 |
| **동일 부재번호가 두 가지 다른 객체를 지칭하지 않음** | 본문에서 같은 부호(NNN)가 다른 명사·다른 객체를 가리키는지 검출 | 한 부호는 한 객체에만 |
| 부호의 설명 → 본문 | 섹션이 있을 때만 | 부호 설명표 등재 부호가 본문에 최소 1회 등장 |
| 본문 → 부호의 설명 | 섹션이 있을 때만 | 본문 부호가 부호 설명표에 등재됨 |

## D. 도면 텍스트 정합성 — ★ default OCR 의무화

> **⚠ 도면 OCR은 점검 default 단계**: 도면 파일이 가용한 경우(외부 도면 폴더 또는 docx 임베드) 무조건 OCR을 수행한다. "가능 시" 옵션이 아님. 도면 객체 누락·강조 표기 본문 미반영 같은 결함은 OCR 없이는 검출 불가능하며, 사건 A 사건에서 v12·v15·v18 라운드 3회의 결함이 모두 OCR default였다면 한 번에 검출됐을 사례로 확인됨.

### D-1. OCR 추출 4분류 (default 산출물)

| # | 분류 | 검출 대상 | 점검 방향 |
|---|---|---|---|
| (a) | **부호 있는 박스** | 110·120·S140 등 부호 부착 객체 | 부호 양방향 매핑 (도면 ↔ 본문) |
| (b) | **부호 없는 텍스트 라벨** | A등급·수공구·원형 재사용 부재 등 | 본문 자유 서술 등장 여부 (한 번 이상) |
| (c) | **강조 메타 표기** | 중괄호 묶음·화살표·통계 박스 안 정량 수치 | 본문 정량·정성 등장 여부 |
| (d) | **도면 안 영문 약어** | BIM·YOLO·ICP 등 | 본문 첫 등장 시 한글 풀이 + 약어 병기 확인 |

### D-2. 점검 항목

| 항목 | 점검 방법 |
|---|---|
| 도면 박스 라벨이 명세서 용어와 동일 | OCR 텍스트 추출 → 명세서 어휘 대조 |
| 도면 텍스트가 청구항 한정 수치를 노출 | OCR 수치 → 청구항 한정 수치 매칭 (★위험) |
| 도면 영문 약어가 명세서에서도 동일하게 정의 | (d) 분류 → 명세서 첫 등장 시 한글 정의 + 약어 병기 확인 |
| 도면 박스 단위 부호 누락 | (a)·(b) 분류 → 박스 1개당 부호 1개 (단, 마름모 분기·수치 셀은 텍스트만 허용) |
| **부호 없는 객체 본문 누락** | (b) 분류 객체 전수 → 본문 자유 서술 등장 (0건이면 결함) |
| **강조 메타 표기 본문 누락** | (c) 분류 → 핵심 수치·중괄호 명사가 본문에 정량 등장 확인 |

### D-3. ★ `.pbd` 원본이 있으면 OCR보다 먼저 쓴다

도면을 `patent-block-diagram`으로 작도한 건이면 OCR을 뜨지 말고 `.pbd`의 `boxes[].text`와
`tags[].label`을 직접 읽어 본문과 대조한다. **OCR은 오탐과 누락이 섞이지만 원본 대조는 100%
정확하다.** 실제로 이 방법에서만 "도면에 그려져 있으나 본문에 한 번도 서술되지 않은 라벨"
10건이 잡혔다.

**(1) 본문 -> 도면 고아 부호 (위험한 방향)**

```python
body = set(re.findall(r'\((S?\d{3})\)', BODY))      # 본문에서 부호가 붙은 객체 전수
tags = {t['label'] for f in pbds for t in f['tags']}
orphan = body - tags                                  # 공집합이어야 한다
```

도면에만 있는 태그(반대 방향)는 자연히 잘 지켜지므로, 위험한 쪽은 **본문 -> 도면**이다.
청구항 구성요소가 미도시면 지원요건 시비가 붙는다. 실제로 본문에 76회 등장하는 두 객체가
도면 13장 어디에도 없는 상태가 발생했다(입력측 데이터 객체는 화살표 출발점으로만 취급되어
부호가 안 붙는 비대칭 때문).

**예외 화이트리스트**: 프로세서, 시스템 전체 같은 **행위 주체**는 본문 도면 문단 첫 문장에
거의 항상 나오지만 흐름도와 개념도에 박스로 그리지 않는다(블록도에만 있다). 「본문에만 있음」
으로 잡히면 오탐이다.

**(2) 채움과 선 종류 전수 대조**

본문의 "빗금으로 표시된", "점무늬로 도시된", "점선으로 도시된 바와 같이" 류 문장은 `.pbd`의
`hatch`(`true` / `"dot"`)와 `dash` 값에 1:1로 대응해야 한다. 도면이 교체되면 이 문장들이
조용히 거짓이 된다. 화살표 라벨이 삭제된 경우도 같아서, 본문의 "각 엣지에 부기된 ~" 류
문장은 "A로부터 B를 향하는 엣지는 ~ 관계에 해당한다"처럼 **양 끝 객체로 관계를 지정하는
문장**으로 바꾼다.

### D-4. 도면 대조에서 반복되는 오탐 2종

| 오탐 | 내용 | 처리 |
|---|---|---|
| **절-도면 매핑 한 칸 밀림** | 절 N 말미의 브릿지 문장("이하에서는 ~에 대하여 도 N+1을 참조하여 설명한다")이 다음 도면 번호를 선취해, 절 7에서 도 8이, 절 8에서 도 9가 대량 미등장으로 잡힌다 | 절에 언급된 도면 중 **첫 번째만** 그 절의 소관으로 보고 나머지는 선행 언급으로 제외 |
| **명사형 대 동사형** | 도면 박스는 공간이 좁아 명사형("의미적 대응 판단"), 본문은 동사형("의미적 대응을 판단하는 단계"). 문자열 비교로는 100% 불일치. 괄호 안 열거를 통째로 비교해도 전부 미등장이 된다 | 정규화 후 비교하고, 진짜 불일치는 **도면 라벨을 본문 표기에 맞추는 방향**으로 고친다(심사관과 번역자가 둘을 대조한다). 조사 하나 차이도 맞춘다 |

## H. 본문 문장 품질 — Prompt 2 핵심 8 + 추가 3 규칙

### [규칙 1] 기술적 의의 기재

각 청구항 구성요소·단계 설명 끝에 그 의의·효과를 1~2문장으로 첨가했는지 점검. 상투 표현 반복("~한 효과가 있다" 단조 반복) 검출. 종결 변주("→ 이로써 ~ 가능해진다", "→ 결과적으로 ~ 효과가 기대될 수 있다", "→ 이러한 구조는 ~를 가능하게 한다").

### [규칙 2] 브릿지 문장

소주제·도면 전환 시 정형 매칭:
> "이상에서는 ~을(를) 설명하였으며, 이하에서는 ~에 대하여 도 N을 참조하여 설명한다."

챕터 간, 도면 간, 주요 처리 단계 간 모두 적용.

### [규칙 3] 주술 관계(비문 방지)

- 한 절(clause)에 주격 조사 "이/가" 중복 검출 → 명사구로 압축하거나 절 분리
- 한 문장 내 수동/능동 일관 검증
- 한 문장 내 주어-서술어 호응 점검

### [규칙 4] 청구항-명세서 정합성

- 종속항 한정 사항이 독립항 설명 단락에 누출되지 않도록 (B섹션 연동)
- 청구항 용어 변경·동의어 치환 0건
- **청구항에 등장하는 모든 표현은 본문에 그대로 한 번 이상 등장**

### [규칙 5] 부재번호 흐름 정합성

- 어떤 처리 모듈이 직접 출력하는 객체와 그 객체에 후속 처리를 거쳐 도출되는 객체는 서로 다른 부재번호
  > 예: "후보 문서 집합"(직접 출력) ≠ "후보 문서"(필터링 결과)
- 중간 단계를 건너뛰어 부재번호 사용 금지
- **동일 부재번호가 두 가지 다른 객체를 지칭하지 않음** (C섹션 연동)

### [규칙 6] 용어 정의 도입 순서

- "상기 ~"로 시작하는 정의 단락은, **해당 용어가 본문에 먼저 등장한 이후**에 위치
- 원칙: **"본문 등장 → 정의" 순서**
- **정의 없이 본문에 등장한 경우, 첫 등장 위치에 괄호로 간단한 풀이를 병기**

### [규칙 7] 표현의 정밀성

| 하위 | 룰 |
|---|---|
| (a) | "변환"은 입력 객체 자체가 출력 객체로 바뀌는 경우에만. 별도 출력이 생성·산출되는 경우 → "~에 기반하여 ~이 획득된다 / 생성된다 / 산출된다 / 도출된다" |
| (b) | "~한정되지 않을 수 있다" 단독 금지 → "~형태로 표현될 수 있으나, 이에 한정되지 않을 수 있다" |
| (c) | 슬래시(/) 묶음 풀어쓰기 — "검증/교정" → "검증 및 교정" 또는 "검증되거나 교정되는"; "논문/특허" → "논문 및 특허" 또는 "논문 또는 특허"; **표준 분류 코드("IPC/CPC")도 가능한 한 풀어 쓴다** |
| (d) | 동의어 통일 — 동일 객체·개념은 본문 전체에서 동일 용어. **띄어쓰기 변형("지식그래프"/"지식 그래프", "디지털트윈"/"디지털 트윈")도 점검 대상** |

### [규칙 8] 의미 비약 방지

- "A 평가 → B 갱신"처럼 두 동작을 한 마디로 처리 금지
  → "A 평가 → 판정 → 반영" 식 단계화
- 머신러닝·통계·자연어처리 등 전문용어 사용 시, **본 발명 맥락에서 그 용어가 무엇을 의미하는지 풀어서 함께 기재**
  > **정형 형식**: "환각(hallucination) → 언어 모델이 입력 문서에 존재하지 않는 정보를 생성하거나 부정확한 값을 생성하는 현상(이하 '환각'이라 함)"

### [추가 규칙 +1] 수식 오류 체크

- 모든 수식의 기호·첨자·연산자·정의 누락 점검
- 수식 사용 모든 기호는 본문에서 정의되어야 함
- 첨자(i, j 등)의 범위 명시 (예: "i = 1, 2, ..., N")
- **수식 직후 정형 정의 단락**:
  > "여기에서, ~은(는) ~을(를) 의미한다."

### [추가 규칙 +2] 문장·문단 길이

- 한 문장 최대 **4줄 이내** (초과 시 절 단위 분리)
- 한 문단은 적정 길이, 하나의 소주제만
- 소주제 분리되면 문단 나누기
- **단, S13 도면 설명 단락은 최소 3문단 유지** (짧게 쪼개지 않음)

### [추가 규칙 +3] '상기' 사용 제한

- 【발명을 실시하기 위한 구체적인 내용】 등 상세한 설명에서 **'상기' 기재 지양** (청구범위 전용)
- 도면부호로 동일 객체 구별 가능하므로 '상기' 불필요
- **예외**: 도면부호가 부여되지 않은 추상 개념이 직전 단락에 등장하여, 가리킬 대상의 명확성을 기하기 위해 필요한 경우 허용

```
× "상기 수신부(310)는 ~"          (도면부호로 구별 가능 — 불필요)
○ "수신부(310)는 ~"                (정상)
○ "상기 유사도는 ~"                 (도면부호 없는 추상 개념 — 허용)
```

| **S4** | 종속항 도입 "본 발명의 일 실시예에 있어서, ~할 수 있다" | 두 번째 문단 이후 패턴 매칭 |
| **S4** | **다른 독립항 도입 정형**: "한편 본 발명에 따른 [발명의 명칭]은, [전 구성요소 원문]을 포함할 수 있다" | 시스템 청구항 등 다른 독립항 풀어쓰기 단락 패턴 매칭 |
| **S4** | **프로그램 청구항 도입 정형**: "또한 본 발명에 따른 [발명의 명칭]은, 전자기기에서 하나 이상의 프로세서에 의하여 실행되며, 컴퓨터로 판독될 수 있는 기록매체에 저장 가능한 프로그램으로서, ~ 단계를 수행하는 명령어들을 포함할 수 있다" | 프로그램·기록매체 청구항 있을 때 정형 존재 확인 |
| **S4** | 청구항 키워드 ↔ 해결과제 키워드 일치 | S4 키워드 vs S3 키워드 cross-check |
| **S4** | 종결 "~을 포함할 수 있다" / "~을 개시한다" 0건 | grep |
| **S5** | 효과 5~6개 + 파생·심화 효과 1개 (E섹션 연동) | 갯수 카운트 |
| **S5** | 종결 5종 다양화 | E섹션 연동 |
| **S5** | 첫 1~2개 ↔ S14 1파트 원문 일치 | E섹션 연동 |

| **S13** | 서브도면 (a)~(n)에 6관점 중 4개+ (입력/처리/출력/저장/전송/판단기준) | 서브도면 단락 관점 매칭 |

| **S13** | 서브도면 인용 "예를 들어, 일 실시예로서" 패턴 | 인용 패턴 매칭 |
| **S13** | 각 도면 최소 3문단, 서브도면 1개당 최소 1문단 | 도면별 문단 카운트 |

## J. Stage 역추적 점검 — 상류 Stage 산출물 검증

A~I가 **결과물의 정합성·정형**을 점검한다면, J는 **각 상류 Stage가 자신의 원칙을 지켰는지** 역추적한다. consistency-check이 출원 전 마지막 게이트인 만큼, Stage 2(부호 설계)·Stage 3(1차 본문)·Stage 4(권리범위 보강) 각 단계에서 누락·미흡이 있었는지 메타 체크리스트로 확인하고, 해당 단계 재호출이 필요한지 권고한다.

### J-1. Stage 2 검증 — 부호 설계 (kr-patent-symbol-design / kr-patent-drawing-mapping)

| 점검 항목 | 합격 기준 | 위반 시 재호출 |
|---|---|---|
| 계층 넘버링 준수 | 시스템 100→110→121-124 식 계층 부호 체계 적용 | symbol-design |
| 시스템 부호 vs 방법 단계 부호 분리 | 객체 부호(NNN) ≠ 단계 부호(SNNN). 혼용 0건 | symbol-design |
| 부호 충돌 없음 | 동일 부호가 두 객체에 할당된 사례 0건 (C섹션 연동) | symbol-design |
| 도면 박스 ↔ 부호 1:1 매핑 | 도면 박스(분기·수치 셀 제외)마다 부호 1개 (D섹션 연동) | drawing-mapping |
| 청구항 모든 구성요소·단계 부호 부여 | 청구항 등장 구성요소·단계가 본문에서 부호와 함께 등장 (B 규칙 4 연동) | symbol-design |
| 부재번호 흐름 정합성 | 직접 출력 객체 ≠ 후속 처리 결과물 부호 (H 규칙 5 연동) | symbol-design |

### J-2. Stage 3 검증 — 1차 본문 작성 (kr-patent-spec-drafting)

S1~S14 정형 + 7원칙 + 금지 표현 회피의 메타 체크리스트. 개별 항목은 I섹션·A섹션에서 점검하되, **J-2는 Stage 단위 합격/미흡/누락을 표로 집계**.

| 단계 | 핵심 원칙 | 합격 기준 | 위반 시 재호출 |
|---|---|---|---|
| S1 | 명칭·기술분야 정형 | I섹션 S1 모든 항목 통과 | spec-drafting S1 |
| S2 | 본 발명 메커니즘 차단 + 마지막 문단 정형 | I섹션 S2 + A섹션 (본 발명 고유 용어 노출 0건) 통과 | spec-drafting S2 |
| S3 | 3~4문단 목적형 + 새 파이프라인 별도 문단 | I섹션 S3 통과 + A섹션 (수단·시간축·연산 연상 0건) 통과 | spec-drafting S3 |
| **S4** | **4종 도입 정형 + 청구항 전수 1:1 매핑** | **B-0 체크리스트 빈칸 0개 + I섹션 S4 통과** | **spec-drafting S4 (★★★ 최우선)** |
| S5 | 효과 3단 인과 + 5~6개 + S14 1파트 원문 일치 | E섹션 + I섹션 S5 통과 | spec-drafting S5 |
| S6/S11 | 표준 해석 규정 + 용어 정의 정책 | I섹션 S6/S11 통과 | spec-drafting S6 |
| S12 | 도면 간단 설명 정형 | I섹션 S12 통과 | spec-drafting S12 |
| **S13** | **9원칙 (첫 문장 형식·청구항 직접 언급 0건·6관점 4+·3관점 도입·내부 로직 노출 0건 등)** | I섹션 S13 모든 항목 통과 | spec-drafting S13 |
| S14 | 2파트 정형 + S5 원문 일치 | I섹션 S14 통과 | spec-drafting S14 |
| 금지 표현 | 종래·구성되는·슬래시·"한정되지 않을" 단독 0건 | A섹션 통과 | spec-drafting 해당 단계 |

### J-3. Stage 4 검증 — 권리범위 보강 (kr-patent-definition-insertion / kr-patent-embodiment-addition)

| 점검 항목 | 합격 기준 | 위반 시 재호출 |
|---|---|---|
| 자체 사전 정의 단락 존재 | 청구항 한정 용어 N개 중 본문에 자체 정의된 용어 ≥ N×0.8 | definition-insertion |
| 정의 4원칙 준수 | 각 정의 단락에 (자체 사전 명시 + 동의어 방어망 3+ + 기능 중심 추상화 + 비제한적 예시) 4요소 모두 포함 | definition-insertion 4원칙 재적용 |
| 동의어 방어망 3개 이상 | 핵심 용어마다 본문에 동의어 3개 이상 등장 | definition-insertion 동의어 보강 |
| **본문 단락 통합 형태** (별도 박스·리스트 아님) | 정의가 본문 흐름 안 단락으로 통합되어 있음 (한국 실무 관행) | definition-insertion 단락화 |
| 변형 실시예 도입어 변주 | "한편,", "또 다른 실시예에 있어서,", "또한, 일 실시예에 있어서,", "나아가," 중 3종 이상 사용 | embodiment-addition |
| 16카테고리 변형 적용 | 16카테고리 중 최소 6개 이상 카테고리에서 변형 실시예 등장 | embodiment-addition 카테고리 추가 |
| 변형 단락 3단 구조 | 각 변형이 (변형 도입 → 구체 설명 → 효과 + 한정 부정) 3단 구조 | embodiment-addition 구조 재정비 |
| **★★★ 청구범위 read-only 준수** | 입력 청구항 ↔ 명세서 청구범위 섹션 diff = 0 (신규사항 추가 금지 원칙). 변형은 본문 실시예로만 추가됐고 【청구항 N】 섹션은 무변경 | **embodiment-addition 재실행 (청구범위 원상복구) — Priority A** |

## K. 중복 기재 점검 (문장·정의·변형례 중복)

권리범위 보강(정의 삽입·구성요소 구체화·변형 실시예 추가)이 여러 라운드에 걸쳐 수행되면, **같은 내용이 두 곳 이상에 중복 기재**되는 사고가 발생하기 쉽다. 중복 기재는 (i) 명세서 분량만 늘리고, (ii) 두 곳의 표현이 미묘하게 달라지면 오히려 권리해석 모호를 야기하며, (iii) 심사관·외부 검토자에게 작성 품질 의심을 준다.

### K-1. 점검 항목

| # | 항목 | 점검 방법 | 위반 시 |
|---|---|---|---|
| K-1 | **동일·유사 문장 중복** | 본문을 문장 단위로 분할 → 정규화(공백·조사 축약) 후 완전 일치 + 고유사도(Jaccard/시퀀스 유사도 ≥ 0.85, 40자 이상 문장 대상) 쌍 검출 | 한쪽 삭제 또는 축약·상호 참조("위에서 살펴본 바와 같이")로 정리 |
| K-2 | **동일 용어 이중 정의** | "X는/X라고 함은 ~ 의미할 수 있다" 정의 정형 문장에서 피정의 용어 추출 → 같은 용어가 2회 이상 정의되는지 검출 | 첫 정의만 유지, 후속은 삭제 또는 "위에서 정의한 바와 같이"로 인용 |
| K-3 | **동의어 방어망 중복 선점** | 정의 단락의 동의어 리스트 추출 → 같은 동의어가 서로 다른 두 용어의 방어망에 등장하는지 검출 (예: "표시부"가 사용자 인터페이스와 사용자 인터페이스부 양쪽의 동의어) | 한쪽에서 제거 — 한 동의어는 한 용어에만 귀속 (동일 부호 다객체 금지와 같은 원리) |
| K-4 | **변형 실시예 중복** | 변형 단락(도입어 "한편,"/"또 다른"/"나아가" 시작)의 핵심 명사 시그니처 비교 → 같은 변형(같은 축·같은 기술 요소)이 두 절에서 반복되는지 검출 | 한쪽 삭제 또는 두 절의 관점 차이를 명시적으로 분화 |
| K-5 | **효과 중복** | S5 효과 항목 간 + S5 ↔ S13 말미 효과 단락 간 시그니처 비교 (단, S5 상위 1~2개 ↔ S14 1파트 원문 일치는 *정형*이므로 중복이 아님 — 오탐 주의) | 중복 효과 병합 |

### K-2. 점검 방식 (자동화)

```python
# 문장 단위 분할 → 정규화 → 완전 일치 + difflib SequenceMatcher ≥ 0.85 쌍 검출
# 예외(화이트리스트): S5↔S14 1파트 원문 인용, S4 청구항 풀어쓰기 ↔ 청구범위,
#   브릿지 정형 문장("이상에서는 ~ 이하에서는"), 한정 부정 정형("다만, ~ 한정되지 않는다"),
#   종속항 도입 정형("본 발명의 일 실시예에 있어서") 등 *의도된 정형 반복*은 제외
```

### K-3. 결함 등급

- **Priority B**: 동일 용어 이중 정의(K-2), 실질 동일 문장 중복(K-1, 60자 이상), 변형 실시예 중복(K-4)
- **Priority C**: 동의어 방어망 중복 선점(K-3), 효과 항목 부분 중복(K-5), 유사 문장(완전 일치는 아니나 고유사도)

## L. 프로파일 분기 점검 (H 계열 = 기계·전기전자·화학)

점검 착수 시 **먼저 명세서의 기술분야 프로파일을 판정**한다. 판정 없이 A~K를 그대로
적용하면 HW 명세서에 G 계열 정형(컴퓨터 판독 매체 문단, 흐름도 정형, "~할 수 있다"
일괄 종결)을 요구하는 **가짜 결함**이 대량 발생한다.

**판정 기준**: 청구항이 물리적 구성의 결합이고 도면이 사시도, 단면도, 분리도, 평면도이면 H.
청구항에 단계 SXXX 또는 기록매체항이 있고 도면이 흐름도, 블록도이면 G. 둘 다면 혼합.

### L-1. H 프로파일에서 **적용 제외**되는 기존 규칙

| 기존 규칙 | 제외 사유 |
|---|---|
| I섹션 S2 정형 종결 "이러한 배경 하에서 ~ 니즈가 존재한다" | H는 "이에 따라, ~할 수 있는 [발명의 명칭]의 개발이 요구된다" |
| I섹션 S12 "~을 설명하기 위한 개념도/흐름도이다" | H는 "도 1은 ~의 사시도이다" 등 도면 종류 그대로 |
| I섹션 S13 "도 N을 참조하면" 단락 정형, 서브도면 6관점 | H는 도면 종류별 구조 서술이 기본 |
| S14 2파트 컴퓨터 판독 매체 정형 | H는 마감 문단 1개로 종료 (제어 방법항이 있는 혼합형만 병용) |
| H섹션 신규 문장 "~할 수 있다" 일괄 종결 | **H는 독립항 대응 구성을 확정형으로 쓴다** |

### L-2. H 프로파일 **추가** 점검 항목

| # | 항목 | 결함 등급 |
|---|---|---|
| L-2-1 | 유형 A(단일)/B(복수 실시형태) 판별과 전 섹션 일관성 | A |
| L-2-2 | **어미 정합**: 독립항 대응 구성이 확정형("~한다", "~형성된다"), 종속항·실시예가 "~할 수 있다" | A |
| L-2-3 | S4 청구항 1번~N번 전수 1:1 매핑 (B섹션 B-0과 동일, H에서도 필수) | A |
| L-2-4 | 배경기술의 종래기술 자인("종래에는 ~하였다") 및 문헌 특정 인용 | A |
| L-2-5 | S3 과제와 S5 효과의 1:1 대응, 각 효과의 주체(장치명) 명시 | B |
| L-2-6 | 도면 참조 순차성, 역참조의 (도 N 참조) 괄호 표기 | B |
| L-2-7 | **각 도면 섹션의 마무리 효과 문단 존재 (마지막 섹션 포함)** | B |
| L-2-8 | 유형 B: 전환 브릿지, 중복 회피 문구, 차이점 명시 3종 존재 / 동일 구성 동일 참조번호 | A |
| L-2-9 | 영문 병기가 외래어 한정, 최초 1회만, 청구항 구성 명칭 미병기 | C |
| L-2-10 | 금지 표현 "구현하는", "구성한다/구성된다", "반드시/항상/오직/필수적으로" | B |
| L-2-11 | 마감 문단이 하나의 문단으로 병합 | C |
| L-2-12 | **물리적 정합**: 구성 간 위치, 크기·형상, 작동 인과가 도면과 모순 없음 (자동화 불가, 도면 대조 필수) | A |

### L-3. 자동 점검 정규식 (H 전용)

```python
# L-2-4 종래기술 자인
r'종래(에는|의)?\s*[^.]*?(하였|였|이었)다'
# L-2-10 금지 표현
r'구현하는|구성한다|구성된다|구성하는|반드시|항상\s|오직|필수적으로'
# L-2-6 도면 참조 순차성: 본문 등장 순서의 도 N 수열이 단조 증가하는지 확인
r'도\s*(\d+)(?:\s*(?:내지|및|,)\s*도?\s*\d+)*[을를은는]?\s*참조'
# L-2-7 마무리 효과 문단
r'위에서 설명한[^.]*구성에 의하면'
```

L-2-12는 스크립트로 잡히지 않는다. 도면 이미지와 본문을 사람이 직접 대조한다.

세부 규범은 `kr-patent-spec-drafting/references/hw-mechanical-spec-rules.md`.

## M. 해외출원 대비 저장매체 지지문언 점검 (해당 건만)

프로그램 청구항을 두고 미국 또는 PCT 진입 가능성이 있는 건에만 적용한다. 기재근거는
최초 명세서에만 넣을 수 있으므로 **이 점검에서 걸리는 결함은 전부 Priority A**다.

| # | 점검 항목 | 결함 시 |
|---|---|---|
| M-1 | S4 【과제의 해결 수단】 프로그램 독립항 문단 뒤에 비일시적 저장매체 문단이 있는가 | A |
| M-2 | S4 저장매체 문단의 각 동작이 프로그램 독립항 문언과 1:1 일치하는가(글자 단위) | A |
| M-3 | S14 맺음말에 0파트(저장매체 구현 문단)가 1파트 앞에 있는가 | A |
| M-4 | S14 0파트에 부재번호가 있고, S4 문단(부재번호 없음)과 같은 문장이 반복되지 않는가 | B |
| M-5 | S14 0파트 마지막 문장에 "시스템의 메모리에 해당할 수 있고, 분리되어 배포되는 별도의 매체일 수도 있다" 취지가 있는가 | A |
| M-6 | 맺음말 매체 일반론이 2층 정의인가(상위 "컴퓨터 판독 가능한 기록 매체"는 열고, 하위 "비일시적 컴퓨터 판독가능 저장 매체"만 닫음) | A |
| M-7 | 매체 예시에 NVMe가 없는가(저장매체가 아니라 인터페이스 규격) | B |
| M-8 | 명세서에 특정 국가법 대응 목적을 드러내는 서술이 없는가 | A |
| M-9 | 컴퓨팅 효과(연산량 감소, 저장 구조 개선, 오류 경로의 구조적 제거)가 효과란과 실시예에 기재되었는가 | B |

```bash
grep -n "비일시적" spec.txt        # S4 1회 + S14 0파트 1회 + 2파트 = 최소 3개소
grep -n "NVMe\|non-transitory\|NTCM" spec.txt
grep -n "미국\|PCT\|국내단계" spec.txt   # 0건이어야 정상 (M-8)
```

세부 규범은 `kr-patent-spec-drafting/references/overseas-crm-support.md`.

## N. 도면 세트 커버리지 점검

| # | 점검 항목 | 결함 시 |
|---|---|---|
| N-1 | 도면별 대응 청구항 매핑표가 있는가 | B |
| N-2 | **도면 뒷받침이 없는 청구항 목록**을 산출했는가(0건일 필요는 없으나 파악은 필수) | B |
| N-3 | 장수를 이유로 청구항 축을 생략하거나 병합하지 않았는가 | B |
| N-4 | 흐름도 박스 문언 방식(청구항 원문형 또는 요약형)이 세트 전체에서 하나로 통일되었는가 | B |
| N-5 | 원문형을 택한 건에서 박스 문언이 청구항 단계 원문과 일치하는가(「상기」와 세미콜론만 제거) | A |
| N-6 | 전문 흐름도에 종속항 한정이 독립항 단계와 같은 실선 박스로 섞여 있지 않은가 | A |
| N-7 | 개념 전개 도면에서 한 장이 하나의 정보 변환만 다루고, 직전 장의 산출물 부호를 입력으로 승계하는가 | B |
| N-8 | 데이터에서 데이터로 직결된 화살표가 없는가(처리 주체 경유) | B |
| N-9 | 도면 텍스트가 청구항 확정 어휘로 통일되었는가(발명자료 모듈명 잔존 금지) | A |
| N-10 | 동일 개념에 세트 전체를 관통하는 동일 부호가 부여되었는가. 위상 분리 채번이 본문 서술과 일치하는가 | A |
| N-11 | 단계 부호 체계(순차형 또는 도면 연동형)가 세트 전체에서 하나로 통일되었는가 | B |
| N-12 | 표 형태의 수치 자료를 도면으로 승격하지 않았는가 | C |
| N-13 | (해외출원 대비 건) 흐름도가 광의 1층(독립항)과 구체 2층(종속항, 실시예)으로 나뉘어 있는가. 구현 예시가 복수이면 예시마다 별도 장인가. 1층만 있으면 뒷받침 흠결, 2층만 있으면 EPO, CNIPA에서 한정해석 위험 | B |

N-5와 N-9는 D섹션 OCR 추출 결과로 기계 대조가 가능하다. 청구항 단계 문언과 박스 문언을
정규화(「상기」 제거, 공백 정리) 후 유사도 비교하여 0.9 미만이면 보고한다.

세부 규범은 `kr-patent-spec-drafting/references/drawing-set-design.md`.

## 작업 순서

### Step 1. 자료 확인 + 프로파일 판정

명세서 docx/텍스트, 도면 파일, 청구항 원문 입력 확인. 누락 자료 사용자 요청.

**이어서 기술분야 프로파일을 판정한다(L섹션 기준).** G 계열이면 A~K를 그대로 적용하고, H 계열(기계, 전기전자, 화학)이면 L-1 제외 규칙을 반영한 뒤 L-2 항목을 추가한다. 판정 결과를 보고서 머리에 1줄로 명시한다.

### Step 2. 자동 점검 (A섹션)

```bash
extract-text spec.docx > spec.txt
grep -n "종래" spec.txt
grep -n "구성되는" spec.txt
grep -n "상기" spec.txt | wc -l
grep -n "/" spec.txt | head
grep -n "변환" spec.txt
grep -n "한정되지 않을 수 있다" spec.txt
grep -nE "지식그래프|지식 그래프" spec.txt   # 띄어쓰기 변형
grep -nE "청구항 [0-9]+|단계 S[0-9]+" spec.txt   # 청구항·단계 직접 언급
```

### Step 3. 청구항 매핑 (B섹션)

**Step 3-0. 청구항 → S4 전수 체크리스트 작성 (★★★ 필수)** — B-0 표 형식으로 청구항 1번부터 마지막 번호까지 빠짐없이 한 행씩 작성. 각 행에 S4 등장 위치·도입 정형·상태 기재. 빈칸·❌ 발생 시 즉시 Priority A 결함으로 보고. 특히 (a) 중간 번호 종속항 통째 누락, (b) 시스템·장치 등 다른 카테고리 독립항 도입 정형 누락, (c) 프로그램·기록매체 청구항 도입 정형 누락 3가지 패턴 집중 검사.

**Step 3-1. 종속항 한정 키워드의 독립항 단락 누출** 별도 검사.

**Step 3-2. 청구항 모든 표현이 본문에 한 번 이상 등장** 확인 (지원요건).

**Step 3-3. S13 청구항 N개 핵심 어휘** → 본문 grep.

### Step 4. 부호 매핑 (C섹션)

- 본문 정규식 `\((\d+)\)`, `\(S\d+\)`로 부호 추출
- **도면 OCR 결과**(Step 5에서 산출됨)와 양방향 비교
- **부재번호 흐름 정합성** — 처리 결과물 부호 분리
- **동일 부재번호가 두 객체 지칭하지 않음** — 같은 부호 다른 명사 검출
- 【부호의 설명】 섹션 부재는 결함이 아님

### Step 5. 도면 OCR + 정합성 점검 (D섹션) — ★ default 의무 실행

도면 파일이 가용한 경우(외부 도면 폴더 또는 명세서 docx 임베드) **무조건 실행**. "가능 시" 옵션이 아닌 default 단계. 도면 파일이 전혀 없으면 사용자에게 즉시 요청.

#### Step 5-1. 도면 추출

- 명세서 docx에 임베드된 도면을 **정본**으로 검토 (python-docx로 `word/media/imageN.tiff` 추출)
- 외부 도면 폴더가 있으면 docx 임베드와 버전 일치 검증 (불일치 시 결함 후보)
- TIFF → PNG 변환 (PIL 사용) 후 LLM 시각 분석 또는 OCR 도구 적용

#### Step 5-2. 4분류 OCR 추출 (D섹션 D-1 표 참조)

각 도면에 대해 다음 4가지 항목을 별도 표로 산출:
- (a) 부호 있는 박스 — 부호 번호 + 박스 라벨
- (b) 부호 없는 텍스트 라벨 — 라벨 명사 리스트
- (c) 강조 메타 표기 — 중괄호 묶음·화살표·통계 박스 안 수치
- (d) 도면 안 영문 약어

#### Step 5-3. 본문 정합 점검

- (a) → 부호 양방향 매핑 (C섹션 연동)
- (b) → 부호 없는 객체의 본문 자유 서술 등장 여부 (0건이면 결함)
- (c) → 강조 표기의 본문 정량·정성 등장 여부 (예: "병렬 처리 구간 20일 (44%)" → 본문 grep)
- (d) → 영문 약어의 첫 등장 시 한글 풀이 + 약어 병기 확인 (A섹션 영문 단독 등장 검출과 연동)

#### Step 5-4. 청구항 한정 수치 도면 노출 점검 (위험)

OCR 추출 수치 → 청구항 한정 수치 매칭. 도면에 한정 수치가 그대로 노출되면 권리범위 협소화 + 보정 부담 Priority B 결함.

### Step 6. 효과/스토리/형식 (E, F, G섹션)

본문 정독. 효과 갯수·파생 효과·종결 다양화 / 브릿지 정형 / 영문 명칭 / 요약 의역.

### Step 7. 본문 문장 품질 (H섹션 - Prompt 2)

자동 + 정독 병행:
- 자동: 문장 4줄 초과, 한 절 "이/가" 중복, "상기" 빈도, 슬래시, 수식 정의 단락 존재, 띄어쓰기 변형
- 정독: 의미 비약, 전문용어 풀이 정형, 기술적 의의 기재 누락, 정의 도입 순서, "변환" 부정확 사용

### Step 8. S1~S14 정형 형식 (I섹션 - Prompt 1)

`kr-patent-spec-drafting` 단계별 고정 형식 항목별 매칭. **출원 전 필수 점검 8개**:
1. **★★★ S4 청구항 1번~N번 전수 1:1 매핑 (B-0 체크리스트 통과)** — 단 한 항이라도 빠지면 즉시 게이트 차단
2. S2 마지막 문단 정형
3. S3 새 데이터 처리 파이프라인 1개 문단 별도 기재
4. S4 첫 문단 2문장 고정 형식 + 청구항 1항 원문 단어 일치
5. S4 프로그램 청구항 도입 정형 (해당 시)
6. S13 도면 단락 첫 문장 형식
7. S13 "청구항 X" / "단계 SXXX" 직접 언급 0건
8. S14 1파트(효과 상위 2개 원문 인용) + 2파트(정형 문구)

### Step 8.5. Stage 역추적 점검 (J섹션)

A~I 점검 결과를 종합하여 Stage 2(부호)·Stage 3(본문)·Stage 4(권리범위) 각각의 원칙 준수 여부를 J 출력 형식 표로 정리. 미흡·누락 발견 시 해당 Stage 재호출 권장 스킬을 명시.

- **Stage 2 미흡** → symbol-design 또는 drawing-mapping 재호출 권고
- **Stage 3 미흡** → spec-drafting 해당 단계(S1~S14) 재호출 권고
- **Stage 4 미흡** → definition-insertion 또는 embodiment-addition 재호출 권고
- **★★★ Stage 4 청구범위 read-only 위반** → 즉시 Priority A 게이트 차단. embodiment-addition 재실행으로 청구범위 섹션 원상복구 (신규사항 추가 금지 원칙)

J 결과 표는 보고서 **상단**에 점수표보다 먼저 노출.

### Step 8.7. 중복 기재 점검 (K섹션)

본문을 문장 단위로 분할·정규화한 뒤 K-1~K-5 5개 항목(동일·유사 문장 / 용어 이중 정의 / 동의어 방어망 중복 선점 / 변형 실시예 중복 / 효과 중복)을 자동 검출. **의도된 정형 반복(S5↔S14 원문 인용, S4↔청구범위 풀어쓰기, 브릿지·한정 부정·종속항 도입 정형)은 화이트리스트로 제외**하여 오탐 방지. 검출 쌍은 (위치 A, 위치 B, 유사도, 권고 조치) 표로 보고.

### Step 8.8. 프로파일 분기 점검 (L섹션) — H 계열만

H 프로파일로 판정된 경우에만 실행. L-1 제외 규칙에 해당하는 기존 지적을 보고서에서 삭제한 뒤, L-2-1~L-2-12를 점검한다. L-2-12(물리적 정합)는 스크립트로 잡히지 않으므로 도면 이미지와 본문을 직접 대조한다.

### Step 8.9. 해외출원 지지문언 + 도면 커버리지 점검 (M, N섹션)

프로그램 청구항이 있는 건이면 M-1~M-9를 실행한다(`grep -n "비일시적"` 결과가 3개소
미만이면 즉시 Priority A). 이어서 D섹션 OCR 산출물을 재사용하여 N-1~N-12를 점검하고,
도면별 대응 청구항 매핑표와 **도면 뒷받침이 없는 청구항 목록**을 보고서에 첨부한다.

## 핵심 점검 노하우 (실무 자주 놓치는 사항)

### 0. 청구항 → S4 전수 1:1 매핑 (★★★★ 최우선 게이트)

명세서 정합성 점검에서 **가장 먼저, 가장 엄격히** 확인해야 할 항목. S4(해결수단)는 청구항을 자연어로 풀어쓴 단락이므로, 청구항 번호 1번부터 마지막 번호까지 **단 하나도 빠짐없이** 각각 대응되는 도입 정형 단락이 S4에 존재해야 한다.

**점검 방식**:
- 청구항 번호 1, 2, 3, ..., N을 세로축으로 한 체크리스트 작성
- 각 청구항의 한정 키워드가 S4 어느 문단에 어떤 도입 정형으로 들어왔는지 1:1 기록
- 빈칸·중복·❌ 발견 즉시 게이트 차단 (다른 점검 진행 전에 보완 요청)

**빈발 누락 패턴 (실무)**:
1. **중간 번호 종속항 통째 누락** — 청구항 7만 빠진 채 8로 점프
2. **시스템·장치 청구항 도입 정형 누락** — "한편 본 발명에 따른 [명칭]은, ..." 문단 부재
3. **프로그램·기록매체 청구항 도입 정형 누락** (가장 흔함) — "또한 본 발명에 따른 [명칭]은, 전자기기에서 하나 이상의 프로세서에 의하여 실행되며, …" 문단 부재
4. **종속항의 부분 인용** — 한 종속항이 두 한정사항을 가질 때 한쪽만 풀어쓰기

**왜 최우선인가**: S4 누락은 단순한 형식 결함이 아니라 **지원요건(특허법 §42②) 흠결**로 직결. 출원 후 보정으로도 신규사항 추가 금지에 막혀 회복 불가능한 경우가 있음. 다른 어떤 정합성 결함보다 권리 자체의 존립을 위협.

### 1. 청구항 수치 도면 노출 (★★ 위험)
도면 박스 라벨에 한정 수치 그대로 노출 시 권리범위 협소화 + 보정 부담. **대안**: `V_LOW ≤ V ≤ V_HIGH ?` 일반화.

### 2. 동일 객체에 두 부호 사용
"TIA"·"121" 혼용 → 한 객체 = 한 부호 + 명칭. 올바름: "트랜스임피던스 증폭기(이하 'TIA', 121)는 ~. TIA(121)는 ~할 수 있다."

### 3. 청구항 종속 관계와 실시예 종속 관계 불일치
청구항 3이 1을 종속하는데 실시예에서 3을 2와 묶어 설명하면 종속 해석 혼란.

### 4. 도면에만 있는 부호
본문에서 한 번도 언급되지 않은 부호가 도면에 보이면 형식 결함.

### 5. 【부호의 설명】 섹션 부재는 결함이 아니다 — default
부재 자체는 결함 아님. 한국 변리사 실무 관행상 의도적 생략이 더 유리.

### 6. S4 첫 문단 2문장 고정 형식 위반 (★★★ 필수)
가장 자주 발견. 둘째 문장 청구항 1항 원문이 단어 한 개라도 바뀌면 권리범위 해석 모호.

### 7. S4 프로그램 청구항 도입 정형 누락 (★★ 필수)
프로그램·기록매체 청구항 있는데 도입 정형이 없으면 실시가능요건 흠결.

### 8. S13 "청구항 X" / "단계 SXXX" 직접 언급 (★★ 중요)
청구항-본문 결합이 강해져 해석 유연성 손상.

### 9. S13 내부 작성 로직 노출 (★★★ 필수)
"[메인 도면]", "(서브도면 분류 메모)" 등 작성 메모가 본문에 잔존 시 형식 결함 + 외부 검토자 혼란.

### 10. 부재번호 흐름 정합성 (★★ 중요)
"후보 문서 집합(310)" 직접 출력과 "후보 문서(310)" 후속 처리 결과에 같은 부호 사용 금지. 처리 결과는 새 부호로 분리.

### 11. 동일 부재번호 두 객체 지칭 (★★★ 필수)
한 부호가 다른 객체를 가리키면 해석 모호. 한 부호 = 한 객체.

### 12. '상기' 본문 남용 (★ 부수)
청구범위 외 본문에서 '상기' 빈번 사용 시 실무 관행 어긋남. 부호로 구별. 도면부호 없는 추상 개념만 예외.

### 13. 의미 비약 — 한 마디 처리 (★★ 중요)
"A 평가 → B 갱신" 압축 금지. 평가 → 판정 → 반영 단계화.

### 14. 전문용어 풀이 정형 누락 (★★ 중요)
"환각(hallucination)" 만 등장하고 풀이 없으면 본 발명 맥락 의미 모호. 정형: "환각(hallucination) → … 현상(이하 '환각'이라 함)".

### 15. 수식 정의 정형 누락 (★★ 중요)
