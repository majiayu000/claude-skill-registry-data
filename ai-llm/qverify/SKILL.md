# Qverify — 검증

이 단계의 목적은 **"됐다"고 말하기 전에 plan.md 목표 대비 증거로 확인하고, 그 증거를 남기는 것**이다.

확신은 증거가 아니다. "될 것이다", "아마", "보기엔 맞다"는 검증이 아니다.
이번에 직접 돌려 보지 않은 명령은 통과했다고 말할 수 없다.

## 누가 검증하나 — 독립 검증자 서브에이전트

QE 작업 폴더가 있는 일이면 **항상 새 검증자 서브에이전트**([verifier-prompt.md](verifier-prompt.md))가
검증한다. 계획 충족 판정과 전체 테스트는 `qe-framework:qa`가, 브랜치 전체 코드 리뷰는
`qe-framework:redteam`이 따로 맡는다(아래 "최종 리뷰"). 판정하는 쪽과 깨뜨리려는 쪽을 나눠야
서로의 맹점을 덮지 않는다. 작은 일도 같다(프롬프트와 보고가 짧아질 뿐이다). 폴더 없이 바로 한
아주 작은 일은 아래 확인 순서만 지킨다. 이유: AI가 "했다"고 보고했는데 실제로는
안 된 일이 반복됐고, 자기가 쓴 코드를 자기가 채점하면 같은 맹점을 공유한다. 깨끗한 컨텍스트의
검증자는 내 설명이 아니라 코드와 실행 결과만 본다. 판단이 필요한 일이니 상위 모델로 덮어쓴다
(생략하면 에이전트의 기본 모델이 쓰인다). 전문 에이전트가 보이지 않으면 일반 서브에이전트로 띄운다.

- **먼저 작업을 커밋한다.** 검수 기록과 done은 커밋 sha로만 남는다. 검증자가 본 트리와 기록된 sha가
  같아야 기록이 뜻을 가진다. 프로젝트가 git이 아니거나 커밋이 없으면 done을 기록할 수 없다고 사용자에게
  말하고 `git init`과 커밋을 제안한다. 그 전에는 state를 `verifying`에 두고 검증자를 되풀이하지 않는다.
- **시작할 때** status.json의 `state`를 `verifying`으로 바꾼다. status.json은 언제나 먼저 읽고,
  hook이 적은 `sessions`·`worktrees`·`project`는 그대로 둔 채 Write로 전체를 쓴다.
- **브랜치가 여럿이면** 먼저 하나로 합치고 그 브랜치를 검증한다. 각각 통과해도 합친 결과는
  아무도 안 본 셈이다.
- 검증자 프롬프트의 `[작업 폴더 이름]`, `[브랜치]`, `[HEAD 커밋 sha]`를 정확히 채운다. qa 검증자는 최종 보고
  **마지막 줄**에 `QE-VERDICT: <작업 폴더 이름> | <충족|일부 미충족|미충족> | <브랜치> | <커밋 sha>`를
  쓰고, SubagentStop hook이 그 줄을 `verdicts/`에 검수 기록으로 남긴다. 완료의 근거는 내 말이 아니라
  이 기록이다. 줄이 없거나 형식이 틀리면 기록되지 않으니, 보고에 그 줄이 있는지 확인한다.
  `verdicts/`는 hook만 쓴다. 직접 만들면 관문이 거부한다.
- **검증자는 포그라운드로 돌리고 결과를 기다린다.** 백그라운드로 띄우고 응답을 끝내면 기록이 생기기 전에
  Stop hook이 검수를 요청하고, 검증자를 하나 더 띄우게 된다.

검증자가 "충족"이라고 보고해도 그대로 믿지 않는다. 핵심 근거 하나 이상은 내가 직접 확인한다.
verify.md 첫 섹션에 검증자와 대상 브랜치·커밋을 한 줄 쓴다.

## 확인 순서

모든 주장 앞에서:

1. **무엇이 이 주장을 증명하나?** 그 명령이나 방법을 정한다.
2. **돌린다.** 새로, 전체를. 예전 실행 결과는 증거가 아니다.
3. **읽는다.** 출력 전체, 종료 코드, 실패 수.
4. **출력이 주장을 뒷받침하나?** 아니면 실제 상태를 증거와 함께 말한다.
5. **그다음에야** 주장한다.

| 주장 | 필요한 것 | 충분하지 않은 것 |
|---|---|---|
| 테스트 통과 | 테스트 명령 출력: 실패 0 | 이전 실행, "통과할 것" |
| 빌드 성공 | 빌드 명령: 종료 코드 0 | 린터 통과 |
| 버그 수정 | 원래 증상을 재현한 테스트가 통과 | 코드를 바꿨으니 고쳐졌을 것 |
| 요구 충족 | plan.md 목표별 확인 목록 | 테스트가 통과했다 |
| 서브에이전트 완료 | diff와 확인 결과를 직접 봄 | 에이전트의 "성공" 보고 |

## plan.md 목표 대비 확인

테스트 통과는 요구 충족이 아니다.

1. plan.md의 목표를 하나씩 목록으로 만든다. "기술적으로 돌아가도 실패인 것"도 포함한다.
2. 각 목표를 무엇으로 확인했는지, 결과가 어땠는지 적는다. 충족 / 미충족 / 확인 못 함.
3. implement-plan.md의 "놓치기 쉬운 경우"가 실제로 덮였는지 본다.
4. 프로젝트 전체 테스트를 돌린다. 내가 만들지 않은 실패도 이름을 적는다.

## 최종 리뷰

목표 충족은 좋은 코드와 같지 않다. 검증 주체와 상관없이 **브랜치 전체**를 코드 리뷰한다.
단계마다 리뷰했어도 단계 사이의 이음새(맞물림, 중복, 일관성)는 아무도 안 봤을 수 있다.
리뷰 기준은 `Qreview`의 [reviewer-prompt.md](../Qreview/reviewer-prompt.md) 한 곳에 있다.
리뷰는 `qe-framework:redteam`에 [verifier-prompt.md](verifier-prompt.md)의 코드 리뷰 항목(4번)을
맡긴다. 작은 변경도 같다(내가 쓴 diff를 내가 읽으면 같은 맹점을 공유한다). 리뷰 기준 자리에 그 파일의
**절대 경로**(이 스킬 폴더 옆 `Qreview` 폴더 안)를 채우거나, 그 파일의 "확인할 것"과 등급 기준을
그대로 붙여 넣는다. 상대 경로는 서브에이전트가 사용자 프로젝트에서 찾지 못한다. 리뷰어에게는
QE-VERDICT 줄을 넘기지 않는다(판정은 qa 검증자의 몫이다). 전문 에이전트가 보이지 않으면 일반
서브에이전트에 같은 항목을 맡긴다. qa 검증과 함께 포그라운드로 돌려도 된다.

지적은 `Qfeedback`으로 하나씩 맞는지 확인하고, **사용자가 겪는 결과**로 등급을 다시
매긴다(치명 / 중요 / 사소). 리뷰어가 "plan.md가 말하지 않아서" 낮게 매긴 것은 그 결과를 보고 다시 판단한다. 리뷰어가 판단을 보류한
항목은 내가 판단해 `판단:` 형식으로 남긴다.

**여기서는 고치지 않는다.** 지적을 등급과 함께 사용자에게 보여 준다. 사용자가 동의한
치명·중요 지적은 implement-plan.md 끝에 `- [ ] 최종 리뷰 수정: <지적>` 단계로 추가한다. 그래야 세션이
끊겨도 남은 일로 다시 안내되고, `Qexecute`가 첫 미체크 단계부터 이어받는다. 이 수정은
**메인이 한 번에** 한다(실행 방식과 상관없이). 각각 재현 테스트가 먼저 실패하는 것을 본 뒤
고치고, 전체 테스트를 다시 돌린다. 중복·일관성처럼 재현 테스트를 만들 수 없는 지적은 그
이유를 verify.md에 쓴다. 고친 뒤에는 새 커밋을 새 검증자로 다시 검증하고 verify.md를 갱신한다.
사용자가 고치지 않기로 한 지적과 사소한 것은 "남은 일"에 적는다.

치명·중요 지적이 미처리로 남아 있는 동안에는 "완료"라고 말하지 않는다. 사용자가 치명·중요 지적을
고치지 않기로 했으면 done으로 쓰지 않는다. 목표를 닫으려면 사용자에게 확인받고 `state`를 `stopped`로 쓴다.

## 계약 갱신

최종 리뷰와 그에 따른 수정이 끝나면 `docs/contracts/` 중 이번 변경이 건드린 흐름의 계약을
`qe-framework:contractor`에게 맡겨 현재 코드와 맞추고, verify.md에 한 줄 남긴다. 전문 에이전트가
보이지 않으면 일반 서브에이전트에 맡긴다. 두 경우 모두 메인 세션이
[계약 양식](../Qunderstand/contract-template.md)을 읽고 양식 본문을 호출 프롬프트에 넣는다.
현재 코드에서 확인한 흐름만 기록하고 `docs/contracts/` 안에서만 쓰도록 요청한다.

## 실행 중 내린 판단 모으기

implement-plan.md의 `판단:` 줄을 빠짐없이 verify.md "실행 중 내린 판단"과 최종 보고에 옮긴다.
"틀리면"까지 그대로. 내가 사용자 대신 내린 결정이 사용자에게 닿는 곳은 여기뿐이다.

## verify.md 쓰기

작업 폴더에 `verify.md`를 [verify-template.md](verify-template.md)로 쓴다. 읽는 사람은
"이게 정말 검증됐나?"를 묻는 미래의 사용자와, "무엇이 남았나?"를 묻는 다음 세션의 AI다.

- 실패와 미확인은 **그대로** 적는다. 좋게 포장한 검증 문서는 없는 것보다 나쁘다.
- 명령은 실제로 돌린 것을, 출력은 통과·실패를 보여 주는 핵심 줄을 적는다.
- 작은 일이면 몇 줄이면 된다.
- 머리의 `결과:` 줄에는 `충족`, `일부 미충족`, `미충족` 중 **하나만** 쓴다. 고친 뒤 다시 검증하면
  이 줄도 갱신한다.

## 보고

사용자에게 짧게 보고한다: 결과(충족 / 일부 미충족 / 미충족), 핵심 근거, 최종 리뷰 지적,
실행 중 내린 판단, 확인 못 한 것, verify.md 경로. 사용자가 HTML·아티팩트로 달라고 하면 `Qreport`의 틀을 쓴다.

- **미충족이 있으면** status.json `state`를 `active`로 되돌리고, `Qexecute`로 돌아가 고칠지, 범위를
  줄일지 사용자와 정한다. 원인을 모르는 미충족이면 고치기 전에 `Qdebugging`으로 원인부터 찾는다.
  고친 뒤에는 다시 검증하고 verify.md를 갱신한다.
- **모두 충족이고 치명·중요 지적이 남지 않았으면** 그때 "완료"라고 말하고 status.json을 완료로 쓴다:
  `state: "done"`, `done: {"commit": "<검증한 sha>", "branch": "<브랜치>", "verdict": "verdicts/<기록 파일>.json"}`.
  Write로 파일 전체를 쓴다(관문은 Edit 결과를 확실히 알 수 없을 때 done이 들어간 Edit을 막는다. Write는 결과가 분명하다). 그 커밋에 대한
  충족 검수 기록이 없으면 PreToolUse hook이 거부한다. 거부되면 우회하지 말고 검증자를 다시 돌린다.
  다음은 `Qfinish`로 마무리한다(merge·PR·유지는 사용자가 고르고, 문서를 프로젝트로 내보낸다).
- **사용자가 이 목표를 그만두기로 하면** `state`를 `stopped`로 쓴다. Stop hook은 stopped·done인 목표를
  더 묻지 않는다.

## 경고 신호

- "될 거야", "아마", "보기엔" 같은 말을 쓰려 할 때
- 확인 전에 만족을 표현하려 할 때 ("좋아요!", "완벽합니다!")
- 에이전트의 성공 보고를 그대로 옮기려 할 때
- "이번 한 번만", "부분 확인이면 충분해"라고 생각할 때

이 생각이 들면 멈추고 위 확인 순서로 돌아간다.
