# code-craft — 코드 쓰는 법

메인 세션이든 QE 전문 에이전트든, 코드를 쓰거나 고칠 때 따른다. 이 규칙은 사용자의
코드 취향이다. 사용자는 **깔끔한 코드와 상세한 문서 주석**을 좋아하고, 문서 주석을
**AI 사이의 계약**으로 여긴다. 다음에 이 코드를 읽는 사람과 에이전트는 주석을 믿고 쓴다.

## 먼저 프로젝트를 읽는다

쓰기 전에 빌드 파일, 포매터·린터 설정, 주변 코드를 읽고 그 관례(프레임워크, 이름 짓기,
오류 처리, 테스트 위치, 문서 주석 스타일)에 맞춘다. 내 취향보다 프로젝트의 관례가 먼저다.
관례끼리 충돌하면 가까운 코드의 관례를 따르고 보고에 한 줄 남긴다.

설계 선택이 필요하면 이 스킬의 디렉터리 기준으로
[언어별 디자인 패턴 목차](../../references/design-patterns/README.md)를 연다.
해당 언어에서 해결하려는 문제에 맞는 문서를 찾아 구현 비용과 주의점을 확인한다.

## 문서 주석은 계약이다

외부에서 쓰는 단위(공개 함수·메서드·클래스·모듈·API)에는 반드시 단다. 내부 단위에는
이름과 시그니처만으로 계약이 자명하지 않을 때 단다. 계약에 담는 것:

- 무엇을 하는가 (어떻게가 아니라)
- 매개변수: 의미, 허용 범위, null·빈 값 처리
- 반환값: 의미, 없을 수 있는 경우
- 던지는 예외·돌려주는 오류와 그 조건
- 전제 조건과 부수 효과 (I/O, 상태 변경, 캐시, 외부 호출)
- 필요하면 스레드 안전성, 성능 특성, 소유권·수명

형식은 그 언어의 표준을 쓴다: Java JavaDoc, Kotlin KDoc, Go godoc, Dart `///` dartdoc,
JavaScript JSDoc, TypeScript TSDoc/JSDoc, C# XML 문서 주석, C++ Doxygen, Python docstring.
도구가 읽을 수 있는 형식이어야 IDE와 문서 생성기, 다음 에이전트가 같은 계약을 본다.

**코드를 바꾸면 계약 주석도 같이 고친다.** 주석과 다르게 동작하는 코드는 버그다.
계약을 바꾸는 변경이면 호출하는 쪽도 확인한다. 계약이 바뀐 것을 보고에 적는다.

## 사설은 쓰지 않는다

주석은 코드가 말하지 못하는 것만 담는다. 다음은 쓰지 않는다:

- 변경 이력이나 작업 과정: `// 버그 수정함`, `// 이제 X를 처리한다`, `// 기존 방식에서 바꿈`.
  이력은 git이 맡는다.
- AI의 생각 서술: `// 여기서는 ~하는 게 좋을 것 같다`, `// 이렇게 하면 될 것이다`.
- 코드를 그대로 다시 읽어 주는 주석: `// i를 1 증가시킨다`.
- 작성자·도구 표시: `// Claude가 추가`, `// generated by AI`.
- 사용자에게 하는 말, 칭찬, 감탄, 이모지.

남기는 것: 코드만 봐서는 알 수 없는 **왜**를 짧게. 외부 제약, 일부러 고른 비직관적
방식, 알려진 함정, 관련 이슈 번호. 그런 "왜" 하나가 사설 열 줄보다 낫다.

## 깔끔하게

- 이름이 설명을 대신하게 짓는다. 주석으로 이름을 보충하고 있다면 이름을 고친다.
- 함수는 한 가지 일을 한다. 요청 범위 밖의 코드는 고치지 않는다(고칠 게 보이면 보고한다).
- 죽은 코드, 주석 처리한 코드, 디버그 출력은 남기지 않는다.
- 끝나면 자기 diff를 다시 읽는다: 계약 주석이 빠진 공개 단위, 사설 주석, 범위 밖 변경이
  있는가?
