相談者として規則ファイル（CLAUDE.md群・基準のガイド・自作Skill の trigger 記述）の棚卸しを行う。`guarantee-audit` Skill（指摘提示→user 裁可→反映の進行）の型を、対象を「メモリ」から「規則」に変えて踏襲する。**プロダクトコード（各リポの src/ 等）は書かない**。書いてよいのは対象節に挙げた規則ファイルと、アンカーを持つ `.claude/RULES.md` のみ。

## 背景

CLAUDE.md・Skill・memory はいずれも「user が書いた規則を AI が読む」構造であり、規則同士の矛盾を検出する仕組みを内蔵していない。規則ファイルは増え続けており、矛盾や陳腐化した規則はいずれ AI の挙動を不安定にする。本 Skill はその棚卸しを場当たりではなく**定期的に**（`schedule` / `loop` からの起動を想定）繰り返すための仕組みであり、毎回全ファイルを読み直すコストを避けるために、前回の棚卸し地点からの差分だけを読む。

## 対象

- `~/.claude/CLAUDE.md`（グローバル）
- 各リポの `CLAUDE.md`（呼び出し元リポ、または user が指定したリポ）
- `docs/*.md` と `.claude/skills/*/reference/*.md`（基準の実体）
- `.claude/skills/*/SKILL.md` のうち、frontmatter `description` が**日本語で書かれているもの**
- `.claude/settings.json` と `.claude/hooks/`（`*.sh` と `README.md`。層1）

層1 を含めるのは、そこが「ガイドが規定していて、実体が別ファイルにある」唯一の層だからである。`repo-standardize` スキルは deny の共通項目・attribution を、`hooks/README.md` はフックの書き方を規定しているが、規定を満たしているかは settings.json と `hooks/` を読まない限り分からない。文書同士の突き合わせだけでは、規定と実体の乖離は永久に検出されない。

**層1 だけは実体が正で、ガイドが従である。** deny を1本増やす・減らすといった判断は運用の中で下されており、それを追認していないガイドの側が古い。他の対象と違い、食い違ったら実体に合わせてガイドを直す。

最後の条件により、Cloudflare 等ベンダー技術リファレンス系Skill（`cloudflare` / `wrangler` / `agents-sdk` / `durable-objects` / `sandbox-sdk` / `web-perf` / `workers-best-practices` 等、description が英語）と Anthropic 標準搭載Skill（`anthropic-skills:*` prefix、`docx` / `pdf` / `pptx` / `xlsx` / `schedule` / `morning` / `setup-cowork` / `skill-creator` / `consolidate-memory` 等）を除外する。これらは user 自身が書いた「規則」ではなく外部ドキュメントの写しか Claude Code 標準機能であり、CLAUDE.md との矛盾を検出する対象にする意味がない。**この判定は実行時に frontmatter を機械的に見て行い、固定の除外リストは保守しない**（Skill の増減に自動で追従させるため）。

**基準の実体は、それを使う skill が持つ。**1本の skill しか読まない基準は `SKILL.md` 本体に、複数の skill が読むものや長いものはその skill の `reference/` に置く。skill に寄せきれないもの（`hooks/README.md` のような仕組みの説明や、`docs/` の個別の覚え書き）だけを MD として残す。棚卸しで基準を独立した MD へ切り出す提案はしない。

## 起点 (`.claude/RULES.md`)

中身はアンカー1行だけである。

`最終棚卸し: {commit} — {日付} — モデル {実行時のモデル ID}`

ファイルごとの要約・相互参照・ハッシュは持たない。それはファイルを読めば分かり、持てば対象が増えるたびに保守が要る。何が変わったかはアンカーからの差分で取る。

モデル ID を書くのは、規則の陳腐化がファイルの変更だけでなく**モデルの世代交代でも起きる**ため。古いモデルの弱点を補うために書いた規則は、その弱点が消えた時点で制約にしかならないが、規則ファイル自体は1文字も変わらないので差分には現れない。記録されたモデル ID が実行時のモデルとメジャー世代で違うときは、差分に出ていないファイルも含め、**モデル特化の記述だけを対象に全件を1周見る**（フェーズ1の観点4）。

アンカーは**棚卸し自身が記録する**。他の push やマージを進捗の目印に使うと、棚卸しをしていない回でアンカーが進み、その手前の規則変更を読まずに素通りする。

## 再び指摘しない判断

user が裁可した方針。次回以降の実行は、これに当たる乖離を指摘として再提起しない。

- **重複の解消** — 同一の規則が複数ファイルにあるとき、片方を消して正本1本にする（参照で繋いで両方残さない）。毎回自動で読まれる CLAUDE.md 層を残し、読まれる契機を持つガイド・skill 側を削るのを既定とする
- **自作 skill の `disable-model-invocation`** — 一覧から消える skill は、別の skill・フック・シェル関数から名指しで引かれる前提の設計であり、不足ではない。判断軸は「自動発火が要るか」ではなく**呼び口を持つか**で、呼び口を持たないものは自動発火のまま残す
- **英語版（`README.en.md`・`*.en.md`）** — 日本語版の従属物であり、規則の実体ではない。棚卸しの対象にしない

新たに「差分のまま残す」と裁可された乖離は、ここに1行で足す。

## フェーズ0: 読む対象を絞る

規則ファイルを1つも読まずに、変わったファイルを機械的に取る。

```sh
git log {anchor}..HEAD --name-only --pretty=format: | sort -u
git status --porcelain          # 未コミット分を足す
```

ここから対象節に入るものだけを残す。RULES.md にアンカーが無いか、アンカーが信用できない（履歴が書き換わった等）ときは対象全件を読む。

## フェーズ1: 現状把握

1. フェーズ0で残したファイルと、それを参照している・それが参照しているファイルだけを読む。**変わったファイルは全文ではなく差分を読む**（`git diff {anchor}..HEAD -- {file}`。未コミット分は `git diff` を重ねる）。差分だけでは前後の文脈が判断できないときに限り、その節を読み足す

   **読む対象が5ファイルを超えるとき、この読み込みは読み取り専用の探索 subagent に投げる。**（`Explore` 等。初回実行と、観点4のモデル世代の掃引は必ず該当する。）本体の文面すべてが親のコンテキストに載ると、裁可の往復に使える残量がその分だけ削れる。subagent には対象ファイルの一覧と観点1〜5を渡し、返させるのは乖離候補だけにする。1件につき「ファイル:該当箇所 → 何と何が食い違うか → 根拠になる原文の引用」。要約や所感を返させない。

   親は返ってきた候補の**引用箇所だけを読み直して裏を取る**。subagent の報告をそのまま指摘として user に出さない。読んでいない原文を根拠に裁可を求めることになるため。裏が取れなかった候補は落とす。

   subagent は読むだけで、編集・裁可・アンカーの更新をしない。それらは親の責務として残す。
2. 精読したファイルについて、次の5観点で乖離を洗い出す
   1. 基準のガイド内部の相互矛盾（例: `guarantee-audit/SKILL.md` と `new-issue/SKILL.md` で基準がずれる）
   2. CLAUDE.md（グローバル/リポ別）と基準のガイドの乖離（CLAUDE.md にしか書かれていない規則がガイドの更新で置き去りになっていないか）
   3. Skill の trigger 記述（`description:`）と本文の乖離（規則が変わったのに Skill の説明が古いまま残っていないか）
   4. モデル世代による陳腐化（アンカーのモデル ID がメジャー世代で変わったときだけ見る）。古いモデルの弱点を補う目的で書かれた記述が、現行モデルでは能力を削ぐ制約になっていないか。徴候は「モデル名やモデル系列で分岐している」「一度に触ってよい範囲を狭めている」「出力の長さ・粒度を一律に縛っている」。**該当しても自動では消さない。** 弱点が本当に消えたのかは実地でしか分からないので、フェーズ2で「まだ必要か」を問う形の指摘として出す
   5. 層1（`settings.json` / `hooks/*.sh`）とガイドの乖離。ガイドが規定する deny の共通項目・フック一覧・attribution が実体に無い、または実体にあるものがガイドに載っていない。**ここは実体が正**なので、提案の向きは常に「ガイドを実体に合わせる」

**5観点の洗い出しが完了するまで、見つけた乖離を1件ずつ user へ提示・確認しない。**フェーズ1を終えてからフェーズ2でまとめて出す。アンカーの更新は、フェーズ2の裁可・反映がすべて終わったあとに行う。

## フェーズ2: 統合

1. 乖離ごとに、どちらが正（基準の実体）かを判定する。同じ規則が複数箇所に重複しているだけなら、正本を残し他方を「正本を参照する」形に薄くする方向で提案を組み立てる（内容そのものを複製しない）
2. 指摘一覧をチャットに提示する（ファイルに書き出さない）。各指摘は「対象ファイル:該当箇所 → 矛盾/陳腐化の内容 → 提案」の形で1件ずつ書く
3. 指摘ごとに user の明示的な裁可（YES/NO/修正）を得てから該当ファイルを編集する。**内容そのものへの同意を毎回得る**（複数の指摘をまとめて一括承認する運用にしない）。user は対話で指示してもよいし、ファイルを直接編集してもよい
4. 裁可された指摘のみを反映する。編集は該当箇所の最小差分に留め、裁可を経ていない周辺の言い回しには手を入れない

## フェーズ3: 仕上げ

1. 反映後、編集した Skill の frontmatter `description` が本文と再び一致しているかを確認する
2. CLAUDE.md 側の `@import` や基準のガイドへの参照が、実体のファイル名・見出しと一致しているかを確認する
3. user が「差分のまま残す」と裁可した乖離を、「再び指摘しない判断」節へ1行で足す
4. `.claude/RULES.md` のアンカー行を、`git rev-parse --short HEAD`・当日の日付・**今回の実行に使ったモデル ID** で書き直す。モデル ID は実行中のセッションのものを書く（推測しない。分からなければ user に聞く）
5. ずれが残っていればフェーズ2に戻る。無ければ変更ファイル一覧・反映済み指摘の要約・**今回読まなかった対象の件数**を報告して終了する（網羅していないことを user から見えるようにする）

## 定期実行

週次程度の定期起動を想定する。設定そのものは本 Skill の責務外で、user が `schedule` Skill 経由で別途組む。

## 制約

- プロダクトコード（各リポの src/ 等）は書かない
- 裁可を経ていない指摘は反映しない。指摘が複数ある場合、要約や「まとめてOK」だけで済ませず、内容ごとの同意を確認する
- コミット・push はしない。変更はワーキングツリーに残し、user がレビューしてコミットする
- `.claude/RULES.md` にはアンカー行以外を書かない
