# 技术体系讲解与选型演示

目标是让特定受众建立正确心智模型，并能把机制、参数、场景和取舍连接起来。与系统 `Presentations` 组合使用：本技能决定研究、叙事、信息压缩和技术页面形式，`Presentations` 负责 PPTX 构建、模板跟随、渲染与基础验证。

## 先定深度和用途

用受众而非素材数量选择深度：

- `L0`：管理层，只需边界、业务影响和选择理由
- `L1`：非技术同事，概念、场景和风险
- `L2`：技术通识，组件关系、关键指标和典型机制
- `L3`：工程实践，架构、数据流、约束、性能与故障模式
- `L4`：专家评审，实验条件、实现细节、反例和不确定性

现场演讲优先理解速度；自阅材料可增加细节，但不得用小字号替代结构。详细的技术资料进入演讲备注或附录。

## 建立证据底座

先把用户材料和检索结果整理成 `evidence-ledger`。AI/计算机前沿优先使用 `ai-computing-research`，当前多来源事实用 `evidence-research`，已有材料摘要用 `research-summarizer`，定量数据可组合 Data Analytics Skills。

以下内容没有来源和 `as-of` 日期时，不得写成确定事实：芯片性能、价格、交付、供货、兼容矩阵、产品路线、benchmark、能耗和政策限制。比较时统一单位、精度、工作负载、硬件数量、软件版本和测试条件；不能统一就显式标注不可比。

## 选择叙事骨架

按任务只选一个主骨架，详见 [叙事与页面模式](references/story-and-pages.md)：

- 体系讲解：问题地图 → 概念 → 架构 → 机制 → 指标 → 场景 → 边界 → 总结
- 技术选型：决策问题 → 评价标准 → 候选 → 归一化证据 → 取舍 → 建议 → 迁移与风险
- 技术培训：心智模型 → 分步机制 → 示例 → 常见误区 → 练习/检查 → 回顾
- 故障与研究：现象 → 影响 → 定位链路 → 根因假设 → 证据 → 修复/研究路径 → 验证标准

每页在进入构建前都要有 `one_message`。标题描述页面真正表达的主题或经证据支持的结论，不使用空泛口号。

## 技术内容压缩

- 一页只承担一个认知任务。概念定义、架构全景、机制细节和产品比较通常应分开。
- 架构先给边界和层级，再逐步下钻；不要把全量拓扑、说明文字和参数表一次塞进同一页。
- 表格只保留服务于结论的列。完整规格移到附录，并在正文突出决定性行列。
- 每个缩写首次出现时解释；单位紧邻数值；对吞吐、延迟、功耗、带宽、容量和成本说明口径。
- 复杂机制优先“总览页 + 局部放大页”，而不是缩成一张无法投影阅读的图。
- 结论、事实、推断和建议使用不同措辞，避免把推测伪装成事实。

## 视觉与构建约束

遵循用户模板；样例仅供灵感时，不复制其 Logo、内部数据或高密度版式。无模板的 16:9 现场演示默认：标题不低于 28pt，正文不低于 17pt，脚注不低于 10pt；自阅模式正文原则上不低于 15pt。先删、拆页、移备注，再考虑缩字。

技术图必须保留清晰阅读路径和编辑性。表格、图表及用户要求可编辑的架构图使用原生对象；照片、纹理和复杂插画使用合适的图像素材。颜色之外再用标签、形状或线型编码状态。中文字体必须覆盖 CJK，避免全角标点孤行。

## 交付前检查

使用 `deck-review` 做内容与视觉验收。至少确认：

- 5 秒能识别每页主题，30 秒能复述其证据和边界
- 关键参数均有来源、单位、口径和截至日期
- 连续页面的密度有节奏，正文没有靠 7–12pt 小字维持
- 没有超宽表格、图文遮挡、变形图片或不可编辑的证据对象
- 演讲备注承载讲解细节、来源和可预期问答，而非复制页面正文


需要产品演示、双栏比较或时间线页面时，按需读取 [叙事与布局参考](references/demo-and-comparison-layout.md)，继续使用现有构建与验证流程。
