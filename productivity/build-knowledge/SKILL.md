# build-knowledge

Close every gap the search left the cheapest honest way: a knowledge page a person approves,
our proposed answer with its basis and context, a note for the prototype, or settled.

**Pipeline position: none.** A member play the Shared Drive Run runs inside a drive's rounds
(R5c), second of `/search-knowledge` → `/build-knowledge` → `/review-knowledge`; it opens and
lands nothing.

## Role

You are the orchestrator. You run the check as a script, and hand the judgment — researching
knowledge pages, drafting proposed answers — to the `knowledge-builder` agent through a JSON
contract over files on disk. You never decide, apply or promote a memory update, and you never
write the product model.

**Agent boundaries:**

| Agent | Domain | Skills it invokes | Phases |
|-------|--------|-------------------|--------|
| `knowledge-builder` | The knowledge a drive's round found missing | `draft-knowledge-page`, `propose-answers` | Build |

`knowledge-builder` is the single **domain agent**; it raises a knowledge page only through the
memory tool's `propose`. Everything else is a script.

## Workflow

### Phase: Build

**Step 1 — Build what the search left** · Owner: `knowledge-builder` · Depends on: pre-flight

    { "task":    "build: close every gap the search left",
      "inputs":  { "search": "<search>/search.json",
                   "sources": ["<the drive's Source evidence folders>"],
                   "issue": "<issue>",
                   "check_script": "<play-dir>/scripts/check_knowledge_build.py" },
      "outputs": { "build": "<working>/build.json",
                   "check_report": "<working>/build-check.json" },
      "task_id": "build-knowledge" }

For each search group found `partly` or `open`, the agent closes it one way: `should-show` → a
note for the prototype; research can answer it → `draft-knowledge-page` (a memory update raised
through `propose`); the context settles it → `settled`, with what settles it; only a person can
confirm it → `propose-answers` drafts our answer with its basis and context.
**SE-1 (F1/C1):** every `partly` or `open` search group is in exactly one build group, and no
`answered` one is.
**SE-2 (F2/C2):** every group closed by `update` names an update the memory tool lists as
waiting for the issue; no update was decided, applied or promoted in this run.
**SE-3 (F3/C3):** every group closed by `proposal` has its answer, basis and context; none is a
question.
**SE-4 (F4/C4):** every `should-show` search group is closed by `prototype-feedback`.
**SE-5 (F5/C5):** every group closed by `settled` says what settles it and what it rests on.

### Phase: Check

**Step 2 — Check the build** · Owner: play (script) · Depends on: Step 1

```bash
python3 scripts/check_knowledge_build.py --search <search>/search.json \
    --build <working>/build.json --issue <issue> \
    --memory-tool .garura/core/tools/memory/memory.py --out <working>/build-check.json
```

Exit 0 — clean. Otherwise send the report back to Step 1 (at most twice), then close HALTED.
**SE-6 (F6/C6):** `run.json` reads `in_drive: true`; every file this run wrote is under
`{stm_base}<issue>/`; `git status` shows no change under the product model.

### Phase: Scenario Validation

**Step 3 — Scenario evals** · Owner: play · Depends on: Step 2
- **SCE-1 (S1 — Kickoff drive, knowledge no screen shows):** a group about a standard or rule
  reads `closed_by: update`, and the memory tool lists that update as waiting.
- **SCE-2 (S2 — Kickoff drive, a gap only the person can confirm):** a group reads
  `closed_by: proposal` with answer, basis and context.
- **SCE-3 (S3 — Kickoff drive, a gap the context settles):** a group reads `closed_by: settled`
  with `why` and `basis`.

## Recovery

| For | Trigger | Direction | Handoff |
|-----|---------|-----------|---------|
| F1 | a gap in no build group or two, or an answered group rebuilt | rebuild from `search.json`'s partly and open groups; re-run the check | autonomous |
| F2 | a researched answer used before approval, a page raised outside the memory tool, or an update decided, applied or promoted | undo the use; raise the page through `propose`; leave it waiting for a person | human |
| F3 | a bare question, or a proposal without basis or context | draft the proposed answer from the source, memory and the run, with its basis and context | autonomous |
| F4 | a missing screen state asked as a question | make it a note for the prototype | autonomous |
| F5 | a gap the context settles kept open, or settled without its basis | close it as settled with what settles it and what that rests on | autonomous |
| F6 | no drive contract, a write outside the issue, or a model write | halt; move the record under the drive's issue; undo the model write | human |

## Pause and Resume

The run's working folder is per round (`context/build-knowledge/round-<n>/`). On entry, skip a
step whose output exists and checks clean; a round already built is not built again.
