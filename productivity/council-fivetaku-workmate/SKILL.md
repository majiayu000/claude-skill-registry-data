# Council — 업무 의사결정 오케스트레이터

> SKILLS_INDEX.md를 읽고, 복잡도에 따라 적절한 스킬/에이전트를 선택·병렬 실행·종합합니다.

---

## WHEN TRIGGERED - EXECUTE IMMEDIATELY

---

## Workflow

### Step 0: 스킬 인덱스 로드 + 복잡도 분류

1. `.claude/skills/SKILLS_INDEX.md` 를 Read
2. 사용자의 요청을 분석하여 복잡도를 분류:

| Tier | 특성 | 라우팅 |
|------|------|--------|
| **Micro** | 단일 파일 읽기, 간단한 질문, 한 단계 작업 | **스킬 종료** → 메인 세션이 직접 처리 |
| **Sprint** | 집중된 멀티스텝 (분석+보고서, 리서치+검증) | 1~3개 스킬/에이전트 선택 |
| **Council** | 전략적 결정, 다관점 필요, 리스크 평가 | 3~5개 독립 에이전트 병렬 실행 + 종합 |

**Micro 판단 기준**:
- 하나의 CSV 읽고 특정 수치 확인
- 단순 용어 질문
- 파일 1개 생성
→ 이런 건 스킬을 종료하고 메인 세션이 직접 처리

**Sprint 판단 기준**:
- "A 분석해서 B 보고서로 만들어" (분석 + 보고서 = 2단계)
- "이 데이터 분석하고 크로스체크해줘" (data-analyst + cross-check)
- 예산, 시간, 단일 주제 내 의사결정

**Council 판단 기준**:
- "공급사 A에서 B로 바꿔야 할까?"
- "이번 분기 예측이 신뢰할 만한가?"
- "이 프로세스를 바꾸는 게 맞는지 전체적으로 봐줘"
- 여러 이해관계자에게 영향, 되돌리기 어려운 결정

---

### Step 1: 스킬/에이전트 매칭 (Sprint / Council)

**Sprint (1~3개)**:
1. SKILLS_INDEX.md에서 요청과 매칭되는 스킬을 1~3개 선택
2. 선택된 스킬을 순차 또는 병렬 실행
3. 예시 조합:
   - 데이터 기반 판단 → `data-analyst` → `cross-check`
   - 보고서 작성 → `data-analyst` → `content-draft` → `xlsx`
   - 리서치 기반 판단 → `deep-research` → `cross-check`

**Council (3~5개 독립 에이전트)**:
1. SKILLS_INDEX.md + 사용자 요청을 기반으로 **관점(perspective)** 정의
2. 관점은 고정이 아니라 요청에 맞춰 동적으로 결정

자주 쓰이는 관점 풀:

| 관점 | 역할 | 언제 사용 |
|------|------|---------|
| **데이터 분석가** | 숫자와 사실 기반 판단 | 항상 |
| **도메인 전문가** | 업계 관행, 해당 업무의 맥락 | 도메인 지식이 필요할 때 |
| **비판가** | 리스크, 실패 모드, 놓친 것 | 의사결정 / 리스크 평가 시 |
| **실행자** | 현실 제약, 실행 가능성, 비용 | 실행 여부를 결정할 때 |
| **고객/사용자 관점** | 최종 사용자나 고객에게 미치는 영향 | 외부 영향이 있을 때 |

3. 각 에이전트에게 **context로 줄 것**:
   - 사용자의 원래 요청
   - 관련 `data/` 파일 내용 (필요시 Read해서 포함)
   - 관련 `references/` 문서 (필요시)
   - `memory/wiki/` 관련 페이지 (필요시)

---

### Step 2: 병렬 실행 (Council만 해당)

**반드시 모든 에이전트를 단일 메시지에서 동시 spawn. 순차 실행 금지.**

각 에이전트 프롬프트에 포함할 것:

```
[역할 설명]
[사용자 요청 + 관련 데이터/참조문서 내용]

INDEPENDENCE PROTOCOL:
- 당신은 이 질문을 분석하는 여러 독립 에이전트 중 하나입니다.
- 다른 에이전트가 무엇을 결론내렸는지 모릅니다. 추측하지 마세요.
- 당신에게 주어진 근거만으로 판단하세요.
- 결론을 응답 맨 앞에 직접적으로 적으세요.
- 모든 주장에 출처(파일명, 데이터, 추론 근거)를 달아주세요.
- 근거가 부족하면 그렇다고 말하세요. 빈칸을 추측으로 채우지 마세요.
- 불편하더라도 솔직한 평가를 내려주세요.
- 200단어 이내로 간결하게.
```

Agent tool 설정:

| Parameter | Value |
|-----------|-------|
| subagent_type | `general-purpose` |
| model | `sonnet` (Sprint) / `opus` (Council) |
| prompt | 위 구조로 구성 |

---

### Step 3: 종합 (Chairman)

모든 에이전트 응답을 수집하고 종합:

1. **수집**: 각 에이전트의 핵심 결론 한 줄 요약
2. **합의**: 2개 이상 에이전트가 수렴하는 포인트
3. **갈등**: 에이전트 간 불일치. 양쪽 근거 제시
4. **빈틈**: 아무도 다루지 않은 중요 측면
5. **가중치**: 구체적 근거(파일명, 데이터)가 있는 결론 > 일반 주장
6. **판정**:

| 판정 | 조건 |
|------|------|
| **Go** | 다수 동의 + 리스크 식별됨 + 관리 가능 |
| **Pivot** | 의견 분열 (50:50) 또는 중요 미지수 |
| **No-Go** | 다수 반대 + 구체적 리스크 근거 |
| **추가 정보 필요** | 핵심 데이터 누락 — 지금 판단 불가 |

### Step 5: 메모리 제안

결과에 durable knowledge가 포함되어 있으면:
- `memory/wiki/decisions/`에 위키 페이지로 기록할 것을 사용자에게 제안
- Sprint 결과가 반복 가능한 분석이면 스킬 후보로 제안

## 핵심 원칙

1. **독립성**: 에이전트 간 결과 공유 금지. 편향 주입 금지.
2. **근거 우선**: 근거 없는 주장은 종합 시 가중치 0.
3. **과잉 오케스트레이션 금지**: Micro 작업에 에이전트 소환하지 않는다.
4. **Graceful degradation**: 에이전트 1개 실패해도 나머지로 진행 (최소 2개 응답 필요).
5. **투명성**: 어떤 관점이 참여했고, 무엇을 말했고, 어떻게 종합했는지 항상 공개.
