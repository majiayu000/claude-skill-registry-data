# MathRSI Meta-Evolve

把已有数学研究变成下一版可用的 MathRSI。输入可以是完整研究交接包、某次失败与修正、用户反馈或一组真实调用记录。执行者读取原件、定位现行实现、作出分层判断，修改现有版本，并实际使用修改后的内容。一次运行应交出可审阅的真实变化及依据；只写经验总结或升级计划不算完成已经授权的实现任务。

这是现有 MathRSI 的外层维护 workflow，基于 [EVOLUTION_WORKFLOW](../../../docs/EVOLUTION_WORKFLOW.md) 和 ARIS meta-optimize／meta-apply 演进。它不替代五个解题子工作流，也不自动成为每道题结束后的第六阶段。基础模型不因技能变化而被训练；版本迭代是研究方法、知识、调用与工具的改进。

**先读本技能，再用它组织本次迭代。** 不在技能之外把插件和新版做好，事后补一份“已按 meta 执行”的日志。已经发生的研究可以作为历史证据，不能改写成它由某个尚未存在的 MathRSI 版本完成。

## 执行地图

| 阶段 | 读什么、实际做什么 | 产物怎样进入下一步 |
|---|---|---|
| 恢复与范围 | 用户要求、现用版本、工作树、本轮维护记录；确认可改文件与源项目只读边界 | 延用已有分支与记录，指定唯一协调者 |
| 取证与回收 | 原目标、关键成功／失败／更正链、wiki导航、实际正文／程序／输出；可并行读 | 能支撑具体判断的证据立即回收，不等全库阅读结束 |
| 分类与比较 | 对照现行技能及实际 caller，判断进入 base、插件、单题，或暂不采用 | 每个拟改行为落到现有文件、输入与消费方 |
| 候选实现 | 原位修改现有版本；插件接既有契约，必要知识与资源随仓 | 实际 diff、可调用入口和可用的例子 |
| 针对性讨论 | ARIS research-review 的维护适配，围绕证据、diff和具体疑问 | 修真实问题；误读用原件回应，不等泛泛共识 |
| 实际使用与修正 | 协调者自己按候选内容执行相关任务；子代理承担具体作者／核对 | 实际产物和命令结果决定接纳、收窄或再修 |
| 采用与交接 | 记录版本、已采用变化、保留条件与下一次可复用经验 | 新任务可选择新版；在途研究不被静默切换 |

不要求每轮新增所有类型的变化。一次只修一个已定位的调用错误，可以直接从相关原件和实际接口进入实现。完整项目吸收才需要较宽的研究地图。

## 0. 在当前版本上开始，或从真实断点继续

读取仓库 AGENTS、用户本次要求及 [WORKFLOWS](../../../docs/WORKFLOWS.md)、[PLUGIN_CONTRACT](../../../docs/PLUGIN_CONTRACT.md)、[WORKSPACE](../../../docs/WORKSPACE.md)。核对当前分支、未提交修改及已有作者的文件归属。新维护没有记录时，在仓库 development/evolution/ 下建立一个本轮目录；已有目录直接复用。

用一份 EVOLUTION.md 或现有维护报告作为主记录，写清：

- 当前基点／版本与用户要达到的结果；
- 可修改的 base、插件、文档范围；源研究能否写入、能否计算；
- 当前在途作者、成熟产物、尚待决定的问题与下一动作。

维护记录放在开发工作区，正式技能放在 base/skills，领域知识放在 plugins。原研究目标、断点、运行日志和题目 wiki 保持在原任务工作区；需要随插件携带的历史副本标明只读来源。不要为了符合新文件名复制多套活跃状态。

恢复时先消费已经交回的材料和实际新输出，接着推进未完成动作。旧文件中的 ACTIVE、旧 Goal 命令、未结束的历史叙述不是本次恢复研究的授权。用户已授权本地维护时，正常可撤回修改继续执行；远端发布、全局安装或新付费研究批次按原有授权判断，不由本技能扩大。

若请求只要求分析，交具体提案而不落地；若请求已明确“迭代、实现、做新版”，不能停在提案后再次索取同一授权。

## 1. 读懂关键研究链，并及时把阅读变成动作

完整项目吸收先建立全目录的内容地图：原目标及变化、数学正文、代码和证书、实验、文献、人工反馈、模型审阅、形式化、wiki与交接各在哪里。然后沿真实轨迹读，不能只读 README 和 query_pack 就总结方法。

一条承重轨迹至少接清：

1. 原来要解决什么，量词、对象及验收是什么；
2. 当时实际用了哪个假设、表示、引理或程序；
3. 哪个原始结果／反例／审阅或人工纠正改变了判断；
4. 随后究竟改了什么，输出怎样接回原目标；
5. 成果现在仍成立的条件，失败实际排除了哪一范围。

**阅读不是无限前置任务。** 优先接通关键成功、重要失败及推翻旧判断的更正。某个改动已有充分证据、当前实现与可观察的改法，就交给下一阶段实现；其他作者继续补与其它改动有关的材料。不要因全库还有未读文件搁置成熟结论，也不要因为时间短就只挑支持自己设计的例子。

用户要求系统了解项目时保留完整地图和实际阅读范围，未知部分如实标记；不把“全文已读”写给仅列目录、解析 JSON 或代理摘要的文件。大量相同归档可复用同一阅读，生成表应检查生成器、数据定义、消费者、覆盖与实际结果，不要求人为逐行重读相同模板。影响本轮判断的冲突与缺件必须回到原件；无关未读材料不阻塞已有修改。

### 按研究链委派，而不是按文件数分摊

可并行时主动使用用户偏好的 worker。给每个 worker 一段有完整因果关系的范围，例如“固定源失败→释放局部约束→新共同覆盖证书”，而不是泛泛要求“总结这个目录”。交代来源路径、需要回答的问题、输出归属、是否允许计算，以及什么时候交回成熟部分。

协调者收回后核关键原件与结论，不重复阅读 worker 已充分核对的全部内容。代理摘要是导航；其证据定位和准确范围才使它可被采用。任何代理读完关键链后立即提交，继续补读不能阻止已成熟材料被使用。

可直接委派：

~~~text
请阅读源项目 <范围> 中与 <关键转折> 有关的原目标、证明、
实际程序/结果和后续更正。交回旧行为、改变依据、实际改法、
结果范围、原件位置和尚缺内容。先交可用于改动的成熟链，
不要为了读完无关目录拖延。只写 <本轮维护目录/你的文件>；
不修改源研究、不恢复旧Goal、不替我先改base或插件。
~~~

### 文献与 wiki 的实际用法

已有 wiki 用来定位论文、失败范围和各版结果，再读当前判断所依赖的实体及原件。需要确认方法是否已有、公开基线是否变化时，读本仓当前宿主 research-lit／wiki-enrich 的完整技能，带具体疑问补查；不要把整项目广搜重复一遍。返回来源版本、定理条件与它改变的动作。

原 wiki 不能因“过长”被几篇摘要替代；也不把它所有历史状态装进每次技能提示。插件内的整理层指出何时查哪个原件，资料层保留完整依据。源项目只读时，在维护记录保存发现，不能借“更新wiki”改写源项目。

取证细节与 DD 转折见 [evidence-and-transfer](references/evidence-and-transfer.md)。它是如何判断的实例，不是每个领域都要使用图构造、SAT 或 Lean。

## 2. 对照当前版本，决定每项经验放在哪一层

先读实际受影响的 SKILL、引用资源、调用者和消费方，再决定增补什么。当前版本已有成熟动作时，复用它、补具体案例或修真实衔接；不要复制同义技能另起主干。一次读到好经验，不等于现有 base 缺这一能力。

| 归属 | 判断依据 | 实际处理 |
|---|---|---|
| Base | 跨领域都需要的研究行为／调用连接，例如输入对齐、错误回流、成本判断 | 修改现有技能中动作发生的位置，并检查其 caller 与返回消费者 |
| 领域插件 | 对象定义、定理条件、构造／排除方法、专用检查器与失败机制 | 接已有插件契约，保留可直接使用的数学及程序，不把领域公式放进全局提示 |
| 单题状态 | 当前参数、特定图／矩阵、某次 UNKNOWN、开放分支、当次额度 | 留在该任务；只读吸收时保存在历史副本，不能变成通用默认 |
| 暂缓／不采用 | 因果证据不足、单次环境问题、收益不明或过度泛化 | 记录原因与什么新证据值得再看，不为了版本名强行纳入 |

同一事件可以产生不同层次的内容。例如一条图修改保距引理属于 DD 插件；“修改数学对象后重新判断哪些旧证据仍适用”可以改善 base；本次第 k 个增点图和运行时间属于单题记录。三者不能揉成一条永远适用的规则。

数学状态与方法价值分开。未解决主问题的条件引理可以保留，只要条件、证明和实际用途准确。样本搜索失败、求解器 UNKNOWN、模型认可分别记实，不升级为全域定理。维护不重新认证全部历史数学，也不把原题验证要求删掉后称为提速。

对每项拟改内容，用自然语言写出可核的变化：

~~~text
触发：什么真实输入让旧行为失效或浪费。
依据：原件、实际结果／更正及适用范围。
现行实现：目前哪个技能、调用处已有什么，准确缺什么。
修改：在哪个既有文件改变什么动作，产物由谁消费。
使用：本次怎样观察它确实被执行，哪些原证据可继续复用。
~~~

这些信息放入同一维护记录即可，不强制一项一份 JSON 或评分。删除无效步骤也是改进；需要完整新领域能力时可以新增实质技能，但新技能应有独立任务和真实输入输出，不按动词拆空目录。

多题吸收时可参考[v3的实际证据与返回](references/v3-evidence.md)：工作集与全域不同、标记在复合变换中丢失、有限秩机制与局部正证书的不同用途、Lean显式参数边界。这些实例帮助定位现行caller的具体缺口，不要求未来每轮都新增四条规则或复制本轮插件。

v4 的 [临界取等与相容见证](../mathrsi-prove/references/critical-equality.md) 是另一种集中增量：Happy Ending 的新工作稿触发同一取等链、合法交换和见证定位；DD 的真实 v2 增点经验则深化已有插件。当前流程已覆盖的反例回流和证据继承只补领域实例，不重复算新 base 能力。实际采用与验证范围见 [v4维护](../../../development/evolution/v4-20261108/EVOLUTION.md)。

## 3. 形成可执行修改，再按已有分工实现

协调者把成熟提案整理为本轮实际修改顺序。优先改变原错误或主要成本来源，不按文件数、模型分数或抽象重要性排序。存在相互依赖的改动就说明共同接口；独立任务交不同作者并行，明确文件所有权。

维护本身也可能局部空转：持续阅读、抽象分类、重写技能或增加检查，却没有修复已定位的真实调用缺口。每批收件先核用户要改变的行为是否已经改变。两批只新增整理而成熟改动未落地，或扩大审阅/重构前，沿 [全局进展重评](../mathrsi-research/references/global-reassessment.md) 由本维护 owner 请求两个独立只读判断并执行下一动作；用本轮 EVOLUTION 作为原目标和唯一记录。已有审阅若覆盖同一全局疑问可复用，不在维护末尾另套一次验收循环；没有停滞的短修改直接完成。

每个作者先读取目标技能及上下游。交给它的是准确问题、源证据、允许修改的文件、要保留的契约和完成后的消费者，不是“写得详细一点”。作者交回真实文件与变更说明；协调者及时整合，不等所有作者收工才读。

修改现有 base 时：

- 保留五个子工作流与有效 ARIS 调用，优先在原步骤补判断、动作、输入／返回及失败处理；
- 同一契约影响多个文件时一起修，例如 specify 固定目标、survey 发现新基线、prove 消费后改变工作队列；
- 不把历史项目的秒数、种子数、模型名或一次暂停变成所有任务的硬限制；
- 数学证明与工程性能问题分开。压缩数据表示、复用未变证明可以降低成本；删必要覆盖、验距或原题连接不能算优化；
- ARIS 原字节副本保持来源记录。MathRSI 的适配写在自身技能与参考，确需改上游时另作清楚的依赖更新。

### 新领域插件：通过现有契约装进去

先读 [PLUGIN_CONTRACT](../../../docs/PLUGIN_CONTRACT.md) 和现有插件的实际使用入口。新插件回答该领域怎样表达问题、哪些方法可用、怎样查已有失败、怎样生成／验证、怎样把结果返给当前 base 阶段；不再复制一个新 mathrsi-research。

整理后的定理要有对象、假设、结论、证明或准确进口、实际调用条件和源码入口。失败要有实际输入、被否定的语句／范围、后续改变及重试条件。程序说明要写输入、执行位置、输出意义和现存依赖，不能只列 source-ref。

插件分成互相连接的两层：整理层（`skills/` 与所需 references）说明何时读、怎样调用、返回什么；原始资料层随仓保留用户提供的 wiki、证明、构造与检查代码、失败实例和审阅。原件可作只读 archive，标明来源、历史范围和原包已省略的大文件，避免旧绝对路径成为新入口的隐含依赖。原程序会写源目录时，把必要输入复制到当前任务的运行目录后调用；已有可移植重建入口直接复用，不另造统一检查器平台。

集成到现有子工作流的实际调用处：prepare／survey 消费领域定义、基线与公开构造；route-loop 消费失败机制和探针；prove 消费构造、归约和具体引理；verify 消费检查器、覆盖论证和形式化连接；assemble 引用已核结论与复现入口。说明各处调用哪个领域技能、返回什么和接着做什么，更新插件契约／使用说明，以及 `.agents/skills/`、`.claude/skills/` 的仓内相对发现别名。不要只增加一个没有消费者的插件目录。

插件的研究技能、知识与原始资料均需能从当前克隆读取。源 wiki 作为历史知识库使用，新题积累写新题自己的 wiki；插件更新由外层维护处理，不在解题时静默改核心。

代码保持薄。先利用现成构造器、检查器、ARIS helper 与 MCP。仅在重复机械操作影响使用时增加少量 Python；不要把数学选择、审阅裁定或所有阶段调度写成一个庞大程序。

## 4. 用跨模型讨论解决具体设计问题

读取本仓当前宿主的 [research-review Codex](../skills-codex/research-review/SKILL.md)／[Claude](../research-review/SKILL.md)，实际模型调用依 [REVIEWER_MCP](../../../docs/REVIEWER_MCP.md)。保留用户指定的 reviewer、model、effort 与现有会话契约；缺服务如实记录，不因此重复新开付费尝试。

这是 research-review 的数学维护组合调用。明确传 `— composed: <本轮 EVOLUTION.md>`，复用其原件阅读、外部讨论与 Step 3 的意见产出；**本适配不执行原 Step 4–5 的论文共识循环与论文产物收束**。一次返回失效路径、证据和最小改法即交回维护协调者，由本技能决定修法及是否需要具体续问。composed 本身只指定记录归属，不会自动取消原技能循环，因此调用时须把这个替换写明；仓内原版技能保持不变。

设计尚有实质分歧时，可以先讨论具体提案；已有可读修改后，交实际文件、diff和源证据。不要让 reviewer 只看作者的成功摘要：

~~~text
请按本仓 research-review 的 composed 维护适配审查。
— composed: <本轮 EVOLUTION.md>
执行原件阅读与 Step 3 意见产出，不执行原 Step 4–5；
本次返回即交回维护协调者，不自行开启论文共识循环。
原研究证据：<原件>；现行技能与修改：<文件/diff>。
本轮问题：<例如基线更新是否真的改变下一任务；
旧否证为何不再适用修改后的对象；新插件能否返回原调用处>。
请读原件，指出实际错误与最小修法；正确部分直接说明。
不要求投稿评分，不额外派发作者或启动另一整套循环。
HERO：不提出无收益的哈希、假想边界防御或新平台。
返回实际阅读/执行范围及原始意见，由维护协调者决定和落实。
~~~

完整保存 prompt、原回应、会话和实际模型／完成状态。把意见落实为具体修改，或引用原件解释不采纳原因；模型没有自动的数学真理否决权。关键修法需要复核时续原会话读新的 diff，未变部分不重复整卷审查。

用户要求的跨模型讨论不能由同家族子代理冒充；同家族核对按实际身份记录。相反，取得跨模型赞同也不能把未执行命令、未闭证明或未读原件写成完成。

## 5. 自己实际使用候选内容，按改动做必要核查

默认由本次协调者或具体执行作者按新内容完成相关工作，子代理帮助写作、调试、计算和核对。**不把“换一个没有历史的 agent 重跑完整流程”设为开工或接纳的必经关卡。** 只有真实疑问需要独立消费、用户要求，或变更风险值得时，才增加有界的独立使用。

新 meta 技能本身可以通过一次真正维护使用来检验：先形成并集成技能，随后读取它，用研究 context 选择提案、修改现有版本、消费审阅、核查实际产物。不能先在技能外完成所有修改，再把历史动作追认成试用。

这次真实维护本身就是使用，完成后进入第 6 节收束，不在结尾再套一轮 meta 验收。多作者分目录修改后，协调者沿实际变化接通“base 调用处 → 插件／下游技能 → 有界命令或原件核对 → 产物被原调用处消费”；各作者单文件写完不能代替这项连接核查。

核查围绕本次改了什么：

- 改入口／相对路径：实际解析当前克隆，检查发现别名与资源；搬移有疑问时在副本调用；
- 改程序或命令：用真实且有界的输入运行受影响命令，读取退出码与实际输出，不能只看脚本存在；
- 改研究行为：让当前执行者使用它处理真实问题，留下所作决定与后继动作，例如根据新基线撤掉无意义队列、保留不受影响的固定目标；
- 改数学解释／验证接口：核对假设、原对象、归约与最终消费者，必要独核仍按该数学任务合同执行；
- 仅新增历史例子：核查原件和范围，不为例子重跑旧大型搜索或全部 Lean。

复用未变证据。一个固定证书重放、实际构建、模型静态审阅和全域第二实现是不同结果，分别说清。普通浮点探索不能冒作严格数值证明；图例、技能包装和文件数不证明研究效率提高。

使用暴露真实错误后，作者修对应文件，再核改变的那一段即可。不要每改一句就重启全套模型审阅／全部数学。若连续修改仍没解决原问题，协调者接管具体卡点、缩小提案或保留未决，而不是增加表格、再审次数或统一评分器。

按 [SKILL_ACCEPTANCE](../../../docs/SKILL_ACCEPTANCE.md) 核 frontmatter、当前入口、资源、实际调用与可读性。命令和状态保存到本轮现有记录；不额外造通用测试框架。

## 6. 接纳本轮改动，保持版本与研究事实清楚

协调者根据实际使用决定采用、部分采用、修订或暂缓。已支持的变化及时纳入，尚缺依赖的能力单列具体未测范围；不要求为一项无关缺件冻结整轮。

主记录收束为可供下一轮直接消费的内容：

- 基点与实际变更文件，为什么改、哪个源证据支持；
- 进入 base、插件、单题或暂不采用的结果；
- 实际使用、命令、审阅及修正的准确范围；
- 哪个旧瓶颈已改变，哪些仍未解决，什么证据值得再迭代；
- 当前分支／提交或未提交状态，用户怎样调用新增能力。

版本名应对应实际变更，不靠图上写 v2 宣称全新系统。保留此前有效工作流，说明哪些步骤增强、哪些删除、哪个领域插件新增。DD、Property B、ECC 的历史结果保持真实来源；没有由新版重做就不写成新版解题率或效率实验。

本地维护授权足够完成本地实现与核查；提交、推送、合并和发布按用户已有指令与仓库身份约定执行，不在本技能里硬塞一轮新的许可仪式。不能覆盖无关未提交内容。

新任务可选择已采用版本；正在解题的工作区由其协调者确认采用位置，保留原规格、证明状态和已用预算，只重核受改变影响的结果。暂停的研究不因插件或 base 更新自动恢复。

若本轮无需 base 改动，只有一个可用领域插件或准确拒绝了不合适的提案，也可以是有效演化结果。诚实交代范围，不为了凑“自我迭代”修改已经正确的指令。
