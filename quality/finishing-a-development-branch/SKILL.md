# Finishing a Development Branch

这个 skill 解决的是“做完之后怎么收尾”。重点不是机械执行 git 命令，而是用稳定出口收束当前分支：先验证，再确定基线分支，再选择 merge、push、保留或丢弃，并明确 worktree 是否清理。

## 何时使用

- 一轮实现已经结束，需要决定怎么把结果并回主线
- 当前分支已经具备可验证的交付物
- 你需要收尾 worktree，而不是无限把临时分支挂在那里

不适用：

- 改动还没完成，甚至还没形成可验证结果
- 当前仍在主要实现阶段，不适合提前谈 merge / discard
- 只是想做一次中途 checkpoint，而不是决定分支出口

## 产物

每次使用本 skill，默认产出以下最小集合：

1. 完成前验证结果
   - 用了哪些命令
   - 是否通过
2. 出口决策
   - 选的是 merge、push、保留还是 discard
   - 基线分支是什么
3. 清理结果
   - 分支是否保留
   - worktree 是否保留
   - 是否还存在待处理风险

默认要求：

- 先验证，再讨论出口
- 出口要结构化，不要只问“接下来怎么办”
- 涉及删除 worktree 或强制删分支时，必须显式确认
- 对远端同步、PR / MR 创建、合并策略等仓库级动作，先遵守当前项目约定

## 工作流

1. 先确认完成前验证
   - 运行当前任务最关键的一组验证命令
   - 至少要能说明“现在为什么可以进入收尾阶段”
   - 若失败，先处理失败，不进入后续出口选择
2. 确定基线分支
   - 优先根据仓库约定判断，例如 `main`、`master` 或项目文档指定分支
   - 若不明确，可用 `git merge-base` 等方式辅助判断
   - 若仍有歧义，明确告诉用户你的假设或直接询问
3. 给出结构化出口
   - 默认提供四个出口：
     1. 本地合回基线分支
     2. 推送并发起 PR / MR
     3. 保留当前分支，稍后再处理
     4. 丢弃当前工作
   - 出口描述保持简洁，让用户明确选择
4. 按出口执行
   - 选项 1：本地 merge
     - 切回基线分支
     - 按仓库约定决定是否先同步远端
     - merge 当前功能分支
     - 对 merge 结果再做一轮关键验证
     - 成功后删除功能分支，并清理对应 worktree
   - 选项 2：推送并发起 PR / MR
     - 推送当前分支
     - 若当前环境已有现成 CLI 或脚本，则用项目既有方式创建 PR / MR
     - 若没有现成工具，至少输出标题、摘要和验证说明，供后续提交
     - 默认保留分支与 worktree，等待评审反馈
   - 选项 3：保留现状
     - 明确报告当前分支名、worktree 路径和后续待办
     - 不清理 worktree
   - 选项 4：丢弃当前工作
     - 必须先做显式确认
     - 确认后再删除分支与对应 worktree
5. 清理 worktree
   - 对选项 1：默认清理
   - 对选项 2：默认保留；只有用户明确要求时才清理
   - 对选项 3：保留
   - 对选项 4：确认后清理
   - 清理前先确认 worktree 是否仍有未提交改动，避免误删现场

## 决策约束

- 验证失败时，不要继续往 merge / PR 阶段推进
- 丢弃是破坏性动作，不能默认执行
- `push + PR / MR` 不等于自动清理本地 worktree
- 若项目有受保护分支、线性历史或 squash 约定，应先遵守项目规则
- 这个 skill 负责收尾决策，不替代质量验证和代码评审

## 失败信号

- 还没验证就开始谈 merge
- 用开放式提问替代结构化出口，导致用户无法快速决策
- 没确认就删除分支或 worktree
- PR 刚发出去就自动删 worktree，后续评审难以跟进
- merge 后没有再次确认关键验证结果

## 常见场景

- 功能已做完，准备本地并回：
  - 先跑关键验证
  - 确认基线分支
  - merge 后再验证
  - 删除功能分支并清理 worktree
- 功能已做完，准备发 PR：
  - 先跑关键验证
  - 推送分支
  - 生成 PR / MR 所需摘要
  - 默认保留 worktree 等待 review
