---

## 何时使用
- 当用户要求审查代码、补丁、PR、实现计划、生成文件、测试、文档或发布变更时使用。
- 当用户明确要求实现而不是审查时不要使用。

## 必要输入
- 审查对象、已声明的规格/设计/验收标准，以及相关变更文件。
- 可获得的测试结果、构建输出、文档、配置和运行时证据。
- 已知约束、隐私/安全预期，以及预期的用户可见行为。

## 第一性原则与边界
- Stage 1 先审查规格和设计一致性，再判断局部代码质量。
- Stage 2 审查正确性、可维护性、安全、隐私、真实用户说明和真实测试。
- 测试必须证明真实行为；如果测试只断言 mock、快照或硬编码成功，却没有验证契约，应标记出来。
- 面向用户的说明必须描述实际支持的行为；应标记占位、误导或虚构的能力。
- 如果 Stage 1 存在实质失败，停止给出整体通过结论，并要求在设计/规格不匹配解决后重新审查。

## 验收标准
- 发现项有证据支撑；在可获得时附文件/行号引用。
- 严重程度应绑定用户影响、安全/隐私风险、契约破坏或发布风险。
- 对实质性规格/设计失败、不安全行为、虚假说明或不真实测试，不得给出通过结论。
- 明确说明剩余不确定性和缺失验证。

## 产出
- Stage 1 结论：符合、部分符合或失败。
- Stage 2 发现项，按严重程度排序。
- 必须修复项、可选改进项，以及验证缺口。

## 输出模板

```markdown
## Stage 1: Spec / Design Compliance
Result: PASS | PARTIAL | FAIL

| Severity | File | Evidence | Issue | Required Fix |
| --- | --- | --- | --- | --- |

## Stage 2: Quality / Security / Test Reality
Result: PASS | PARTIAL | FAIL | NOT RUN

| Severity | File | Evidence | Issue | Required Fix |
| --- | --- | --- | --- | --- |

## Verification Gaps
- ...

## Final Gate
PASS | BLOCKED
```
