# /no-issue

この会話では、Issue 番号の無い作業指示を起票せずに着手する。人間だけが打てる。

起動したら、**この会話が終わるまで**下のルールを効かせる。1回の作業だけで元に戻してはならない。

## なぜ起票の例外にしてよいか

#682 は「どのルートでも Issue を作ってから作業する。例外は置かない」と決めた。作り忘れると、目的や完了条件の記録は取り戻せないからである。

この Skill は、その決定に置いた1つだけの例外である。人間しか打てない（`disable-model-invocation: true`）ので、#682 が却下した「AI が『小さい』と自分で判定して起票を省く」抜け道にはならない。起票を省くかどうかは、人間が会話ごとに決める。

引き換えに、目的・完了条件・相談の答えは Issue に残らない。残す場所はコミット本文だけなので、後述のとおり「なぜ」を必ず書く。

## 変えること

CLAUDE.md の起票ルールを、この会話では次のとおり読み替える。

- **起票しない**：作業指示を `/quick-issue` でも `/to-issues` でも Issue にしない。`/grill-me` や Plan モードで相談したあとも Issue にせず、人間が実装を指示したら着手する
- **起票に連なる手順を行わない**：着手時の `npm run close-issues` と `npm run move-issue-card`、タスク一覧のチェック、`/pr-body` と `Closes` 行
- **コミットの件名に `(#番号)` を付けない**：番号を確認することもしない。代わりに、コミット本文に「なぜ」を必ず書く（`/git-commit` の規定）
- **PR 本文は自分で書かない**：push すれば `pipeline.yml` が PR を作る。本文はコミットメッセージから生成される
- **「着手時」を、最初にファイルを編集する直前に読み替える**：実装フローの Skill の起動も、起票した Issue の編集も無いからである。この時点で `npm run prune-merged-branches-and-worktrees` を1回打ち、並行セッションを数える（`/git-commit`）。worktree を切るときの名前は `../cdt-<Issue番号>` でなく `../cdt-<ブランチ名の説明部分>` にする

## 変えないこと

- 本筋外の課題（割れ窓）と人間からの指摘の起票。この Skill が止めるのは作業指示の起票だけで、見つけた問題が会話内の報告だけで流れるのを防ぐ
- 進め方の提案（新しい機能なら `/grill-me`、既存の改善なら Plan モード）
- 不可逆な操作の前の確認
- 変更種別ごとのレビュー Skill（直接編集した場合の `/quick-doc-review` など）

境目の例：

- ❌ 作業中に見つけた別ファイルの放置 TODO を、会話で報告するだけにする → ✅ `/broken-window-issue` で起票する
- ❌ 人間に「件名の書式が違う」と指摘され、直して終える → ✅ 直したうえで、再発防止案を起票する
- ❌ 2つ目の作業指示を、起票してから着手する → ✅ この会話が続くかぎり、起票せずに着手する

## 使い方

```
/no-issue                                # 以降の作業指示を、起票せずに受け付ける
/no-issue READMEの誤字を直して           # 作業の指示と一緒に打つ。この会話の以降の作業も起票しない
```
