# Origin Search（一次資料だけで調べる）

web を調べて答えるとき、根拠を**発信元の原典**だけに限るスキル。原典で確かめられなかったことは答えない。

## なぜこれが要るか

web 検索の結果には、誰かが要約・解釈した記事が大量に混ざる。それを根拠にすると、間違いが伝言ゲームで増幅されたまま回答に入り、出典を見ても間違いに気づけない。原典に当たれば、書いてあるかどうかがその場で決まる。

出典を主張ごとに付けるのも同じ理由である。URLを1つずつ紐づけると、原典に無いことは書けなくなる。

## 一次資料の定義

判定に迷ったら一つだけ問う。**それを書いたのは、その主張の当事者か。** 当事者でなければ一次資料ではない。

- **一次資料（根拠にしてよい）**
  - 公式ドキュメント・公式サイトの記述
  - 仕様書（RFC・W3C・ECMA など）
  - 論文の原文、法令・官公庁の原文
  - 企業・団体の公式発表・プレスリリース
  - ソースコード本体・公式リポジトリの README
  - 公式のリリースノート・変更履歴・GitHub Issue/PR
- **一次資料ではない（根拠にしない）**
  - 個人・企業のブログ記事
  - まとめ記事・入門記事
  - ニュース記事・報道
  - Qiita・Zenn・Stack Overflow
  - AI が生成した解説
  - 非公式の和訳・ミラーサイト

二次資料は**原典への道案内としてだけ**使ってよい。記事が引用している原典を辿り、原典そのものを開く。記事の主張は回答に載せない。

## 手順

### 1. 確かめる点を宣言する

検索を始める前に、「この問いに答えるには、何を一次資料で確かめればよいか」を箇条書きで出す。**ユーザーの返事は待たず、そのまま2へ進む**（取り違えていればユーザーが割り込む）。

項目は問いの言い換えではなく、**原典に書いてあるかどうかで白黒が付く形**にする。

- ❌ X は安全か → ✅ X の公式ドキュメントに、認証の扱いがどう書かれているか
- ❌ X は速いか → ✅ X の公式ベンチマーク結果に、どの条件で何ミリ秒と出ているか

### 2. 原典を探して開く

確かめる点を1項目ずつ処理する。

- **検索語は原典の言語で組む**（多くは英語）。日本語だけで検索すると、解説記事や非公式の和訳に流れて原典に届かない
- **検索結果のスニペットを出典にしてはならない。必ず WebFetch で開いて本文を読む**。スニペットは検索エンジンが要約したものであり、原典ではない
- 原典を1件見つけて確かめられたら、その項目は終了して次へ進む
- 見つからないときは **web 検索2回・原典を開くのは3件**で打ち切り、その項目を「確認できなかった」とする
- 開けなかった原典（有料の壁・403 など）も、開こうとした3件に数える

### 3. 答える

下の出力形式で、日本語で答える。

## 出力形式

宣言した「確かめる点」の全項目に、確かめられたものと確かめられなかったものを分けて答える。

**確かめられた項目**は、主張の直後に出典URLを置く。

- **<確かめる点>**：<原典に書いてあったこと>（`[<資料名>](URL)`）

末尾に参考URL一覧をまとめる形式は取らない。どの一文がどの原典から来たか復元できなくなるからである。原典の記述と自分の言い換えがずれそうなら、原文を短く引用する。

**確かめられなかった項目**は、探した範囲だけを書く。

- **<確かめる点>**：一次資料では確認できなかった。<探した範囲を1文で>

二次資料で見当が付いていても、その中身は書かない。書いてよいのは「一次資料では確認できなかった」ことだけである。

## 出す前の自己チェック

> [!IMPORTANT]
> **（AI・必須）** 回答を出す前に次を問い、すべて「はい」になるまで書き直す。
>
> - 出典として挙げたURLを、すべて実際に WebFetch で開いて本文を読んだか
> - 出典URLが付いていない主張が残っていないか
> - 出典がすべて「一次資料の定義」の左列に当たるか
> - 一次資料で確かめられなかったことを、それらしく書いていないか
> - 宣言した「確かめる点」の全項目に答えたか

## 使用方法

```
/origin-search <調べたいこと>
```

例：

```
/origin-search TypeScript の satisfies 演算子はどのバージョンで入ったか
```
