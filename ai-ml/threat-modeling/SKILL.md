# 威脅建模 Skill

依 OWASP Threat Modeling Process 的四步主線工作：界定範圍、辨識威脅、決定對策、評估結果。先理解系統和資料流，再套用 STRIDE；不要只列出六類名詞就宣稱模型完整。來源整理及限制見 [`references/source-basis.md`](references/source-basis.md)，輸出格式見 [`references/deliverable-template.md`](references/deliverable-template.md)。

**主要依據：OWASP Foundation 官方社群頁面 [Threat Modeling Process (Historical)](https://community.owasp.org/Threat_Modeling_Process#data-flow-diagrams)。** 本 Skill 依該頁四步流程組織分析：界定範圍、辨識威脅、決定對策與緩解、評估工作成果。該頁明確標示為 Historical；引用時應說明這是 OWASP 社群方法參考頁，不宣稱它是 OWASP 現行唯一或最新標準。來源摘要與可讀狀態見 [`references/source-basis.md`](references/source-basis.md)。

## 何時使用

- 使用者要求威脅建模、STRIDE 分析、DFD／信任邊界分析或威脅模型報告。
- 設計新功能、API、資料流、登入授權、外部整合或資料儲存時，需要在安全檢核中同步辨識設計風險。
- 對既有專案進行逆向分析時，已有原始碼、架構圖、API 文件或部署資料可用來還原威脅模型。

## 引導使用者

把建模當成與系統負責人共同釐清風險的過程。面對新手時，一次只問一個容易回答的問題，先說明問題用途，並提供可照抄的回答例子。使用者不知道的資訊記為「未知／待確認」，不要以猜測補齊；可先從程式碼、既有文件和專案結構找線索，再請使用者確認。

先釐清系統或變更範圍、主要使用者與業務流程、最重要的資料／資產，以及外部服務。若範圍尚不清楚，先提出一個有來源依據的候選範圍，請使用者確認後再擴展。

## 工作流程

### 1. 界定範圍並繪製 DFD

從一張可讀的系統脈絡圖開始，再依風險需要拆解核心流程。DFD 至少辨識：

- 外部實體：使用者、管理者、合作系統或第三方服務。
- 處理程序：API、服務、工作排程、驗證或資料轉換邏輯。
- 資料儲存：資料庫、檔案、快取、佇列、日誌或 Token 儲存位置。
- 資料流：請求、回應、憑證、個資、管理命令及其方向。
- 信任邊界：不同網路區域、權限層級、租戶、組織或第三方控制範圍之間的交界。

同時列出資產／敏感資料、入口點、出口點、外部依賴、角色與其信任等級。說清楚哪些資料穿越哪條信任邊界；不要只畫元件方塊而省略流向、資料種類或權限差異。若採 Mermaid，使用清楚的節點類型標籤與信任邊界子圖，並加圖例；其他圖表工具也遵守相同語意。

分析既有系統時，逐項標記「程式／文件可見事實」、「使用者確認」、「AI 推論」及「未知」。關鍵節點與連線應附可追溯的來源，例如檔案路徑、行號、API 文件章節或圖表來源 ID。不得將來源編號當成流程步驟或風險嚴重度。

### 2. 依 DFD 元素辨識威脅

以 STRIDE 作為檢視提示，針對相關處理程序、資料流、資料儲存與信任邊界提出具體情境：

| 類別 | 檢視問題 |
|:--|:--|
| S 身分冒用 | 是否能偽造、重放或竊取使用者、服務或裝置身分？ |
| T 資料竄改 | 請求、傳輸、設定或儲存資料是否可能被未授權修改？ |
| R 否認行為 | 關鍵操作是否缺少可供追查的可信紀錄？ |
| I 資訊洩露 | 是否可能讀取、傳送或記錄不該暴露的資料？ |
| D 阻斷服務 | 是否能以資源耗盡、流量或依賴故障影響可用性？ |
| E 權限提升 | 是否能跨越角色、租戶或信任邊界取得更高權限？ |

每筆威脅描述攻擊者／能力、入口或前置條件、攻擊路徑、受影響資產、業務／安全影響、既有控制、證據和未知事項。STRIDE 是分類輔助，不是完整性保證；依情境補充濫用流程、隱私、供應鏈、營運及業務濫用等風險。

### 3. 決定對策、緩解措施並排序

依威脅情境評估可用的對策，將每筆優先威脅連結到一項或多項可執行處置：降低風險、避免風險、移轉風險，或由責任人核准接受風險。具體控制可包括伺服器端物件授權、輸入驗證、Token 限制、速率限制、敏感資料遮罩、稽核紀錄或失效安全行為；避免只寫「加強安全性」。

排序時依組織情境記錄可能性、影響、業務後果及修復複雜度／成本等考量與假設。這些是 OWASP 頁面列舉的常見因素，不是固定風險公式；如組織未提供正式風險矩陣，可用低／中／高作為暫定討論尺度，明確標示「初步排序，待風險負責人確認」，不得把 AI 排序說成正式核定嚴重度。先整理少量最高優先項目供決策，再保留完整清單；風險多時可按共同攻擊路徑或根因合併，避免重複列項掩蓋優先事項。

將每個控制連結到負責角色、待辦或安全需求，以及可檢查的驗收／測試證據。若同時執行 SSDLC 安全基準檢核，將掃描結果當作訊號與證據之一：發現項目應連回 DFD 元素、威脅情境及修復工作；掃描未發現問題不代表沒有設計威脅。威脅模型與檢核結果應同步更新，但須分清「模型假設」、「工具發現」和「已驗證缺陷」。

### 4. 評估工作成果並維護模型

依 OWASP 頁面的評估方向，確認分析工作已留下可檢視的範圍／DFD、威脅清單及控制或緩解清單。交付前再檢查假設是否清楚、重要資料流與信任邊界是否涵蓋、威脅能否映射到圖中元素、排序依據是否可解釋、控制是否有驗證方式，以及殘餘風險是否有人負責。記錄未回答問題、負責確認者與後續期限（若已知）。

當架構、資料種類、身分驗證、外部依賴、部署邊界或安全控制變更時，重看受影響的 DFD 與威脅；保留已接受風險的決策脈絡。靜態分析或模型文件不能取代核准、實際測試或部署環境驗證。

## 產出

依 [`references/deliverable-template.md`](references/deliverable-template.md) 產出適合專案的文件，通常包括：範圍與假設、DFD／圖例、信任邊界、資產及入口／出口、威脅登錄表、排序理由、建議控制、驗證方式、殘餘風險和待確認事項。小型變更可精簡輸出，但保留可追溯性。

任何主動測試、正式環境請求、帳號操作或資料修改，都先確認使用者授權與測試範圍。威脅建模本身以文件、圖表與靜態證據分析為主，不要把未執行的檢查描述成已驗證。
